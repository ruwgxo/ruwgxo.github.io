Section 9.2: Extraction Taxonomy

Section Overview

One Line Summary

Four extraction goals -- functionality, fidelity, decision-boundary, and prompt -- define what adversaries are stealing, how many queries they need, and which detection primitive will catch them; the taxonomy is the filing system for every attack and defence section that follows.

Why This Section Exists

Without a taxonomy, extraction looks like a single undifferentiated threat: an adversary queries the model too many times. That framing produces undifferentiated defences -- rate limits that do not distinguish between a distillation campaign and a boundary-mapping campaign, and detection signals that fire on volume alone rather than on the structural properties of the query distribution. The four extraction goals are meaningfully different in what the adversary wants, how many queries are required, what query patterns they produce, and which detection primitive covers them. A functionality extractor needs a model that generalises across the full input distribution -- thousands to millions of queries, distributed across the input space. A fidelity extractor needs exact match on a specific input set -- potentially hundreds of queries, concentrated on a narrow region. A decision-boundary extractor needs the geometry of the classification surface -- queries that deliberately straddle classification boundaries. A prompt extractor needs the system prompt -- a small number of carefully constructed inference queries that elicit system configuration disclosure. The taxonomy built here is the scaffold for attack sections 9.3 through 9.9 and for the detection primitive design in Section 9.10. Every attack lives in one of four goal quadrants. Every detection primitive covers one or more quadrants. The mental model built in Section 9.2 is what makes Section 9.10 legible and Section 9.11 defensible.

Title

Why the Taxonomy Matters Before the Attacks

Body

Every chapter in Part 2 has opened with a framing section before the attack sections because the framing determines the detection architecture. Chapter 6 opened with the injection threat model before building the classifier. Chapter 8 opened with the poisoning taxonomy before building the auditing pipeline. Section 9.2 does the same for extraction. The risk of skipping the taxonomy is concrete. A defender who treats extraction as a single threat class -- adversary queries model excessively -- will deploy a single-dimensional defence: a volume threshold that fires when any user exceeds N queries per hour. That defence has two failure modes. First, it blocks legitimate high-volume users (researchers, batch evaluation pipelines, automated testing) at the same rate it blocks adversaries. Second, a patient adversary who stays below N queries per hour can complete a full functionality extraction in weeks without ever triggering the threshold. A taxonomy-aware defender deploys different detection signals for different goals. A functionality extractor''s queries will spread across the input distribution; a boundary extractor''s queries will cluster near decision surfaces; a prompt extractor''s queries will target system configuration disclosure patterns. Each signal fires for the right adversary and not for the benign high-volume user whose queries are well-distributed across legitimate use cases. The four-goal taxonomy is not a theoretical nicety. It is the reason Section 9.10 builds five distinct detection primitives rather than one. Each primitive was designed for a specific quadrant of the taxonomy matrix.

Title

Functionality Extraction: Building a Deployable Clone

Body

Functionality extraction is the dominant extraction goal in commercial threat models. The adversary''s objective is a surrogate model that behaves like the victim across the full input distribution -- not just on specific inputs, not just near decision boundaries, but on the distribution of real-world queries that the product would receive. A successful functionality extraction produces a deployable model: the adversary can stand up their own inference endpoint serving the victim''s capability at their own infrastructure cost. The adversary motivation is economic. Training a capable model from scratch is expensive: data collection, compute, engineering time. A commercial model that represents months of training effort can be functionally extracted in days of querying if the extraction campaign is well-designed. The attacker pays query fees against the victim''s API and training cost for the surrogate; the total cost is far below the victim''s training cost if the surrogate achieves sufficient fidelity. The canonical technique is knowledge distillation (Section 9.4): the adversary uses the victim API as a teacher, queries it on a large input set, and trains a student model on the victim''s outputs. The student learns to mimic the teacher without access to the teacher''s weights or training data. The resulting surrogate can be deployed, fine-tuned, and distributed without the adversary bearing the original training cost. Query budget for functionality extraction scales with the input distribution complexity. A narrow-domain classifier (medical imaging, sentiment analysis) may extract in tens of thousands of queries. A general-purpose LLM requires a much larger query set to achieve broad functionality coverage. Active distillation (Section 9.4) reduces the budget by selecting queries that maximally reduce the student''s uncertainty, but the fundamental requirement is coverage: the surrogate must see enough of the input space to generalise. Detection signal: functionality extraction queries are broadly distributed across the input space. The query distribution of a legitimate user clusters around their use case. The query distribution of a functionality extractor spans diverse topics, domains, and input structures -- attempting to cover the victim model''s full capability surface. Query diversity is the primary detection signal.

Title

Fidelity Extraction: Replicating Specific Behaviour

Body

Fidelity extraction is targeted where functionality extraction is broad. The adversary does not need a general-purpose clone -- they need exact behavioural match on a specific set of inputs that they care about. The goal is not distributional coverage but replication fidelity on a well-defined target input set. The threat model for fidelity extraction differs from functionality extraction in two important ways. First, the adversary knows which inputs they care about before beginning the campaign. A financial institution might extract a competitor''s credit-scoring model behaviour on a specific portfolio of applicant profiles. A security researcher might extract a malware classifier''s behaviour on a specific family of samples. The target input set is defined by the adversary''s use case, not by the victim model''s full capability. Second, fidelity extraction can succeed with far fewer queries than functionality extraction because the adversary does not need to cover the full input distribution. If the target set contains 10,000 inputs, the adversary needs approximately 10,000 to 50,000 queries to achieve high fidelity on that set -- far fewer than the queries required for broad distributional coverage. The surrogate from fidelity extraction is not a general-purpose clone. It may behave arbitrarily outside the target input set. For the adversary''s purpose, this is not a limitation -- they only need the model to behave correctly on the inputs they care about. Detection signal: fidelity extraction queries are concentrated in a narrow region of the input space -- the target set. Unlike functionality extraction (broad distribution) or boundary extraction (decision surface clustering), fidelity extraction produces query concentration on a semantically coherent input cluster. The user concentration analyser in Section 9.10 catches this: a user whose queries all fall in a narrow semantic neighbourhood is exhibiting fidelity extraction rather than legitimate varied usage.

Title

Decision-Boundary Extraction: Mapping the Classification Surface

Body

Decision-boundary extraction has a different goal from the other three: the adversary wants the geometry of the victim model''s classification surface rather than a deployable clone or a stolen prompt. The objective is to understand where the model transitions between classes -- to map the boundary precisely enough to generate inputs that sit on or near it. Why is the decision boundary itself valuable? Two reasons. First, a precise boundary map enables adversarial example generation (Chapter 10): the adversary can construct inputs that the model misclassifies with high confidence, which is the prerequisite for evasion attacks against classifiers used in security-critical contexts (malware detection, fraud scoring, content moderation). Second, a boundary map reveals the model''s internal logic: what features drive the classification boundary, where the model''s confidence is lowest, and which inputs are closest to being misclassified without any perturbation. The technique is black-box decision boundary mapping (Section 9.3): the adversary submits input pairs that straddle the classification boundary, using the model''s responses to triangulate the boundary''s position in input space. Active learning drives query selection: each query is chosen to maximally reduce uncertainty about the boundary''s position, making boundary extraction significantly more budget-efficient than random sampling. Query budget for boundary extraction is lower than for functionality extraction when the input space is high-dimensional but the boundary is locally linear. For neural networks with complex, non-linear boundaries, the budget scales with the boundary''s complexity rather than the distribution''s coverage. Detection signal: boundary extraction queries cluster near the decision surface. Pairs of inputs with opposite class labels and small input distance are the signature of boundary probing. The OOD detector and boundary query detector in Section 9.10 target this signal specifically: benign users do not systematically submit near-boundary input pairs.

Title

Prompt Extraction: Stealing the Operational Configuration

Body

Prompt extraction is the lowest-budget and most immediately actionable of the four extraction goals. The adversary does not need to replicate model weights or map decision boundaries -- they need to reconstruct the system prompt or hidden instructions that configure the model''s behaviour for a specific deployment. The value of a system prompt extends beyond its literal text. A system prompt encodes commercial IP (the product''s unique interaction design, persona, and behavioural constraints), security configuration (what the model is and is not permitted to do, which tools it can access, which content categories it filters), and operational parameters (output format requirements, escalation rules, compliance constraints). Extracting the system prompt gives the adversary a blueprint for replicating the product''s behaviour, a roadmap for finding security configuration gaps, and proprietary design decisions that represent engineering investment. Chapter 6 Section 6.2 covered single-prompt system prompt extraction as an injection technique: a single carefully crafted query attempts to elicit the system prompt directly. Prompt extraction at scale (Section 9.5) is different in mechanism and in defence requirements. The scaled version uses many queries -- some direct, some indirect -- to aggregate partial leakages into a full reconstruction. No single query needs to succeed completely; the aggregation of many small leakages reconstructs the full prompt over many requests. Query budget for prompt extraction is orders of magnitude lower than for functionality or boundary extraction. A short system prompt (a few hundred tokens) may reconstruct in 50 to 200 queries using aggregation techniques. A long, complex system prompt requires more, but the budget remains far below the query counts required for the other extraction goals. Detection signal: prompt extraction queries target system configuration disclosure. Direct queries explicitly ask the model to reveal its instructions. Indirect queries probe the model''s behavioural constraints through carefully constructed inputs whose outputs reveal prompt content probabilistically. The query pattern monitor in Section 9.11 includes a prompt reconstruction track that identifies both direct and indirect prompt extraction patterns.

Title

Budget-Fidelity Tradeoffs and Targeted vs Untargeted Extraction

Body

Every extraction goal has a budget-fidelity tradeoff curve: as query count increases, extraction fidelity increases, up to an asymptotic ceiling determined by the adversary''s access level and the goal''s information requirements. Understanding these curves is what makes defensive rate limiting principled rather than arbitrary. For functionality extraction, the curve rises steeply at first (the first few thousand queries capture the bulk of the model''s common-case behaviour) then flattens as the adversary covers increasingly rare input regions. The asymptote is the victim model''s full capability -- achievable in theory given infinite queries, but practically approached to 80 to 90 percent fidelity in far fewer queries than the full training budget requires. For fidelity extraction on a fixed target set, the curve rises quickly and plateaus at near-100 percent fidelity once the target set is covered. The plateau is lower in query count than functionality extraction because the adversary is not trying to cover the full distribution. For decision-boundary extraction, the curve''s shape depends on boundary complexity. Locally linear boundaries near a target region approach high fidelity in hundreds of queries. Complex non-linear boundaries in high- dimensional spaces require more, but active learning (choosing boundary- straddling queries) provides the steepest possible ascent for the budget. For prompt extraction, the curve is steep and short: the first few dozen queries capture most of the prompt structure, and the curve plateaus once the aggregation has covered the prompt''s full content. A small query budget produces high-fidelity prompt reconstruction. The targeted versus untargeted distinction cuts across all four goals. Untargeted extraction replicates the victim''s behaviour across the full input distribution -- only functionality extraction is inherently untargeted (though it can be targeted to a domain). Fidelity, boundary, and prompt extraction are all targeted by definition: the adversary specifies the input set, boundary region, or prompt content they care about before beginning. Targeted extraction is more budget-efficient and more dangerous for specific use cases; untargeted extraction produces more generally useful surrogates.

Part

7

Title

Choosing the Right Defence for the Right Goal

Body

The taxonomy is not just an analytical tool -- it is the design input for the detection and defence architecture. Each extraction goal requires a different combination of detection primitives, and a defender who applies the taxonomy correctly can prioritise investment based on the threat model most relevant to their deployment. Functionality extraction is best addressed by query diversity monitoring (catching adversaries who cover the input space too broadly) combined with adaptive rate limiting (imposing budget constraints that make full distributional coverage expensive). Output watermarking provides post-hoc ownership evidence when functionality extraction succeeds despite prevention. Fidelity extraction is best addressed by user concentration analysis (catching queries concentrated in a narrow semantic region) and query cluster detection. The rate limiter contributes but fidelity extraction often stays below volume thresholds because the target set is small. Decision-boundary extraction is best addressed by the boundary query detector (catching near-boundary input pairs) and OOD detection (boundary- probing queries often fall outside the model''s legitimate input distribution). Output perturbation (Section 9.12) degrades the information content of boundary-probing queries, forcing higher budget for the same boundary fidelity. Prompt extraction is best addressed by the prompt reconstruction pattern detector in the query monitor and by output-side perturbation that reduces the per-query leakage of system configuration. A single direct prompt extraction query may be caught by the Chapter 6 injection classifier; scaled aggregation prompt extraction requires the query pattern monitor to track the cumulative pattern. The goal-to-detection-signal mapping is the design document for Section 9.10''s detection primitive library. Each primitive exists because a specific goal required it. Sections 9.11 and 9.12 wire these primitives into production controls that cover all four quadrants of the taxonomy matrix.

# budget_fidelity_model.py
# Chapter 9 Section 9.2 -- Budget-Fidelity Tradeoff Model
# Single quotes throughout per book convention.

import math
from dataclasses import dataclass
from typing import Dict, List, Optional, Tuple


@dataclass
class BudgetFidelityParams:
    goal: str
    access_level: str
    # Logistic growth model: fidelity = ceiling / (1 + exp(-k * (q - q_half)))
    # ceiling: maximum achievable fidelity (0.0 to 1.0)
    # k: growth rate (steepness of the curve)
    # q_half: query count at which fidelity reaches ceiling/2
    ceiling: float
    k: float
    q_half: float
    note: str


# Parameters derived from published extraction research (approximate).
# Tramer et al. 2016, Papernot et al. 2017, Carlini et al. 2021.
BUDGET_FIDELITY_PARAMS: Dict[Tuple[str, str], BudgetFidelityParams] = {
    ('functionality', 'black_box'): BudgetFidelityParams(
        goal='functionality', access_level='black_box',
        ceiling=0.92, k=0.00003, q_half=80000,
        note='Narrow-domain classifier. LLM ceiling is lower (~0.75) at similar budget.',
    ),
    ('functionality', 'grey_box'): BudgetFidelityParams(
        goal='functionality', access_level='grey_box',
        ceiling=0.94, k=0.00015, q_half=20000,
        note='Soft-label output provides ~5x effective budget increase.',
    ),
    ('fidelity', 'black_box'): BudgetFidelityParams(
        goal='fidelity', access_level='black_box',
        ceiling=0.99, k=0.001, q_half=3000,
        note='Target set of 1000 inputs; fidelity on target set, not full distribution.',
    ),
    ('fidelity', 'grey_box'): BudgetFidelityParams(
        goal='fidelity', access_level='grey_box',
        ceiling=0.99, k=0.005, q_half=600,
        note='Soft-label provides ~5x budget reduction for target set coverage.',
    ),
    ('decision_boundary', 'black_box'): BudgetFidelityParams(
        goal='decision_boundary', access_level='black_box',
        ceiling=0.88, k=0.0002, q_half=15000,
        note='Regional boundary map; ceiling limited by curse of dimensionality.',
    ),
    ('decision_boundary', 'grey_box'): BudgetFidelityParams(
        goal='decision_boundary', access_level='grey_box',
        ceiling=0.95, k=0.001, q_half=3000,
        note='Confidence scores greatly accelerate boundary triangulation.',
    ),
    ('prompt', 'black_box'): BudgetFidelityParams(
        goal='prompt', access_level='black_box',
        ceiling=0.97, k=0.05, q_half=100,
        note='Short-to-medium system prompt (100-500 tokens). Ceiling near-perfect.',
    ),
    ('prompt', 'grey_box'): BudgetFidelityParams(
        goal='prompt', access_level='grey_box',
        ceiling=0.97, k=0.05, q_half=100,
        note='Grey-box provides no advantage for text prompt reconstruction.',
    ),
}


def project_fidelity(goal: str, access_level: str, query_budget: int) -> Optional[float]:
    '''
    Estimate achievable fidelity for a given query budget, extraction goal,
    and adversary access level. Returns None if the combination is not modelled.
    '''
    params = BUDGET_FIDELITY_PARAMS.get((goal, access_level))
    if params is None:
        return None
    exponent = -params.k * (query_budget - params.q_half)
    fidelity = params.ceiling / (1.0 + math.exp(exponent))
    return round(min(fidelity, params.ceiling), 4)


def queries_for_fidelity(goal: str, access_level: str, target_fidelity: float) -> Optional[int]:
    '''
    Estimate the query budget required to reach a target fidelity level.
    Returns None if the target is above the ceiling or the combination is not modelled.
    '''
    params = BUDGET_FIDELITY_PARAMS.get((goal, access_level))
    if params is None:
        return None
    if target_fidelity >= params.ceiling:
        return None  # above ceiling; not achievable
    ratio = params.ceiling / target_fidelity - 1.0
    queries = params.q_half - math.log(ratio) / params.k
    return max(1, int(math.ceil(queries)))


def render_tradeoff_table(query_counts: Optional[List[int]] = None) -> None:
    if query_counts is None:
        query_counts = [100, 1000, 10000, 100000, 500000]
    print('BUDGET-FIDELITY TRADEOFF TABLE -- Chapter 9 Section 9.2')
    print(f'{"Goal + Access":<30} ' + ' '.join(f'{q:>8}q' for q in query_counts))
    print('-' * (30 + 10 * len(query_counts)))
    for (goal, level), params in BUDGET_FIDELITY_PARAMS.items():
        label = f'{goal}/{level}'
        row = f'{label:<30} '
        for q in query_counts:
            fidelity = project_fidelity(goal, level, q)
            if fidelity is not None:
                row += f'{fidelity:>8.1%} '
            else:
                row += f'{"N/A":>8} '
        print(row)
        print(f'  {"Note:":<28} {params.note}')


if __name__ == '__main__':
    render_tradeoff_table()
    print()
    # Example: estimate budget required for 80% fidelity functionality extraction
    budget = queries_for_fidelity('functionality', 'black_box', 0.80)
    print(f'Queries for 80% functionality fidelity (black-box): {budget:,}')
    budget_grey = queries_for_fidelity('functionality', 'grey_box', 0.80)
    print(f'Queries for 80% functionality fidelity (grey-box):  {budget_grey:,}')

@dataclass
class GoalHypothesis:
    goal: str
    confidence: float  # 0.0 to 1.0
    matched_signals: List[str]
    contradicted_signals: List[str]
    recommended_primitives: List[str]
    escalation_action: str


def classify_query_pattern(observed_signals: List[str]) -> List[GoalHypothesis]:
    '''
    Classify an observed query pattern into ranked extraction goal hypotheses.
    Returns goals sorted by confidence (descending).
    Confidence = (positive_matches - negative_matches) / total_profile_signals,
    clamped to [0.0, 1.0].
    '''
    observed_set: Set[str] = set(observed_signals)
    hypotheses: List[GoalHypothesis] = []

    for profile in GOAL_SIGNAL_PROFILES:
        matched = [s for s in profile.positive_signals if s in observed_set]
        contradicted = [s for s in profile.negative_signals if s in observed_set]
        total_signals = len(profile.positive_signals) + len(profile.negative_signals)
        raw_score = len(matched) - len(contradicted)
        confidence = max(0.0, raw_score / total_signals) if total_signals > 0 else 0.0
        hypotheses.append(GoalHypothesis(
            goal=profile.goal,
            confidence=round(confidence, 4),
            matched_signals=matched,
            contradicted_signals=contradicted,
            recommended_primitives=profile.recommended_primitives,
            escalation_action=profile.escalation_action,
        ))

    hypotheses.sort(key=lambda h: h.confidence, reverse=True)
    return hypotheses

Common Mistakes

Id

1

Description

Treating all extraction attempts as the same threat and deploying a single undifferentiated volume threshold

Why It Happens

Extraction is perceived as a query-volume problem: the adversary queries too much. A volume threshold feels like a complete defence because it targets the one property all extraction attacks share. Teams skip the taxonomy because it requires more design effort than a single rate limit.

Consequence

The threshold blocks legitimate high-volume users (batch evaluation, automated testing, research pipelines) while missing patient adversaries who stay below the volume ceiling. A prompt extractor needs 50 to 500 queries -- well below any reasonable volume threshold. A boundary extractor issues individually benign queries at a low rate. Neither is caught by volume alone.

Correct Approach

Deploy detection primitives aligned to each extraction goal: diversity monitoring for functionality, concentration analysis for fidelity, boundary pair detection for decision-boundary, and prompt elicitation pattern detection for prompt. Volume thresholds are one input to the adaptive rate limiter, not the complete defence.

2

Description

Conflating prompt extraction with single-prompt injection (the Chapter 6 threat model)

Why It Happens

Both attacks involve system prompts. Chapter 6 Section 6.2 covered single- prompt injection where a single carefully crafted query attempts to elicit the system prompt. Readers carry that frame into Chapter 9 and assume the Chapter 6 classifier handles prompt extraction.

Consequence

The Chapter 6 injection classifier catches obvious direct elicitation attempts but has no visibility into aggregation-based prompt extraction: the adversary issues many indirect queries, each individually benign, that together reconstruct the system prompt. The classifier scores each query independently and finds nothing actionable.

Correct Approach

Prompt extraction at scale requires cumulative query pattern monitoring (Section 9.11) rather than single-request classification. The Chapter 6 classifier remains in the ensemble for single-prompt injection; Section 9.11 adds a prompt reconstruction track that accumulates indirect leakage signals across many requests.

Description

Assuming decision-boundary extraction only matters for image classifiers

Why It Happens

The canonical boundary extraction literature (Tramer et al. 2016, Section 9.3) focuses on image classifiers and tabular ML models. The visual intuition of a decision boundary applies more naturally to classification than to text generation. Readers assume LLMs are not vulnerable to boundary extraction.

Consequence

LLMs used as classifiers -- content moderation, spam detection, safety filtering, intent classification -- have decision boundaries that are exploitable via the same probing techniques. An adversary who maps the safety filter''s boundary can construct inputs that consistently evade it. This is the Chapter 10 connection: boundary extraction is the precursor to adversarial example generation against any classifier, including LLM-based ones.

Correct Approach

Apply boundary extraction threat modelling to any model that makes binary or categorical decisions, regardless of architecture. For LLMs used as text generators, boundary extraction is less applicable; for LLMs used as classifiers (the increasingly common deployment pattern), it is directly relevant.

Description

Using query budget estimates from black-box scenarios to design defences against grey-box APIs

Why It Happens

Budget-fidelity curves from the literature are typically reported for black-box access because it is the harder extraction scenario and produces more conservative (defender-friendly) estimates. Teams use these estimates to set rate limits without checking whether their API actually returns soft labels or probability distributions.

Consequence

The rate limit is set based on a 100,000-query extraction scenario when the API returns soft labels and the actual attack requires 2,000 to 20,000 queries. The adversary completes the extraction campaign well within the rate limit budget before the defender''s threshold fires.

Correct Approach

Audit the API''s output fields before setting rate limits. If the API returns probability distributions, apply grey-box budget estimates (5 to 50x lower than black-box) to the rate limit design. Consider removing probability distributions from the API response if the product does not require them.

Mapping extraction goals to ATLAS techniques and stopping there without connecting to detection controls

Why It Happens

ATLAS mapping is a compliance and reporting requirement in many security programmes. Teams complete the taxonomy exercise, record the ATLAS technique IDs, and move on. The mapping is treated as documentation rather than as the input to detection control design.

Section Summary

Compact

Four extraction goals define the Chapter 9 attack landscape. Functionality extraction builds a deployable clone matching the victim across the full input distribution -- the dominant commercial threat because it produces a working product replacement. Fidelity extraction targets exact behavioural match on a specific input set -- targeted, budget-efficient, and sufficient for the adversary''s use case. Decision-boundary extraction maps the classification surface for adversarial example generation -- the precursor to Chapter 10 evasion attacks. Prompt extraction reconstructs the system prompt and operational configuration at very low query budget -- cheap, immediately actionable, and leaking both IP and security configuration. The four goals differ in query budget, query pattern, required adversary access level, and optimal detection primitive. Undifferentiated volume thresholds cover none of them adequately. The taxonomy matrix and defender decision tree in this section are the design inputs for the detection primitive library in Section 9.10 and the production controls in Sections 9.11 and 9.12.

Key Takeaways

  • Functionality extraction is the dominant commercial threat; it produces a deployable clone via distillation
  • Prompt extraction is the lowest-budget and most immediately actionable goal; 50-500 queries reconstruct a typical system prompt
  • Decision-boundary extraction is the precursor to adversarial example generation; it connects extraction (Chapter 9) to evasion (Chapter 10)
  • Grey-box APIs give adversaries a 5-50x query budget discount for functionality and boundary extraction; output design is a security decision
  • Each extraction goal requires a different detection primitive; volume thresholds alone cover none adequately
  • The defender decision tree classifies observed query patterns to the most likely goal, enabling targeted primitive deployment

Preview

Section 9.2 named the four extraction goals and placed them in a taxonomy matrix. Section 9.3 builds the first attack implementation: black-box decision boundary mapping, the foundational primitive that underpins decision-boundary extraction and informs the distillation attacks in Section 9.4. The section establishes the canonical Tramer et al. 2016 result -- a linear model extracted in O(d) queries -- and builds the active learning loop that makes boundary mapping budget-efficient. The detection insight from Section 9.3 is the one that drives the boundary query detector in Section 9.10: extraction queries cluster near decision boundaries while benign queries cluster in high-density input regions. Understanding why that clustering occurs mechanistically is what makes the detector design defensible rather than heuristic.
