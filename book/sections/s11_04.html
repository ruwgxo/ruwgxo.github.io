Section Overview

One Line Summary

MITRE ATT&CK provides the enterprise-wide adversary behaviour taxonomy; MITRE ATLAS extends it for adversarial ML attacks; together they supply the technique-to-detection chain that converts every gateway track into a measurable, communicable, and improvable coverage position.

Why This Section Exists

Sections 11.01 through 11.03 established that coverage must be measured rather than assumed, and that every detection primitive belongs to a defined layer of the architecture. But measurement requires a common vocabulary: a shared taxonomy of attack techniques that every detection rule can reference, every heat map can visualise, and every stakeholder — from SOC analyst to CISO — can read without translation. MITRE ATT&CK and MITRE ATLAS are that vocabulary. Without ATT&CK and ATLAS anchors, a detection programme can only say "we have seven tracks." With them, it can say "we have confirmed coverage of AML.T0051, AML.T0054, AML.T0043, AML.T0015, AML.T0040, and AML.T0020 at the specified detection layers, with two Layer 3 and one Layer 4 gap mapped to Chapter 12 and 13 remediation." That is the difference between a detection programme and a detection engineering discipline. This section also completes the technique-to-detection-to-Sigma chain for all Part 2 attack families: every ATLAS technique the book has covered now has a named detection opportunity, a named detection layer, a named Sigma rule, and a named gateway track. Section 11.05 visualises that chain as a heat map.

Position In Chapter

Section 11.04 is the framework literacy section. Section 11.03 placed tracks in layers; Section 11.04 names the techniques those layers detect. The chain is now complete: ATLAS technique → detection layer → Sigma rule → gateway track → alert. Section 11.05 measures coverage along that chain.

Part 1 Attck For Enterprise

Heading

MITRE ATT&CK for Enterprise: Structure and AI Relevance

Body

MITRE ATT&CK (Adversarial Tactics, Techniques, and Common Knowledge) is a globally accessible knowledge base of adversary behaviour based on real-world observations. The Enterprise matrix — the most widely used — organises adversary behaviour into 14 tactics, each representing a high-level adversary goal: Reconnaissance, Resource Development, Initial Access, Execution, Persistence, Privilege Escalation, Defence Evasion, Credential Access, Discovery, Lateral Movement, Collection, Command and Control, Exfiltration, and Impact. Under each tactic sit techniques (what the adversary does to achieve the tactic) and sub-techniques (specific implementations of a technique). For AI security practitioners, ATT&CK for Enterprise matters for two reasons. First, AI systems are targets of standard enterprise attack techniques. An attacker who wants to compromise an LLM-based application may begin with Reconnaissance (T1590 — Gather Victim Network Information) to map the API endpoints, proceed to Initial Access (T1190 — Exploit Public-Facing Application) to reach the model serving layer, and then move to Collection (T1119 — Automated Collection) to exfiltrate model outputs at scale. These are standard ATT&CK techniques; the target is an AI system but the tactics are generic adversary behaviour. Second, AI systems can be attack vectors — a compromised AI model can execute adversary objectives that traditional techniques cannot. A backdoored model serves as a persistent Execution (T1059) capability that activates on trigger input. A data-poisoned recommendation system manipulates user behaviour in ways that map to Impact (T1485 — Data Destruction, in the sense of integrity destruction). ATT&CK does not currently have native techniques for AI-as-attack-vector; that is precisely the gap that ATLAS fills. The practical consequence for detection engineering: AI security programmes need both ATT&CK coverage (detecting attacks on the AI system using standard techniques) and ATLAS coverage (detecting adversarial ML attacks that exploit the model itself). The seven-track gateway primarily addresses ATLAS coverage; the broader AI security programme also requires standard ATT&CK coverage of the infrastructure hosting the model, the API gateway, and the training pipeline.

Part 2 Atlas Overview

Heading

MITRE ATLAS: Adversarial ML Extension

Body

MITRE ATLAS (Adversarial Threat Landscape for Artificial-Intelligence Systems) is a knowledge base of adversarial ML tactics and techniques, maintained by MITRE in collaboration with AI security practitioners. It follows the ATT&CK structure — tactics, techniques, case studies — but models attacks specific to ML systems: the model itself, the training pipeline, the inference API, and the supply chain of datasets and pre-trained weights. ATLAS organises adversarial ML behaviour into tactic categories that parallel ATT&CK but address ML-specific objectives: ML Attack Staging covers how adversaries prepare attacks against ML systems before executing them: acquiring training data samples (AML.T0002), acquiring ML artifacts such as pre-trained models (AML.T0000), and developing adversarial capabilities (AML.T0017 — Develop Capabilities for ML attacks). These staging techniques are the prerequisites for all subsequent attack execution. They are largely invisible to the production inference API because they happen in attacker-controlled environments. ML Model Access covers how adversaries reach the model to execute attacks: ML model inference API access (AML.T0040) — querying the production API as a black-box — and physical environment access for camera-facing or embodied systems (AML.T0021). Detection opportunity: AML.T0040 is detectable via query rate, query variance, and output entropy monitoring — exactly what Track 6 implements. Adversarial ML covers the core attack execution techniques: crafting adversarial data (AML.T0043 — the generic technique for adversarial examples), evading ML models (AML.T0015 — the evasion outcome technique), poisoning training data (AML.T0020), backdooring ML models (AML.T0019), and prompt injection for LLMs (AML.T0051, AML.T0054). These are the techniques that Chapters 6–10 studied in depth and that the seven-track gateway detects. Exfiltration via ML covers attacks that use the model as an exfiltration channel: model inversion (AML.T0024 — recovering training data from model outputs) and membership inference (AML.T0024.000 — determining whether a specific example was in the training set). These techniques were covered in Chapter 8 (Privacy). They are not currently detected by the gateway's seven tracks — a coverage gap that maps to a future Chapter 15 topic rather than Chapters 12–13. ML Supply Chain Compromise covers attacks on the dependencies of ML systems: compromising ML software libraries (AML.T0010), poisoning public data repositories (AML.T0018), and compromising hardware used for ML (AML.T0016). Supply chain attacks are detection-hard because they occur outside the production inference path; they are addressed by software composition analysis and supply chain security controls rather than runtime detection rules.

Part 3 Atlas Extends Attck

Heading

How ATLAS Extends ATT&CK: The Integration Model

Body

ATLAS extends ATT&CK in two ways. First, it adds ML-specific techniques to standard ATT&CK tactic categories: a prompt injection attack (AML.T0051) is a form of Initial Access in ATT&CK terms — it is the adversary gaining a foothold in the model's inference context in the same way that a traditional initial access technique gains a foothold in a network. ATLAS assigns it an AML technique ID and provides ML-specific detection guidance, while the ATT&CK tactic category (Initial Access) provides the strategic context. Second, ATLAS introduces tactic categories that have no ATT&CK equivalent because they address ML-specific concerns: the distinction between black-box model access (querying the API without model weights) and white-box access (full model access, typical of insider threats or supply chain compromise) has no direct ATT&CK mapping but is central to the ATLAS access model. Similarly, the distinction between inference-time attacks (adversarial examples, prompt injection) and training-time attacks (data poisoning, backdoors) maps imperfectly to ATT&CK's execution-vs- persistence distinction. For detection engineers, the practical integration model is: use ATT&CK for infrastructure-level detection (the API gateway, the model serving host, the training pipeline infrastructure) and ATLAS for model-level detection (the inference API, the prompt, the model output, the training data). The seven-track gateway operates at the model level and therefore uses ATLAS technique IDs exclusively. The broader AI security programme uses ATT&CK for the infrastructure surrounding the model. The technique-to-detection-to-Sigma chain that Chapter 11 establishes connects both frameworks: an attack may traverse ATT&CK Initial Access techniques to reach the model serving layer, then ATLAS techniques to attack the model itself. A complete detection programme has Sigma rules for both segments of the attack chain.

Part 4 Technique Inventory

Heading

ATLAS Technique Inventory: Chapters 6–10

Body

Every attack family studied in Part 2 has a named ATLAS technique. The following inventory is the reference that Section 11.05 uses to generate the coverage heat map and that the atlas_attack_tree_mapper.py deliverable encodes programmatically. AML.T0051 — LLM Prompt Injection. The technique covering direct and indirect injection of adversarial instructions into LLM prompt context. Studied in Chapter 6. Detection layer: L1 (Track 1 Sigma keywords), L2 (Track 1 centroid-similarity gate, Track 2 perplexity), L3 (Track 1 injection classifier). Coverage status: partial — direct injection and the obfuscation families in the classifier's training data are detected; injection variants unlike anything labelled are an L3 anomaly-detection gap (Chapter 12 fills it with an Isolation Forest and an intent classifier). AML.T0054 — Prompt Injection via Adversarial Role-play. The jailbreak-specific technique: using role-play framing to bypass alignment. Studied in Chapter 7. Detection layer: L1 (Track 1 Sigma jailbreak keywords, Track 3 shot count), L2 (Track 2 perplexity), L3 (Track 1 semantic jailbreak classifier), L4 (Tracks 4 and 5 for multi-turn erosion and payload splitting). Coverage status: partial — known templates and multi-turn patterns within a session are detected; novel role-play framings outside the classifier's training distribution are a residual gap. AML.T0043 — Craft Adversarial Data. The generic technique for generating adversarial examples: FGSM, PGD, C&W, black-box boundary attack, adversarial patches. Studied in Chapters 7 and 10. Detection layer: L2 (Track 2 perplexity for optimised adversarial text suffixes; Track 7 squeezer disagreement and consistency check), L3 (Track 7 adversarial classifier). Coverage status: partial — gradient-based adversarial examples detected; novel attack families outside Track 7 training distribution are an L3 gap. AML.T0015 — Evade ML Model. The evasion outcome technique: inputs that cause misclassification without triggering detection. Studied as the objective across Chapters 6, 7, and 10. Detection layer: L2 (Track 7 squeezer), L3 (Track 7 adversarial classifier). Coverage status: partial — same gap as AML.T0043. AML.T0020 — Poison Training Data. The training-time attack technique: corrupting labelled training data to induce model misbehaviour on specific inputs. Studied in Chapter 8. Detection layer: L1 (the Chapter 8 poisoning monitor's label-distribution Sigma rule, which runs upstream on training data rather than in the gateway). Coverage status: partial — overt label distribution anomalies detected; slow-drift poisoning below per-batch threshold is L4 gap (Chapter 13 fills with drift monitor). AML.T0018 — Backdoor ML Model. The model backdoor technique: training a trigger mechanism into model weights. Adjacent to data poisoning (Chapter 8). Detection layer: L1 (subset of the Chapter 8 poisoning rules — specific label pattern anomalies consistent with backdoor trigger insertion). Coverage status: low — training-time detection only; inference-time backdoor trigger detection requires a dedicated track not yet built. AML.T0040 — ML Model Inference API Access. The model extraction access technique: systematic querying of the production API to reconstruct model behaviour. Studied in Chapter 9. Detection layer: L1 (Track 6 per-request Sigma), L4 (Track 6 per-user query monitor and cross-user correlator). Coverage status: partial — per-user extraction is detected, and the cross-user correlator links accounts whose queries share structure; distributed extraction across accounts with nothing observable in common is an L4 gap (Chapter 13 fills). AML.T0017 — Develop Capabilities. ML attack staging technique: developing adversarial tools, crafting attack datasets, building surrogate models. Studied as staging context in Chapters 9–10. Detection layer: not detectable at inference time — staging occurs in attacker-controlled environment. Coverage status: none (no runtime detection possible; addressed by threat intelligence, not gateway rules). AML.T0043 — Adversarial Patch. Physical-domain adversarial attack: patches that cause misclassification of camera inputs. Studied in Chapter 10 Section 10.8. Detection layer: L2 (Section 10.8 patch_detector.py — spatial region anomaly detection). Coverage status: deployment-specific — only relevant for camera-facing systems; not included in the generic seven-track gateway. The seven-track gateway does not cover AML.T0043; camera-facing deployments require a separate Track 8 extension. AML.T0024.000 — Membership Inference Attack. Privacy attack: determining whether a specific record was in the training set. Studied in Chapter 8. Detection layer: not detectable by inference-time gateway rules — requires differential privacy instrumentation and query audit logs. Coverage status: none in gateway; addressed by DP-SGD training and membership inference monitoring (Chapter 8 deliverables). AML.T0024.001 — Invert ML Model. Model inversion: recovering approximations of training data from model outputs. Studied in Chapter 8. Coverage status: none in gateway — detection requires output analysis for reconstruction patterns, not yet implemented.

Part 5 Detection Chain

Heading

The Technique-to-Detection-to-Sigma Chain

Body

The technique-to-detection-to-Sigma chain is the operational connection between the ATLAS taxonomy and the production detection programme. For each ATLAS technique, the chain specifies four things: what observable evidence the technique leaves, which detection layer can observe it, which Sigma rule (or Python detector) captures it, and which gateway track deploys it. When the chain is complete for a technique, that technique has measurable detection coverage. When it is incomplete at any link, there is a gap. Applying the chain to AML.T0040 (ML Model Inference API Access): Observable evidence: the technique produces elevated query rates from a single source, reduced variance in query parameters (systematic probing produces more uniform queries than normal usage), and output entropy trending toward zero across a session as the attacker homes in on decision boundaries. Detection layer: L1 for per-request signals (a single anomalously structured query), L4 for cross-session signals (accumulation of query rate, variance, and entropy metrics across the session window). Sigma rule: extraction_detector.yml (L1 Sigma rule on per-request anomaly fields) and the Track 6 query monitor (Python, not Sigma, because Sigma does not natively support stateful per-user accumulation). Gateway track: Track 6. The per-request Sigma rule runs inline; the query monitor's per-user accumulation runs asynchronously against the state store. Chain complete? Partially. The per-request and per-user extraction chains are complete, and the cross-user correlator links accounts whose queries share structure. The distributed multi-account extraction chain is incomplete at the L4 link for accounts with nothing observable in common. Detecting such a coordinated campaign requires a fleet-level aggregation layer that Chapter 13 builds. Applying the chain to AML.T0017 (Develop Capabilities): Observable evidence: none at inference time. Capability development happens in attacker-controlled environments. The only observable evidence is in threat intelligence feeds (known adversarial toolkits, published attack codebases) or in staging artefacts if the attacker tests their tools against a shadow of the production system. Detection layer: none at runtime. This technique is addressed by threat intelligence consumption, not by gateway rules. Chain complete? No detection chain exists for AML.T0017 in the gateway. This is correct: not every ATLAS technique produces runtime-observable evidence. Documenting that the chain is intentionally incomplete for a technique is as important as documenting gaps that should be filled. The distinction between intentional gaps (no runtime evidence exists) and actionable gaps (runtime evidence exists but no rule captures it) is critical for the coverage heat map. Section 11.05 introduces a three-tier coverage score: 0 (no detection, gap is actionable), 1 (partial detection, gap exists but some coverage), and 2 (full detection). Techniques with intentional gaps receive a special notation rather than a 0 score, so they do not inflate the gap backlog with work that cannot be done.

Part 6 Navigator

Heading

ATT&CK Navigator: Reading and Building Heat Maps

Body

ATT&CK Navigator is MITRE''s open-source tool for visualising ATT&CK and ATLAS coverage. It renders the technique matrix as a colour-coded heat map: techniques with no detection coverage appear with no fill or in red; techniques with partial coverage in amber; techniques with full coverage in green. The heat map is generated from a JSON layer file that maps technique IDs to scores and colour values. For AI security programmes, the Navigator heat map serves two audiences with different needs. Detection engineers use it as a coverage backlog: the red cells are the gap backlog, ordered by the likelihood and impact scores assigned during gap analysis in Section 11.05. CISO and security leadership use it as a programme communication artefact: a single slide with the heat map communicates the detection programme''s current state, its known gaps, and its improvement trajectory without requiring the audience to understand Sigma rule syntax or Python detector code. The Navigator layer JSON structure is simple. Each technique entry has a techniqueID (the ATT&CK or ATLAS technique ID), a score (typically 0–2 for no/partial/full coverage), and an optional comment field (the name of the Sigma rule or detector providing coverage). The full layer file also has a name, a description, and a domain field (enterprise-attack for ATT&CK, atlas for ATLAS). The attck_navigator_export.py deliverable generates this layer file from the seven-track gateway''s current rule inventory. It reads the mitre_technique fields from each rule''s metadata (validated by rule_metadata_validator.py from Section 11.02), computes coverage scores from the technique inventory in atlas_attack_tree_mapper.py, and outputs a Navigator-compatible JSON file that can be loaded directly into the Navigator UI at attack.mitre.org/versions/v14/nav. Navigator heat maps degrade over time as new ATLAS techniques are published and new attack families emerge. The quarterly coverage review cadence (Section 11.05) includes regenerating the Navigator export from the current rule inventory, comparing it to the previous quarter''s export, and identifying any newly published techniques that are undetected. Techniques that move from "not in ATLAS" to "in ATLAS but undetected" are added to the detection backlog at the priority appropriate to their likelihood and impact.

    L3 = 'L3_ml'

def coverage_score(status: CoverageStatus) -> int:
    scores = {
        CoverageStatus.FULL: 2,
        CoverageStatus.PARTIAL: 1,
        CoverageStatus.LOW: 0,
        CoverageStatus.NONE_INTENTIONAL: -1,   # intentional; exclude from gap backlog
        CoverageStatus.NONE_ACTIONABLE: 0,
    }
    return scores[status]

def print_technique_report(techniques: list[ATLASTechnique]) -> None:
    print('\nATLAS Technique Coverage Report — Chapters 6-10')
    print(f'Techniques in inventory: {len(techniques)}\n')

    actionable = [t for t in techniques if t.coverage_status == CoverageStatus.NONE_ACTIONABLE]
    partial = [t for t in techniques if t.coverage_status in (CoverageStatus.PARTIAL, CoverageStatus.LOW)]
    intentional = [t for t in techniques if t.coverage_status == CoverageStatus.NONE_INTENTIONAL]
    full = [t for t in techniques if t.coverage_status == CoverageStatus.FULL]

    print(f'Full coverage:          {len(full)}')
    print(f'Partial / Low:          {len(partial)} (actionable gaps)')
    print(f'None — actionable:      {len(actionable)} (evidence exists; rule not built)')
    print(f'None — intentional:     {len(intentional)} (no runtime evidence; correct gap)')
    print()

    print('Actionable gaps (build these next):')
    for t in actionable + partial:
        score = coverage_score(t.coverage_status)
        print(f'  [{score}/2] {t.technique_id} — {t.name}')
        print(f'    Gap:  {t.residual_gap[:100]}...' if len(t.residual_gap) > 100 else f'    Gap:  {t.residual_gap}')
        print(f'    Next: {t.actionable_next_step[:100]}...' if len(t.actionable_next_step) > 100 else f'    Next: {t.actionable_next_step}')

    print()
    print('Intentional gaps (no action required):')
    for t in intentional:
        print(f'  {t.technique_id} — {t.name}: {t.chain_gap_link}')

def get_navigator_scores(techniques: list[ATLASTechnique]) -> dict[str, int]:
    '''Returns technique_id → Navigator score (0-2) for attck_navigator_export.py.'''
    return {
        t.technique_id: max(0, coverage_score(t.coverage_status))
        for t in techniques
    }

def build_navigator_layer(
    layer_name: str = 'AI Security Mastery — Seven-Track Gateway Coverage',
    description: str = 'Chapter 11 Section 11.04 — ATLAS technique coverage for the seven-track gateway',

    scores = get_navigator_scores(TECHNIQUES)

    technique_entries: list[dict] = []
    for technique in TECHNIQUES:
        score = scores[technique.technique_id]
        intentional = technique.coverage_status == CoverageStatus.NONE_INTENTIONAL

        entry: dict = {
            'techniqueID': technique.technique_id,
            'comment': (

                f'Coverage: {technique.coverage_status.value}. '

Common Mistakes

Id

CM11.04.1

Mistake

Treating MITRE ATLAS as a complete replacement for ATT&CK in an AI security programme

Why It Happens

ATLAS is AI-specific and therefore feels more directly relevant. Practitioners building AI security programmes sometimes focus exclusively on ATLAS and neglect the ATT&CK coverage for the infrastructure hosting the model.

Why It Matters

An attacker who cannot successfully execute an ATLAS technique against the model will pivot to ATT&CK techniques against the infrastructure: compromising the model serving host, accessing the training data store, or exfiltrating model weights through the host file system. An AI security programme with ATLAS coverage but no ATT&CK coverage protects the model while leaving the surrounding infrastructure unmonitored.

Correct Approach

Use ATLAS for model-layer detection (the seven-track gateway). Use ATT&CK for infrastructure-layer detection (the model serving host, the API gateway, the training pipeline infrastructure, the data store). Both frameworks are required for a complete AI security detection programme.

Id

CM11.04.2

Mistake

Counting intentional gaps (no runtime evidence) in the detection gap backlog

Why It Happens

The heat map shows grey cells for intentional gaps. Without understanding the distinction between intentional and actionable gaps, practitioners add all uncoloured cells to the detection backlog.

Why It Matters

AML.T0017 (Develop Capabilities) has no runtime detection chain because staging occurs in attacker-controlled environments. Adding it to the detection backlog creates work that cannot be completed, demoralises the team, and inflates the apparent gap count without reflecting real risk.

Correct Approach

Distinguish explicitly between intentional gaps (no runtime evidence; documented and accepted) and actionable gaps (evidence exists; rule not yet built). The Navigator export uses grey for intentional gaps and red for actionable gaps. Only red cells belong in the detection backlog.

Id

CM11.04.3

Mistake

Using ATT&CK technique IDs (TNNNN) in Sigma rules for model-layer detections

Why It Happens

ATT&CK is the more widely known framework. Practitioners familiar with ATT&CK default to its technique IDs even for adversarial ML detections.

Why It Matters

ATT&CK technique IDs in model-layer Sigma rules produce incorrect coverage heat maps: the rule appears to cover an enterprise IT technique rather than an adversarial ML technique. The ATLAS heat map shows the model-layer gap as uncovered even though a rule exists, because the rule''s mitre_technique field references the wrong framework.

Correct Approach

Use ATLAS technique IDs (AML.TNNNN) in Sigma rules for all model-layer detections. Use ATT&CK technique IDs (TNNNN) for infrastructure-layer detections. The rule_metadata_validator.py from Section 11.02 validates technique IDs against the known-techniques list; extend that list to include all ATLAS IDs as they are mapped.

Id

CM11.04.4

Mistake

Treating partial coverage as equivalent to full coverage when communicating to leadership

Why It Happens

Amber cells on the Navigator heat map look similar to green cells at a glance. When presenting to leadership under time pressure, practitioners sometimes describe partial coverage as covered without qualification.

Why It Matters

A technique marked as partially covered has a confirmed residual gap. If the residual gap corresponds to a high-likelihood attack variant (e.g. obfuscated injection variants for AML.T0051), presenting it as covered misrepresents the security posture and may delay investment in the Chapter 12 remediations.

Correct Approach

Always present coverage with the partial/full distinction. The Navigator legend makes this clear visually. In written reports, list partial coverage techniques with their residual gap description alongside the full coverage techniques.

Id

CM11.04.5

Mistake

Generating the Navigator heat map once and treating it as static documentation

Why It Happens

Generating the Navigator export takes effort. Once produced, it feels complete. The heat map goes into a report and is not updated until the next major review.

Why It Matters

MITRE ATLAS adds new techniques as new adversarial ML research matures. A heat map that was accurate when generated becomes stale as new techniques are published. Techniques that did not exist when the heat map was generated appear as neither covered nor gapped — they are simply invisible, which is worse than a documented gap.

Correct Approach

Regenerate the Navigator export quarterly from the current rule inventory using attck_navigator_export.py. Compare to the previous quarter''s export to identify newly published techniques. Add any newly undetected techniques to the detection backlog at the appropriate priority.

Section Summary

What You Learned

MITRE ATT&CK for Enterprise and MITRE ATLAS together supply the technique taxonomy that converts detection coverage from an assertion into a measurement. ATT&CK covers the infrastructure surrounding the AI system; ATLAS covers the model layer itself. For the seven-track gateway, eleven ATLAS techniques are relevant: six have partial or low coverage with actionable gaps; two have intentional gaps where no runtime detection chain is possible; three are currently undetected with actionable future tracks. The technique-to-detection-to-Sigma chain is now complete for all detectable techniques: ATLAS technique → detection layer → Sigma rule or Python detector → gateway track. Section 11.05 visualises this chain as a coverage heat map.

Key Terms

Term

MITRE ATT&CK

Definition

A globally accessible knowledge base of adversary behaviour organised into 14 tactics and hundreds of techniques, based on real-world observations. Used for infrastructure-layer detection coverage measurement in AI security programmes.

Term

MITRE ATLAS

Definition

An extension of ATT&CK for adversarial ML systems. Covers techniques specific to ML model attacks: prompt injection, adversarial examples, data poisoning, model extraction, and supply chain compromise. Used for model-layer detection coverage.

Term

Technique-to-detection chain

Definition

The four-link chain connecting an ATLAS technique to production detection: ATLAS technique → observable evidence → detection layer → Sigma rule or Python detector → gateway track → alert. A complete chain means the technique has measurable coverage.

Term

Actionable gap

Definition

A coverage gap where runtime evidence of the technique exists but no detection rule captures it. Belongs in the detection engineering backlog. Distinguished from intentional gaps where no runtime evidence is possible.

Term

Intentional gap

Definition

A coverage gap where no runtime detection chain is possible because the technique occurs in an attacker-controlled environment (e.g. AML.T0017 — Develop Capabilities). Documented and accepted; does not belong in the detection engineering backlog.

Term

ATT&CK Navigator

Definition

MITRE''s open-source heat map tool for visualising ATT&CK and ATLAS technique coverage. Takes a JSON layer file as input and renders a colour-coded matrix. Green = full coverage, amber = partial, red = no coverage, grey = intentional gap.
