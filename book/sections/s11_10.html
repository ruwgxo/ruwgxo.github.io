Detection Engineering Workflow: Hypothesis to Production

By the end of this section
  • Execute all seven workflow phases for a new detection rule, naming the exit criterion and responsible role for each phase
  • Write a falsifiable detection hypothesis for an ATLAS technique, distinguishing it from a vague detection goal
  • Apply the design phase to determine log source, feature selection, FPR target, and test case structure before writing a single line of Sigma
  • Calculate time-to-detect for a completed detection and explain why TTD is a security metric rather than an engineering productivity metric
  • Identify which workflow phase each Section 11.02–11.09 tool belongs to and confirm integration between tools across phase boundaries
  • Describe the rule improvement phase trigger conditions: FPR breach, false negative confirmation, coverage score regression, and quarterly review

Section Overview

One Line Summary

The seven-phase detection engineering workflow — Hypothesis, Design, Build, Test, Deploy, Monitor, Improve — is the repeatable procedure that converts a threat intelligence signal or a coverage gap into a production detection rule within a measurable, tracked time-to-detect window.

Why This Section Exists

Sections 11.02 through 11.09 built the infrastructure: a DaC pipeline, a coverage measurement system, a Sigma rule format, a maturity model, and FPR management tooling. Infrastructure is not a workflow. A detection team that has all of these tools but no shared procedure for how to use them will use them inconsistently: some engineers write tests before rules, others after deployment; some start from a threat intelligence report, others from an analyst complaint about a missed alert; some set FPR targets before building, others calibrate post-deployment when the SOC is already fatigued. The seven-phase workflow standardises that procedure. It specifies what happens in what order, what documentation must exist at each phase gate, and what the exit criterion is before the rule advances to the next phase. It integrates all tools from Sections 11.02 through 11.09 into a single coherent procedure — the DaC pipeline enforces phase gates 4 and 5, the FPR manager enforces phase 6, the coverage heat map validates phase 7. The workflow also introduces time-to-detect (TTD) as the programme-level security metric that measures how quickly a known threat translates into a deployed detection. TTD is not an engineering metric. It is a security metric: the longer the TTD, the longer the adversary operates undetected. A programme with excellent tools but a 30-day average TTD is less secure than one with simpler tools and a 5-day TTD.

Position In Chapter

Section 11.10 is the integration section. It binds together everything built in Sections 11.02–11.09 into the operating procedure the team runs for every new detection. Section 11.11 immediately applies this workflow to all ten OWASP LLM Top 10 vulnerabilities, demonstrating the workflow at scale.

Prose Content

Part 1 Workflow Overview

Heading

The Seven-Phase Workflow: Why Order Matters

Body

Detection engineering without a defined workflow produces a common anti-pattern: rules that exist but are not trusted, coverage that is claimed but not measured, and detection programmes that grow in rule count while declining in defensive value. The seven-phase workflow imposes an order that prevents each of these failure modes. The order matters because each phase produces an output that is an input to the next. A hypothesis (Phase 1) that is not falsifiable produces a design (Phase 2) that cannot be tested, which produces tests (Phase 3) that do not validate the actual security question, which produces a deployed rule (Phase 5) that no one trusts. Conversely, a well-formed hypothesis directly constrains the design: the hypothesis names the observable evidence, the log fields that carry it, the threshold or matching pattern that distinguishes signal from noise, and the FPR target that defines acceptable collateral detection. By the time the engineer sits down to write Sigma, all of these decisions are already made. The Build phase (Phase 3) is execution of a design, not a design session. The seven phases and their phase-gate exit criteria: Phase 1 — Hypothesis: falsifiable detection hypothesis documented. Phase 2 — Design: log source, feature, rule logic, FPR target, and test cases documented; design review approved. Phase 3 — Build: Sigma rule authored; positive and negative tests written; metadata complete. Phase 4 — Test: CI passes lint, test, and coverage diff; no regression. Phase 5 — Deploy: PR reviewed; pipeline merge to staging; 24-hour staging observation; merge to main. Phase 6 — Monitor: FPR tracking active; first analyst dispositions collected within 7 days. Phase 7 — Improve: rule refinement from FP/FN feedback; exception updates; retirement trigger defined. Each phase gate is enforced by a combination of tooling (phases 4–6) and process (phases 1–3 and 7). Tooling enforcement is the stronger control: the CI pipeline physically prevents a rule from deploying if it fails phase 4. Process enforcement depends on team discipline and is supported by the documentation templates in the detection_engineering_workflow.py deliverable.

Part 2 Hypothesis

Heading

Phase 1 — Hypothesis: Falsifiable, Specific, and Grounded

Body

A detection hypothesis is not a detection goal. "Detect prompt injection" is a goal. A hypothesis is a testable prediction: given that an adversary is attempting technique AML.T0051 against the production inference API, they will leave the following observable evidence in the ai_gateway log, distinguishable from legitimate traffic by the following characteristics, detectable by the following mechanism, with a false positive rate within the following bounds. The three properties of a well-formed detection hypothesis: Falsifiable: the hypothesis predicts specific observable evidence. If the evidence is not present in the logs when the attack occurs, the hypothesis is wrong and the detection rule built from it will miss the attack. A hypothesis that cannot be falsified cannot produce a rule that can be validated. "Detect malicious prompts" is not falsifiable — there is no log field called malicious_prompt. "Detect prompts where injection_score exceeds 0.90 as computed by Track 1''s injection classifier" is falsifiable — if injection_score is absent or consistently below 0.90 during a confirmed attack, the hypothesis is falsified and must be revised. Specific: the hypothesis names the attack variant, the observable evidence field, the detection mechanism, and the evasion variants that will and will not be caught. "Detect direct injection via keyword prefix matching — covers unobfuscated variants; does not cover base64-encoded variants (separate hypothesis required for Track 1's centroid-similarity gate)" is specific. "Detect injection attempts" is not. Grounded: the hypothesis is grounded in a threat intelligence source, an ATLAS technique, an analyst observation, or a coverage gap from Section 11.05. A hypothesis that is not grounded in evidence of adversary behaviour may detect a theoretical attack that no adversary is actually using, consuming engineering effort without improving actual security posture. The detection_hypothesis_ generator.py deliverable takes an ATLAS technique ID or OWASP LLM category as input and generates the hypothesis scaffold grounded in the technique''s known observable evidence. Hypothesis inputs: the three primary sources are (1) threat intelligence — a new ATLAS technique, a published adversarial ML paper, or a threat actor report that names a novel attack variant; (2) coverage gap — a score-0 or score-1 technique on the heat map with identified actionable evidence; (3) analyst observation — a SOC analyst who observed suspicious behaviour that no rule caught. Each source is valid; each produces a different quality of initial hypothesis that the Phase 2 design validates or refutes before building begins.

Part 3 Design

Heading

Phase 2 — Design: Decisions Made Before a Line of Sigma Is Written

Body

The design phase converts the hypothesis into a complete specification that a different engineer could implement without asking questions. A design that requires the implementer to make decisions is an incomplete design; those decisions will be made inconsistently across the team and will produce rules with undocumented assumptions that are invisible to reviewers. The seven design decisions, in order: Decision 1 — Log source: which AI gateway log category carries the evidence named in the hypothesis? The ai_log_field_taxonomy.py from Section 11.06 is the reference. If the required field is not in the taxonomy, it is a new field that requires a coordinated change with the gateway engineering team before the rule can be built. A rule that depends on a field that does not yet exist cannot advance past Phase 2 until the field is added to the log schema. Decision 2 — Feature selection: which specific field or fields carry the signal? For a rate-based detection, what is the aggregation field and the grouping field? For a compound detection, which two or more fields must simultaneously satisfy conditions? Feature selection is the decision that most directly determines both TPR and FPR: a feature that is specific to adversarial behaviour produces a high- TPR low-FPR rule; a feature that correlates with adversarial behaviour but also with legitimate unusual behaviour produces a high-FPR rule that requires the compound condition design pattern from Section 11.06 to reduce. Decision 3 — Rule logic: keyword, field threshold, rate aggregation, or compound? The five operator types from Section 11.06 map to specific detection scenarios. The design names the operator type and the specific condition structure, including any NOT conditions for known-good exclusions. Decision 4 — FPR target: from the per-track targets in Section 11.09 Table 1. If the new rule is for an existing track, use the documented target. If the new rule introduces a new track, set the target based on the alert action (block rules: ≤1%, flag rules: 2–5%) and document the rationale. Decision 5 — Test cases: write the positive and negative test cases before writing the rule. At minimum: two positive cases (minimum-evasion attack and one obfuscated variant), two negative cases (representative legitimate user prompt and a technical edge-case prompt close to the detection boundary). These test cases are the contract: the rule is correct if and only if it passes all four. Decision 6 — Evasion assessment: which evasion variants does this rule miss? Every rule has a known evasion surface. The design documents it explicitly, maps it to the coverage score it will produce (partial, not full), and names the complementary Layer 2 or Layer 3 detection that covers the evasion surface if one exists. Decision 7 — Owner: the GitHub handle of the engineer responsible for this rule through its entire lifecycle, including FPR monitoring, quarterly review, and retirement decision. Rules without a documented owner are nobody''s responsibility and will not be maintained.

Part 4 Build

Heading

Phase 3 — Build: Execution of a Complete Design

Body

If the design is complete, the build phase is mechanical. The engineer authors the Sigma rule using the format from Section 11.06, populating every field from the design document. The metadata fields (title, id, status, author, tags) are filled from the design. The logsource block is filled from Decision 1. The detection block implements Decision 3 using the operators from Decision 2. The level field is set from the FPR target in Decision 4. The build phase has one creative task that the design does not pre-specify: writing the test cases as executable pytest fixtures. The test case descriptions from Decision 5 are inputs that generate actual prompt strings, expected detection scores, and assertion conditions. The fixture authoring requires choosing specific prompt text that represents the attack at minimum evasion — close enough to the real attack to validate detection, not so extreme that it validates detection only on an attack variant that no real adversary would use. Three build anti-patterns to avoid: Anti-pattern 1 — Writing the rule before writing the tests. The rule will be written to pass; the tests will be written to pass the rule rather than to validate the security requirement. Tests written after the rule are not a test of the rule; they are a documentation of what the rule does. Write tests first. Anti-pattern 2 — Copying a rule from a public Sigma repository without adapting the logsource and field names to the gateway schema. Public Sigma rules target standard SIEM log schemas (Windows Event Log, Sysmon, CloudTrail). A Track 1 rule copied from a public repository will reference EventID, CommandLine, or ParentProcessName — none of which exist in the ai_gateway log category. The rule will pass lint but fire on nothing in production. Anti-pattern 3 — Setting status: stable on the first commit. New rules start at status: experimental. They graduate to test after two weeks on staging with no critical FPR breach. They graduate to stable after confirmed true positives in production. The CI pipeline enforces this: experimental rules do not deploy to production.

Part 5 Test And Deploy

Heading

Phase 4 and 5 — Test and Deploy: Gate Enforcement

Body

Phase 4 and Phase 5 are the most automated phases in the workflow. The CI pipeline from Section 11.02 enforces both gate conditions without human intervention. Phase 4 — Test gate: the CI pipeline runs three checks on the PR: (a) sigma check confirms Sigma syntax; yamllint confirms YAML formatting; rule_metadata_validator.py confirms all eight metadata fields are present and valid. (b) pytest runs the test suite for the tracks touched by the PR, including the new positive and negative fixtures. A test failure blocks the PR with the test name and assertion that failed. (c) attck_coverage_heatmap.py --diff runs against the current baseline. If the new rule''s ATLAS tag advances a technique score (e.g. a previously score-0 technique gains a rule and moves to score 1), the diff shows the improvement. If the PR inadvertently regresses a coverage score — possible if the PR also modifies an existing rule — the diff triggers a CI warning that must be resolved before merge. Phase 5 — Deploy gate: merge to staging triggers lint, test, and deploy-to-staging. The staging deployment runs against a shadow copy of production traffic for 24 hours. The false_positive_manager.py from Section 11.09 monitors the staging alert rate against the FPR target during the 24-hour window. If the staging FPR exceeds the target by more than 50% relative (a more permissive threshold than the production 20% relative breach, because staging traffic samples are smaller), the merge-to-main PR is blocked with the FPR observation. After 24 hours at acceptable FPR, the merge-to-main PR is opened by the pipeline automatically. A second CI run confirms tests pass on main. The merge triggers production deployment. The rule is live. The TTD clock starts at Phase 1 (hypothesis documented) and stops at Phase 5 (production deployment). Target TTD: under 7 days for catalogued ATLAS techniques with known observable evidence. Under 24 hours for actively exploited zero-days where the detection hypothesis is already formed by the threat intelligence team and the Phase 1–2 cycle is compressed. A TTD above 14 days for a catalogued technique is a programme efficiency problem that the workflow template''s time tracking identifies.

Part 6 Monitor

Heading

Phase 6 — Monitor: The Production Feedback Loop

Body

A rule that has been deployed is not finished. Phase 6 is the production observation phase that determines whether the rule performs as designed. Three monitoring signals feed the Phase 7 improvement cycle: Signal 1 — Per-rule FPR from false_positive_manager.py. Within 7 days of production deployment, the rule should have accumulated enough analyst dispositions to produce a meaningful 7-day rolling FPR estimate. The rule''s FPR against the production traffic sample is compared to the FPR target set in Phase 2. A rule that performs as designed stays in monitoring. A rule whose FPR exceeds the target by 20% relative triggers a DaC queue ticket and advances immediately to Phase 7. Signal 2 — True positive confirmation. Within the first 30 days of production deployment, at least one confirmed true positive should appear if the threat is actively present. For low-prevalence attacks (model inversion, backdoor triggers), this signal may take longer to materialise. For high-prevalence attacks (direct injection, jailbreak templates), the absence of confirmed true positives within 30 days on a public API is a signal that the rule may not be firing on real attacks — prompting a Phase 4 regression check with recent production traffic as the test corpus. Signal 3 — Quarterly rule review. All production rules are reviewed quarterly as part of the detection programme cadence. The review checks four conditions: (a) the rule''s ATLAS technique has not been updated with a new evasion variant that the rule cannot detect; (b) the log fields the rule references still exist in the current gateway schema (schema changes can silently break rules); (c) the FPR has been stable within target for the quarter; (d) the rule is still relevant — the threat it addresses has not been eliminated by a preventive control, making the detection rule redundant.

Part 7 Improve

Heading

Phase 7 — Improve: Refinement, Retirement, and Backfill

Body

Phase 7 is the improvement cycle triggered by Phase 6 monitoring signals. Three trigger conditions produce three different Phase 7 responses: Trigger 1 — FPR breach: the 7-day rolling FPR exceeds the target by more than 20% relative. Response: run threshold_calibration_harness.py to identify whether the threshold needs recalibration; review the exception list for expired entries that should have been renewed; inspect the top-10 recent false positive inputs for a common pattern that can be addressed by adding a NOT condition to the rule. The improvement is implemented as a calibrate/ branch PR, not a direct main commit. Trigger 2 — False negative confirmation: a confirmed attack was not detected by this rule. Response: add the attack input as a positive test fixture (it is now a known-bad input that the rule must catch). If the current rule logic cannot be adjusted to catch this variant without unacceptable FPR increase, it is a residual gap that gets added to the coverage backlog as a new detection hypothesis in Phase 1. The confirmed false negative is not hidden in the quarterly review — it is documented in the rule''s false_positive_notes field as a known miss with the date and the attack variant description. Trigger 3 — Retirement: the quarterly review determines the rule is no longer relevant. Response: the two-step retirement process from Section 11.02 — first, set status: deprecated and suppress alerts for two weeks; second, if no confirmed true positives appear during the two-week window, remove the rule from the repository. The retirement PR documents the reason and the date in the commit message and in the ATLASTechnique registry residual_gap field if the rule was the only coverage for a technique. Backfill: every Phase 7 improvement produces a regression test if it was triggered by a false positive or false negative. The regression test prevents the improvement cycle from re-introducing the original problem. After three or more Phase 7 cycles on the same rule, the detection engineering team reviews whether the root cause is the rule itself (which can be improved) or the detection approach for the technique (which may require a different Layer or a different primitive entirely).

Part 8 Ttd

Heading

Time-to-Detect: The Security Metric of the Workflow

Body

Time-to-detect (TTD) is the elapsed time from threat discovery to deployed production detection rule. It is a security metric — not a productivity metric — because it measures the window during which the adversary operates undetected. A shorter TTD means a smaller adversary advantage window. TTD is measured per detection rule from Phase 1 start to Phase 5 production deployment. It is tracked in the detection_engineering_workflow.py as a timestamp on each phase completion. The programme reports median TTD, 90th-percentile TTD, and TTD by threat source (catalogued technique vs analyst-discovered vs zero-day). Target TTD by threat source: Catalogued ATLAS technique with full documentation: under 7 days. A technique listed on atlas.mitre.org with known observable evidence, existing field mappings in the gateway log taxonomy, and a clear detection layer assignment should produce a hypothesis in Phase 1 within one day, a design in Phase 2 within one day, a Sigma rule in Phase 3 within one day, CI passing in Phase 4 within one day, and staging + production in Phase 5 within two days. Seven days is a conservative target that accounts for review cycles. Analyst-discovered attack (no ATLAS entry): under 14 days. The Phase 1 hypothesis may require additional investigation to establish the observable evidence pattern. The Phase 2 design may require a new log field if the attack produces evidence not yet in the gateway schema. The additional complexity justifies a 14-day target. Actively exploited zero-day: under 24 hours. When threat intelligence confirms active exploitation in the wild, the Phase 1–2 cycle is compressed: the detection_hypothesis_generator.py produces an initial hypothesis from the threat report in minutes; the Phase 3 build uses an emergency rule template that omits non-critical metadata (filled post-deployment); the Phase 4–5 pipeline runs the expedited path that bypasses the 24-hour staging window (the staging observation is conducted in parallel with production deployment, not as a prerequisite). A TTD above 14 days for a catalogued technique is a workflow efficiency problem. The workflow template identifies which phase consumed the most time. Common root causes: Phase 2 blocked on log field not in taxonomy (resolved by expediting the gateway schema change); Phase 4 blocked on test failures that reveal a design flaw (resolved by returning to Phase 2); Phase 5 blocked on staging FPR above target (resolved by threshold recalibration or exception addition). Each root cause has a documented resolution path in the workflow template.

#!/usr/bin/env python3
'''detection_engineering_workflow.py
Seven-phase detection engineering workflow manager.
Tracks phase completions, computes TTD, enforces phase gate documentation.
Chapter 11, Section 11.10 — AI Security Mastery
Author: Raghav Dinesh | github: ruwgxo

Usage:
  python3 detection_engineering_workflow.py --new-rule "AML.T0051" "ruwgxo"
  python3 detection_engineering_workflow.py --advance <rule_id> --phase 2
  python3 detection_engineering_workflow.py --status
  python3 detection_engineering_workflow.py --ttd-report
'''

from __future__ import annotations
import argparse
import json
import pathlib
import sys
import uuid
from dataclasses import dataclass, field
from datetime import datetime, timedelta, timezone
from typing import Literal

DATA_DIR = pathlib.Path('workflow_data')
WORKFLOW_FILE = DATA_DIR / 'active_rules.json'

Phase = Literal[1, 2, 3, 4, 5, 6, 7]

PHASE_NAMES = {
    1: 'Hypothesis',
    2: 'Design',
    3: 'Build',
    4: 'Test',
    5: 'Deploy',
    6: 'Monitor',
    7: 'Improve',
}

PHASE_EXIT_CRITERIA = {
    1: 'Falsifiable hypothesis document: ATLAS technique, observable evidence, mechanism, evasion surface, FPR expectation',
    2: 'Seven design decisions documented and peer-reviewed; log field in taxonomy confirmed',
    3: 'Sigma rule authored; 4 test cases written; all metadata fields populated; status: experimental',
    4: 'CI passes: sigma check, yamllint, metadata validator, pytest, coverage diff (no regression)',
    5: 'Staging FPR within 150% of target after 24h; production deployment complete',
    6: '7-day rolling FPR within target; first analyst dispositions recorded; quarterly review scheduled',
    7: 'FPR breach resolved OR false negative documented OR rule retired per two-step process',
}

TTD_TARGETS_DAYS = {
    'catalogued': 7,
    'analyst_discovered': 14,
    'zero_day': 1,
    'backlog_gap': 30,
}

# ---------------------------------------------------------------------------
# Data model
# ---------------------------------------------------------------------------

@dataclass
class PhaseRecord:
    phase: int
    name: str
    entered_at: str
    completed_at: str = ''
    exit_criterion_met: bool = False
    notes: str = ''

@dataclass
class WorkflowRule:
    rule_id: str
    atlas_technique: str
    owner: str
    threat_source: str
    ttd_target_days: int
    current_phase: int
    phases: list[dict] = field(default_factory=list)
    created_at: str = ''
    deployed_at: str = ''
    retired: bool = False

    @property
    def ttd_elapsed_hours(self) -> float:
        if not self.created_at:
            return 0.0
        start = datetime.fromisoformat(self.created_at)
        end_str = self.deployed_at or datetime.now(timezone.utc).isoformat()
        end = datetime.fromisoformat(end_str)
        return (end - start).total_seconds() / 3600

    @property
    def ttd_elapsed_days(self) -> float:
        return self.ttd_elapsed_hours / 24

    @property
    def ttd_status(self) -> str:
        if self.deployed_at:
            return 'COMPLETE'
        elapsed = self.ttd_elapsed_days
        target = self.ttd_target_days
        if elapsed > target * 1.5:
            return 'OVERDUE'
        if elapsed > target:
            return 'AT_RISK'
        return 'ON_TRACK'

# ---------------------------------------------------------------------------
# Storage
# ---------------------------------------------------------------------------

def _load() -> list[dict]:
    if not WORKFLOW_FILE.exists():
        return []
    with open(WORKFLOW_FILE) as f:
        return json.load(f)

def _save(rules: list[dict]) -> None:
    DATA_DIR.mkdir(parents=True, exist_ok=True)
    with open(WORKFLOW_FILE, 'w') as f:
        json.dump(rules, f, indent=2)

def _find(rules: list[dict], rule_id: str) -> dict | None:
    return next((r for r in rules if r['rule_id'] == rule_id), None)

# ---------------------------------------------------------------------------
# Workflow operations
# ---------------------------------------------------------------------------

def new_rule(
    atlas_technique: str,
    owner: str,
    threat_source: str = 'catalogued',
) -> str:
    rules = _load()
    rule_id = str(uuid.uuid4())[:8]
    ttd_target = TTD_TARGETS_DAYS.get(threat_source, 7)
    now = datetime.now(timezone.utc).isoformat()
    phase_record = PhaseRecord(
        phase=1,
        name=PHASE_NAMES[1],
        entered_at=now,
    )
    rule = WorkflowRule(
        rule_id=rule_id,
        atlas_technique=atlas_technique,
        owner=owner,
        threat_source=threat_source,
        ttd_target_days=ttd_target,
        current_phase=1,
        phases=[phase_record.__dict__],
        created_at=now,
    )
    rules.append(rule.__dict__)
    _save(rules)
    print(f'New workflow rule created: {rule_id}')
    print(f'  ATLAS technique: {atlas_technique}')
    print(f'  Threat source:   {threat_source}')
    print(f'  TTD target:      {ttd_target} day(s)')
    print(f'  Owner:           {owner}')
    print(f'\nPhase 1 exit criterion:')
    print(f'  {PHASE_EXIT_CRITERIA[1]}')
    return rule_id

def advance_phase(rule_id: str, to_phase: int, notes: str = '') -> None:
    rules = _load()
    rule = _find(rules, rule_id)
    if not rule:
        print(f'Rule {rule_id} not found.')
        return
    current = rule['current_phase']
    if to_phase != current + 1:
        print(f'Cannot advance from Phase {current} to Phase {to_phase}. Phases must be sequential.')
        return
    now = datetime.now(timezone.utc).isoformat()
    # Close current phase
    for p in rule['phases']:
        if p['phase'] == current and not p['completed_at']:
            p['completed_at'] = now
            p['exit_criterion_met'] = True
            p['notes'] = notes
    # Open next phase
    next_phase = PhaseRecord(phase=to_phase, name=PHASE_NAMES[to_phase], entered_at=now)
    rule['phases'].append(next_phase.__dict__)
    rule['current_phase'] = to_phase
    if to_phase == 5:
        pass  # deployed_at set when Phase 5 is completed via --complete-deploy
    _save(rules)
    print(f'Rule {rule_id} advanced to Phase {to_phase} — {PHASE_NAMES[to_phase]}')
    print(f'Exit criterion for Phase {to_phase}:')
    print(f'  {PHASE_EXIT_CRITERIA[to_phase]}')

def complete_deploy(rule_id: str) -> None:
    rules = _load()
    rule = _find(rules, rule_id)
    if not rule:
        print(f'Rule {rule_id} not found.')
        return
    now = datetime.now(timezone.utc).isoformat()
    rule['deployed_at'] = now
    for p in rule['phases']:
        if p['phase'] == 5 and not p.get('completed_at'):
            p['completed_at'] = now
            p['exit_criterion_met'] = True
    created = datetime.fromisoformat(rule['created_at'])
    deployed = datetime.fromisoformat(now)
    ttd_days = (deployed - created).total_seconds() / 86400
    target = rule['ttd_target_days']
    status = 'WITHIN TARGET' if ttd_days <= target else 'EXCEEDED TARGET'
    _save(rules)
    print(f'Rule {rule_id} deployed to production.')
    print(f'  TTD: {ttd_days:.1f} days (target: {target} days) — {status}')

def print_status() -> None:
    rules = _load()
    active = [r for r in rules if not r.get('retired') and not r.get('deployed_at')]

def print_ttd_report() -> None:
    rules = _load()
    deployed = [r for r in rules if r.get('deployed_at')]
    if not deployed:
        print('No deployed rules yet — TTD report unavailable.')
        return
    ttds = []
    for r in deployed:
        wr = WorkflowRule(**{k: v for k, v in r.items()})
        ttds.append(wr.ttd_elapsed_days)
    ttds.sort()
    median = ttds[len(ttds) // 2]
    p90 = ttds[int(len(ttds) * 0.9)]
    within_target = sum(1 for r in deployed
                        if WorkflowRule(**{k: v for k, v in r.items()}).ttd_elapsed_days
                        <= r['ttd_target_days'])
    print(f'\nTTD Report — {len(deployed)} deployed rule(s)')
    print(f'  Median TTD:        {median:.1f} days')
    print(f'  90th percentile:   {p90:.1f} days')
    print(f'  Within target:     {within_target}/{len(deployed)}')

Common Mistakes

Id

CM11.10.1

Mistake

Writing a vague detection goal instead of a falsifiable hypothesis in Phase 1

Why It Happens

"Detect injection attacks" is intuitive and fast to write. The engineering discipline of forming a falsifiable prediction requires more effort and feels like unnecessary formalism when the engineer already knows what attack they are targeting.

Why It Matters

A vague detection goal produces a design (Phase 2) without a clear feature selection, a rule (Phase 3) that matches a wide class of inputs, and a test suite (Phase 4) that validates the rule fires on some injection examples without confirming it fires on the specific evidence the adversary will actually produce. The rule deploys with unknown FPR and unknown true positive coverage for the specific attack variant.

Correct Approach

The hypothesis must name the ATLAS technique, the log field that carries the observable evidence, the threshold or pattern that distinguishes signal from noise, and the evasion surface that this detection will not cover. Use detection_hypothesis_generator.py to generate the scaffold; fill in the deployment-specific details from the Phase 2 design.

Id

CM11.10.2

Mistake

Starting Phase 3 (Build) before Phase 2 (Design) is complete and peer-reviewed

Why It Happens

Building is more tangible than designing. Engineers who are confident they know what the rule should do skip the design document and start writing Sigma immediately.

Why It Matters

Phase 3 decisions made without a Phase 2 design are made implicitly and inconsistently. The log source is chosen by habit rather than by taxonomy confirmation. The FPR target is not set before deployment. The test cases are written to match the rule rather than to validate the security requirement. A Phase 2 gap in any of the seven design decisions produces a Phase 7 improvement cycle that could have been avoided.

Correct Approach

Phase 2 is a synchronous gate: the Phase 2 design document is reviewed and approved by a second engineer before Phase 3 begins. The design review confirms that the log source field is in the ai_log_field_taxonomy, that the FPR target is documented, and that the four test cases are written in terms of specific prompt text and expected detection scores — not in abstract terms.

Id

CM11.10.3

Mistake

Treating the 24-hour staging observation window as optional when TTD pressure is high

Why It Happens

Under TTD pressure — a threat actor is actively exploiting a technique — the 24-hour staging window feels like an obstacle to protecting production. The temptation is to merge directly to main.

Why It Matters

A rule deployed to production without staging observation may have a calibration issue that is invisible in the test corpus but visible in production traffic. A rule that floods production with false positives requires an emergency rollback that adds 15–30 minutes to the TTD for the rollback itself and disrupts SOC operations during the flood period. The net TTD is worse than waiting 24 hours.

Correct Approach

For zero-day threats, run staging and production in parallel: deploy to production immediately with status: experimental (which prevents the rule from being SOC-visible in production) while the staging observation runs. After 24 hours at acceptable FPR on staging, promote to status: test and make the rule SOC-visible in production. This achieves fast deployment without skipping calibration.

Id

CM11.10.4

Mistake

Not tracking TTD per rule, making the programme's improvement trajectory invisible

Why It Happens

TTD feels like a project management metric rather than a security metric. Detection teams focus on rule quality, coverage, and FPR — not on how long the detection took to build.

Why It Matters

A programme with excellent rules that take 45 days on average to deploy leaves a 45-day adversary advantage window for every new technique. This window is invisible until TTD is tracked. Without TTD data, the programme cannot identify whether the bottleneck is Phase 1 (slow threat intelligence intake), Phase 2 (blocked on log schema), or Phase 4 (recurring test failures indicating design problems).

Correct Approach

Use detection_engineering_workflow.py to track phase completion timestamps for every new detection rule. Report median TTD and 90th-percentile TTD in the quarterly detection programme review. Any rule with TTD above the applicable target (7 days for catalogued, 14 days for analyst-discovered) triggers a retrospective to identify the phase that consumed the most time and the root cause.

Id

CM11.10.5

Mistake

Retiring a rule immediately when false negative is confirmed rather than first improving it

Why It Happens

A confirmed false negative feels like a failed rule. If the rule missed a real attack, it seems like the rule does not work and should be replaced.

Why It Matters

Most confirmed false negatives indicate a specific evasion variant that the rule does not cover — not a fundamental flaw in the detection approach. Retiring the rule removes whatever coverage it did provide for the non-evading variants of the attack. If the rule detected 80% of attack variants and missed the 20% that used a specific encoding, retiring it removes the 80% coverage without improving the 20% gap.

Correct Approach

A confirmed false negative triggers Phase 7 — Improve, not retirement. The false negative input is added as a positive test fixture. If the rule logic can be adjusted to catch this variant without unacceptable FPR increase, it is improved. If it cannot, the variant is documented as a residual gap and a new detection hypothesis is opened in Phase 1 for the evasion variant. The original rule stays in production; the new rule adds coverage for the evasion surface.

Section Summary

What You Learned

The seven-phase detection engineering workflow converts threat intelligence and coverage gaps into production detection rules through a defined, gate-enforced procedure. Each phase has a specific exit criterion enforced by tooling (phases 4–6) or peer review (phases 1–3 and 7). Hypotheses must be falsifiable: they name the ATLAS technique, the observable evidence field, the detection mechanism, and the evasion surface. Phase 2 design decisions — log source, feature, logic, FPR target, test cases, evasion assessment, and owner — are made before a line of Sigma is written. Time-to-detect is the security metric of the workflow: under 7 days for catalogued techniques, under 24 hours for zero-days. Phase 7 improvement is triggered by FPR breach, confirmed false negative, coverage regression, or quarterly review, and produces improvements as PRs through the full pipeline rather than direct edits.

Falsifiable hypothesis

Definition

A detection hypothesis that names specific observable evidence in a named log field, distinguishable from legitimate traffic by a named mechanism, with a named FPR expectation and a named evasion surface. Can be proven wrong by examining logs during a confirmed attack.

Term

Time-to-detect (TTD)

Definition

The elapsed time from Phase 1 hypothesis documentation to Phase 5 production deployment. A security metric measuring the adversary advantage window. Target: under 7 days for catalogued techniques, under 24 hours for zero-days.

Term

Phase gate

Definition

The exit criterion that must be satisfied before a detection rule advances from one workflow phase to the next. Phases 4 and 5 gates are enforced by the CI/CD pipeline. Phases 1–3 and 7 gates are enforced by peer review and documentation requirements.

Term

Phase 7 — Improve

Definition

The workflow phase triggered by FPR breach, confirmed false negative, coverage regression, or quarterly review. Produces rule refinements as calibrate/ PRs through the full pipeline, not direct SIEM edits. A confirmed false negative triggers Phase 7 — not retirement.

Term

Zero-day TTD path

Definition

The compressed workflow for actively exploited zero-days: deploy to production with status experimental (SOC-invisible) immediately while staging observation runs in parallel; promote to SOC-visible after 24-hour staging FPR passes. Achieves fast deployment without skipping calibration.

OWASP LLM Top 10 Detection Coverage Matrix

Teaser

Section 11.11 applies the seven-phase detection engineering workflow at scale: all ten OWASP LLM Top 10 vulnerabilities assessed against the seven-track gateway, producing a coverage score (0–2) and a gap description for each. LLM01 (Prompt Injection) and LLM10 (Model Theft) are the strongest coverage areas. LLM02 (Insecure Output Handling) and LLM06 (Sensitive Information Disclosure) have no current gateway coverage — output-side detection is the most common gap in gateway- first architectures. LLM03 (Training Data Poisoning) and LLM05 (Supply Chain) have intentional runtime gaps that require build-time controls rather than inference-time detection. The section produces an OWASP coverage matrix alongside the ATLAS heat map and a gap closure roadmap mapping each OWASP gap to the Chapter 12–15 deliverable that addresses it.
