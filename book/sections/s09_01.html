Section 9.1: Inference-Time Extraction Threat Model

Section Overview

One Line Summary

Chapter 9 returns to the real-time gateway architecture of Chapters 6 and 7, facing a new threat actor -- the API consumer who reconstructs model behaviour without training access -- and frames the two-surface defence that closes OWASP LLM10.

Why This Section Exists

Chapter 8 retrained your instincts toward batch jobs, CI/CD gates, and offline auditing pipelines. Section 9.1 reverses that shift before it becomes a liability. The threat actor in Chapter 9 is not a data pipeline contributor with training access; it is an API consumer with a query budget and no model internals. The attack surface is the deployed model''s inference API. The detection architecture is real-time and per-request, not batch and asynchronous. Without this reset, the rest of Chapter 9 makes no architectural sense: you would design batch auditors for a threat that operates at inference time, miss the query budget constraint that defines extraction economics, and build defences that detect the wrong signals at the wrong latency tier. Section 9.1 establishes the threat model so Sections 9.2 through 9.12 build the right architecture. It also introduces the OWASP LLM10 (Model Theft) framework and the three ATLAS sub-techniques that Chapter 9 covers, giving the reader a compliance and taxonomy anchor before the attack sections begin.

Position In Chapter

Section 9.1 of 13. Threat model foundation for the full chapter. All attack sections (9.2 through 9.9) and all defence sections (9.10 through 9.12) inherit the threat model, adversary access ladder, and architectural framing established here.

Title

The Threat Actor Has Changed

Body

Chapter 8 placed you inside the data pipeline. The threat actor was a contributor -- a researcher who could influence training batches, a vendor whose dataset appeared in a supply chain audit, an insider with write access to the preprocessing stage. The attack surface was the training run itself: offline, asynchronous, auditable in CI/CD. The detection architecture matched: a batch auditing pipeline that ran before model deployment, flagging poisoned samples before they could influence production weights. Chapter 9 removes that access entirely. The threat actor cannot touch the training pipeline. The model is already deployed. Weights are fixed. The only interface the adversary has is the same interface every legitimate user has: the inference API. This is not a relaxed threat model -- it is a different one. The adversary in Chapter 9 has no training-time leverage but has something Chapter 8''s threat actor typically lacked: an operational budget and patience. An attacker who can issue a thousand queries a day, sustained across weeks, can reconstruct what a model knows without ever touching its weights. The training-time defender had a window: poison the data before the run, and the attack persists in the deployed model. The inference-time adversary has no such window -- every attack is a series of queries, and every query costs money and leaves a trace. That trace is the detection surface. The practical consequence for defenders: stop thinking in batch jobs. The detection architecture returns to the real-time per-request pattern Chapters 6 and 7 established. Latency budgets matter again. The classifier must run within the request lifecycle, not in a nightly CI pipeline.

Title

The Inference-Time Threat Model

Body

The inference-time threat model has five defining properties that Chapter 8 did not require. Fixed model. The production model is deployed and its weights do not change during the attack. The adversary cannot influence what the model has learned. Every response the model gives is a deterministic or stochastically bounded function of its fixed weights and the adversary''s input. This is what makes extraction possible: the model''s behaviour is stable across queries, so systematic querying can map that behaviour. Real-time per-request analysis. Detection must operate on each request as it arrives, within the latency budget of a synchronous API call. Chapter 8''s auditing pipeline had minutes to hours to process a training batch. Chapter 9''s gateway classifier has milliseconds. The Chapter 6 and Chapter 7 ensemble ran at P99 latency under 100ms -- Chapter 9 extends that ensemble with query monitoring as a sixth parallel track, within the same budget. Query sequence visibility. A single query reveals little. It is the sequence -- the distribution of queries over time, their positions relative to each other in input space, their concentration around decision boundaries -- that signals extraction. The detection architecture must be stateful across requests, not memoryless per request. Query budget as the binding constraint. Every extraction attack has a query budget: the number of API calls an adversary can afford before cost or rate limits stop them. Budget determines fidelity. A defender who doubles the query budget required for a given fidelity level has halved the attack''s economics. This reframing -- defending against budget rather than against existence -- is the central insight of Chapter 9 detection design. Blast radius asymmetry. A successful injection or jailbreak affects one conversation. A successful extraction attack produces a deployable clone: a model the adversary can query at their own infrastructure, sell, or use to generate adversarial examples against the original. The blast radius of extraction is the full downstream deployment of the surrogate -- orders of magnitude larger than a single-conversation injection.

Title

The Adversary Access Ladder

Body

Chapter 9 threat actors occupy one of three rungs on an adversary access ladder. The rung determines what the adversary can observe, which extraction technique is most efficient, and how many queries are needed. Black-box access. The adversary sees only the model''s outputs: final predictions, generated text, classification labels. No probability distributions. No logits. No gradients. This is the realistic commercial API scenario: the model returns a response string or a top-1 class label. Black-box extraction requires more queries than the alternatives but is the most common real-world adversary position. Section 9.3 establishes the fundamental black-box extraction primitive; Sections 9.4 and 9.5 extend it to distillation and prompt extraction. Grey-box access. The adversary sees the model''s output distribution -- soft labels, logit vectors, or top-k class probabilities. Many commercial ML APIs return confidence scores or probability distributions alongside predictions. This is a common production configuration that significantly reduces extraction query budget. Soft-label distillation (Section 9.4) exploits grey-box access: a probability vector over classes contains exponentially more information about the model''s decision boundary than a single class label. The consequence for defenders: output design is a security decision. Returning probability distributions when a hard label suffices leaks extraction information unnecessarily. White-box access. The adversary has full model access: weights, architecture, and gradients. This access level is relevant in Chapter 9 for model inversion (Section 9.7) -- gradient-based inversion reconstructs training data from weights -- and as a threat model for open-weight models deployed with restricted fine-tuning licences. White-box extraction is the most powerful but the least common real-world scenario against commercial deployments. Budget implications by rung: black-box extraction of a classifier typically requires O(d) to O(d log d) queries for linear models where d is the feature dimension, far more for neural networks. Grey-box access reduces budget by 5 to 50x because each query returns a full probability vector rather than a single bit of decision boundary information. White-box access eliminates the query budget constraint entirely for model structure -- the adversary already has the model.

Title

Detection Architecture: Gateway vs Auditing Pipeline

Body

The two detection architectures in this book -- the real-time gateway classifier (Chapters 6 and 7) and the offline auditing pipeline (Chapter 8) -- are not competing designs. They address different attack surfaces at different latency tiers. The mistake is applying the wrong architecture to a threat. Chapter 8''s auditing pipeline operated offline. It received training batches as asynchronous inputs, ran multi-pass statistical tests and provenance checks across the full batch, and gated model deployment at the end of the CI/CD pipeline. Latency budget: minutes to hours. Detection unit: a training batch or dataset. State: the pipeline maintained cross-batch history to detect distributed poisoning across multiple uploads. The Chapter 6 and 7 gateway classifier operated in real time. It received each user request as a synchronous input, ran five parallel detection tracks (injection classifier, OOD detector, semantic consistency checker, pattern analyser, jailbreak ensemble), and returned a routing decision within 50ms P99. Detection unit: a single request, though jailbreak detection in Chapter 7 introduced limited session-level context. State: minimal per-session context. Chapter 9''s detection architecture extends the gateway pattern, not the auditing pipeline. The attack surface is inference-time; the detection unit is the query sequence; the latency budget is synchronous. Chapter 9 adds a sixth parallel track to the Chapter 6/7 ensemble: query monitoring with per-user state tracking. This is the one architectural extension relative to Chapters 6 and 7: the state is now persistent per-user across many requests, not just per-session. The rate limiter (Section 9.11) acts on that state to turn detection into prevention. The output-side defence (Section 9.12) is architecturally novel: it operates post-inference, on the model''s response before it is returned to the user. Neither the Chapter 6/7 gateway nor the Chapter 8 auditing pipeline had an output-side stage. This is the structural extension Chapter 9 contributes to the book''s overall defensive architecture.

Title

OWASP LLM10 and ATLAS Taxonomy Anchors

Body

OWASP LLM10 -- Model Theft -- defines the framework Chapter 9 operationalises. The framework covers intentional copying of a model''s functionality via API queries, reconstruction of model behaviour through systematic querying, direct theft of model weights, and extraction of proprietary system prompts and operational configuration. Chapter 9 builds complete detection coverage for each of these in the attack sections (9.2 through 9.9) and deploys production controls in the capstone sections (9.11 and 9.12). OWASP LLM10 closure with Chapter 9 mirrors the pattern established for LLM01 (injection and jailbreak, closed in Chapter 7) and LLM03 (training data poisoning, closed in Chapter 8). Each OWASP category receives a full attack catalogue followed by production detection. Chapter 9 completes the three-category coverage arc across Part 2 of the book. MITRE ATLAS provides sub-technique granularity. Three ATLAS techniques anchor Chapter 9. AML.T0040 -- ML Model Inference API Access. The adversary uses the inference API to query the model systematically. This is the foundational technique for all extraction attacks: every extraction begins with AML.T0040. Query monitoring (Section 9.11) is the principal detection control. AML.T0044 -- Full ML Model Access. The adversary obtains weights or architecture directly, either through white-box model access or by successfully completing a functional extraction that produces a deployable surrogate. AML.T0044 describes the outcome of a successful extraction campaign, not just the access method. Output watermarking (Section 9.12) provides post-hoc evidence of AML.T0044 by detecting the victim model''s signature in a suspected surrogate. AML.T0024 -- Exfiltration via ML Inference API. The adversary exfiltrates model intellectual property -- weights, decision boundaries, system prompts -- through the inference API as the exfiltration channel. AML.T0024 combines the access method of AML.T0040 with an exfiltration goal. The Sigma rule completed in Section 9.11 targets AML.T0040 and AML.T0024 together: the same query pattern that indicates inference API abuse also indicates exfiltration in progress.

6

Title

Why Extraction Defences Differ from Injection and Jailbreak Defences

Body

The Chapter 6 injection classifier and Chapter 7 jailbreak ensemble both operate on single-request intent: a request either contains an injection payload or it does not; a request either attempts a jailbreak or it does not. The classifier reads one request and makes a binary decision. Session context in Chapter 7 extended this slightly -- carry-over instructions across turns -- but the fundamental detection unit remained the request. Extraction defences cannot operate this way. A single extraction query is indistinguishable from a benign query. An adversary issuing boundary-probing queries at one query per minute -- well within legitimate API usage -- produces individually normal-looking requests. The extraction signal lives in the distribution of queries over time: their clustering in input space, their concentration near decision boundaries, their entropy relative to benign queries, the convergence of the adversary''s query distribution toward the model''s decision surface. This has three architectural consequences. First, extraction detection requires persistent per-user state across requests -- the state store that Section 9.11 builds is not optional. Second, the detection signal is statistical rather than deterministic: extraction is detected when the query distribution crosses an anomaly threshold, not when any single query crosses a content threshold. Third, rate limiting is a security control, not just an operational one: it is the actuator that turns a statistical detection into a prevention response. The practical difference in implementation: Chapter 6 and 7 classifiers have near-zero memory of prior requests from the same user. Chapter 9''s query monitor maintains a rolling window of query statistics per user, updated on every request, compared against extraction-profile baselines. The computational cost of this memory is the primary engineering challenge of the Section 9.11 implementation.

def _wrap(text: str, width: int) -> List[str]:
    words = text.split()
    lines: List[str] = []
    current = ''
    for word in words:
        if len(current) + len(word) + 1 <= width:
            current = f'{current} {word}'.strip()
        else:
            if current:
                lines.append(current)
            current = word
    if current:
        lines.append(current)
    return lines or ['']


def render_contrast_report(dimensions: List[ContrastDimension]) -> None:
    col_width = 38
    header = (
        f'{"Dimension":<22} '
        f'{"Training-Time (Ch8)":<{col_width}} '
        f'{"Inference-Time (Ch9)":<{col_width}}'
    )
    separator = '-' * len(header)
    print(separator)
    print('THREAT MODEL CONTRAST: Chapter 8 vs Chapter 9')
    print(separator)
    print(header)
    print(separator)
    for dim in dimensions:
        t_lines = _wrap(dim.training_time, col_width)
        i_lines = _wrap(dim.inference_time, col_width)
        max_lines = max(len(t_lines), len(i_lines))
        t_lines += [''] * (max_lines - len(t_lines))
        i_lines += [''] * (max_lines - len(i_lines))
        for idx, (t_line, i_line) in enumerate(zip(t_lines, i_lines)):
            label = dim.dimension if idx == 0 else ''
            print(f'{label:<22} {t_line:<{col_width}} {i_line:<{col_width}}')
        print()


if __name__ == '__main__':
    render_contrast_report(CONTRAST_DIMENSIONS)

        budget_multiplier=0.05,
        budget_note='5-50x budget reduction. Each query returns full probability distribution.',
        defensive_implication='Return hard labels unless soft labels are required by the product.',
        atlas_relevance=['AML.T0040', 'AML.T0024'],
        config_signals=['returns_probabilities', 'returns_logits', 'returns_top_k'],

    AccessLevel(

        observables=['hard_labels', 'generated_text', 'top_1_prediction'],

        budget_multiplier=1.0,
        budget_note='Baseline. O(d) to O(d log d) queries for linear models.',
        defensive_implication='Query pattern monitoring (Section 9.11) is the primary control.',
        atlas_relevance=['AML.T0040', 'AML.T0024'],
        config_signals=[],
    ),
]


def classify_api_design(api_config: Dict[str, bool]) -> AccessLevel:
    '''
    Classify an API configuration into the adversary access level it exposes.
    Evaluated in descending severity order: white_box > grey_box > black_box.

    api_config keys:
        returns_probabilities (bool): API returns soft-label probability vectors
        returns_logits (bool):        API returns raw logit scores
        returns_top_k (bool):         API returns top-k predictions with scores
        weights_accessible (bool):    Model weights are accessible
        gradients_accessible (bool):  Gradient access is available
    '''
    for level in ACCESS_LADDER:
        if any(api_config.get(signal, False) for signal in level.config_signals):
            return level
    # No elevated signals -- black_box is the fallback (last in list)
    return ACCESS_LADDER[-1]


def render_access_ladder() -> None:
    print('ADVERSARY ACCESS LADDER -- Chapter 9 Section 9.1')
    print('=' * 60)
    for i, level in enumerate(ACCESS_LADDER, 1):
        print(f'\nRung {i}: {level.name.upper()}')
        print(f'  Observables:    {", ".join(level.observables)}')
        print(f'  Best technique: {level.optimal_technique}')
        print(f'  Budget:         {level.budget_note}')
        print(f'  Defence:        {level.defensive_implication}')
        print(f'  ATLAS:          {", ".join(level.atlas_relevance)}')


if __name__ == '__main__':
    render_access_ladder()
    print()

        'weights_accessible': False,
        'gradients_accessible': False,
    }
    level = classify_api_design(example_config)
    print(f'Example API classification: {level.name}')
    print(f'Defensive implication: {level.defensive_implication}')

# Chapter 9 Section 9.1 -- Detection Architecture Selector
# Single quotes throughout per book convention.

from dataclasses import dataclass, field
from typing import Dict, List, Tuple


@dataclass
class ThreatScenario:
    name: str
    attack_surface: str       # 'training_pipeline' or 'inference_api'
    detection_timing: str     # 'pre_deployment' or 'runtime'
    latency_requirement: str  # 'batch' or 'realtime'
    state_requirement: str    # 'stateless' or 'stateful'


@dataclass
class ArchitectureRecommendation:
    architecture: str
    rationale: str
    chapter_reference: str
    extension_notes: str


@dataclass
class ArchitectureRule:
    name: str
    conditions: Dict[str, str]
    recommendation: ArchitectureRecommendation


ARCHITECTURE_RULES: List[ArchitectureRule] = [
    ArchitectureRule(
        name='offline_auditing_pipeline',
        conditions={
            'attack_surface': 'training_pipeline',
            'detection_timing': 'pre_deployment',
            'latency_requirement': 'batch',
        },
        recommendation=ArchitectureRecommendation(
            architecture='offline_auditing_pipeline',
            rationale='Training-time attack surface requires pre-deployment batch auditing. Real-time gateway adds no coverage for this threat class.',
            chapter_reference='Chapter 8 Section 8.15',
            extension_notes='No Chapter 9 extension applicable. Use Chapter 8 auditing pipeline.',
        ),
    ),
    ArchitectureRule(
        name='gateway_classifier_with_query_monitoring',
        conditions={
            'attack_surface': 'inference_api',
            'detection_timing': 'runtime',
            'latency_requirement': 'realtime',
        },
        recommendation=ArchitectureRecommendation(
            architecture='gateway_classifier_with_query_monitoring',
            rationale='Inference-time attack surface requires real-time per-request analysis. Extend Chapter 6/7 gateway with Chapter 9 query monitoring (Track 6) and output-side watermarking and perturbation.',
            chapter_reference='Chapter 6 Section 6.17, Chapter 7 Section 7.14, Chapter 9 Sections 9.11 and 9.12',
            extension_notes='Add per-user state store. Add Track 6 (query monitor). Add output-side stage (watermarker and perturbator). Maintain sub-100ms P99 across all tracks.',
        ),
    ),
]


def select_architecture(scenario: ThreatScenario) -> ArchitectureRecommendation:
    '''
    Select the correct detection architecture for a given threat scenario.
    Scores each rule by number of matching conditions. Returns the highest-
    scoring recommendation. Returns an undetermined result if no rule matches.
    '''
    scored: List[Tuple[int, ArchitectureRecommendation]] = []
    for rule in ARCHITECTURE_RULES:
        score = sum(
            1 for field_name, expected in rule.conditions.items()
            if getattr(scenario, field_name, None) == expected
        )
        scored.append((score, rule.recommendation))
    scored.sort(key=lambda x: x[0], reverse=True)
    best_score, best_rec = scored[0]
    if best_score == 0:
        return ArchitectureRecommendation(
            architecture='undetermined',
            rationale='Scenario does not match known architecture patterns. Manual review required.',
            chapter_reference='Chapter 9 Section 9.1',
            extension_notes='Review attack surface and detection timing requirements against Table 4.',
        )
    return best_rec

Common Mistakes

Id

1

Description

Applying the Chapter 8 offline auditing architecture to inference-time extraction threats

Why It Happens

Chapter 8 trained readers to think in batch jobs and CI/CD gates. After building a well-functioning auditing pipeline, it is natural to reach for the same architecture when a new threat appears. Extraction looks like a data exfiltration problem -- and data exfiltration is often addressed by audit logs and batch analysis.

Consequence

Batch auditors run too late to prevent extraction in progress. By the time a nightly audit flags anomalous query patterns, the adversary has completed the extraction campaign and the surrogate is already training. The defender discovers the theft after it has happened, with no opportunity to intervene.

Correct Approach

Inference-time threats require real-time gateway detection. Use the Chapter 6/7 gateway pattern extended with query monitoring (Section 9.11). Batch audit logs are valuable for post-hoc forensics and incident reconstruction (Section 9.9), not for real-time extraction prevention.

Id

2

Description

Treating individual extraction queries as the detection unit

Why It Happens

Injection and jailbreak detection (Chapters 6 and 7) operated on single requests. Readers carry that habit into Chapter 9 and build classifiers that evaluate each query in isolation for extraction intent. A single boundary-probing query looks benign in isolation -- the classifier always returns false.

Consequence

The detector has zero detection power. Every extraction query that is not obviously malformed passes the single-request classifier. The adversary issues ten thousand individually-benign queries and extracts the model undetected.

Correct Approach

The detection unit for extraction is the query sequence, not the query. Build per-user state that accumulates query distribution statistics across requests. Detection fires when the distribution crosses an anomaly threshold, not when any individual query crosses a content threshold. See Section 9.11.

3

Description

Treating rate limits as operational controls rather than security controls

Why It Happens

Rate limits are traditionally set by engineering or product teams to protect infrastructure from overload. The limit reflects throughput capacity, not extraction threat modelling. Security teams inherit the limit without questioning its security properties.

Consequence

A throughput-based rate limit may be set high enough to permit a complete extraction campaign within one billing period. An adversary who stays below the throughput limit while systematically probing decision boundaries extracts the model within the rate limit''s budget.

Correct Approach

Rate limits against extraction must be extraction-aware: they enforce query budget constraints against systematic boundary probing, not just peak throughput. Section 9.11 builds an adaptive rate limiter with extraction-aware policy dimensions including OOD query rate, per-user cumulative extraction signal, and cross-user collusion scoring.

Id

4

Description

Returning soft-label probability vectors when hard labels suffice

Why It Happens

API designers default to returning full model output distributions because they are more informative and provide better user experience in legitimate use cases. Confidence scores and probability vectors are seen as a feature, not a risk.

Consequence

Grey-box access reduces the adversary''s query budget by 5 to 50x compared to hard-label-only APIs. An extraction that would require 100,000 queries against a hard-label API completes in 2,000 to 20,000 queries against a soft-label API. The API has granted the adversary a substantial budget discount without any business requirement to do so.

Correct Approach

Audit every output field in the API response. Return probability distributions only when the use case genuinely requires them. For classification APIs where the product only needs a decision, return the hard label. See Section 9.12 for output perturbation as a further defence when soft labels cannot be removed.

5

Description

Assuming watermarking prevents extraction rather than providing post-hoc evidence

Why It Happens

Output watermarking (Section 9.12) sounds like it prevents the theft: if the output is marked, the adversary cannot use it without revealing the mark. Readers conflate the detection function (watermark proves ownership) with the prevention function (watermark blocks extraction).

Consequence

Deploying watermarking as the sole extraction control provides no real-time prevention. The adversary extracts the model successfully; the watermark transfers to the surrogate but does not stop the extraction. The defender has ownership evidence but the model has already been stolen.

Correct Approach

Watermarking is a post-hoc ownership and attribution control, not a prevention control. It is complementary to, not a replacement for, input-side query monitoring and rate limiting (Section 9.11). Combine both surfaces: prevent where possible with query monitoring and adaptive rate limiting; detect post-hoc with watermarking when prevention fails.

Section Summary

Compact

Chapter 9 returns to inference-time gateway detection after Chapter 8''s training-time auditing pipeline. The threat actor is now an API consumer with a query budget rather than a pipeline contributor with training access. The attack surface is the deployed model''s inference API; the attack goal is reconstructing what the model knows or how it behaves without the cost of training from scratch. Detection requires stateful per-user query pattern analysis -- not single-request intent classification -- because individual extraction queries are indistinguishable from benign queries. The detection architecture extends the Chapter 6/7 real-time gateway with a sixth parallel track (query monitoring) and a new output-side stage (watermarking and perturbation). The chapter closes OWASP LLM10 (Model Theft) and maps to three ATLAS sub-techniques: AML.T0040 (inference API access), AML.T0044 (full model access), and AML.T0024 (exfiltration via inference API).

Key Takeaways

  • The threat actor has changed from pipeline contributor to API consumer; the detection architecture must change with it
  • Query budget is the primary economic constraint -- defend by increasing required budget, not by trying to block existence of the attack
  • Extraction detection is statistical and cross-request; it cannot be reduced to single-request intent classification
  • Grey-box APIs give adversaries a 5-50x query budget discount; output design is a security decision
  • Watermarking provides post-hoc evidence of extraction; it does not prevent extraction in progress
  • OWASP LLM10 closes with Chapter 9 via two defensive surfaces: input-side query monitoring and output-side watermarking and perturbation
