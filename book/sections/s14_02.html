Architecture Patterns: API Gateway, Sidecar, and Inline

Section Overview

One Line Summary

The API gateway, sidecar, and inline patterns place detection at different points in the request path, trading latency against coupling, deployment independence, and blast radius; the pattern choice is the first production decision and it constrains every performance and resilience decision that follows.

Why This Section Exists

Section 14.01 named placement as the first deployment concern: where in the request path detection sits. This section answers it. Before latency can be budgeted, before failure policy can be set, before scaling can be planned, the detection system must be placed somewhere in the path between the client and the model service, and there are three canonical ways to do it. The API gateway pattern puts detection in a separate service in front of the model. The sidecar pattern co-locates detection beside the application as its own process. The inline pattern embeds detection directly in the application request path. Each places detection at a different point, and each trades the same four properties -- latency, coupling, deployment independence, and blast radius -- against one another. This section works through the three patterns, the trade-offs, where each one puts the Chapter 13 detection tiers, how to select a pattern by requirement, and how the patterns combine, so that the placement decision is made deliberately rather than inherited from whatever was easiest to wire up.

Position In Chapter

Section 14.02 is the first of the two placement sections (14.02-14.03) and the first response to a named deployment concern from the 14.01 taxonomy. It fixes where detection sits; Section 14.03 then fixes where in the request lifecycle each detector hooks in (pre-processing versus post-processing). Together they complete placement before the performance sections (14.04-14.05) engineer latency and scaling against the chosen pattern.

Prose Content

Part 1

Title

Placement Is the First Production Decision

Body

The taxonomy in Section 14.01 listed six deployment concerns and put placement first. The ordering was not incidental. You cannot budget the latency of a detector until you know where it runs, you cannot set its failure policy until you know what process it runs in, and you cannot plan its scaling until you know whether it scales with the application or apart from it. Every later decision in the chapter is made against a fixed placement, so placement is decided first. Placement is the question of where, in the path between the client and the model service, the detection system sits. The behavioural monitoring gateway of Chapter 13 is a logical object: it says a request is inspected by four detection layers across three tiers, but it does not say what process that inspection runs in or where in the network topology it happens. Turning that logical object into a running one means choosing a physical placement, and there are three canonical choices: a separate gateway service in front of the model, a sidecar process co-located with the application, or code embedded inline in the application request path. The three are not three flavours of the same thing. They place detection at genuinely different points, and that difference propagates through the rest of the system. The point at which detection sits determines how much latency it adds, how tightly it is coupled to the application, whether it can be deployed and scaled on its own, and how far a fault in a detector spreads. Those four properties -- latency, coupling, deployment independence, and blast radius -- are the axes on which the patterns trade against one another, and the rest of this section is about that trade.

Part 2

Title

The API Gateway Pattern: Detection as a Service in Front of the Model

Body

The API gateway pattern places detection in a separate service that sits in front of the model service. Every request from the client passes through the gateway, is inspected, and is either forwarded to the model or blocked; every response passes back through the gateway on its way out. Detection is a distinct deployable, with its own process, its own release cycle, and its own fleet. This placement has three properties that make it the default for a security team. First, it is a clear choke point: all traffic to the model crosses one place, so there is a single point at which every request is guaranteed to be inspected, with no way for a caller to reach the model while skipping detection. Second, it gives full deployment independence: the detection service is released without touching the application, so the security team can ship a new detector or tune a threshold on its own schedule. Third, it scales independently: the gateway fleet is sized to the detection workload, not to the application workload, so a heavy detector can be given more capacity without scaling the application. The cost of these properties is a network hop. Because the gateway is a separate service, the request and the response each cross the network to reach it and return, and that hop is added latency on the hot path that the inline detectors must fit within their budget. The gateway also becomes a component that must itself be made highly available, because a choke point that is down is a total outage. The gateway pattern is the right default when a separate team owns detection, independent deployment and scaling are wanted, and the latency budget can absorb the hop -- which is the common case for the sub-50ms inline budget, where a single well-engineered hop is affordable.

Part 3

Title

The Sidecar Pattern: Detection Co-Located Beside the Application

Body

The sidecar pattern places detection in its own process, but co-located with the application rather than in a separate fleet. In a container platform the sidecar is a second container in the same pod as the application; the application calls it over loopback, and it inspects the request or enriches it before the application proceeds. The sidecar is a middle point between the gateway and the inline patterns, and it is deliberately positioned to keep some of the strengths of each. From the gateway pattern it keeps deployment independence. The sidecar is a separate image with its own release cycle, so detection is still deployed without editing and redeploying the application code -- the security team updates the sidecar image and the platform rolls it out beside the application. From the inline pattern it keeps a low latency floor. Because the sidecar is co-located, the call to it is a loopback call within the pod rather than a cross-network hop, so it avoids most of the latency the gateway pays while still running as a separate process. What the sidecar gives up is on the scaling and blast-radius axes. Because it lives in the application pod, it scales as the application scales: you cannot give the detection sidecar more replicas than the application without changing the pod model, so independent scaling is limited. And because it shares a host with the application, a misbehaving sidecar -- one that leaks memory or saturates CPU -- can affect the application instance it sits beside, though the blast radius is bounded to the pod rather than the whole fleet. The sidecar is the right choice when independent deployment is wanted but a full network hop is not tolerable, and when detection scaling can follow the application.

Part 4

Title

The Inline Pattern: Detection Embedded in the Request Path

Body

The inline pattern embeds detection directly in the application request path as an in-process call. There is no separate service and no separate process: the application handler calls the detector as a function, gets a verdict, and proceeds. This is the placement with the lowest possible latency floor, because there is no hop and no loopback -- the detector runs in the same process, sharing the same memory, and the only cost is the compute of the detector itself. That latency floor is the reason to reach for inline. When the budget is so tight that it cannot absorb even a loopback call -- a detector that must run in single-digit milliseconds as part of a larger hot path -- inline is the only pattern that fits, because it adds no transport cost at all. For the cheapest, most latency-critical signature and heuristic checks of the inline tier, running them in-process is sometimes the only way to stay within budget. The price is paid on every other axis. Coupling is at its tightest: detection ships with the application, so a detector change means an application release, and the security team loses the ability to deploy on its own schedule. Deployment independence is gone entirely. And the blast radius is at its widest, because the detector runs inside the application process: a detector that throws, hangs, or leaks does so in the application itself, so a detector fault is an application fault. Inline trades away independence and isolation for raw latency, and it should be chosen only when the latency budget genuinely forces it, because the failure policy and circuit breaking of the later sections are harder to apply cleanly when detection and application share a process.

Part 5

Title

The Trade-Off Space and Pattern Selection

Body

Laid side by side, the three patterns form a single trade-off space along one dominant axis: latency floor versus independence and isolation. Inline has the lowest latency floor and the least independence and isolation; the gateway has the most independence and isolation and the highest latency floor; the sidecar sits between them, buying most of the gateway independence while paying only a loopback. Moving toward lower latency moves toward tighter coupling and a wider blast radius, and the choice is where on that axis the system belongs. Three requirements drive the choice. The latency budget sets the floor: a budget that cannot absorb a network hop rules out the gateway, and a budget that cannot absorb even a loopback forces inline. Team ownership sets the coupling: when a separate security team owns detection and must deploy on its own schedule, the gateway or the sidecar is required, because inline binds detection to the application release. The scaling model sets the fleet: when detection must scale independently of the application -- a heavy ML detector that needs more capacity than the application does -- the gateway is required, because the sidecar scales with the pod and inline scales with the application. The selector deliverable for this section encodes exactly this logic: it takes the latency budget, the ownership model, the scaling requirement, and the network-hop tolerance, and returns a pattern with the reasoning and the cautions attached. The point of writing the selection down as a procedure is that the placement decision then has a stated rationale that later sections can rely on, rather than being an accident of which wiring was convenient on the day.

Part 6

Title

Combining Patterns and Placing the Chapter 13 Tiers

Body

The three patterns are not mutually exclusive, and a real production gateway usually combines them along the Chapter 13 tier boundaries. The reason is that the pattern choice matters most for the inline tier and barely at all for the others. The inline tier is on the hot path, so it pays the pattern latency floor on every request, and the choice between gateway, sidecar, and inline is felt directly. The near-real-time and batch tiers run off the hot path in every pattern: they consume events asynchronously, so they are placed the same way regardless of how the inline tier is placed. Placement is therefore primarily an inline-tier decision. That observation licenses the canonical combined architecture. Use an API gateway for the inline detection layer, so that the security team gets a central choke point, independent deployment, and independent scaling for the detectors that must block before the model call, paying one engineered network hop within the sub-50ms budget. Use a sidecar for near-real-time enrichment, co-located with the application to gather session context cheaply and forward it without a full hop. And run the batch tier entirely off-path as scheduled jobs over the event store, where no request-path pattern applies at all. Each tier gets the pattern that suits its latency and state profile. This combination also sets up the sections that follow. The pattern choice fixes the latency floor that Section 14.04 must budget against, fixes the process boundaries that Section 14.06 makes fail-open or fail-closed decisions across, and fixes the scaling model that Section 14.05 plans. Placement is the first production decision precisely because it is the one that constrains all the others, and with the pattern chosen and the tiers placed, Section 14.03 can turn to where in the request lifecycle each detector hooks in.

Deliverable 1

Title

Architecture Pattern Selector

Filename

architecture_pattern_selector.py

Description

Selects the API gateway, sidecar, or inline pattern from a requirements record -- latency budget, whether detection deploys independently, whether a separate team owns it, whether it scales separately, and whether a network hop is tolerable -- and returns the recommended pattern with its rationale and cautions. Runs a set of worked scenarios.

Implementation Notes

Python 3.12, single quotes throughout per book convention, no external dependencies, prints the recommended pattern with reasons and cautions per scenario.

Code

# architecture_pattern_selector.py
# Section 14.02: Architecture Pattern Selector
# 20260121 | AI Security Mastery -- Chapter 14 by Raghav Dinesh
# Single quotes throughout per book convention

from dataclasses import dataclass, field
from typing import List, Optional


@dataclass
class PatternRequirements:
    latency_budget_ms: float
    deploy_detection_independently: bool
    owned_by_separate_team: bool
    scale_detection_separately: bool
    tolerate_extra_network_hop: bool


@dataclass
class PatternRecommendation:
    pattern: str
    rationale: List[str]
    cautions: List[str]


def select_pattern(req: PatternRequirements) -> PatternRecommendation:
    rationale: List[str] = []
    cautions: List[str] = []

    # Inline is the only pattern with no added network hop, so a very tight
    # latency budget that cannot absorb a hop forces inline.
    if req.latency_budget_ms < 10 and not req.tolerate_extra_network_hop:
        rationale.append('Latency budget under 10ms cannot absorb a network hop, so detection must run in-process')
        if req.deploy_detection_independently:
            cautions.append('Inline couples detection to the application release cycle; independent deploy is lost')
        if req.owned_by_separate_team:
            cautions.append('Inline embeds detection in application code; a separate security team loses ownership isolation')
        return PatternRecommendation('inline', rationale, cautions)

    # A separate team plus independent deploy plus a clear choke point favours
    # the API gateway, at the cost of a hop.
    if req.owned_by_separate_team and req.deploy_detection_independently and req.scale_detection_separately:
        rationale.append('Separate ownership, independent deploy, and separate scaling all favour a centralised gateway')
        rationale.append('The gateway is a single choke point in front of the model service')
        if not req.tolerate_extra_network_hop:
            cautions.append('The gateway adds a network hop; verify the latency budget absorbs it')
        return PatternRecommendation('api_gateway', rationale, cautions)

    # Independent deploy without wanting a full extra hop favours the sidecar:
    # co-located, so the hop is loopback, but still deployed independently.
    if req.deploy_detection_independently and not req.tolerate_extra_network_hop:
        rationale.append('Independent deploy wanted but a full network hop is not tolerable')
        rationale.append('The sidecar co-locates detection with the application over loopback while deploying independently')
        if req.scale_detection_separately:
            cautions.append('The sidecar scales with the application pod; independent scaling is limited')
        return PatternRecommendation('sidecar', rationale, cautions)

    # Default: gateway when a hop is tolerable, otherwise sidecar.
    if req.tolerate_extra_network_hop:
        rationale.append('A network hop is tolerable and centralisation simplifies operation, so the gateway is the default')
        return PatternRecommendation('api_gateway', rationale, cautions)
    rationale.append('No tight in-process constraint but a hop is not tolerable, so the sidecar balances the trade-offs')
    return PatternRecommendation('sidecar', rationale, cautions)


SCENARIOS = [
    ('Tight inline classifier', PatternRequirements(5.0, False, False, False, False)),
    ('Central security gateway', PatternRequirements(40.0, True, True, True, True)),
    ('Independent deploy, no hop', PatternRequirements(30.0, True, False, False, False)),
    ('Relaxed budget, hop ok', PatternRequirements(80.0, False, False, False, True)),
]


def run_scenarios() -> None:
    print('=' * 78)
    print('ARCHITECTURE PATTERN SELECTOR')
    print('Selects API gateway, sidecar, or inline by latency, ownership, and scaling')
    print('=' * 78)
    for name, req in SCENARIOS:
        rec = select_pattern(req)
        print()
        print(f'SCENARIO: {name}')
        print(f'  Budget {req.latency_budget_ms}ms | indep_deploy={req.deploy_detection_independently} '
              f'| sep_team={req.owned_by_separate_team} | sep_scale={req.scale_detection_separately} '
              f'| hop_ok={req.tolerate_extra_network_hop}')
        print(f'  -> PATTERN: {rec.pattern}')
        for r in rec.rationale:
            print(f'     reason : {r}')
        for c in rec.cautions:
            print(f'     caution: {c}')


if __name__ == '__main__':
    run_scenarios()

Common Mistakes

Mistake 1

Description

Choosing the inline pattern for its low latency without accounting for the loss of deployment independence and the widened blast radius

Why It Happens

Inline has the lowest latency floor and is the simplest to wire up -- a function call in the handler -- so it looks like the obvious choice when latency is the visible concern and the coupling costs are not yet felt.

Consequence

Every detector change becomes an application release, the security team loses its own deploy schedule, and a detector that throws or hangs takes the application process down with it, because detection and application share a process.

Correct Approach

Reach for inline only when the latency budget genuinely cannot absorb even a loopback call, and prefer the sidecar or gateway otherwise so that detection keeps independent deployment and its fault stays isolated from the application.

Mistake 2

Description

Defaulting to the API gateway everywhere without checking that the latency budget can absorb the network hop

Why It Happens

The gateway is the cleanest pattern to reason about -- one central choke point, independent deploy and scaling -- so it is adopted as a blanket default without measuring the hop against the specific budget of the hot path it sits on.

Consequence

The added network hop consumes a large share of the sub-50ms inline budget, leaving too little for the detectors themselves, and the gateway is later blamed for latency that the placement decision caused.

Correct Approach

Confirm the latency budget can absorb one engineered network hop before choosing the gateway, and if it cannot, drop to a sidecar for the loopback saving or inline for the tightest budgets.

Mistake 3

Description

Treating the three patterns as mutually exclusive and forcing every detection tier into one pattern

Why It Happens

A single uniform pattern is simpler to describe and operate, and the tiers are easy to treat as an internal detail rather than as the natural seam along which patterns should be combined.

Consequence

The batch tier is awkwardly forced through a request-path gateway it does not need, or the inline tier is denied the gateway choke point it does need, and the architecture fights the tier structure instead of using it.

Correct Approach

Combine patterns along the Chapter 13 tier boundaries: a gateway for the inline hot path, a sidecar for near-real-time enrichment, and off-path jobs for batch, because the pattern choice matters most for the inline tier and barely affects the off-path tiers.

Mistake 4

Description

Assuming the pattern choice affects all three detection tiers equally

Why It Happens

The pattern is described as a property of the whole detection system, so it is natural to assume it applies uniformly, without noticing that only the inline tier is actually on the hot path where the pattern latency floor is paid.

Consequence

Effort is spent optimising the pattern placement of the near-real-time and batch tiers, which consume events asynchronously in every pattern, while the real leverage on the inline tier is under-analysed.

Correct Approach

Recognise that placement is primarily an inline-tier decision: analyse the pattern choice hardest for the inline tier on the hot path, and place the off-path tiers the same way regardless of the inline pattern.

Mistake 5

Description

Making the placement decision implicitly, by whatever wiring was easiest, rather than against a stated rationale

Why It Happens

Placement often falls out of the existing deployment topology -- detection is added wherever there was a convenient hook -- so the pattern is inherited rather than chosen, and no rationale is recorded.

Consequence

The later sections that depend on the placement -- latency budgeting, failure policy, scaling -- have no stated basis to build on, and when the placement turns out to constrain them badly there is no record of why it was chosen or what to revisit.

Correct Approach

Make the placement decision explicitly against the latency budget, ownership, and scaling drivers, using the pattern selector so that the choice carries a documented rationale the performance and resilience sections can rely on.

Section Summary

Compact

The API gateway, sidecar, and inline patterns place detection at different points in the request path and trade the same four properties -- latency floor, coupling, deployment independence, and blast radius -- against one another. The gateway runs detection as a separate service in front of the model, giving a central choke point, independent deploy, and independent scaling at the cost of a network hop. The sidecar co-locates detection as its own process, keeping independent deployment and a loopback latency floor but scaling with the pod. Inline embeds detection in the application handler for the lowest latency floor at the cost of the tightest coupling and the widest blast radius. Moving toward lower latency moves toward tighter coupling and wider blast radius, so the choice is a trade-off driven by three requirements: the latency budget sets the floor, team ownership sets the coupling, and the scaling model sets the fleet. The patterns are not mutually exclusive; a real gateway combines them along the Chapter 13 tier boundaries -- a gateway for inline detection, a sidecar for near-real-time enrichment, off-path jobs for batch -- because the pattern choice matters most for the inline tier on the hot path and barely affects the off-path tiers. Placement is the first production decision because it fixes the latency floor, process boundaries, and scaling model that every later section engineers against.
