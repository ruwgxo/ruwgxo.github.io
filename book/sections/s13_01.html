Behavioural Detection Taxonomy: From Per-Request Verdicts to Cross-Request Signals

Section Overview

One Line Summary

Per-request classification and behavioural analysis detect disjoint attack classes: the per-request classifiers of Chapter 12 see one request at a time, behavioural analysis holds state across requests -- Chapter 13 builds the layer that sees what spans requests.

Why This Section Exists

Chapter 12 trained four classifiers, and every one of them answers a question about a single request: is this prompt an injection, a jailbreak, a PII leak, an anomalous API call. The request is the unit of detection. That assumption is correct for a large class of attacks and silently wrong for an equally large class. A multi-turn jailbreak escalates gradually, and every individual turn is benign enough to pass the per-turn classifier while the trajectory across the session is the attack. A data exfiltration campaign issues thousands of individually unremarkable queries whose only tell is their rate and pattern over time. A compromised account behaves acceptably per request but diverges from its own historical baseline. A coordinated abuse network shares no single suspicious request but forms a detectable structure as a graph. None of these are visible to a classifier that sees one request at a time. Before building any behavioural detector, the engineer needs a taxonomy of behavioural signal families. Without this map, the progression through Chapter 13 reads as an arbitrary sequence of monitoring techniques -- session features, then baselines, then drift, then rate limiting, then profiling, then graphs. With it, every section is a deliberate choice driven by three questions: what attack class does this detector target, what state must be held to detect it, and what detection latency does that state requirement permit? Section 13.01 answers those questions systematically. It establishes the four behavioural signal families, maps each to the attack class it covers and the state it requires, and defines where each sits relative to the Chapter 12 per-request gateway.

Position In Chapter

Section 13.01 is the taxonomy anchor for all 11 subsequent sections of Chapter 13. It is the map that makes every later section a deliberate choice rather than an arbitrary technique selection. It mirrors the role Section 12.01 played in Chapter 12: establishing the taxonomy and the deployment logic before the implementation sections begin. Where 12.01 organised the ML families by labelled-data availability, 13.01 organises the behavioural families by the state they hold and the attack class they catch.

Prose Content

Part 1

Title

The Unit-of-Detection Assumption and Where It Breaks

Body

Every detector in Chapter 12 shares one structural assumption: the request is the unit of detection. The feature pipeline extracts features from a request. The classifier scores a request. The ensemble combines per-request scores into a per-request verdict. The gateway blocks or passes a request. This is a clean, stateless architecture, and statelessness is an operational virtue: it scales horizontally, it has no shared mutable state to corrupt, and any gateway instance can score any request with no coordination. The assumption is correct for a large class of attacks. A single-turn jailbreak whose full payload is in one prompt is detectable in that prompt. A direct injection that carries its entire instruction-override in one request is detectable in that request. A PII leak in one response is detectable in that response. For these attacks, the request genuinely is the unit, and Chapter 12 catches them. The assumption breaks for any attack whose signal is not in any single request but in the relationship between requests. Consider four concrete cases. First, a multi-turn jailbreak: the adversary spends ten turns gradually moving a roleplay scenario toward a harmful output, and each individual turn is benign enough to pass the per-turn classifier. The attack is the trajectory, not any turn. Second, an exfiltration campaign: the adversary issues ten thousand individually reasonable queries to reconstruct a proprietary dataset, and no single query is suspicious. The attack is the rate and the coverage pattern. Third, an account takeover: a legitimate user's credentials are compromised, and the attacker's requests are individually plausible but collectively unlike how that specific user has ever behaved. The attack is the divergence from the entity's own baseline. Fourth, a coordinated network: a hundred accounts each behave acceptably alone but share a creation pattern, an IP range, and synchronised activity. The attack is the structure across accounts. None of these four has a per-request signal. A stateless classifier scoring each request in isolation passes every one of them. They are not edge cases; they are the dominant attack patterns against mature LLM APIs, precisely because adversaries adapt to the detection in place. Once per-request classification is deployed, the rational adversary moves to attacks that per-request classification cannot see. Behavioural analysis is the layer that closes that gap by holding state across requests and detecting in that state.

Part 2

Title

The Four Behavioural Signal Families

Body

Four behavioural signal families are relevant to LLM API security. They differ in the state they hold, the detection latency that state permits, and the attack class each covers. Session-level signals aggregate the requests within a single session into a session object and detect patterns across the turns of that session. The state is the session: bounded, attributable to one entity, and held for the session's lifetime. Session analysis catches the multi-turn jailbreak and the accumulation attack, where the signal is the trajectory across turns -- score slope, topic drift, refusal-then-retry. Session state is small and short-lived, so session scoring can run in near-real-time, updated on each turn. Sections 13.02 (session modelling) and 13.09 (multi-turn context analysis) implement this family. Temporal signals treat a behavioural metric -- request rate, refusal rate, error rate -- as a time series and detect deviation from its historical envelope. The state is the metric history per entity or per endpoint, held as a rolling window. Temporal analysis catches the sudden burst and the slow ramp: the two opposite signatures of abuse over time. Because the metric history can be large and the analysis involves seasonal decomposition, temporal detection runs as near-real-time or scheduled analysis rather than on the request hot path. Sections 13.03 (statistical baselines), 13.04 (time-series anomaly detection), and 13.05 (drift detection) implement this family. Drift is a special case: it watches the detectors and the model rather than the user, catching silent degradation. Entity-level signals build a persistent profile of how an entity behaves across all of its sessions and score new activity against that profile. The state is the persistent entity profile: aggregated baselines, historical risk events, and a behavioural fingerprint, held indefinitely with decay. Entity analysis catches account compromise -- divergence from the entity's own fingerprint -- and makes a requester's history a first-class input to every verdict. Persistent state cannot be queried inline at full depth on the request path, so the profile is summarised into a risk score that is cheap to read inline while the full profile updates asynchronously. Sections 13.07 (rate-based detection), 13.08 (smart rate limiting), and 13.10 (user behaviour profiling) implement this family. Graph-level signals model the relationships between entities -- shared infrastructure, synchronised timing, behavioural similarity -- as a graph and detect coordinated structure. The state is the entity-relationship graph, the largest and most expensive state of the four. Graph analysis catches the coordinated abuse network and the Sybil cluster, which no single-entity detector reveals. Graph construction and community detection are batch operations run on a schedule, not inline. Section 13.11 implements this family and integrates the behavioural layer into the gateway.

Part 3

Title

The Event Stream: How Chapter 12 Output Becomes Chapter 13 Input

Body

Behavioural analysis does not re-score requests. It consumes the per-request verdicts that the Chapter 12 gateway already produced. This is the central architectural relationship of the two chapters: Chapter 12 is the sensor layer, and Chapter 13 is the analysis over the sensor output. Every request that passes through the Chapter 12 seven-track gateway emits an event. The event carries the request metadata (entity identifier, session identifier, endpoint, timestamp), the per-track classifier scores (injection score, jailbreak score, anomaly score, PII score), the ensemble verdict and tier, and the action taken (passed, flagged, blocked). This event stream is the input to all four behavioural families. The session modeller aggregates events by session identifier. The baseline and time-series detectors aggregate the numeric fields by entity and endpoint over time. The entity profiler accumulates events into persistent per-entity state. The graph detector links entities by the shared attributes carried in the events. The consequence is that behavioural detection quality is bounded by event quality. If the Chapter 12 gateway does not emit the per-track scores, the behavioural layer cannot use the trajectory of those scores across a session. If the event lacks a stable entity identifier, the entity profiler cannot accumulate history and the graph detector cannot link accounts. The event schema is therefore a shared contract between the two chapters, and Section 13.02 treats its design as the first task of behavioural modelling rather than an afterthought. This also clarifies why behavioural detection is additive rather than a replacement. The per-request gateway must keep running -- it is the sensor that produces the stream. Removing it to rely on behavioural analysis alone is removing the sensor and keeping the analytics, which detects nothing. The two layers compose: per-request classification catches the single-request attack and produces the event stream, and behavioural analysis catches the cross-request attack by analysing that stream.

Part 4

Title

State Requirement Drives Detection Latency

Body

The four families are ordered by the state they hold, and that ordering determines where each can run. This coupling between state requirement and detection latency is the single most important architectural fact in Chapter 13, because it dictates which detectors can sit on the request hot path and which cannot. Stateless per-request scoring -- the Chapter 12 baseline -- runs inline with single-digit millisecond latency because it holds no state to query. Session scoring holds small, short-lived state and runs in near-real-time: the session object is updated on each turn and scored within the session, which adds a small inline cost or a fast asynchronous follow-up. Temporal and entity analysis hold larger state -- metric histories and persistent profiles -- that cannot be queried at full depth within a request's latency budget. These families run as near-real-time asynchronous analysis, and their output is summarised into a compact signal (a baseline-deviation score, an entity risk score) that is cheap to read inline. Graph analysis holds the largest state and runs as scheduled batch jobs, with its findings written back as entity risk adjustments that the inline path reads. This produces a layered timing model. On the request hot path, the gateway reads the per-request classifier scores and the compact summaries that behavioural analysis has already computed -- the entity risk score, the current rate-limit state, the session accumulator. Near-real-time, the session scorer, the baseline detectors, and the entity profiler update their state from the event stream. In batch, the graph detector and the drift monitors run on a schedule and write their findings back as risk adjustments and alerts. The practical rule that follows: never put a query against deep behavioural state on the request path. A rate-limit decision reads a precomputed counter, not a full recomputation of the entity's history. A gateway verdict reads a precomputed entity risk score, not a live graph traversal. Behavioural detection earns its coverage by doing the expensive analysis off the hot path and exposing only cheap summaries to the latency-sensitive path.

Part 5

Title

The Behavioural Layer in the Detection Stack and the Chapter Roadmap

Body

Chapter 11 Section 11.03 defined the layered detection stack: signature detection (Sigma rules), heuristic detection (rule-based scoring), ML detection (trained classifiers), and behavioural detection. Chapter 11 built the signature and heuristic layers. Chapter 12 built the ML layer. Chapter 13 builds the fourth and final layer of that stack. Each layer catches what the layers below it miss: signatures catch known patterns, ML catches novel variants of known attack classes, and behavioural analysis catches attacks whose signal spans requests and therefore has no per-request representation for any of the lower layers to score. The layers are strictly additive in coverage and strictly ordered in cost. Signature detection is cheapest and narrowest. ML detection is more expensive and broader. Behavioural detection is the most expensive, because it holds state, and the broadest, because it sees the cross-request attacks the other three layers cannot. A detection system is not complete until all four layers are present; a system with only the first three has a structural blind spot for escalation, exfiltration, compromise, and coordination. The rest of Chapter 13 implements the four behavioural families in an order that builds state from small to large. Section 13.02 builds session modelling and the shared behavioural feature pipeline. Sections 13.03 and 13.04 build the statistical baselines and time-series anomaly detection that define and detect temporal deviation. Section 13.05 builds drift detection, which keeps the Chapter 12 detectors from failing silently. Section 13.06 builds model behavioural monitoring, which detects injection success in the model's output rather than injection attempts in the input. Sections 13.07 and 13.08 build rate-based detection and adaptive smart rate limiting for aggregate abuse. Section 13.09 builds multi-turn context analysis for the escalation attacks that defeat per-turn scoring. Section 13.10 builds the persistent user behaviour profile and entity risk score. Section 13.11 builds graph-based detection and integrates the whole behavioural layer into the Chapter 12 gateway as the capstone. Section 13.12 closes the chapter and previews Chapter 14's production deployment. Each section is a deliberate choice on the taxonomy this section establishes: it targets a named attack class, holds a defined state, and runs at the detection latency that state permits. The taxonomy is the map; the chapter is the territory.

# behavioural_family_selector.py
# Section 13.01: Behavioural Family Selection Decision Logic
# 20260621 | AI Security Mastery -- Chapter 13 by Raghav Dinesh

from dataclasses import dataclass
from typing import List, Optional


@dataclass
class AttackScenario:
    name: str
    signal_spans_requests: bool
    signal_is_within_one_session: bool
    signal_is_metric_over_time: bool
    signal_is_divergence_from_own_history: bool
    signal_is_across_multiple_entities: bool
    signal_is_model_output_shift: bool


@dataclass
class FamilyRecommendation:
    scenario: str
    family: str
    state_required: str
    detection_latency: str
    sections: List[str]
    rationale: str


def select_family(s: AttackScenario) -> FamilyRecommendation:
    # First gate: is this even a behavioural problem?
    if not s.signal_spans_requests:
        return FamilyRecommendation(
            scenario=s.name,
            family='Per-request (Chapter 12) -- not behavioural',
            state_required='None (stateless)',
            detection_latency='Inline, single-digit ms',
            sections=['Chapter 12 -- per-request classifiers'],
            rationale='The signal is in a single request; the Chapter 12 ensemble handles it. No behavioural state is required.',
        )

    # Model output-side shift -> output monitoring (temporal, output-side)
    if s.signal_is_model_output_shift:
        return FamilyRecommendation(
            scenario=s.name,
            family='Temporal (output-side) -- model behaviour monitoring',
            state_required='Per-endpoint output distribution baseline',
            detection_latency='Post-inference, off the response path',
            sections=['Section 13.06 (model behaviour monitoring)'],
            rationale='Injection success shows as output distribution shift, not input score; monitor the output against its baseline.',
        )

    # Within one session -> session family
    if s.signal_is_within_one_session:
        return FamilyRecommendation(
            scenario=s.name,
            family='Session-level',
            state_required='Session object (short-lived)',
            detection_latency='Near-real-time (per turn)',
            sections=['Section 13.02 (session modelling)', 'Section 13.09 (multi-turn analysis)'],
            rationale='The signal is the trajectory across turns of one session; aggregate the session and score the trajectory.',
        )

    # Metric over time -> temporal family

            scenario=s.name,
            family='Temporal',

                'Section 13.07 (rate-based detection)',
            ],
            rationale='The signal is a metric deviating from its historical envelope; establish a baseline and detect temporal deviation.',
        )

    if s.signal_is_divergence_from_own_history:
        return FamilyRecommendation(
            scenario=s.name,
            family='Entity-level',
            state_required='Persistent entity profile (with decay)',
            detection_latency='Async update; risk score read inline',
            sections=['Section 13.10 (user behaviour profiling)', 'Section 13.08 (smart rate limiting)'],
            rationale='The signal is divergence from the entity own fingerprint; build a persistent profile and score against it.',
        )

    # Across multiple entities -> graph family
    if s.signal_is_across_multiple_entities:
        return FamilyRecommendation(
            scenario=s.name,
            family='Graph-level',
            state_required='Entity-relationship graph (largest state)',
            detection_latency='Batch (scheduled)',
            sections=['Section 13.11 (graph-based detection)'],
            rationale='The signal is the structure between entities; build the relationship graph and detect coordinated structure.',
        )

    return FamilyRecommendation(
        scenario=s.name,
        family='Unclassified -- refine the signal description',
        state_required='Unknown',
        detection_latency='Unknown',
        sections=['Revisit Section 13.01 taxonomy'],
        rationale='The scenario spans requests but does not match a single family signature; decompose it further.',
    )

from dataclasses import dataclass, field
from typing import Dict, List, Optional


@dataclass
class GatewayEvent:
    # Identity and routing
    entity_id: Optional[str]
    session_id: Optional[str]
    endpoint: Optional[str]
    timestamp: Optional[float]
    source_ip: Optional[str]
    credential_id: Optional[str]
    # Per-track classifier scores from the Chapter 12 ensemble
    injection_score: Optional[float]
    jailbreak_score: Optional[float]
    anomaly_score: Optional[float]
    pii_score: Optional[float]
    # Ensemble verdict
    ensemble_tier: Optional[str]
    action_taken: Optional[str]


# Each family lists the event fields it requires to function
FAMILY_REQUIREMENTS: Dict[str, List[str]] = {
    'Session-level': ['session_id', 'timestamp', 'injection_score', 'jailbreak_score'],
    'Temporal': ['entity_id', 'endpoint', 'timestamp'],
    'Entity-level': ['entity_id', 'timestamp', 'ensemble_tier'],
    'Graph-level': ['entity_id', 'source_ip', 'credential_id', 'timestamp'],
}


def missing_fields(event: GatewayEvent, required: List[str]) -> List[str]:
    gaps = []
    for fieldname in required:
        if getattr(event, fieldname, None) is None:
            gaps.append(fieldname)
    return gaps


def assess_event(event: GatewayEvent) -> None:
    print('Behavioural Event Coverage Assessment')
    print('-' * 42)
    for family, required in FAMILY_REQUIREMENTS.items():
        gaps = missing_fields(event, required)
        if not gaps:
            print(f'[x] {family}: can be fed (all {len(required)} required fields present)')
        else:
            print(f'[ ] {family}: cannot be fed -- missing {", ".join(gaps)}')
    print()

Common Mistakes

Mistake 1

Description

Treating behavioural analysis as a replacement for the per-request gateway and reducing investment in the Chapter 12 classifiers once behavioural detection is deployed

Why It Happens

Behavioural detection catches the sophisticated cross-request attacks that look most impressive in a detection report: the multi-turn jailbreak, the coordinated network, the account takeover. Next to these, per-request classification can look like a solved, lower-tier problem. Engineers reallocate attention to the behavioural layer and let the per-request classifiers stagnate.

Consequence

Behavioural detection consumes the event stream that the per-request gateway produces. If the per-request classifiers degrade, the per-track scores in the event stream degrade, and every session and entity detector that relies on score trajectory degrades with them. Worse, the single-request attacks that only the per-request layer catches start passing again. The behavioural layer cannot compensate -- it was never designed to catch the single-request attack, and it depends on the per-request layer as its sensor.

Correct Approach

Treat the two layers as a composed system with a shared contract. The per-request gateway is the sensor that catches single-request attacks and emits the event stream; the behavioural layer is the analysis that catches cross-request attacks over that stream. Both must be maintained. The event schema is the contract between them, and degrading either side degrades the whole.

Mistake 2

Description

Putting a query against deep behavioural state on the request hot path -- recomputing entity history or traversing the graph inline to make a gateway decision

Why It Happens

The entity profile and the relationship graph contain the richest detection signal in the system. When making a per-request gateway decision, it is tempting to query that signal directly: traverse the graph to check whether this entity is in a known abuse cluster, recompute the full rate history to decide whether to throttle. The richer the inline query, the better the inline decision seems.

Consequence

Deep behavioural state cannot be queried within a request latency budget. A graph traversal or a full-history recomputation adds tens to hundreds of milliseconds to every request, blowing the sub-50ms gateway budget established in Chapter 11. The product team disables the behavioural layer within a week because it made the API slow. The detection that would have caught the attack is removed because it was placed on the wrong path.

Correct Approach

Keep the expensive analysis off the hot path and expose only cheap summaries to it. The entity profiler updates the profile asynchronously and writes a compact risk score; the graph detector runs in batch and writes back a risk adjustment. The hot path reads a precomputed score, never recomputes state. State requirement and detection latency are coupled: the families that hold large state must run async or batch, and the request path reads their summarised output.

Mistake 3

Description

Doing anomaly detection without first establishing an explicit per-entity baseline, flagging deviation from a single global threshold

Why It Happens

A global threshold is simpler to implement than per-entity baselines. Setting one request-rate limit for all users, one refusal-rate threshold for all sessions, requires no per-entity state and no cold-start handling. It looks like behavioural detection because it triggers on behaviour.

Consequence

Normal behaviour varies enormously by entity. A request rate that is an attack for a casual user is a Tuesday for a heavy integration. A global threshold set high enough not to flag the power user is too high to catch the compromised low-volume account; set low enough to catch the compromised account, it floods on every power user. The detector produces false positives on legitimate heavy users and false negatives on the attacks it was meant to catch. This is covered in depth in Section 13.03, but the failure begins here, in the taxonomy: treating a temporal-family problem as if it needed no baseline state.

Correct Approach

Recognise from the taxonomy that temporal and entity families require state -- a baseline or a profile -- precisely so that deviation is measured per entity rather than against a global constant. The state requirement is not incidental; it is what makes the detection correct. Section 13.03 builds the per-entity baselines that every temporal detector scores against.

Mistake 4

Description

Designing the gateway event stream without the fields the behavioural families need, then discovering the gap only when building the detectors

Why It Happens

The Chapter 12 gateway is designed to make a per-request verdict. For that purpose, it needs the request and the classifier scores; it does not strictly need a stable cross-session entity identifier, a source attribution, or the per-track score breakdown in the emitted event. An engineer focused on the per-request verdict emits a minimal event that records only the final decision.

Consequence

Every behavioural family is bounded by what the event carries. An event without a stable entity identifier silently disables entity profiling and graph detection -- there is no key to accumulate history or link accounts. An event without the per-track scores disables session trajectory analysis. The gap is invisible until the behavioural detector is built and produces nothing, at which point the gateway must be re-instrumented and all historical events are already lost.

Correct Approach

Treat the event schema as a shared contract designed up front, before the behavioural detectors are built. The event must carry a stable entity identifier, a session identifier, source and credential attribution, the per-track classifier scores, and the timestamp. The behavioural_event_schema.py deliverable makes this contract explicit and checkable so the gap is caught at design time, not at detector-build time.

Mistake 5

Description

Classifying every cross-request attack as a single behavioural problem and building one monolithic detector instead of matching each attack class to its family

Why It Happens

All four behavioural families share the property of holding state across requests, which makes them look like one problem. An engineer builds a single behavioural detector intended to catch escalation, exfiltration, compromise, and coordination all at once, reasoning that they are all just behaviour over time.

Consequence

The four attack classes have fundamentally different signals and state requirements. Escalation lives in a session trajectory; exfiltration lives in a metric over time; compromise lives in divergence from an entity baseline; coordination lives in the structure between entities. A single detector that tries to cover all four either holds the union of all state -- making it as expensive as the graph family for every request -- or compromises on each, catching none well. The monolith is both slow and weak.

Correct Approach

Use the taxonomy to match each attack class to the family whose state and latency profile fit it. Session attacks get session state and near-real-time scoring; temporal attacks get metric history; entity attacks get persistent profiles; coordination gets the batch graph. Each detector holds exactly the state its attack class requires and runs at the latency that state permits. The families are separate by design because the attacks are separate by nature.

Section Summary

Compact

Chapter 13 builds the behavioural layer of the detection stack, the fourth layer above the Chapter 11 signature and heuristic layers and the Chapter 12 ML layer. Per-request classification and behavioural analysis detect disjoint attack classes: the per-request gateway sees one request at a time and catches the single-request attack, while behavioural analysis holds state across requests and catches the attack whose signal spans them. Four behavioural signal families cover the cross-request threat surface, ordered by the state they hold: session-level (short-lived session state, catches multi-turn escalation), temporal (metric history, catches burst and slow-ramp abuse and detector drift), entity-level (persistent profile, catches account compromise and low-and-slow abuse), and graph-level (entity-relationship graph, catches coordinated networks). Behavioural detection consumes the per-request event stream the Chapter 12 gateway emits -- Chapter 12 is the sensor, Chapter 13 is the analysis. State requirement and detection latency are coupled: families that hold large state run async or in batch and expose only cheap summaries to the request hot path. The taxonomy is the map for the rest of the chapter: each section targets a named attack class, holds a defined state, and runs at the latency that state permits.

Key Takeaways

  • Per-request classification and behavioural analysis detect disjoint attack classes: the per-request gateway catches the single-request attack, behavioural analysis catches the attack whose signal spans requests
  • The four behavioural families are ordered by state held: session (short-lived), temporal (metric history), entity (persistent profile), and graph (entity-relationship graph)
  • Behavioural detection consumes the per-request event stream rather than replacing the gateway -- Chapter 12 is the sensor that produces the stream, Chapter 13 is the analysis over it
  • State requirement and detection latency are coupled: families holding large state run async or batch and expose only cheap precomputed summaries to the request hot path
  • Anomaly detection requires an explicit per-entity baseline because normal behaviour varies by entity -- a global threshold floods on power users and misses compromised low-volume accounts
  • Match each attack class to its family rather than building a monolith: escalation to session, rate abuse to temporal, compromise to entity, coordination to graph -- the families are separate because the attacks are separate

Section 13.02: Session Modelling and Behavioural Feature Engineering -- Aggregating the Request Stream

Summary

Section 13.02 builds the session modelling and behavioural feature pipeline that every session-level and entity-level detector in Chapter 13 consumes -- the behavioural analogue of the Section 12.02 feature pipeline that every per-request classifier shared. The session is the first aggregation unit above the request: bounded, attributable to one entity, and semantically coherent. The section addresses session boundary definition (time-window, explicit token, and inactivity-timeout strategies and their detection trade-offs), aggregation of the per-request event stream into a session object, and the behavioural features extracted from it: turn count, refusal rate, request cadence, inter-request interval distribution, and intra-session topic drift -- the high-signal escalation feature that measures how far a conversation moves from its opening topic. It builds the session store with streaming aggregation and configurable retention, and applies feature-importance analysis to identify which session signals carry independent detection signal. A well-modelled session with a topic-drift feature lets a downstream detector catch the gradual jailbreak that no per-turn classifier flags; a naive session model that only counts turns misses it entirely.
