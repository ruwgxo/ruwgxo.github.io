6.16.1

Title

Research Background: CTF Exploits and Security Research Documentation

Content

In 2023, OpenAI launched the ChatGPT plugin ecosystem, allowing third-party developers to register plugins that ChatGPT could call as tools during conversations. Plugins enabled capabilities ranging from web search and code execution to email access, calendar management, and e-commerce integration. Within weeks of the plugin ecosystem's launch, security researchers documented injection exploits through Capture the Flag exercises and structured red team research. The most significant documented exploits came from researcher Johann Rehberger, who ran a series of CTF challenges specifically designed to demonstrate plugin injection. The challenges showed that adversarially crafted content retrieved through one plugin could influence ChatGPT to call a second plugin with adversary-specified parameters -- achieving data exfiltration, unintended external API calls, and in some cases access to information the user had not intended to share with a third party. Parallel research by multiple teams examined the AutoGPT and LangChain agent frameworks, which had been released around the same time. These open-source frameworks implemented tool-augmented LLM agents with persistent memory and multi-step planning. The research found that indirect injection via tool outputs could redirect the agent's goal, causing it to take actions inconsistent with the user's stated objective. This section synthesises the documented research into a structured incident analysis. The technical mechanisms are grounded in published public sources: the CTF challenge documentation, researcher blog posts, and academic papers on agentic injection. The analysis applies the five-layer RCA format established in Section 6.14 and used in Section 6.15, completing the three- incident block with the most consequential injection class for future AI deployments: agentic tool-call chain injection.

Key Point

GPT plugin injection research established that agentic tool-call chain injection is exploitable at production scale. The CTF documentation provided concrete attack chains showing data exfiltration via multi-plugin injection -- the highest-impact injection outcome class in a tool-augmented deployment.

6.16.2

Title

Technical Reconstruction: The Confused Deputy Attack Chain

Content

The confused deputy attack chain in plugin injection has four components: the injection vector (the source of the adversary's payload), the confused deputy (the LLM agent using its legitimate plugin permissions), the tool call (the action taken with those permissions), and the outcome (what the adversary achieves). The injection vector: in the documented CTF exploits, the injection vector was content retrieved through a first plugin -- typically a web fetch or document retrieval plugin. The fetched content contained injection payloads in HTML hidden text, document text, or API response fields. This matches exactly the indirect injection mechanisms from Sections 6.7 (web), 6.9 (database/API), and 6.6 (RAG). The novel element in the plugin context is not the injection vector -- it is the confused deputy target. The confused deputy: ChatGPT with plugin access had legitimate permissions to call each registered plugin. The user granted these permissions when enabling the plugins. The LLM, operating as the user's agent, was authorised to call any enabled plugin on the user's behalf. An injection payload that caused the LLM to call a plugin with adversary-specified parameters was exploiting the LLM's legitimate, user-granted permissions for an adversary purpose. The adversary did not need to acquire the permissions themselves; they caused the LLM to misuse the permissions it already had. The documented exploit chain: the user enables two plugins -- a web browsing plugin and a data export or communication plugin (email, Zapier, external API). The user asks the LLM to browse a page or retrieve information. The LLM calls the web browsing plugin. The retrieved page contains an injection payload instructing the LLM to call the communication plugin with specific content -- typically exfiltrating information from the conversation context. The LLM, processing the injection as a legitimate instruction within the task flow, calls the communication plugin. The communication plugin executes with its legitimate permissions, transmitting data to the adversary-controlled destination. Cross-plugin injection: the more sophisticated variant uses the injection from plugin call 1's output to poison plugin call 2's input in a way that causes plugin call 2's output to contain a secondary injection, which then influences plugin call 3. Each plugin in the chain relays and potentially amplifies the injection. Attribution becomes progressively harder as the chain grows.

Key Point

The confused deputy attack uses the LLM's legitimate plugin permissions to serve the adversary's objectives. The adversary does not need to acquire permissions; they cause the LLM to misuse the permissions it already holds. Cross-plugin injection uses multi-step chains to relay and amplify the initial injection, degrading attribution.

6.16.3

Title

Root Cause Analysis: Five-Layer Framework Applied

Content

Immediate cause: injection payloads in content retrieved through plugin calls caused the LLM to make subsequent plugin calls with adversary-specified parameters, executing actions with the LLM's legitimate plugin permissions that the user had not authorised. Contributing cause: plugin architectures did not apply injection classification to plugin output before that output entered the LLM's context and reasoning process. Plugin outputs were treated as trusted data from a legitimate tool, equivalent in trust to the user's own instructions. No mechanism distinguished adversary-controlled content returned by a plugin from the plugin's legitimate functional output. Systemic cause: the plugin ecosystem's trust model did not account for indirect injection via plugin output. The threat model assumed that plugins returned legitimate data and that the LLM's use of that data was bounded by its alignment training. The capability expansion from enabling plugins -- each plugin added real-world actions with real permissions -- was not matched by a proportional expansion of the security architecture to classify content entering from each new tool output pathway. Detection failure: the injection-to-action chain in plugin exploits was rapid -- typically two to three plugin calls from injection to outcome. No real-time monitoring of the plugin call sequence for injection propagation was in place. The CTF exploits were detected because the researcher designed them to be observable; in a production setting with a less observant user, the exfiltration would have completed without automated detection. Remediation gap: the primary absent control was plugin output classification -- applying the injection classifier to plugin return values before those values entered the LLM's reasoning context (Section 6.12.4 tool call graph analysis applied to the plugin context). Secondary absent control: plugin call allowlisting specifying which plugin-to-plugin call sequences are permitted, preventing a web browse result from triggering an email send.

Key Point

The systemic root cause is the trust model mismatch: the threat model assumed plugin outputs were trusted data, but plugins return content from adversary-influenced sources. Each plugin added real-world permissions without a corresponding classifier on its output. The security architecture did not scale with the capability expansion.

6.16.4

Title

Exfiltration via Plugin: The Highest-Impact Injection Outcome

Content

Exfiltration via plugin is the most consequential plugin injection outcome because it achieves data exfiltration from the LLM's conversation context to an adversary-controlled external destination, using the LLM's legitimate plugin permissions, without the user taking any action beyond their original benign request. The exfiltration mechanism: the user's conversation context contains sensitive information -- the contents of documents the user asked the LLM to process, the user's personal information shared during the conversation, or the system prompt's configuration details. An injection payload in a retrieved document or API response instructs the LLM to call a communication plugin (email, webhook, external API) with specific content drawn from the conversation context. The LLM assembles the exfiltration payload from the conversation context and calls the plugin. The plugin executes the call with its legitimate credentials, transmitting the exfiltrated content. The user sees no indication that anything anomalous has occurred. The LLM may continue responding to the original query normally. The communication plugin's call log records the outbound transmission, but without monitoring of plugin call parameters for anomalous content, this log entry produces no alert. The adversary receives the conversation context at their external endpoint. The documented CTF exploits demonstrated this chain specifically with email plugins and webhook plugins. The injection caused the LLM to send an email to an adversary-controlled address containing the conversation context, or to make a POST request to an adversary-controlled webhook with the context as the request body. Both exploits worked because the plugin had the necessary permissions and the LLM processed the injection instruction as a legitimate task. The impact magnitude distinguishes exfiltration via plugin from all other injection outcomes discussed in this chapter. In RAG injection, web injection, and most indirect injection classes, the adversary influences what the model says to the user. In plugin exfiltration, the adversary receives the conversation context directly at their endpoint. The model is a proxy; the user's sensitive data leaves the controlled environment.

Key Point

Exfiltration via plugin is the highest-impact injection outcome: sensitive conversation context reaches the adversary's external endpoint using the LLM's legitimate plugin permissions, without any anomalous user action. The user has no indication; the LLM continues normally; the data is gone.

6.16.5

Title

Plugin Security Architecture: Allowlisting, Sandboxing, and Call Graph Monitoring

Content

The plugin security architecture addresses the confused deputy attack through three complementary controls: plugin call allowlisting (which plugin-to-plugin call sequences are permitted), plugin output sandboxing (classifying plugin return values before context delivery), and plugin call graph monitoring (detecting anomalous call sequences in real time). Plugin call allowlisting defines permitted call graph edges. A policy that says "a web browse result may trigger a search but may not trigger an email send" prevents the primary exfiltration chain even if injection succeeds in the browse result. Allowlisting is specified as a directed permission graph: plugin A output may trigger plugin B call but not plugin C call. The LLM's tool-calling architecture enforces this at the function-call routing layer, refusing to invoke restricted plugin combinations regardless of what the model's reasoning suggests. Plugin output sandboxing: before any plugin's return value enters the LLM's reasoning context, the injection classifier runs on the return value content. This is the tool call output classification from Section 6.12.4 (tool call graph analysis) applied specifically to the plugin layer. Return values above the injection threshold are either redacted from the context or returned to the model with an annotation indicating potential injection content. The LLM can still see that the plugin returned content but the potentially injected portion is marked, reducing the model's probability of following it as an instruction. Plugin call graph monitoring: real-time monitoring of the sequence of plugin calls made during a conversation, specifically looking for patterns consistent with injection propagation. The primary pattern: a read plugin (web browse, document retrieve, API get) returns content with an elevated injection score, followed by a write plugin (email send, webhook post, database write, API post) call with parameters that include conversation context content. This sequence -- read with injection-scored output followed by context-bearing write -- is the exfiltration pattern. An alert fires; the write plugin call is queued for human review or blocked pending review. The principle of least privilege applied to plugin permissions: plugins should be granted the minimum permissions required for their legitimate function. A web browsing plugin does not need write access to email or databases. A document summarisation plugin does not need to make outbound API calls. Least privilege is enforced at plugin registration: each plugin's permitted action scope is defined and enforced independently of what the LLM's reasoning suggests.

Key Point

Three controls address the confused deputy: allowlisting (which plugins may follow which), sandboxing (classifying plugin outputs before context delivery), and call graph monitoring (detecting read-then-write exfiltration sequences in real time). Least privilege at plugin registration limits the available exfiltration channels regardless of injection success.

Title

Detection Opportunity Map and Lessons for Tool-Augmented Deployments

Content

Detection opportunity mapping for the GPT plugin incidents identifies five detection points, ordered by how early in the attack chain each would have intervened. Opportunity 1 -- Plugin output injection classifier (pre-context delivery): the primary pre-execution detection opportunity. If the injection classifier had run on the web browse plugin's return value before that value entered the LLM's reasoning context, the injection payload in the retrieved page would have been scored and either excluded or annotated. This is the same retrieval-time classifier from Section 6.14's Opportunity 1, applied to the plugin output pathway rather than a standalone web retrieval function. Opportunity 2 -- Plugin call allowlisting (pre-execution structural): a policy preventing web browse results from triggering email send or webhook calls would have blocked the exfiltration step regardless of whether the injection survived the output classifier. Allowlisting is a structural prevention that operates at the architecture layer, not the content layer. Opportunity 3 -- Call graph anomaly detection (real-time execution): monitoring the read-then-write pattern in real time would have detected the exfiltration attempt before the write plugin completed its call. Alert fires when an injection-scored read result is followed by a context- bearing write call; the write is queued for review rather than immediately executed. Opportunity 4 -- Plugin parameter anomaly detection (pre-execution): monitoring the parameters passed to write plugins for conversation context content appearing where a write plugin would not normally receive it. An email plugin called with a body parameter containing lengthy conversation text is anomalous. Opportunity 5 -- Least privilege enforcement (structural): if the user's web browsing plugin did not have permission to trigger email sends or webhook calls, the exfiltration chain was structurally impossible regardless of injection success. This is the principle of least privilege applied at plugin registration. Generalised lesson for tool-augmented deployments: each tool added to an LLM deployment adds a confused deputy attack surface proportional to the tool's permission scope. The addition of each new tool should trigger a security review that: (1) defines the tool's minimum required permission scope, (2) adds the tool output to the injection classifier pipeline, (3) updates the call graph allowlist to include or exclude the new tool as a follow-on caller, and (4) adds the tool's write operations to the call graph monitoring anomaly patterns.

Key Point

The primary detection opportunity was plugin output classification -- the same control absent in the Bing Chat and Copilot incidents, now applied to tool outputs. The structural prevention was plugin call allowlisting, which would have blocked the exfiltration chain architecturally regardless of injection content. Both controls are required; structural prevention is more robust than content classification alone.

Subsection 7

Number

6.16.7

Title

Three-Incident Synthesis: The Architecture Lesson Across All Three Cases

Content

The three incidents analysed in Sections 6.14, 6.15, and 6.16 span three distinct deployment architectures -- web-augmented conversational AI, code assistant IDE integration, and tool-augmented agentic deployment -- but share a single architectural root cause: content from external sources entered the LLM's context without injection classification. In the Bing Chat incident, retrieved web page content entered the LLM context through the web browsing pipeline without classification. The absent control was a retrieval-time classifier on web content. In the Copilot incident, code comments and package documentation entered the code assistant's context window without classification. The absent control was a comment-level classifier on context sources. In the GPT plugin incident, plugin return values -- which may include content from any external source the plugin accessed -- entered the LLM's reasoning context without classification. The absent control was a plugin output classifier on tool return values. The unified architectural lesson: wherever external content enters an LLM's context, a classifier must stand between that content and the context assembly stage. This is the definition of the pre-assembly classifier pattern that Section 6.17's production classifier implements. The three incidents provide the empirical justification for this pattern from three different angles: a major consumer AI deployment, a developer productivity tool, and an agentic platform. All three converge on the same absent control. The progression of impact across the three incidents also illustrates the stakes escalation in agentic deployments. The Bing Chat incident caused persona adoption and system prompt revelation -- embarrassing and a security concern but not directly causing data exfiltration. The Copilot incident caused malicious code suggestion -- requiring the developer to accept and run code for impact. The plugin incident caused automatic data exfiltration -- no additional user action required. As deployments become more agentic and tools accumulate more permissions, the impact per successful injection escalates proportionally.

Key Point

All three incidents share one architectural root cause: external content entered LLM context without a classifier. The pre-assembly classifier pattern from Section 6.17 is the unified response. Impact escalates with agentic capability: Bing Chat caused persona adoption; Copilot caused malicious suggestions; plugin injection caused automatic data exfiltration.

#!/usr/bin/env python3
"""
plugin_call_graph_detector.py
Section 6.16 -- Plugin Call Graph Anomaly Detector
Monitors plugin call sequences for injection propagation patterns.
Detects read-then-write exfiltration chains and cross-plugin injection.
Author: Raghav Dinesh | ai-security-mastery
"""

import json
import re
from dataclasses import dataclass, field, asdict
from pathlib import Path
from typing import Optional


# Plugin classification
READ_PLUGINS = {
    "web_browse", "web_fetch", "document_retrieve", "database_query",
    "file_read", "search", "rag_retrieve", "api_get",
}
WRITE_PLUGINS = {
    "email_send", "webhook_post", "api_post", "file_write",
    "database_write", "calendar_create", "slack_send", "sms_send",
}
NEUTRAL_PLUGINS = {
    "code_execute", "calculator", "translate", "summarise",
}

# Injection signals in plugin output
PLUGIN_OUTPUT_SIGNALS = [
    r"\b(next action|your next step|proceed to|now call)\b",
    r"\b(call|invoke|use|execute)\b.{0,20}\b(the|a|your)\b.{0,20}\b(plugin|tool|function|api)\b",
    r"\bnote (for|to) (the agent|ai|assistant|llm)\b",
    r"\b(based on|given) this (result|output)\b.{0,20}\b(you should|please|now)\b",
    r"\b(send|transmit|forward|post|email)\b.{0,30}\b(to|at|the following)\b",
    r"\bignore\b.{0,30}\b(previous|prior|all)\b.{0,20}\b(instruction|directive)\b",
    r"\byour (updated|new|actual) (task|objective|goal)\b",
]

# Context content indicators in write plugin parameters
CONTEXT_CONTENT_SIGNALS = [
    r"\b(system prompt|conversation|context|history|prior message)\b",
    r"\b(user said|user mentioned|the user)\b",
    r"\b(confidential|sensitive|internal|private)\b",
    r"[A-Za-z0-9]{40,}",  # long token strings that may be auth/session data
]


def score_plugin_output(output: str) -> tuple[float, list[str]]:
    ol = output.lower()
    matched = [p[:60] for p in PLUGIN_OUTPUT_SIGNALS
               if re.search(p, ol, re.IGNORECASE)]
    return min(1.0, len(matched) * 0.25), matched


def score_write_parameters(params: dict) -> tuple[float, list[str]]:
    """Check if write plugin parameters contain conversation context content."""
    params_text = json.dumps(params).lower()
    matched = [p[:60] for p in CONTEXT_CONTENT_SIGNALS
               if re.search(p, params_text, re.IGNORECASE)]
    return min(1.0, len(matched) * 0.30), matched


@dataclass
class PluginCall:
    call_id: int
    plugin_name: str
    plugin_type: str          # read | write | neutral | unknown
    parameters: dict
    output: str
    output_injection_score: float
    output_matched_signals: list[str]
    write_param_score: float
    write_param_signals: list[str]


@dataclass
class CallGraphAnomaly:
    anomaly_type: str
    call_id: int
    triggering_call_id: Optional[int]
    description: str
    risk_level: str           # HIGH | CRITICAL


@dataclass
class CallGraphReport:
    conversation_id: str
    total_calls: int
    read_calls: int
    write_calls: int
    injection_scored_outputs: int
    anomalies: list[CallGraphAnomaly]
    overall_decision: str     # CLEAN | FLAG | ALERT
    plugin_calls: list[PluginCall]


def analyse_call_graph(
    conversation_id: str,
    raw_calls: list[dict],
    output_flag_threshold: float = 0.25,
    output_block_threshold: float = 0.50,
    param_flag_threshold: float = 0.25,
) -> CallGraphReport:
    calls = []
    for i, raw in enumerate(raw_calls):
        plugin_name = raw.get("plugin", "unknown")
        if plugin_name in READ_PLUGINS:
            ptype = "read"
        elif plugin_name in WRITE_PLUGINS:
            ptype = "write"
        elif plugin_name in NEUTRAL_PLUGINS:
            ptype = "neutral"
        else:
            ptype = "unknown"

        output = raw.get("output", "")
        params = raw.get("params", {})

        out_score, out_signals = score_plugin_output(output)
        param_score, param_signals = (
            score_write_parameters(params)
            if ptype == "write" else (0.0, [])
        )

        calls.append(PluginCall(
            call_id=i + 1,
            plugin_name=plugin_name,
            plugin_type=ptype,
            parameters=params,
            output=output[:100],
            output_injection_score=round(out_score, 4),
            output_matched_signals=out_signals[:3],
            write_param_score=round(param_score, 4),
            write_param_signals=param_signals[:3],
        ))

    anomalies = []

    # Pattern 1: Injection-scored read output followed by write call
    for i, call in enumerate(calls[:-1]):
        next_call = calls[i + 1]
        if (call.output_injection_score >= output_flag_threshold
                and call.plugin_type == "read"
                and next_call.plugin_type == "write"):
            risk = ("CRITICAL" if call.output_injection_score >= output_block_threshold
                    else "HIGH")
            anomalies.append(CallGraphAnomaly(
                anomaly_type="INJECTION_READ_THEN_WRITE",
                call_id=next_call.call_id,
                triggering_call_id=call.call_id,
                description=(
                    f"Read plugin '{call.plugin_name}' returned injection-scored output "
                    f"({call.output_injection_score:.3f}); immediately followed by "
                    f"write plugin '{next_call.plugin_name}'"
                ),
                risk_level=risk,
            ))

    # Pattern 2: Write plugin called with context content in parameters
    for call in calls:
        if call.plugin_type == "write" and call.write_param_score >= param_flag_threshold:
            anomalies.append(CallGraphAnomaly(
                anomaly_type="CONTEXT_CONTENT_IN_WRITE_PARAMS",
                call_id=call.call_id,
                triggering_call_id=None,
                description=(
                    f"Write plugin '{call.plugin_name}' called with parameters "
                    f"containing conversation context indicators "
                    f"(param_score={call.write_param_score:.3f})"
                ),
                risk_level="HIGH",
            ))

    # Pattern 3: Multiple read plugins with injection-scored outputs (chain)
    injection_scored_reads = [c for c in calls
                              if c.plugin_type == "read"
                              and c.output_injection_score >= output_flag_threshold]
    if len(injection_scored_reads) > 1:
        anomalies.append(CallGraphAnomaly(
            anomaly_type="MULTI_STEP_INJECTION_CHAIN",
            call_id=injection_scored_reads[-1].call_id,
            triggering_call_id=injection_scored_reads[0].call_id,
            description=(
                f"Multiple read plugins with injection-scored outputs: "
                f"{[c.plugin_name for c in injection_scored_reads]} -- "
                f"possible cross-plugin injection chain"
            ),
            risk_level="HIGH",
        ))

    read_count = sum(1 for c in calls if c.plugin_type == "read")
    write_count = sum(1 for c in calls if c.plugin_type == "write")
    scored_count = sum(1 for c in calls
                       if c.output_injection_score >= output_flag_threshold)

    critical = any(a.risk_level == "CRITICAL" for a in anomalies)
    has_anomaly = len(anomalies) > 0

    decision = "ALERT" if critical else ("FLAG" if has_anomaly else "CLEAN")

    return CallGraphReport(
        conversation_id=conversation_id,
        total_calls=len(calls),
        read_calls=read_count,
        write_calls=write_count,
        injection_scored_outputs=scored_count,
        anomalies=anomalies,
        overall_decision=decision,
        plugin_calls=calls,
    )


def print_report(report: CallGraphReport) -> None:
    print(f"\n{'='*68}")
    print(f"PLUGIN CALL GRAPH REPORT [{report.overall_decision}] "
          f"conv={report.conversation_id}")
    print(f"{'='*68}")
    print(f"Calls: {report.total_calls} | Read: {report.read_calls} | "
          f"Write: {report.write_calls} | "
          f"Injection-scored: {report.injection_scored_outputs}")
    print()
    for c in report.plugin_calls:
        flag = " [INJECTION]" if c.output_injection_score >= 0.25 else ""
        ctx_flag = " [CONTEXT_IN_PARAMS]" if c.write_param_score >= 0.25 else ""
        print(f"  [{c.call_id:02d}] {c.plugin_name:<22} ({c.plugin_type:<7}) "
              f"out={c.output_injection_score:.3f}{flag}{ctx_flag}")
        for sig in c.output_matched_signals[:1]:
            print(f"         output_signal: {sig}")
    if report.anomalies:
        print()
        print("Anomalies:")
        for a in report.anomalies:
            print(f"  [{a.risk_level}] {a.anomaly_type} (call {a.call_id})")
            print(f"         {a.description[:80]}")
    print("=" * 68)

#!/usr/bin/env python3
"""
plugin_security_checklist.py
Section 6.16 -- Plugin Security Architecture Checklist
Validates plugin-enabled LLM deployment against four security controls.
Author: Raghav Dinesh | ai-security-mastery
"""

import json
from dataclasses import dataclass, asdict
from pathlib import Path


@dataclass
class PluginSecurityControl:
    control_id: str
    name: str
    implemented: bool
    description: str
    attack_scenario_if_missing: str
    implementation_guidance: str
    section_reference: str
    risk_level: str    # CRITICAL | HIGH | MEDIUM


@dataclass
class PluginDeploymentConfig:
    deployment_name: str
    enabled_plugins: list[str]
    output_classifier_deployed: bool = False
    call_allowlist_defined: bool = False
    call_graph_monitoring_deployed: bool = False
    least_privilege_enforced: bool = False
    human_review_before_write: bool = False


def evaluate_plugin_security(config: PluginDeploymentConfig) -> list[PluginSecurityControl]:
    has_write_plugins = any(
        p in {"email_send", "webhook_post", "api_post", "file_write",
              "database_write", "calendar_create", "slack_send"}
        for p in config.enabled_plugins
    )

    return [
        PluginSecurityControl(
            control_id="PS01",
            name="Plugin output injection classifier",
            implemented=config.output_classifier_deployed,
            description=(
                "Every plugin return value passes through the injection classifier "
                "before entering the LLM reasoning context."
            ),
            attack_scenario_if_missing=(
                "Injection payload in a read plugin's return value (web page, API response, "
                "document content) enters the LLM context without detection. LLM follows "
                "adversary instructions embedded in the plugin output, leading to "
                "unintended tool calls including potential data exfiltration."
            ),
            implementation_guidance=(
                "Deploy Section 6.17 classifier as middleware on all plugin return values. "
                "Flag responses above threshold; block or annotate before context delivery."
            ),
            section_reference="Section 6.12.4 / Section 6.17",
            risk_level="CRITICAL",
        ),
        PluginSecurityControl(
            control_id="PS02",
            name="Plugin call allowlist (directed permission graph)",
            implemented=config.call_allowlist_defined,
            description=(
                "A directed permission graph defines which plugins may trigger "
                "calls to which other plugins. Read plugins may not trigger write plugins."
            ),
            attack_scenario_if_missing=(
                "A web browse or document retrieve result containing an injection payload "
                "causes the LLM to call an email, webhook, or database write plugin. "
                "The exfiltration chain completes without structural restriction."
            ),
            implementation_guidance=(
                "Define allowlist at plugin registration. Enforce at the tool-calling "
                "routing layer, not at the LLM prompt level. "
                "Default: read plugins may not trigger write plugins."
            ),
            section_reference="Section 6.16.5",
            risk_level="CRITICAL" if has_write_plugins else "HIGH",
        ),
        PluginSecurityControl(
            control_id="PS03",
            name="Plugin call graph anomaly detection",
            implemented=config.call_graph_monitoring_deployed,
            description=(
                "Real-time monitoring of plugin call sequences. Flags injection-scored "
                "read plugin output followed by write plugin call with context content."
            ),
            attack_scenario_if_missing=(
                "Exfiltration chain completes silently. No alert generated. "
                "Post-incident investigation requires manual call log review. "
                "Detection lag may extend to days or weeks in production."
            ),
            implementation_guidance=(
                "Deploy plugin_call_graph_detector.py on the conversation plugin call log. "
                "Alert on INJECTION_READ_THEN_WRITE and CONTEXT_CONTENT_IN_WRITE_PARAMS patterns."
            ),
            section_reference="Section 6.16.5 / Section 6.12.4",
            risk_level="HIGH",
        ),
        PluginSecurityControl(
            control_id="PS04",
            name="Least privilege at plugin registration",
            implemented=config.least_privilege_enforced,
            description=(
                "Each plugin's permitted action scope is explicitly defined and enforced. "
                "Plugins have only the permissions required for their legitimate function."
            ),
            attack_scenario_if_missing=(
                "A web browsing plugin has implicit access to trigger email sends. "
                "A document retrieval plugin can write to a database. "
                "Any injection into a read plugin's output can leverage the full "
                "permission scope of any other enabled plugin."
            ),
            implementation_guidance=(
                "Define minimum required permissions per plugin at registration. "
                "Review each new plugin addition: what write permissions does it expose? "
                "Remove permissions not required for the plugin's stated function."
            ),
            section_reference="Section 6.16.5",
            risk_level="HIGH",
        ),
        PluginSecurityControl(
            control_id="PS05",
            name="Human review before write plugin execution",
            implemented=config.human_review_before_write,
            description=(
                "Write plugin calls (email, webhook, database write) are queued for "
                "human review before execution when called during a context that "
                "includes retrieved external content."
            ),
            attack_scenario_if_missing=(
                "Injection-triggered write plugin calls execute immediately. "
                "Exfiltration completes before any human can intervene. "
                "Human review provides a final backstop even when structural controls fail."
            ),
            implementation_guidance=(
                "Queue write plugin calls for confirmation when the current context "
                "includes any injection-flagged retrieved content. "
                "Draft-and-hold pattern from Section 6.8.7 applied to all write plugins."
            ),
            section_reference="Section 6.8.7",
            risk_level="MEDIUM",
        ),
    ]


def print_checklist(config: PluginDeploymentConfig, controls: list[PluginSecurityControl]) -> None:
    compliant = sum(1 for c in controls if c.implemented)
    critical_gaps = [c for c in controls if not c.implemented and c.risk_level == "CRITICAL"]

    print(f"\n{'='*68}")
    print(f"PLUGIN SECURITY CHECKLIST: {config.deployment_name}")
    print(f"Plugins enabled: {config.enabled_plugins}")
    print(f"Compliant: {compliant}/{len(controls)}")
    print(f"Critical gaps: {len(critical_gaps)}")
    print("=" * 68)

    for c in controls:
        status = "PASS" if c.implemented else f"FAIL [{c.risk_level}]"
        print(f"\n  [{status}] {c.control_id}: {c.name}")
        if not c.implemented:
            print(f"         Risk: {c.attack_scenario_if_missing[:80]}...")
            print(f"         Ref : {c.section_reference}")

    overall = "READY" if not critical_gaps else "NOT READY -- critical gaps present"
    print(f"\n  Deployment status: {overall}")
    print("=" * 68)

The adversary does not acquire permissions; they cause the LLM to misuse the permissions it already holds. Exfiltration via plugin is the highest-impact injection outcome in this taxonomy: sensitive conversation context reaches the adversary's external endpoint using legitimate plugin credentials, with no additional user action and no user indication. The five-layer RCA identified the systemic root cause as trust model mismatch: each plugin added real-world permissions without a corresponding classifier on its output. The four plugin security controls address this: output classifier (primary, pre-execution), call allowlist (structural prevention), call graph monitoring (real-time detection), and least privilege (blast radius limitation). The three-incident synthesis across Sections 6.14, 6.15, and 6.16 converges on one architectural root cause: external content entered LLM context without a classifier. This convergence from three different deployment types -- web- augmented, code assistant, agentic -- validates the pre-assembly classifier pattern from Section 6.17 as the primary production control. Section 6.17 builds that classifier. Section 6.18 synthesises all of Chapter 6 into the unified injection defence architecture.
