Production ML Gateway Capstone: Four-Detector Ensemble in the Seven-Track Architecture

Section Overview

One Line Summary

The production ML gateway is the Chapter 12 capstone: it assembles every component built across the chapter into a single deployable detection system that runs four ML detectors in parallel alongside the Chapter 11 signature rules within the 50ms P99 budget.

Why This Section Exists

Chapter 12 built the pieces of an ML detection system across sixteen sections: five detector families, a feature pipeline, calibration, inference optimisation, a model registry, live curation, an ensemble, and a benchmarking layer. Each piece was developed and validated in isolation. Section 12.17 assembles them into the production gateway that actually runs in front of the LLM, integrating the Chapter 12 ML detection layer into the Chapter 11 seven-track architecture. The assembly is where the design decisions made across the chapter are realised together. The four input-side detectors are distributed across the gateway tracks based on their coverage profiles -- the embedding detector and XGBoost on the injection track, the GRU and DistilBERT on the jailbreak tracks, the Isolation Forest on the extraction track. The ensemble combines them. The PII scanner runs as an output-side stage outside the seven tracks. The feature pipeline and inference optimisation keep the whole system within the 50ms P99 budget. The model registry governs the deployed configuration. The result is a defence-in-depth system: novel attack variants that evade the signature layer are caught by the ML classifiers, and uncertain ML outputs are flagged for analyst review rather than blocked or silently passed. The capstone also addresses the production realities that the isolated sections did not. Graceful degradation: when the latency budget is threatened under load, the gateway sheds the highest-latency detectors first and falls back to signature-only mode rather than breaching the SLO. The deployment checklist: the gateway enforces the registry gate conditions before any new detector version handles traffic. The monitoring dashboard: the gateway exposes the metrics that make the ML detection layer observable in production. And the ATLAS AML.T0040 Sigma rule: the gateway detects adversaries probing for the ML classifiers' decision boundaries, the meta-attack against the detection system itself. Section 12.17 is the section where the ML detection layer becomes a deployable system that slots into the Chapter 11 gateway and bridges to the behavioural analysis of Chapter 13.

It consumes the ensemble (12.15), the feature pipeline (12.11), the inference optimisation (12.12), the model registry (12.13), the calibration (12.10), the PII scanner (12.09), and the benchmarking (12.16), and produces the complete production ML gateway. Prose Content

Part 1

Title

Design Brief: ML Detectors in the Seven-Track Gateway

Body

The Chapter 11 gateway is a seven-track architecture: seven parallel detection tracks, each covering a class of threats, with a signature-based Sigma rule layer providing the baseline detection. The Chapter 12 ML detection layer does not replace this gateway -- it extends it. The ML detectors are added to the tracks they cover, running in parallel with the signature rules, so each track has both signature detection (fast, precise on known patterns) and ML detection (slower, covers novel variants). The design brief is to integrate the four-detector ensemble into the seven tracks without breaching the 50ms P99 budget and without creating single points of failure. The integration principle is complementarity at the track level: the signature layer catches known attacks with high precision and near-zero latency; the ML layer catches the novel variants the signatures miss. A track with both layers is more robust than either alone -- the signature miss on a novel variant is caught by the ML detector, and the ML false positive on an unusual benign request is moderated by the signature layer's confident non-match. The defence-in-depth structure has a specific failure semantics. If the ML layer is degraded or shed under load, the signature layer continues to provide baseline detection -- the gateway never goes fully blind. If a novel attack evades the signatures, the ML layer covers it. The two layers fail independently, so the gateway's detection survives the failure of either. This is the property that makes the integrated gateway more reliable than a pure-ML or pure-signature gateway. The end-to-end request lifecycle through the integrated gateway has five stages. Ingestion parses the request and extracts the features (Section 12.11). Signature detection runs the Sigma rules (Chapter 11). ML detection runs the four-detector ensemble in parallel (Section 12.15) on the async architecture (Section 12.12). The decision stage combines the signature and ML signals into the block-flag-monitor routing. The response stage acts on the decision and, for allowed requests, runs the output-side PII scanner (Section 12.09) on the model response before delivery. The production_ml_gateway.py in deliverable_1 implements this lifecycle.

Part 2

Title

Track Assignment: Which Detector Covers Which Track

Body

Each ML detector is assigned to the gateway tracks its coverage profile fits, based on the coverage complementarity analysis from Section 12.15. The assignment is not uniform -- a detector runs on the tracks where it adds coverage, not on every track, so the per-track latency is controlled by running only the relevant detectors on each track. Track 1 (injection) runs the embedding similarity detector and the XGBoost injection classifier in parallel. The embedding detector catches paraphrase variants of known injections; the XGBoost catches the structural patterns of injection attempts. Together they cover the injection track's attack surface -- the direct injections the signatures catch, plus the paraphrase and structural variants the signatures miss. Tracks 2 through 5 (jailbreak) run the GRU sequence detector and the DistilBERT neural classifier. The GRU catches multi-turn jailbreak escalation -- the attacks that build across conversation turns, which single-message detection cannot see. The DistilBERT catches single-turn jailbreaks with the highest precision of the supervised classifiers. The jailbreak tracks need both because jailbreaks come in both single-turn and multi-turn forms. The output-side PII stage runs the PII scanner after inference; like the Section 9.12 output watermark it is not one of the seven tracks, and it is the only output-side detector. It does not run in parallel with the input-side detectors -- it runs after model inference on the model response, scanning for the PII leakage that no input-side detector can catch. Track 6 (extraction) runs the Isolation Forest anomaly detector on the API usage patterns. Data exfiltration and model extraction attacks manifest as anomalous API usage -- unusual request patterns, atypical parameter combinations -- which the anomaly detector flags as deviations from the benign usage distribution. Track 7 (adversarial) runs the adversarial example detectors from Chapter 10, integrated into the gateway as the adversarial-input detection track. The track_ml_assignment.py in deliverable_2 documents the full assignment with the coverage justification for each detector-track pairing.

Part 3

Title

Latency Budget with ML Detectors

Body

Adding the ML detectors to the gateway consumes latency budget that the signature-only gateway did not. The integrated gateway must still meet the 50ms P99 SLO, which requires careful budget allocation across the signature layer, the feature pipeline, and the ML detectors. The budget allocation gives the signature layer a small slice (the Sigma rules are fast, under 2ms), the feature pipeline up to 5ms (Section 12.11), and the ML detectors the parallel-scoring slice of around 15ms (Section 12.12, the maximum of the four detectors run concurrently, not the sum). The PII scanner runs output-side and is budgeted separately from the input-side budget because it runs after model inference. The remaining budget is headroom for network, serialisation, and load spikes. The per-track latency is controlled by running only the relevant detectors on each track. Track 1 runs the embedding detector (3ms) and XGBoost (2ms) in parallel, for a 3ms track latency. The jailbreak tracks run the GRU (12ms) and DistilBERT (7ms) in parallel, for a 12ms track latency -- the GRU dominates. The tracks run in parallel with each other as well, so the total ML detection latency is the maximum across the tracks, around 12-15ms, not the sum. The async architecture from Section 12.12 is what makes this parallel composition possible. The latency must be validated, not assumed. The ml_gateway_latency_benchmark.py in deliverable_4 measures the full gateway P99 latency with and without the ML detectors, confirming that the ML layer addition stays within the budget. The with-and-without comparison isolates the ML detection latency contribution, showing exactly how much budget the ML layer consumes, which is the measurement that validates the integrated gateway meets the SLO. If the measurement shows the P99 at risk, the graceful degradation policy (part 4) provides the load-shedding that recovers the budget under load.

Part 4

Title

Graceful Degradation Under Load

Body

Under high load, the gateway's latency increases due to CPU contention, cache eviction, and queueing. If the latency approaches the SLO under load, the gateway must shed work to stay within budget rather than breaching the SLO and being disabled. Graceful degradation is the policy that sheds the highest-cost detectors first while preserving the most detection coverage per unit of latency. The degradation has tiers. At normal load, all detectors run. As the latency budget comes under pressure, the gateway sheds the highest-latency detector first -- the DistilBERT at 7ms -- because it consumes the most budget and its coverage (single-turn jailbreaks) is partly covered by the other detectors. If the pressure continues, the gateway sheds the GRU next, falling back to the fast detectors (Isolation Forest, XGBoost, embedding). At the most severe pressure, the gateway sheds all ML detectors and falls back to signature-only detection -- the Sigma rules from Chapter 11, which are fast and provide baseline detection. The shedding order is determined by the latency cost and the coverage redundancy. The DistilBERT is shed first because it has the highest latency and its coverage is partly redundant with the other detectors. The fast detectors are shed last because they are cheap and provide the most coverage per millisecond. The signature layer is never shed -- it is the floor that keeps the gateway detecting even under the most severe load. The gateway_graceful_degradation.py in deliverable_3 implements the priority ranking and the signature-only fallback. The principle is that some detection is better than none, and staying within the SLO is better than breaching it. A gateway that breaches the SLO under load is disabled by the operational response, leaving zero detection. A gateway that sheds its slowest detectors under load keeps the fast detectors and the signatures running, providing degraded but non-zero detection while staying within the budget. Graceful degradation trades coverage for SLO compliance, which is the correct trade because SLO compliance keeps the gateway running and a running degraded gateway beats a disabled complete one.

Part 5

Title

The ATLAS AML.T0040 Sigma Rule: Detecting the Meta-Attack

Body

The ML detectors defend against attacks on the LLM. But the ML detectors are themselves a target: a sophisticated adversary attacks the detection system by probing for the ML classifiers' decision boundaries, learning which payloads are flagged and which pass, and crafting payloads that evade the classifiers. This is the meta-attack -- an attack on the detector rather than on the model -- catalogued as MITRE ATLAS AML.T0040 (ML classifier evasion through boundary probing). The detection signal for AML.T0040 is a behavioural pattern, not a single payload. An adversary probing the decision boundary sends a sequence of semantically similar requests with small variations, observing which are flagged. The signature of this probing is a cluster of requests from the same source that are semantically similar to each other (small embedding distances) and concentrated near the decision boundary (calibrated scores in the uncertain 0.4-0.6 range). A legitimate user does not send a stream of near-duplicate requests hovering at the decision boundary; an adversary probing for the boundary does exactly that. The Sigma rule for AML.T0040 encodes this pattern. It triggers when a source sends multiple requests within a time window that are semantically similar (above an embedding similarity threshold) and concentrated near the decision boundary (calibrated scores clustered in the uncertain range). The rule's detection logic combines the embedding similarity from the Section 12.07 detector and the calibrated scores from the Section 12.10 calibration -- the same components that serve the primary detection, repurposed to detect the probing of those components. The aml_t0040_sigma_rule_generator.py in deliverable_5 produces the completed Sigma rule. When the rule fires, the response is not just to flag the individual requests (which are individually near-benign) but to flag the source as conducting boundary probing, which warrants a stronger response: rate-limiting the source, escalating to analyst review, or blocking the source entirely. Detecting the meta-attack protects the detection system itself, which is essential because a successful boundary-probing campaign produces evasion payloads that defeat the primary detection.

Part 6

Title

Production Deployment Checklist

Body

Deploying the ML gateway to production -- or deploying a new detector version into it -- is a high-stakes operation. A misconfigured or unvalidated detector handling production traffic can flood the analyst queue, breach the SLO, or silently miss attacks. The deployment checklist enforces the validations that must pass before any detector handles production traffic, turning the deployment from a manual operation prone to skipped steps into a gated process. The checklist enforces the Section 12.13 model registry gate conditions and the production validations from across the chapter. Calibration verification confirms each detector's ECE is below threshold (Section 12.10) -- an uncalibrated detector corrupts the ensemble. Shadow mode validation confirms the detector was run in shadow on production traffic and its decisions compared against the production model (Section 12.13) -- offline validation alone is insufficient. Canary promotion confirms the detector served a traffic fraction with automated rollback monitoring before full promotion (Section 12.13). Latency validation confirms the detector's P99 is within its budget slice (Section 12.12). Monitoring dashboard confirms the detector's metrics are exposed and the dashboard is configured (part 7) -- an unmonitored detector is undeployable because its degradation would go unnoticed. The checklist is a hard gate, not a recommendation. Each item must pass before the deployment proceeds, with no expedient bypass for any item. The bypass is exactly where, under deadline pressure, the shadow validation or the calibration check gets skipped, and the skipped check is where the production incident originates. The ml_gateway_deployment_checklist.py in deliverable_6 implements the checklist as an enforced sequence: it runs each validation, reports the result, and permits the deployment only when every item passes. The checklist connects the chapter's components into the deployment gate. Each item corresponds to a validation built in a prior section -- calibration (12.10), shadow and canary (12.13), latency (12.12), monitoring (part 7) -- so the checklist is the integration point where the chapter's validations are enforced together before production. The checklist is what makes the deployment governed rather than ad hoc.

Part 7

Title

Monitoring Dashboard: Observability for the ML Layer

Body

A deployed ML detection layer that is not observable is undeployable, because its degradation -- a drifting threshold, a dropping cache hit rate, a latency regression -- would go unnoticed until it caused a visible incident. The monitoring dashboard exposes the metrics that make the ML layer observable, so its health is continuously visible and its degradation is caught early. The dashboard exposes four categories of metrics. Detection metrics: the per-detector and ensemble flag rates, the block-flag-monitor tier distribution, and the per-attack-family detection rates that surface coverage gaps. Latency metrics: the P50, P95, and P99 latency per detector and for the full gateway, with the budget threshold marked so a latency regression is immediately visible. Quality metrics: the calibration ECE per detector, the threshold drift signal from Section 12.10, and the online-offline divergence from Section 12.16. Operational metrics: the feature cache hit rate (Section 12.11), the model versions currently in production (Section 12.13), the graceful degradation state (which detectors are currently shed), and the annotation throughput from the curation flywheel (Section 12.14). The metrics are exposed via Prometheus -- the standard metrics format for production monitoring -- and visualised in Grafana dashboards. The Prometheus metrics are instrumented into the gateway: each detector inference records its latency and decision, each ensemble combination records its tier, each feature extraction records its cache hit, and these are aggregated into the Prometheus time series. The Grafana dashboard panels visualise the time series with the thresholds marked, so an on-call engineer can see at a glance whether the ML layer is healthy. The dashboard is the operational interface to the ML detection layer. It connects to the alerting that fires when a metric crosses a threshold -- the latency P99 approaching the budget, the calibration ECE rising, the cache hit rate dropping, the threshold drift firing. The ml_gateway_monitoring_dashboard.py in deliverable_7 produces the Prometheus metric definitions and the Grafana dashboard configuration. Observability is not an afterthought -- it is the property that makes the ML layer a managed production system rather than a black box that degrades silently.

Part 8

Title

The Complete System: From Chapter 11 to Chapter 13

Body

The production ML gateway is the synthesis of Chapter 12. It takes the seven-track gateway from Chapter 11 and adds the ML detection layer built across this chapter: the four-detector ensemble on the input side, the PII scanner on the output side, the feature pipeline and inference optimisation keeping it within budget, the model registry governing the configuration, the live curation keeping it current, the benchmarking validating it, and the monitoring making it observable. The result is a complete, deployable ML detection system. The system's place in the broader architecture is specific. Upstream, the Chapter 11 gateway provides the seven-track structure, the signature layer, and the request routing that the ML layer plugs into. The ML layer is not a standalone system -- it is a detection layer within the gateway, complementing the signatures. Downstream, the Chapter 13 behavioural analysis wraps the gateway's detection in the longer-horizon behavioural context: the gateway makes the per-request detection decision, and the behavioural analysis aggregates these decisions across sessions and sources to detect the patterns that no single request reveals -- the slow campaigns, the coordinated probing, the account takeover sequences. The chapter's central thesis is realised in this capstone: ML-based detection is not a replacement for signature-based detection but a complement, and the two together provide defence-in-depth that neither achieves alone. The signatures provide fast, precise, interpretable detection of known attacks. The ML detectors provide coverage of the novel variants the signatures miss, at the cost of higher latency and lower interpretability, managed by the calibration, the ensemble, the inference optimisation, and the monitoring built across the chapter. The integrated gateway is more robust than either layer alone because they cover each other's gaps and fail independently. The production realities the capstone addresses -- graceful degradation, the deployment checklist, the monitoring dashboard, the meta-attack detection -- are what separate a detection system that works in a notebook from one that survives production. A detector that is accurate but breaches the SLO under load is disabled; a detector that is deployed without the checklist introduces a regression; a detector that is not monitored degrades silently; a detection system that does not detect the meta-attack is defeated by boundary probing. The capstone integrates the validations and the operational controls that make the ML detection layer deployable, observable, and defensible in production, which is the bar a real detection system must meet.

Deliverable 1

Title

Production ML Gateway

Filename

production_ml_gateway.py

Description

Seven-track gateway with the Chapter 12 four-detector ensemble integrated, async parallel scoring, and 50ms P99 validated. Implements the end-to-end request lifecycle from ingestion through signature and ML detection to the block-flag-monitor response and the output-side PII scan.

Implementation Notes

Python 3.12, single quotes throughout per book convention. Requires: asyncio, numpy. Integrates the ensemble (12.15), feature pipeline (12.11), inference optimisation (12.12), and PII scanner (12.09).

Code

# production_ml_gateway.py
# Section 12.17: Production ML Gateway Capstone
# 20260606 | AI Security Mastery -- Chapter 12 by Raghav Dinesh
# Single quotes throughout per book convention

from __future__ import annotations

import asyncio
import time
from dataclasses import dataclass, field
from enum import Enum
from typing import Callable, Dict, List, Optional


class GatewayAction(Enum):
    BLOCK = 'block'
    FLAG = 'flag'
    MONITOR = 'monitor'
    ALLOW = 'allow'


@dataclass
class GatewayDecision:
    action: GatewayAction
    signature_match: bool
    ensemble_score: float
    ensemble_tier: str
    detector_scores: Dict[str, float]
    degradation_tier: int
    input_detection_ms: float
    pii_redacted: bool = False
    explanation: str = ''


class ProductionMLGateway:
    '''
    Seven-track gateway integrating the Chapter 12 ML ensemble with the
    Chapter 11 signature layer.

    Lifecycle: ingest -> signature -> ML ensemble (parallel) -> decide -> respond.
    Output-side PII scan runs on the model response after inference.
    '''

    def __init__(
        self,
        feature_pipeline,       # Section 12.11 ProductionFeaturePipeline
        ensemble,               # Section 12.15 DetectorEnsemble
        signature_fn: Callable, # Chapter 11 Sigma rule matcher
        pii_gateway=None,       # Section 12.09 PIIGateway
        degradation_controller=None,  # Section 12.17 deliverable_3
        detector_fns: Optional[Dict[str, Callable]] = None,
    ) -> None:
        self.feature_pipeline = feature_pipeline
        self.ensemble = ensemble
        self.signature_fn = signature_fn
        self.pii_gateway = pii_gateway
        self.degradation_controller = degradation_controller
        self.detector_fns = detector_fns or {}

    async def _run_detectors(
        self,
        feature_vector,
        active_detectors: List[str],
    ) -> Dict[str, float]:
        '''Run the active detectors in parallel.'''
        loop = asyncio.get_event_loop()
        tasks = {
            name: loop.run_in_executor(None, self.detector_fns[name], feature_vector)
            for name in active_detectors if name in self.detector_fns
        }
        scores = {}
        for name, task in tasks.items():
            scores[name] = float(await task)
        return scores

    async def process_request(
        self,
        request,                # PipelineRequest-like
    ) -> GatewayDecision:
        t0 = time.perf_counter()

        # Stage 1: Ingestion + feature extraction
        features = self.feature_pipeline.extract(request)

        # Stage 2: Signature detection (fast baseline)
        sig_match = bool(self.signature_fn(request.message_text))

        # Stage 3: Determine active detectors (graceful degradation)
        if self.degradation_controller is not None:
            active = self.degradation_controller.active_detectors()
            degradation_tier = self.degradation_controller.current_tier()
        else:
            active = list(self.detector_fns.keys())
            degradation_tier = 0

        # Stage 4: ML detection (parallel)
        detector_scores = await self._run_detectors(features.vector, active)

        # Stage 5: Ensemble combination
        if detector_scores:
            ensemble_result = self.ensemble.evaluate(detector_scores)
            ensemble_score = ensemble_result.combined_score
            ensemble_tier = ensemble_result.tier.value
        else:
            ensemble_score = 0.0
            ensemble_tier = 'pass'

        # Stage 6: Combine signature + ML into a decision
        action = self._combine_decision(sig_match, ensemble_tier, ensemble_score)

        input_ms = (time.perf_counter() - t0) * 1000
        return GatewayDecision(
            action=action,
            signature_match=sig_match,
            ensemble_score=ensemble_score,
            ensemble_tier=ensemble_tier,
            detector_scores=detector_scores,
            degradation_tier=degradation_tier,
            input_detection_ms=input_ms,
            explanation=self._explain(sig_match, ensemble_tier, detector_scores),
        )

    def _combine_decision(
        self,
        sig_match: bool,
        ensemble_tier: str,
        ensemble_score: float,
    ) -> GatewayAction:
        # Signature match OR strong ensemble agreement -> block
        if sig_match or ensemble_tier == 'block':
            return GatewayAction.BLOCK
        if ensemble_tier == 'flag':
            return GatewayAction.FLAG
        if ensemble_tier == 'monitor':
            return GatewayAction.MONITOR
        return GatewayAction.ALLOW

    def _explain(
        self,
        sig_match: bool,
        ensemble_tier: str,
        detector_scores: Dict[str, float],
    ) -> str:
        parts = []
        if sig_match:
            parts.append('signature match')
        if ensemble_tier != 'pass':
            top = sorted(detector_scores.items(), key=lambda kv: kv[1], reverse=True)[:2]
            drivers = ', '.join(f'{n}={s:.2f}' for n, s in top)
            parts.append(f'ensemble {ensemble_tier} ({drivers})')
        return '; '.join(parts) if parts else 'no detection'

    def scan_response(self, request, response_text: str) -> tuple:
        '''Output-side PII scan on the model response (output stage, outside the seven tracks).'''
        if self.pii_gateway is None:
            return response_text, False
        decision = self.pii_gateway.process_response(response_text, request.message_text)
        redacted = decision.action.value in ('redact', 'block')
        return decision.delivered_text, redacted

from __future__ import annotations

from collections import deque
from dataclasses import dataclass, field
from typing import Deque, Dict, List, Optional

import numpy as np


@dataclass
class DegradationTier:
    tier: int
    name: str
    active_detectors: List[str]
    shed: List[str]


# Shedding order: highest latency / most redundant coverage shed first.
# The signature layer is never shed.
DEGRADATION_TIERS: List[DegradationTier] = [
    DegradationTier(0, 'normal',
                    ['isolation_forest', 'xgboost', 'gru', 'embedding'], []),
    DegradationTier(1, 'tier_1_pressure',
                    ['isolation_forest', 'xgboost', 'embedding'], ['distilbert']),
    DegradationTier(2, 'tier_2_pressure',
                    ['isolation_forest', 'xgboost', 'embedding'], ['distilbert', 'gru']),
    DegradationTier(3, 'tier_3_pressure',
                    ['isolation_forest', 'xgboost'], ['distilbert', 'gru', 'embedding']),
    DegradationTier(4, 'severe_signature_only',
                    [], ['distilbert', 'gru', 'embedding', 'isolation_forest', 'xgboost']),
]


class GracefulDegradationController:
    '''
    Adjusts the active detector set based on the live latency pressure.
    Sheds the highest-latency detectors first; the signature layer is the
    floor and is never shed.

    The principle: degraded detection within the SLO beats full detection
    that breaches the SLO and gets the gateway disabled.
    '''

    def __init__(
        self,
        budget_ms: float = 50.0,
        pressure_threshold: float = 0.8,    # fraction of budget that triggers shedding
        recovery_threshold: float = 0.6,    # fraction below which to recover a tier
        window: int = 100,
    ) -> None:
        self.budget_ms = budget_ms
        self.pressure_threshold = pressure_threshold
        self.recovery_threshold = recovery_threshold
        self._latencies: Deque[float] = deque(maxlen=window)
        self._tier = 0

    def record_latency(self, latency_ms: float) -> None:
        self._latencies.append(latency_ms)

    def _current_p99(self) -> float:
        if not self._latencies:
            return 0.0
        return float(np.percentile(self._latencies, 99))

    def update_tier(self) -> int:
        '''Adjust the degradation tier based on the current P99 pressure.'''
        if len(self._latencies) < 10:
            return self._tier
        p99 = self._current_p99()
        pressure = p99 / self.budget_ms

        if pressure >= self.pressure_threshold and self._tier < len(DEGRADATION_TIERS) - 1:
            self._tier += 1
            print(f'DEGRADE -> tier {self._tier} ({DEGRADATION_TIERS[self._tier].name}); '
                  f'P99 {p99:.1f}ms ({pressure:.0%} of budget)')
        elif pressure <= self.recovery_threshold and self._tier > 0:
            self._tier -= 1
            print(f'RECOVER -> tier {self._tier} ({DEGRADATION_TIERS[self._tier].name}); '
                  f'P99 {p99:.1f}ms ({pressure:.0%} of budget)')
        return self._tier

    def active_detectors(self) -> List[str]:
        return DEGRADATION_TIERS[self._tier].active_detectors

    def current_tier(self) -> int:
        return self._tier

    def is_signature_only(self) -> bool:
        return len(self.active_detectors()) == 0

from __future__ import annotations

import asyncio
import time
from dataclasses import dataclass
from typing import Callable, Dict, List

import numpy as np


@dataclass
class GatewayLatencyComparison:
    signature_only_p99: float
    with_ml_p99: float
    ml_contribution_p99: float
    budget_ms: float
    slo_met: bool


class MLGatewayLatencyBenchmark:
    '''
    Measures the gateway P99 with and without the ML detectors to isolate
    the ML latency contribution and validate the SLO.
    '''

    def __init__(self, budget_ms: float = 50.0) -> None:
        self.budget_ms = budget_ms

    async def _measure(
        self,
        process_fn: Callable,
        n_requests: int,
        concurrency: int,
    ) -> List[float]:
        latencies: List[float] = []
        semaphore = asyncio.Semaphore(concurrency)

        async def one():
            async with semaphore:
                t0 = time.perf_counter()
                await process_fn()
                latencies.append((time.perf_counter() - t0) * 1000)

        await asyncio.gather(*[one() for _ in range(n_requests)])
        return latencies

    async def compare(
        self,
        signature_only_fn: Callable,
        with_ml_fn: Callable,
        n_requests: int = 500,
        concurrency: int = 20,
    ) -> GatewayLatencyComparison:
        sig_latencies = await self._measure(signature_only_fn, n_requests, concurrency)
        ml_latencies = await self._measure(with_ml_fn, n_requests, concurrency)

        sig_p99 = float(np.percentile(sig_latencies, 99))
        ml_p99 = float(np.percentile(ml_latencies, 99))

        return GatewayLatencyComparison(
            signature_only_p99=sig_p99,
            with_ml_p99=ml_p99,
            ml_contribution_p99=ml_p99 - sig_p99,
            budget_ms=self.budget_ms,
            slo_met=ml_p99 <= self.budget_ms,
        )


def print_comparison(comp: GatewayLatencyComparison) -> None:
    print(f'ML Gateway Latency Benchmark (SLO: {comp.budget_ms:.0f}ms P99)')
    print('=' * 55)
    print(f'  Signature-only P99:  {comp.signature_only_p99:.1f}ms')
    print(f'  With ML P99:         {comp.with_ml_p99:.1f}ms')
    print(f'  ML contribution:     {comp.ml_contribution_p99:.1f}ms')
    print(f'  SLO met:             {comp.slo_met}')
    if not comp.slo_met:
        print('  WARN: ML layer pushes P99 over budget; enable graceful degradation.')


if __name__ == '__main__':
    benchmark = MLGatewayLatencyBenchmark(budget_ms=50.0)

    async def signature_only():
        await asyncio.sleep(0.003)   # ~3ms signature + feature

    async def with_ml():
        await asyncio.sleep(0.003)    # signature + feature
        await asyncio.sleep(0.012)    # parallel ML detectors (max ~12ms)

    comparison = asyncio.run(benchmark.compare(signature_only, with_ml, n_requests=200))
    print_comparison(comparison)

class BoundaryProbingDetector:
    '''
    Runtime detector that implements the AML.T0040 Sigma rule logic.
    Tracks per-source request patterns and fires when the probing signature appears.
    '''

    def __init__(
        self,
        similarity_threshold: float = 0.85,
        uncertainty_low: float = 0.4,
        uncertainty_high: float = 0.6,
        min_requests: int = 5,
        window_seconds: int = 600,
    ) -> None:
        self.similarity_threshold = similarity_threshold
        self.uncertainty_low = uncertainty_low
        self.uncertainty_high = uncertainty_high
        self.min_requests = min_requests
        self.window_seconds = window_seconds
        self._source_requests: Dict[str, Deque] = {}

    def record_request(
        self,
        source_id: str,
        timestamp: float,
        embedding: np.ndarray,
        calibrated_score: float,
    ) -> bool:
        '''Record a request; return True if the probing signature fires.'''
        if source_id not in self._source_requests:
            self._source_requests[source_id] = deque(maxlen=100)
        window = self._source_requests[source_id]
        # Drop expired
        cutoff = timestamp - self.window_seconds
        while window and window[0][0] < cutoff:
            window.popleft()
        window.append((timestamp, embedding, calibrated_score))

        # Check the probing signature
        near_boundary = [
            (e, s) for _, e, s in window
            if self.uncertainty_low <= s <= self.uncertainty_high
        ]
        if len(near_boundary) < self.min_requests:
            return False

        # Semantic similarity among near-boundary requests
        embs = [e for e, _ in near_boundary]
        similarities = []
        for i in range(len(embs)):
            for j in range(i + 1, len(embs)):
                na, nb = np.linalg.norm(embs[i]), np.linalg.norm(embs[j])
                if na > 0 and nb > 0:
                    similarities.append(np.dot(embs[i], embs[j]) / (na * nb))
        mean_sim = float(np.mean(similarities)) if similarities else 0.0
        return mean_sim >= self.similarity_threshold

        print(f'  [{symbol}] {i.name} ({i.source_section}): {i.detail}')
    print('-' * 60)
    print(f'  Deployment: {"PERMITTED" if verdict.can_deploy else "BLOCKED"}')


if __name__ == '__main__':
    checklist = MLGatewayDeploymentChecklist()

    # Passing deployment
    verdict = checklist.run(
        'distilbert_injection_v2',
        ece=0.03, shadow_validated=True, canary_promoted=True,

from __future__ import annotations

import json
from dataclasses import dataclass, field
from typing import Dict, List, Optional


@dataclass
class MetricDefinition:
    name: str
    metric_type: str    # counter, gauge, histogram
    help_text: str
    labels: List[str] = field(default_factory=list)
    alert_threshold: Optional[str] = None


# The metrics the ML gateway exposes for observability
GATEWAY_METRICS: List[MetricDefinition] = [
    # Detection metrics
    MetricDefinition('ml_gateway_flag_total', 'counter',
                     'Total requests flagged by detector and tier',
                     ['detector', 'tier']),
    MetricDefinition('ml_gateway_family_detection_rate', 'gauge',
                     'Per-attack-family detection rate',
                     ['attack_family'],
                     alert_threshold='family rate drop > 10%'),
    # Latency metrics
    MetricDefinition('ml_gateway_detector_latency_ms', 'histogram',
                     'Per-detector inference latency',
                     ['detector'],
                     alert_threshold='P99 > budget slice'),
    MetricDefinition('ml_gateway_total_latency_ms', 'histogram',
                     'End-to-end gateway latency',
                     [],
                     alert_threshold='P99 > 50ms'),
    # Quality metrics
    MetricDefinition('ml_gateway_calibration_ece', 'gauge',
                     'Per-detector calibration ECE',
                     ['detector'],
                     alert_threshold='ECE > 0.05'),
    MetricDefinition('ml_gateway_threshold_drift', 'gauge',
                     'Threshold drift signal (realised vs target FPR)',
                     ['detector'],
                     alert_threshold='drift firing'),
    MetricDefinition('ml_gateway_online_offline_divergence', 'gauge',
                     'Online-offline metric divergence',
                     ['metric'],
                     alert_threshold='divergence widening'),
    # Operational metrics
    MetricDefinition('ml_gateway_cache_hit_rate', 'gauge',
                     'Feature cache hit rate',
                     ['cache'],
                     alert_threshold='hit rate < 0.5'),
    MetricDefinition('ml_gateway_degradation_tier', 'gauge',
                     'Current graceful degradation tier (0 = normal)',
                     [],
                     alert_threshold='tier > 0 sustained'),
    MetricDefinition('ml_gateway_annotation_throughput', 'gauge',
                     'Curation annotation throughput per day',
                     [],
                     alert_threshold='throughput dropping'),
]


class MLGatewayMonitoringDashboard:
    '''
    Defines the Prometheus metrics and generates the Grafana dashboard
    configuration for the ML-enabled gateway.
    '''

    def __init__(self, metrics: List[MetricDefinition] = None) -> None:
        self.metrics = metrics or GATEWAY_METRICS

    def prometheus_definitions(self) -> List[str]:
        '''Return the Prometheus metric declarations.'''
        lines = []
        for m in self.metrics:
            labels = ', '.join(f"'{l}'" for l in m.labels)
            lines.append(f"# {m.metric_type.upper()}: {m.name} -- {m.help_text}")
            lines.append(f"{m.name}{{labels=[{labels}]}}")
        return lines

    def grafana_dashboard(self) -> Dict:
        '''Generate a Grafana dashboard configuration.'''
        panels = []
        categories = {
            'Detection': [m for m in self.metrics if 'flag' in m.name or 'family' in m.name],
            'Latency': [m for m in self.metrics if 'latency' in m.name],
            'Quality': [m for m in self.metrics if any(k in m.name for k in ('ece', 'drift', 'divergence'))],
            'Operational': [m for m in self.metrics if any(k in m.name for k in ('cache', 'degradation', 'annotation'))],
        }
        panel_id = 1
        y_pos = 0
        for category, metrics in categories.items():
            for m in metrics:
                panels.append({
                    'id': panel_id,
                    'title': f'{category}: {m.name}',
                    'type': 'timeseries' if m.metric_type == 'histogram' else 'stat',
                    'gridPos': {'h': 8, 'w': 12, 'x': (panel_id % 2) * 12, 'y': y_pos},
                    'targets': [{'expr': m.name, 'legendFormat': '{{' + (m.labels[0] if m.labels else '') + '}}'}],
                    'alert_threshold': m.alert_threshold,
                })
                panel_id += 1
                if panel_id % 2 == 1:
                    y_pos += 8
        return {
            'dashboard': {
                'title': 'ML Detection Gateway',
                'tags': ['ml-detection', 'gateway', 'security'],
                'panels': panels,
                'refresh': '30s',
            }
        }

    def alerting_rules(self) -> List[Dict]:
        '''Return the alerting rules for the metrics with thresholds.'''
        return [
            {'metric': m.name, 'condition': m.alert_threshold}
            for m in self.metrics if m.alert_threshold
        ]


if __name__ == '__main__':
    dashboard = MLGatewayMonitoringDashboard()

    print('Prometheus metric definitions:')
    for line in dashboard.prometheus_definitions()[:8]:
        print(f'  {line}')

    print(f'\nGrafana dashboard: {len(dashboard.grafana_dashboard()["dashboard"]["panels"])} panels')

    print('\nAlerting rules:')
    for rule in dashboard.alerting_rules():
        print(f'  {rule["metric"]}: {rule["condition"]}')

Common Mistakes

Mistake 1

Description

Replacing the signature layer with the ML detectors instead of running them together, losing the fast precise baseline detection

Why It Happens

The ML detectors are more sophisticated than the signature rules and cover more attack variants, so the engineer treats them as a replacement for the signatures. The signature layer is removed to simplify the gateway, leaving only the ML detection.

Consequence

The signature layer provided fast, precise, interpretable detection of known attacks at near-zero latency, and a baseline that never goes blind. Removing it loses this floor: when the ML detectors are degraded under load (graceful degradation), there is nothing left, and the gateway goes fully blind. The known attacks that the signatures caught with certainty now depend on the ML detectors, which are slower and less certain on them.

Correct Approach

Run the ML detectors alongside the signature layer, not instead of it. The signatures provide the fast baseline and the floor for graceful degradation; the ML detectors provide the coverage of novel variants. The two layers are complementary -- defence-in-depth -- and the gateway is more robust with both than with either alone.

Mistake 2

Description

Running all four ML detectors on every track instead of assigning detectors to the tracks they cover, wasting latency budget

Why It Happens

Running every detector on every track is simpler than the per-track assignment. The engineer wires all four detectors into every track for completeness, reasoning that more detection is better.

Consequence

The injection track runs the GRU even though multi-turn escalation is not an injection-track concern, and the extraction track runs the DistilBERT even though anomalous API usage is the Isolation Forest's domain. The unnecessary detectors consume latency budget on every track without adding coverage, pushing the per-track latency up and the total over budget.

Correct Approach

Assign each detector to the tracks its coverage profile fits, per the track_ml_assignment.py. The embedding detector and XGBoost on the injection track, the GRU and DistilBERT on the jailbreak tracks, the Isolation Forest on the extraction track. Each track runs only the detectors that add coverage, controlling the per-track latency.

Mistake 3

Description

Breaching the SLO under load instead of degrading gracefully, getting the entire detection layer disabled

Why It Happens

The gateway runs all detectors regardless of load. Under high load, the latency rises and breaches the SLO. There is no degradation policy because the gateway was designed for the normal-load latency, and the engineer did not anticipate the load-induced latency spike.

Consequence

The SLO breach triggers the operational response of disabling the detection layer to recover the latency, leaving zero detection during exactly the high-load period when attacks are most likely. The gateway that ran all detectors under load ends up running none, which is worse than a gateway that shed its slowest detectors and kept the rest.

Correct Approach

Implement graceful degradation with the gateway_graceful_degradation.py. Under latency pressure, shed the highest-latency detectors first and fall back toward signature-only, keeping the gateway within the SLO. Degraded detection within the SLO beats full detection that breaches the SLO and gets the whole layer disabled.

Mistake 4

Description

Deploying a new detector without the deployment checklist, bypassing the shadow, canary, or monitoring validations

Why It Happens

The new detector passed the offline benchmark and the registry gates. Under deadline pressure, the engineer deploys it directly, skipping the shadow period or the monitoring configuration because they add time and the detector "obviously works."

Consequence

The detector that skipped the shadow validation regresses on the production distribution, or the detector that skipped the monitoring configuration degrades silently because no dashboard surfaces its metrics. The skipped checklist item is exactly where the production incident originates -- the validation that would have caught the problem was bypassed.

Correct Approach

Enforce the deployment checklist with the ml_gateway_deployment_checklist.py as a hard gate. Every item -- calibration, shadow, canary, registry gates, latency, monitoring -- must pass before the detector handles production traffic, with no expedient bypass. The checklist is the integration point where the chapter's validations are enforced together before production.

Mistake 5

Description

Ignoring the meta-attack, leaving the ML classifiers undefended against boundary probing that produces evasion payloads

Why It Happens

The ML detectors defend against attacks on the LLM, and the engineer considers the detection complete. The possibility that the detectors themselves are a target -- that an adversary probes their decision boundaries to craft evasions -- is not considered, so no detection for the probing is built.

Consequence

A sophisticated adversary sends a stream of near-duplicate requests hovering at the decision boundary, learning which payloads are flagged. The individual requests are near-benign and pass individually. The adversary uses the learned boundary to craft an evasion payload that defeats the ML classifiers, and the primary detection is bypassed by an attack the gateway never detected because it was an attack on the detector, not on the model.

Correct Approach

Deploy the AML.T0040 Sigma rule with the aml_t0040_sigma_rule_generator.py. It detects the boundary-probing pattern -- a cluster of semantically similar requests concentrated near the decision boundary from the same source -- and flags the source for a stronger response (rate-limiting, escalation, blocking). Detecting the meta-attack protects the detection system itself, which is essential because a successful probing campaign defeats the primary detection.

Section Summary

Compact

The production ML gateway is the Chapter 12 capstone, integrating every component built across the chapter into a single deployable detection system. The four input-side detectors are distributed across the seven gateway tracks by coverage profile -- embedding and XGBoost on injection, GRU and DistilBERT on jailbreak, Isolation Forest on extraction -- and combined by the ensemble; the PII scanner runs as an output-side stage outside the seven tracks. The ML layer extends the Chapter 11 signature layer rather than replacing it, providing defence-in-depth: the signatures catch known attacks fast and precisely, the ML detectors catch the novel variants the signatures miss, and the two fail independently so the gateway never goes fully blind. The feature pipeline and inference optimisation keep the integrated gateway within the 50ms P99 budget, validated with-and-without the ML detectors. Graceful degradation sheds the highest-latency detectors first under load, falling back toward signature-only rather than breaching the SLO, because degraded detection within the SLO beats full detection that gets the gateway disabled. The deployment checklist enforces the registry gate conditions, shadow, canary, latency, and monitoring as a hard gate before any detector handles traffic. The AML.T0040 Sigma rule detects the meta-attack -- adversaries probing the classifier decision boundaries to craft evasions. The monitoring dashboard exposes the detection, latency, quality, and operational metrics that make the ML layer observable. The result is a complete detection system that slots into the Chapter 11 gateway and bridges to the Chapter 13 behavioural analysis.

Key Takeaways

  • The ML layer extends the signature layer, it does not replace it: the signatures provide the fast precise floor and the baseline that never goes blind, the ML detectors cover the novel variants, and the two fail independently for defence-in-depth
  • Assign each detector to the tracks its coverage profile fits, not every detector to every track: embedding and XGBoost on injection, GRU and DistilBERT on jailbreak, Isolation Forest on extraction, controlling per-track latency
  • Prefer graceful degradation to SLO breach: shed the highest-latency detectors first and fall back toward signature-only under load, because degraded detection within the SLO beats full detection that gets the gateway disabled
  • Enforce the deployment checklist as a hard gate: calibration, shadow, canary, registry gates, latency, and monitoring must all pass before a detector handles traffic, with no expedient bypass where a skipped check becomes an incident
  • Detect the meta-attack with the AML.T0040 Sigma rule: adversaries probing the classifier decision boundaries through near-duplicate requests near the boundary are attacking the detection system itself, and a successful probing campaign defeats the primary detection
  • Make the ML layer observable: the monitoring dashboard exposes the detection, latency, quality, and operational metrics, because an unmonitored detection layer degrades silently until it causes a visible incident
