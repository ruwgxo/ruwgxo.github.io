Chapter 16 · Section 3 · ~6 pages

Splunk Integration: HEC and Add-ons

Section Overview

One Line Summary

The first platform connector: detections pushed into Splunk through the HTTP Event Collector, with the detection-event schema mapped to Splunk's envelope so a detection becomes a searchable, alertable event, and the generated Sigma rules deployed alongside so Splunk evaluates the portable logic against the ingested events.

Why This Section Exists

Section 16.02 built the portable detection logic; this section delivers the detections themselves to a real platform for the first time. Splunk is the archetype: a widely deployed SIEM with a well-defined ingestion path, the HTTP Event Collector, and it is the natural first connector because its model -- push events over HTTP to a token-authenticated endpoint -- is the simplest instance of the push integration the chapter uses three times. The section does three things. It maps the detection-event schema to the Splunk HEC envelope, promoting the detector, verdict, and severity to indexed fields so Splunk can alert and dashboard on them efficiently while the full detection stays searchable in the event body. It packages that mapping as a Splunk add-on -- the unit Splunk uses to ship an integration's index, sourcetype, and field extractions -- so the detection events land with the right structure rather than as opaque blobs. And it deploys the generated Sigma rules into Splunk, so the portable logic of 16.02 runs on the platform against the events this connector delivers. The whole path is tested end to end on a stub HEC transport, so the connector is proven without a live Splunk.

Position In Chapter

Section 16.03 is the first of the three platform connectors (Splunk, Datadog, Elastic) and the first push integration. It consumes the detection-event schema of 16.01, deploys the Sigma rules of 16.02, and establishes the connector shape -- schema-to-platform mapping, a stubbed transport, an end-to-end test, and a secret-aware config -- that the Datadog (16.04) and Elastic (16.05) connectors follow.

Prose Content

Part 1

Title

The HTTP Event Collector as the Ingestion Path

Body

Splunk ingests external events through the HTTP Event Collector, a token-authenticated HTTP endpoint that accepts JSON event envelopes. For the detection gateway, HEC is close to ideal: the gateway already produces structured detection events, and HEC wants structured JSON, so the connector is mostly a matter of shaping the event into Splunk's envelope and POSTing it. Authentication is a token the Splunk admin issues for a specific input; the connector presents it in an Authorization header, and Splunk routes the event to the index the token is scoped to. This makes the Splunk connector a push integration in the sense of Section 16.01: the gateway initiates delivery, POSTing each detection to HEC the moment it is made, and the gateway owns the reliability of that delivery -- retries, batching, backpressure are its concern, not Splunk's. HEC is the simplest instance of the push model, which is why the chapter builds it first; the Datadog and Elastic connectors are variations on the same shape. The connector wraps the HEC transport behind a small interface so it can be tested against an in-memory stub, and everything below is proven that way -- no live Splunk required to know the mapping and delivery are correct.

Part 2

Title

Mapping the Schema to the Splunk Envelope

Body

A Splunk HEC event is an envelope with a handful of well-known keys. Time is the event's epoch timestamp, so the connector converts the detection event's ISO-8601 timestamp to epoch seconds -- getting this right is what puts the detection at the correct point on Splunk's timeline. Index, sourcetype, host, and source identify and route the event: index and sourcetype come from configuration (detections land in a dedicated ai_security index with an ai:detection sourcetype), host identifies the gateway, and source carries the emitting gateway instance from the detection event. The event key holds the body -- the full detection event, verbatim. One mapping decision matters more than the rest: which fields to promote. Splunk searches the event body fine, but fields it indexes are far faster to filter, alert, and dashboard on. So the connector promotes the three fields a responder pivots on -- detector, verdict, and severity -- into the envelope's indexed fields, while leaving the complete detection in the body. The promotion is an optimisation, not a replacement: the full event, including the scores, the evidence, the session, and the surface, stays searchable, because an analyst investigating an alert needs the whole detection, not the three fields that surfaced it. Promoting a summary while dropping the detail would make the common query fast and the investigation impossible.

Part 3

Title

Packaging as a Splunk Add-on

Body

Delivering JSON to HEC gets the events into Splunk, but events that arrive without structure are opaque: Splunk has no way to know that verdict is a field worth faceting on or that severity should drive alert urgency. A Splunk add-on is the unit that supplies that structure. It packages the index definition, the sourcetype, the field extractions, and any saved searches or dashboards that go with the integration, so that when detection events arrive they are parsed into the fields the add-on declares rather than left as raw text. Shipping the integration as an add-on is what turns a stream of POSTed JSON into a first-class Splunk data source. The add-on declares the ai:detection sourcetype and the fields the connector promotes, so the searches, alerts, and dashboards a security team builds reference stable field names rather than parsing the body ad hoc. It is the difference between detections that are technically in Splunk and detections that Splunk understands. The connector's job is to deliver events that match the add-on's expectations; the add-on's job is to make those events queryable and alertable the moment they land.

Part 4

Title

Deploying the Generated Sigma Rules into Splunk

Body

The events are only half the integration. The detection logic -- the rules that say a blocked injection is a high-severity alert -- comes from the generated Sigma rules of Section 16.02. Splunk is one of the platforms with a Sigma compiler, so the generated rules deploy into Splunk as saved searches or correlation searches that evaluate against the ingested detection events. The portable logic written once in 16.02 now runs on the Splunk platform, against the events this connector delivers, producing Splunk-native alerts. This is where the two halves of the chapter's surface meet on one platform. The connector delivers the events; the Sigma rules evaluate them; the add-on gives both the field structure they rely on. Because the rules are generated and versioned, redeploying them into Splunk after a detector change is the same hash-driven step from 16.02 -- the Splunk-side detection logic stays in sync with the detectors without anyone hand-editing a Splunk search. Splunk becomes a place where the suite's detections are both stored and acted on, with the detection logic kept current automatically.

Part 5

Title

Testing the Integration End to End

Body

The connector is validated end to end on the stub HEC transport, which records what would be POSTed and returns Splunk's success envelope. The test walks the whole path: a detection event goes in, and the test asserts that the resulting Splunk envelope carries the right index and sourcetype, that the promoted fields hold the correct detector, verdict, and severity, and -- most importantly -- that the full detection body survives, so an investigation has everything the detection knew. It checks that batches of events all deliver, that the timestamp becomes epoch seconds rather than a string, and that an invalid configuration is rejected loudly rather than silently sending to nowhere. Testing against a stub rather than a live Splunk is a deliberate choice that the Datadog and Elastic connectors repeat. The connector's correctness is in the mapping and the delivery contract, not in Splunk itself, so a stub that captures the POST proves what matters: the detection reaches the platform in a form the platform can search and alert on. When the stub tests pass -- correct envelope, promoted fields, preserved body, batched delivery -- the connector is ready, and pointing it at a real HEC endpoint is a configuration change, not a code change. With Splunk delivering events and evaluating rules, Section 16.04 builds the same integration for Datadog.

Deliverable 1

Title

The Splunk HEC Connector

Filename

splunk_integration.py

Description

The Splunk connector: maps the detection-event schema to the HEC envelope with promoted indexed fields, and pushes events to HEC behind a swappable transport. SplunkConnector batches events into one newline-delimited POST; to_splunk_envelope does the schema mapping including the ISO-to-epoch timestamp conversion. Runs standalone on an in-memory StubHECTransport.

Implementation Notes

Python 3.12, single quotes throughout per book convention, standard-library json, time, dataclasses, and typing only. The DetectionEvent is represented as a dict via sample_event so the file runs standalone; in the suite it imports DetectionEvent from detection_event_schema.py. StubHECTransport records POSTs and returns Splunk's success envelope; the real transport POSTs to the HEC endpoint with an Authorization: Splunk <token> header. Self-checks the mapping, promoted fields, and batched delivery.

Code

# splunk_integration.py
# Section 16.03: Splunk Integration -- HEC and Add-on
# 20260121 | AI Security Mastery -- Chapter 16 by Raghav Dinesh
# Single quotes throughout per book convention
#
# The first platform connector. It delivers detection events into Splunk through
# the HTTP Event Collector (HEC), mapping the detection-event schema to Splunk's
# envelope so a detection becomes a searchable, alertable Splunk event. A push
# integration: the gateway owns delivery and POSTs each event to HEC.

import json
import time
from dataclasses import dataclass
from typing import Any, Dict, List, Optional


def sample_event() -> Dict[str, Any]:
    return {
        'schema_version': '1.0', 'event_id': 'req-1001:prompt_injection',
        'timestamp': '2026-01-21T10:15:03Z', 'detector': 'prompt_injection',
        'verdict': 'block', 'severity': 'critical', 'score': 0.92, 'confidence': 0.94,
        'latency_ms': 3.4, 'surface': 'input', 'request_id': 'req-1001',
        'session_id': 'sess-42', 'source': 'prod-gateway-1',
        'evidence': [{'source': 'pattern', 'label': 'instruction_override', 'detail': 'ignore previous'}],
        'iocs': [], 'labels': {},
    }


class HECTransport:
    def send(self, url: str, token: str, payload: str) -> Dict[str, Any]:
        raise NotImplementedError


class StubHECTransport(HECTransport):
    '''In-memory HEC stand-in. Records what would be POSTed and returns Splunk's
    success envelope, so the connector runs end to end without a live Splunk.'''
    def __init__(self) -> None:
        self.sent: List[Dict[str, Any]] = []
    def send(self, url: str, token: str, payload: str) -> Dict[str, Any]:
        for line in payload.strip().split('\n'):
            self.sent.append(json.loads(line))
        return {'text': 'Success', 'code': 0}


@dataclass
class SplunkConfig:
    hec_url: str = 'https://splunk.internal:8088/services/collector'
    hec_token: str = 'REPLACE_WITH_HEC_TOKEN'
    index: str = 'ai_security'
    sourcetype: str = 'ai:detection'
    host: str = 'detection-gateway'

    def validate(self) -> None:
        assert self.hec_url.startswith('http'), 'hec_url must be an http(s) URL'
        assert self.index and self.sourcetype, 'index and sourcetype are required'


def _iso_to_epoch(ts: str) -> float:
    return time.mktime(time.strptime(ts, '%Y-%m-%dT%H:%M:%SZ'))


def to_splunk_envelope(event: Dict[str, Any], cfg: SplunkConfig) -> Dict[str, Any]:
    '''Map a detection event to the Splunk HEC envelope. detector, verdict, and
    severity are promoted to indexed fields; the full event stays in the body.'''
    return {
        'time': _iso_to_epoch(event['timestamp']),
        'host': cfg.host, 'source': event['source'],
        'sourcetype': cfg.sourcetype, 'index': cfg.index,
        'fields': {'detector': event['detector'], 'verdict': event['verdict'],
                   'severity': event['severity']},
        'event': event,
    }


class SplunkConnector:
    '''Pushes detection events into Splunk via HEC. Batches envelopes into one
    newline-delimited POST.'''
    name = 'splunk'
    model = 'push'

    def __init__(self, transport: Optional[HECTransport] = None,
                 config: Optional[SplunkConfig] = None) -> None:
        self._transport = transport if transport is not None else StubHECTransport()
        self._cfg = config if config is not None else SplunkConfig()

    def send(self, events: List[Dict[str, Any]]) -> Dict[str, Any]:
        self._cfg.validate()
        envelopes = [to_splunk_envelope(e, self._cfg) for e in events]
        payload = '\n'.join(json.dumps(env, sort_keys=True) for env in envelopes)
        resp = self._transport.send(self._cfg.hec_url, self._cfg.hec_token, payload)
        return {'sent': len(envelopes), 'ok': resp.get('code') == 0, 'response': resp}


if __name__ == '__main__':
    stub = StubHECTransport()
    conn = SplunkConnector(transport=stub)
    events = [sample_event(),
              {**sample_event(), 'event_id': 'req-1002:pii_scanner', 'detector': 'pii_scanner',
               'verdict': 'flag', 'severity': 'medium', 'request_id': 'req-1002'}]
    result = conn.send(events)
    print('send result :', {k: result[k] for k in ('sent', 'ok')})
    print('indexed fields:', stub.sent[0]['fields'])
    assert result['sent'] == 2 and result['ok']
    assert stub.sent[0]['index'] == 'ai_security' and stub.sent[0]['sourcetype'] == 'ai:detection'
    assert stub.sent[0]['fields']['severity'] == 'critical'
    assert stub.sent[1]['event']['detector'] == 'pii_scanner'
    print('splunk hec mapping + delivery: ok')

# splunk_integration_test.py
# Section 16.03: Splunk Integration End-to-End Test
# 20260121 | AI Security Mastery -- Chapter 16 by Raghav Dinesh
# Single quotes throughout per book convention
#
# Confirms the integration end to end on the stub transport: a detection event
# goes in, a Splunk HEC envelope comes out with the right index, sourcetype, and
# promoted fields, and the searchable event body preserves the full detection.

from splunk_integration import (SplunkConnector, StubHECTransport, SplunkConfig,
                                to_splunk_envelope, sample_event)


def test_envelope_mapping() -> None:
    env = to_splunk_envelope(sample_event(), SplunkConfig())
    assert env['index'] == 'ai_security'
    assert env['sourcetype'] == 'ai:detection'
    assert env['fields']['severity'] == 'critical'
    assert env['event']['request_id'] == 'req-1001'
    assert isinstance(env['time'], float)


def test_delivery_batches() -> None:
    stub = StubHECTransport()
    result = SplunkConnector(transport=stub).send([sample_event() for _ in range(5)])
    assert result['sent'] == 5 and result['ok']
    assert len(stub.sent) == 5


def test_searchable_body_preserved() -> None:
    stub = StubHECTransport()
    SplunkConnector(transport=stub).send([sample_event()])
    body = stub.sent[0]['event']
    for key in ('detector', 'verdict', 'score', 'confidence', 'evidence', 'session_id'):
        assert key in body, key


def test_bad_config_rejected() -> None:
    try:
        SplunkConnector(config=SplunkConfig(index='')).send([sample_event()])
    except AssertionError:
        return
    raise AssertionError('expected invalid config to be rejected')


if __name__ == '__main__':
    tests = [test_envelope_mapping, test_delivery_batches,
             test_searchable_body_preserved, test_bad_config_rejected]
    for t in tests:
        t()
        print(f'PASS {t.__name__}')
    print(f'{len(tests)}/{len(tests)} splunk integration tests passed')

Title

Splunk Integration Configuration

Filename

splunk_config.py

Description

Configuration for the connector: the HEC URL, index, sourcetype, and host as data, with the HEC token read from the environment rather than hardcoded. validate enforces https and TLS verification in production; resolve_token fails loudly on a missing token; redacted prints the config without leaking the secret. Ships production and lab profiles.

Implementation Notes

Python 3.12, single quotes throughout per book convention, standard-library os, dataclasses, and typing only. The token_env_var indirection keeps the secret out of source control -- the single most important operational property of the config. Self-checks that both profiles validate and that the token resolves from the environment.

Code

# splunk_config.py
# Section 16.03: Splunk Integration Configuration
# 20260121 | AI Security Mastery -- Chapter 16 by Raghav Dinesh
# Single quotes throughout per book convention
#
# Configuration for the Splunk connector. The HEC token is a secret and is never
# hardcoded -- it is read from the environment so it stays out of source control.

import os
from dataclasses import dataclass, asdict
from typing import Any, Dict


@dataclass
class SplunkDeploymentConfig:
    hec_url: str = 'https://splunk.internal:8088/services/collector'
    index: str = 'ai_security'
    sourcetype: str = 'ai:detection'
    host: str = 'detection-gateway'
    verify_tls: bool = True
    token_env_var: str = 'SPLUNK_HEC_TOKEN'

    def resolve_token(self) -> str:
        token = os.environ.get(self.token_env_var, '')
        assert token, f'{self.token_env_var} is not set -- HEC token required'
        return token

    def validate(self) -> None:
        assert self.hec_url.startswith('https'), 'HEC must use https in production'
        assert self.index and self.sourcetype, 'index and sourcetype are required'
        assert self.verify_tls, 'TLS verification must stay enabled in production'

    def redacted(self) -> Dict[str, Any]:
        d = asdict(self)
        d['token'] = '(from ' + self.token_env_var + ')'
        return d


PRODUCTION = SplunkDeploymentConfig()
LAB = SplunkDeploymentConfig(hec_url='https://localhost:8088/services/collector', index='ai_security_lab')


if __name__ == '__main__':
    os.environ.setdefault('SPLUNK_HEC_TOKEN', 'demo-token-not-real')
    for name, cfg in [('production', PRODUCTION), ('lab', LAB)]:
        cfg.validate()
        print(f'{name:11} index={cfg.index}')
    print('token resolves :', bool(PRODUCTION.resolve_token()))
    print('all splunk profiles valid')

Common Mistakes

Mistake 1

Description

Promoting a few fields for indexing but dropping the full detection from the event body

Why It Happens

Indexed fields make the common queries fast, so it feels efficient to send only those and skip the rest of the event.

Consequence

The alert fires on detector and severity, but an analyst opening it finds no scores, evidence, session, or surface, and cannot investigate.

Correct Approach

Promote detector, verdict, and severity for fast filtering, and keep the complete detection in the searchable body so the investigation has everything.

Mistake 2

Description

Sending the ISO timestamp string to HEC instead of converting it to epoch seconds

Why It Happens

The detection event already has a perfectly readable ISO-8601 timestamp, so it seems fine to pass it straight through.

Consequence

Splunk mis-parses or defaults the event time, so detections land at the wrong point on the timeline and time-based correlation breaks.

Correct Approach

Convert the ISO timestamp to epoch seconds for the HEC time key, so each detection sits at the correct moment on Splunk's timeline.

Mistake 3

Description

Hardcoding the HEC token in the connector or config source

Why It Happens

It is the quickest way to get a working POST, and the token is right there when you are testing against a real endpoint.

Consequence

The token -- a credential that can write to the SIEM -- ends up in source control, where it leaks and grants anyone who finds it ingest access.

Correct Approach

Read the token from the environment and fail loudly if it is missing, so the secret stays out of source and a misconfigured deploy is obvious.

Mistake 4

Description

Delivering events to Splunk but never deploying the Sigma rules that evaluate them

Why It Happens

Once the events are searchable in Splunk, the integration looks complete -- the data is there.

Consequence

The detections sit in an index no rule watches, so nothing alerts; the events are stored but not actioned, which was the whole point.

Correct Approach

Deploy the generated Sigma rules into Splunk alongside the connector, so the ingested events are evaluated into Splunk-native alerts.
