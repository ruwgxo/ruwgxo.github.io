Section Overview

One Line Summary

Four detection layers — signature, heuristic, ML-based, and behavioural — form the architecture that no single detection primitive can replicate alone; the seven-track gateway is an instance of this model, and understanding which track sits in which layer explains both its strengths and its gaps.

Why This Section Exists

Sections 11.01 and 11.02 established that the seven-track gateway is L1 in maturity and that detection-as-code governance is the path to L3. Neither section explained why the gateway has the shape it does: seven tracks, each detecting a different signal, each with a different latency budget and false positive profile. Without a conceptual model, the gateway looks like an arbitrary collection of detectors. With the four-layer model, it becomes legible: each track occupies a defined position in the architecture, with known complementarity and known failure modes. The layered detection model is also the planning tool for Chapters 12 and 13. Chapter 12 (ML-Based Detection) fills Layer 3 with trained classifiers. Chapter 13 (Behavioral Analysis) extends Layer 4 beyond Track 6's stateful query monitor. This section establishes the model those chapters populate.

Position In Chapter

Section 11.03 is the architectural section of Chapter 11. Section 11.02 built the governance infrastructure; Section 11.03 establishes the conceptual model that determines what gets governed. Every detection rule and detector in Chapters 11–14 belongs to one of the four layers defined here.

Prose Content

Part 1 Why Layers

Heading

Why One Detection Layer Is Never Enough

Body

Every detection primitive has a characteristic failure mode. Signature detection fails against obfuscation. Heuristic detection fails against inputs that are unusual but legitimate. ML-based detection fails against adversarial examples crafted to evade the classifier. Behavioural detection fails to catch single-request attacks that leave no cross-session footprint. These failure modes are not bugs to be fixed. They are structural properties of the detection mechanisms. A signature rule that fires on the literal string "ignore previous instructions" will never fire on a base64-encoded or leetspeak-obfuscated version of the same instruction. A heuristic rule that fires on high token entropy will fire on legitimate technical prompts written in unusual domain language. An ML classifier trained on labelled prompt injection examples will not generalise to a novel injection technique that its training corpus did not include. A stateful session monitor will miss a single-shot extraction attack delivered in one large query. The response to structural failure modes is not to find a better single detector. It is to compose detectors whose failure modes are non-overlapping. An attacker who encodes their injection to evade the signature layer still faces the heuristic layer, which fires on the encoding's elevated entropy. An attacker who crafts a low-entropy encoded payload to evade both signature and heuristic still faces the ML layer, which may classify the semantic content of the decoded prompt as adversarial even when the surface form is unusual. An attacker who crafts inputs that evade all three per-request layers and conducts the attack over many sessions still faces the behavioural layer, which accumulates cross-session signals invisible to per-request detectors. Defence in depth for detection: each layer adds a detection surface. An attacker who evades all four layers simultaneously must understand and circumvent four distinct detection mechanisms — a combinatorially harder problem than evading any one.

Part 2 Layer1 Signature

Heading

Layer 1 — Signature Detection

Body

Signature detection matches inputs against a fixed set of patterns: regular expressions, keyword lists, byte sequences, or structural templates. It is the fastest and cheapest detection layer. A regex match on a prompt string costs microseconds and requires no model inference. It scales to any request volume without compute constraint. The signature layer's strengths: extremely low false positive rate on well-defined patterns, zero inference overhead, deterministic behaviour (the same input always produces the same result), and easy auditability (the rule is human-readable). For known-bad patterns — prompt prefixes that appear in public jailbreak catalogues, known adversarial trigger tokens, training API calls with specific malicious label values — signature detection is the correct and sufficient tool. The signature layer's failure mode is obfuscation. Any transformation of the attack input that preserves semantic meaning but changes surface form defeats a signature rule. Base64 encoding, character substitution (l33tsp34k), Unicode lookalikes, token splitting across whitespace boundaries, and instruction fragmentation across multi-turn conversation history all break signature rules while leaving the attack semantically intact. In the seven-track gateway, the Layer 1 components are the keyword conditions of the LLM01 Sigma rule that fronts Track 1 (injection_patterns.yml for known injection prefixes, jailbreak_sequences.yml for known jailbreak templates) and Track 3, the shot-count detector, which counts example dialogue turns in the assembled context. Both are regex and counting logic on raw text: fast and reliable on unobfuscated attacks and blind to obfuscated variants. Outside the gateway, the Chapter 8 poisoning monitor also has Layer 1 components: Sigma rules that match specific label distribution anomalies in training API calls are pattern-based and deterministic. The practical implication: Layer 1 runs first on every request. It is the cheapest gate. Requests that fire Layer 1 are blocked or flagged immediately, without incurring the cost of Layer 2 or Layer 3. Requests that pass Layer 1 proceed to Layer 2. This gate-and-proceed structure is what makes layered detection computationally tractable at scale.

Part 3 Layer2 Heuristic

Heading

Layer 2 — Heuristic Detection

Body

Heuristic detection computes features from the input and applies rule-based thresholds to those features. Unlike signature rules, which match surface patterns, heuristic rules fire on derived properties: token entropy, prompt length, ratio of instruction tokens to content tokens, character class distribution, sentence embedding distance from a known-good centroid. These properties are harder to manipulate than surface patterns because they reflect the statistical structure of the input rather than its literal form. The heuristic layer's strengths: robust to surface-level obfuscation (base64-encoding a prompt does not change its information density in ways that systematically evade entropy-based rules), interpretable (the feature value that triggered the rule can be inspected), and tunable (the threshold is a single number that can be calibrated against production traffic). The heuristic layer's failure modes: legitimate unusual inputs produce false positives. A technical prompt written in domain-specific notation (mathematical proofs, code with unusual character distributions, multilingual inputs) may trigger entropy or character-class heuristics without being adversarial. The heuristic layer has a higher false positive rate than the signature layer, and the threshold calibration in Section 11.09 is primarily concerned with the heuristic layer's thresholds. A second failure mode: adaptive adversaries who understand the heuristic rules can craft inputs that satisfy the feature constraints. An attacker who knows the entropy threshold can pad their injection with high-entropy filler to stay below the trigger point, or lower the entropy of an encoded payload by using a less compressible encoding. Heuristic evasion requires attacker knowledge of the specific thresholds — which is why threshold confidentiality (not publishing exact threshold values) is a minor operational control worth maintaining. In the seven-track gateway, Layer 2 holds Track 1's centroid-similarity gate, Track 2 (the perplexity detector) and Track 7's feature squeezer. Track 1's gate computes a derived feature (embedding distance from the known-bad prompt centroid) and applies a fixed threshold. Track 2 scores how improbable the input's token sequence is under a reference language model -- a heuristic that catches adversarial suffixes and heavy obfuscation. Track 7's squeezer disagreement score — the delta in model prediction before and after feature squeezing — is a derived heuristic property of the input.

Part 4 Layer3 Ml

Heading

Layer 3 — ML-Based Detection

Body

ML-based detection uses trained classifiers — or anomaly detectors — to score inputs based on learned representations of the attack surface. Unlike heuristic rules, ML models do not require explicit feature engineering: they learn from labelled examples which input properties predict attack behaviour. Unlike signature rules, ML models can generalise to novel attack variants not present in the training corpus, as long as those variants share distributional properties with the training examples. The ML layer's strengths: adaptability to novel attack variants (within the distribution of the training data), high coverage on the attack families represented in the training corpus, and the ability to detect attacks that are semantically adversarial without matching any known pattern or violating any heuristic threshold. The ML layer's failure modes: it requires labelled training data, which the signature and heuristic layers generate over time. A detection programme that skips Layers 1 and 2 and deploys ML detection from day one trains on synthetic data that does not reflect production traffic patterns, producing classifiers with poor production precision. The ML layer also fails against adversarial examples crafted to evade the specific classifier — a known problem that Chapter 12 addresses with adversarial training of the detection classifier itself. And it is expensive: a transformer-based prompt classifier adds 10–50ms of inference latency per request, which is significant in a gateway with a 100ms latency budget. In the seven-track gateway, Track 1 is the main Layer 3 component: the Section 6.17 injection classifier and the Section 7.14 semantic jailbreak classifier are trained models over learned sentence representations rather than explicit feature engineering. Track 7's adversarial classifier — the small binary classifier trained on squeezer output features — is the other fully ML Layer 3 component. Chapter 12 will expand the ML layer significantly, training Isolation Forest and One-Class SVM anomaly detectors for novel injection detection and fine-tuning a transformer classifier for prompt intent classification at 95%+ accuracy. Those Chapter 12 detectors fill the Layer 3 slots that the current gateway populates only partially. The compute cost management strategy for Layer 3: gate it. Run Layer 1 and Layer 2 on every request. Run Layer 3 only on requests that pass Layers 1 and 2 but exhibit borderline Layer 2 signal — a similarity score between 0.70 and 0.85, or an entropy value in the flagging band rather than the blocking band. This gating strategy reduces the fraction of requests that incur ML inference cost to those where ML adds the most marginal value, typically 5–15% of production traffic.

Part 5 Layer4 Behavioral

Heading

Layer 4 — Behavioral Detection

Body

Behavioural detection is stateful: it accumulates signals across multiple requests, multiple sessions, or extended time windows, and fires when the accumulated pattern crosses a threshold. It is the only detection layer that can catch attacks that are individually innocuous but collectively adversarial — the model extraction campaign that spreads thousands of probing queries across many sessions, each query looking like a legitimate API call in isolation. The behavioural layer's strengths: it closes the gap between per-request detection (Layers 1–3) and campaign-level attack patterns. A model extraction attack generates no single query that triggers injection or adversarial input heuristics. The attacker's strategy is precisely to avoid per-request detection by keeping each individual query below all thresholds. Behavioural detection sees the campaign pattern that individual request analysis cannot: query rate above baseline, systematic variance reduction in query parameters, output entropy trending toward zero across the session window, duplicate query ratio rising. The behavioural layer's failure modes: it requires stateful infrastructure (a session store, a streaming aggregation layer, or a SIEM with time-window queries) that adds engineering complexity. It introduces alert latency: a behavioural rule that fires after 500 queries in a 24-hour window cannot fire until those 500 queries have occurred. For attacks that succeed in fewer queries or in shorter windows, the behavioural layer fires too late to prevent the attack — it produces a forensic record and a basis for account suspension, not a real-time block. And stateful detection is harder to test: positive test cases must simulate realistic attack campaign progressions across time, not single-request inputs. In the seven-track gateway, three tracks are Layer 4. Track 4 (the trajectory anomaly scorer) and Track 5 (the coherence analyser) keep per-session state to catch gradual erosion and payload splitting across turns. Track 6 (the query monitor) keeps per-user state across sessions, tracking query rate, query variance and output entropy across rolling windows. Tracks 1, 2, 3 and 7 are stateless per request. Chapter 13 (Behavioral Analysis) will extend Layer 4 significantly: multi-user correlated session analysis, graph-based prompt relationship modelling, and time-series anomaly detection on session-level feature vectors.

Part 6 Gateway Mapping

Heading

Mapping the Seven-Track Gateway to the Four Layers

Body

The seven-track gateway built in Part 2 is an instance of the four-layer model. Not all four layers are fully populated — the ML layer and the behavioural layer each have a partial implementation — and that incompleteness is precisely what Chapters 12 and 13 address. But the structure is present, and mapping each track to its layer makes the architecture legible. Track 1 — Injection and Semantic Classifiers: Layers 1, 2 and 3. The LLM01 Sigma rule's keyword conditions (injection_patterns.yml, jailbreak_sequences.yml) are Layer 1. The centroid-similarity gate inside injection_classifier.py is Layer 2: cosine similarity to a known-bad centroid with a fixed 0.85 threshold (semantic_similarity.yml). The injection classifier and the semantic jailbreak classifier are Layer 3. All three fire independently; an attacker must evade all of them to bypass Track 1. Track 2 — Perplexity Detector: Layer 2. Perplexity of the full text and of the final suffix under a reference model, against fixed thresholds. Catches optimised adversarial suffixes (GCG, AutoDAN) and heavy character-level obfuscation; vulnerable to attackers who constrain their suffixes to fluent text. Track 3 — Shot-Count Detector: Layer 1. Counts example dialogue turns in the assembled context (system prompt, retrieved content and user turn). Deterministic and cheap; blind to many-shot attacks that disguise their examples as prose. Tracks 4 and 5 — Trajectory Anomaly Scorer and Coherence Analyser: Layer 4. Both keep per-session state: Track 4 scores gradual erosion and context manipulation across turns, Track 5 scores payload fragments that only form an attack when joined. Neither fires on a single request. Track 6 — Query Monitor and Rate Limiter: Layer 1 and Layer 4. The per-request Sigma rule (extraction_detector.yml) is Layer 1. The query monitor's per-user windows, the four-dimension rate limiter and the cross-user correlator are Layer 4 — stateful, accumulating signals across requests and accounts. Track 6 straddles both layers because model extraction has within-request signals (unusual query structure) and cross-request signals (budget accumulation). Track 7 — Adversarial Detection: Layer 2 and Layer 3. Feature squeezing (comparing the prediction before and after input transformation) and the consistency checker are Layer 2: derived heuristic scores. The adversarial classifier (a small binary classifier trained on squeezer output features) is Layer 3: a trained ML model. Sigma rule: adversarial_detection.yml. The gateway ensemble (seven_track_gateway_ensemble.py) is not a layer: it combines the tracks' scores into one decision. The Chapter 8 poisoning monitor sits outside the request path altogether. Layer 4 gap: Tracks 4 and 5 keep state only within a session, and Track 6's cross-user correlation looks only for extraction patterns. A distributed jailbreak campaign in which each account or session contributes one step of a multi-turn attack is invisible to all seven tracks. Chapter 13 addresses this gap. Layer 3 gap: the trained components (Track 1's classifiers and Track 7's adversarial classifier) are supervised: they recognise the attack families in their training data. There is no anomaly detector for novel injection patterns unlike anything labelled. Chapter 12 trains the Isolation Forest and prompt intent classifiers that fill this gap.

Part 7 Ordering And Cost

Heading

Layer Ordering, Compute Cost, and the Gating Strategy

Body

The layer ordering — signature first, heuristic second, ML third, behavioural fourth in terms of per-request evaluation order — is not arbitrary. It follows from the compute cost of each layer: Layer 1 (signature): microseconds per request. Can run on every request with no performance budget concern. Run first. Layer 2 (heuristic): milliseconds per request, depending on the number of features computed. Embedding computation for Track 1's centroid gate requires a forward pass through a small sentence encoder — approximately 2–5ms at CPU inference. Still fast enough to run on every request in most gateway configurations. Run second. Layer 3 (ML): 10–50ms per request for transformer-based classifiers, 1–5ms for shallow ML classifiers (RandomForest, SVM on pre-computed features). Too expensive to run on every request in a gateway with a 100ms total latency budget when there are multiple ML tracks. Run on gated subset. Gate condition: Layer 2 signal in the flagging band (not high enough to block, high enough to warrant deeper inspection). Layer 4 (behavioural): no per-request cost in the sense of synchronous inference. The stateful accumulation runs asynchronously or in a streaming pipeline; the per-request cost is a session store lookup and update. But the alert latency is high — the rule fires after accumulating evidence across many requests, not on the triggering request. Run concurrently with all other layers, but accept that it fires late. The gating strategy for the seven-track gateway: Track 1's Sigma conditions and centroid gate, Track 2 and Track 3 run on every request (Layers 1 and 2, fast). Track 1's classifiers (Layer 3) run only when the gate or the Sigma conditions flag. Track 7's squeezer (Layer 2) runs pre-inference on every request; Track 7's adversarial classifier (Layer 3) runs post-inference only when squeezer disagreement is above the flagging threshold. Tracks 4 and 5 update their session state on every turn, and Track 6 runs its Sigma component (Layer 1) on every request and its per-user accumulation (Layer 4) asynchronously. This gating strategy produces a gateway with the following effective latency profile: clean requests (pass all layers): ~5ms overhead. Flagging requests (Layer 2 signal, Layer 3 invoked): ~15–30ms overhead. Blocking requests (Layer 1 or Layer 2 block): ~3ms overhead (blocked before ML inference). Extraction-campaign requests (Layer 4 fires): no added latency per request; alert is async.

Author: Raghav Dinesh | github: ruwgxo

from dataclasses import dataclass, field
from enum import Enum
from typing import Callable

# ---------------------------------------------------------------------------
# Enumerations
# ---------------------------------------------------------------------------

class DetectionLayer(Enum):
    SIGNATURE = 1
    HEURISTIC = 2
    ML = 3
    BEHAVIORAL = 4

class AttackFamily(Enum):
    DIRECT_INJECTION = 'direct_injection'
    OBFUSCATED_INJECTION = 'obfuscated_injection'
    JAILBREAK_KNOWN = 'jailbreak_known_template'
    JAILBREAK_NOVEL = 'jailbreak_novel_template'
    JAILBREAK_ADVERSARIAL_SUFFIX = 'jailbreak_adversarial_suffix'
    JAILBREAK_MANY_SHOT = 'jailbreak_many_shot'
    JAILBREAK_MULTI_TURN = 'jailbreak_multi_turn'
    DATA_POISONING_OVERT = 'data_poisoning_overt'
    DATA_POISONING_SUBTLE = 'data_poisoning_subtle'
    MODEL_EXTRACTION = 'model_extraction'
    MODEL_EXTRACTION_DISTRIBUTED = 'model_extraction_distributed'
    ADVERSARIAL_INPUT_FGSM = 'adversarial_input_fgsm'
    ADVERSARIAL_INPUT_NOVEL = 'adversarial_input_novel_family'
    MULTI_SESSION_CAMPAIGN = 'multi_session_campaign'

# ---------------------------------------------------------------------------
# Data model
# ---------------------------------------------------------------------------

@dataclass
class DetectionPrimitive:
    '''A single detection function within a layer.'''
    name: str
    layer: DetectionLayer
    track: int              # gateway track number (1-7); 0 = upstream, outside the request path
    stateful: bool          # True for Layer 4 primitives
    latency_ms: float       # approximate per-request latency
    covers: set[AttackFamily]
    misses: set[AttackFamily]
    primary_failure_mode: str

@dataclass
class LayerResult:
    layer: DetectionLayer
    primitives: list[DetectionPrimitive]
    covered_families: set[AttackFamily] = field(default_factory=set)
    missed_families: set[AttackFamily] = field(default_factory=set)

    def __post_init__(self) -> None:
        for p in self.primitives:
            self.covered_families.update(p.covers)
            self.missed_families.update(p.misses)
        # A family covered by any primitive is covered at this layer
        self.missed_families -= self.covered_families

def build_layer_results(primitives: list[DetectionPrimitive]) -> dict[DetectionLayer, LayerResult]:
    results: dict[DetectionLayer, LayerResult] = {}
    for layer in DetectionLayer:
        layer_primitives = [p for p in primitives if p.layer == layer]
        results[layer] = LayerResult(layer=layer, primitives=layer_primitives)
    return results

def cumulative_coverage(layer_results: dict[DetectionLayer, LayerResult]) -> set[AttackFamily]:
    covered: set[AttackFamily] = set()
    for lr in layer_results.values():
        covered.update(lr.covered_families)
    return covered

def print_coverage_report(primitives: list[DetectionPrimitive]) -> None:
    layer_results = build_layer_results(primitives)
    all_covered = cumulative_coverage(layer_results)
    uncovered = ALL_FAMILIES - all_covered

    print('\nLayered Detection Architecture — Coverage Report')
    print(f'Total attack families tracked: {len(ALL_FAMILIES)}')
    print(f'Cumulative coverage (all layers): {len(all_covered)}/{len(ALL_FAMILIES)}')
    if uncovered:
        print(f'Uncovered families: {", ".join(f.value for f in uncovered)}\n')

    layer_labels = {
        DetectionLayer.SIGNATURE: 'Layer 1 — Signature',
        DetectionLayer.HEURISTIC: 'Layer 2 — Heuristic',
        DetectionLayer.ML:        'Layer 3 — ML-based',
        DetectionLayer.BEHAVIORAL:'Layer 4 — Behavioral',
    }
    total_latency_sync = sum(
        p.latency_ms for p in primitives
        if not p.stateful and p.layer != DetectionLayer.ML
    )

    for layer in DetectionLayer:
        lr = layer_results[layer]
        label = layer_labels[layer]
        print(f'{label}')
        print(f'  Primitives: {len(lr.primitives)}')
        print(f'  Covers:     {", ".join(f.value for f in lr.covered_families) or "none"}')
        print(f'  Misses:     {", ".join(f.value for f in lr.missed_families) or "none at this layer"}')
        for p in lr.primitives:
            stateful_tag = " [stateful]" if p.stateful else ''
            where = f'Track {p.track}' if p.track else 'Upstream'
            print(f'    {where}: {p.name} (~{p.latency_ms}ms){stateful_tag}')
        print()

    print(f'Synchronous latency budget (L1+L2, every request): ~{total_latency_sync:.1f}ms')
    print(f'With L3 gating (flagged requests only):             +15-30ms additional')
    print(f'L4 contribution:                                     async, no request latency')

# ---------------------------------------------------------------------------
# Entry point
# ---------------------------------------------------------------------------

if __name__ == '__main__':
    print_coverage_report(PRIMITIVES)

Common Mistakes

Id

CM11.03.1

Mistake

Deploying only Layer 3 (ML classifiers) and skipping Layers 1 and 2 because ML feels more sophisticated

Why It Happens

ML-based detection is technically interesting. Practitioners with ML backgrounds default to trained classifiers and view regex rules as primitive.

Why It Matters

ML classifiers require labelled training data that the signature and heuristic layers generate over time. Without Layers 1 and 2 producing confirmed true positives and confirmed false positives, the ML classifier trains on synthetic data that does not reflect production traffic. Production precision is poor. And the compute cost of running ML on every request without Layer 1 and 2 gating blows the latency budget.

Correct Approach

Follow the layer ordering. Signature first: it is free and catches known attacks immediately. Heuristic second: it catches obfuscated variants with low compute overhead. ML third, gated on Layer 2 signal: it generalises beyond known patterns but only runs on the fraction of traffic that warrants it.

Id

CM11.03.2

Mistake

Treating Layer 4 (behavioral) as a substitute for Layers 1–3 rather than a complement

Why It Happens

Behavioural detection sounds comprehensive. If the system can detect campaign-level patterns, individual request analysis seems redundant.

Why It Matters

Layer 4 has high alert latency by design — it fires after accumulating evidence, not on the triggering request. A single-shot attack (one request that succeeds) is completely invisible to the behavioural layer. Without Layers 1–3 catching individual requests, single-shot attacks go undetected until post-incident forensics.

Correct Approach

All four layers are complementary. Layer 4 catches what Layers 1–3 miss (campaigns). Layers 1–3 catch what Layer 4 cannot (single-request attacks). Removing any layer leaves a coverage gap that a knowledgeable adversary will exploit.

Id

CM11.03.3

Mistake

Running all layers on every request without gating, causing latency budget overrun

Why It Happens

The defence-in-depth argument sounds like every request should traverse all layers. Implementing gating requires additional logic and seems like premature optimisation.

Why It Matters

A transformer-based classifier adds 15–50ms per request. Running Layer 3 on every request in a gateway with five ML tracks adds 75–250ms of ML inference latency before gating, which violates typical API latency SLAs. Users experience degraded service on clean traffic.

Correct Approach

Gate Layer 3 on Layer 2 signal. Run Layer 1 and Layer 2 on every request. Run Layer 3 only when Layer 2 flags — typically 5–15% of traffic. This keeps median request latency at ~5ms while maintaining full detection coverage on suspicious requests.

Id

CM11.03.4

Mistake

Assuming that the seven-track gateway provides complete detection coverage

Why It Happens

Seven tracks across five attack families sounds comprehensive. The gateway blocks real attacks in testing. It feels complete.

Why It Matters

The gateway has two confirmed Layer 3 gaps (no ML anomaly detector for novel injection, no transformer intent classifier) and one confirmed Layer 4 gap (no multi-session campaign detection beyond model extraction). These gaps are known and documented; treating the gateway as complete prevents prioritising the Chapter 12 and 13 remediation work.

Correct Approach

Use the coverage gap table from Section 11.03 as the detection backlog. Chapters 12 and 13 fill the gaps systematically. The gateway is L1 maturity and approaching L3; it is not production-complete until the Chapter 12 and 13 detectors are integrated.

Id

CM11.03.5

Mistake

Mapping tracks to layers based on the track number rather than the detection mechanism

Why It Happens

The tracks are numbered 1–7 and the layers are numbered 1–4, which invites a misreading that tracks map sequentially to layers.

Why It Matters

Several tracks span multiple layers (Track 1 is L1, L2 and L3; Track 6 is L1 and L4; Track 7 is L2 and L3), and the numbers do not line up: Track 4 is Layer 4 but Track 2 is Layer 2 and Track 3 is Layer 1. A sequential mapping produces incorrect layer assignments, wrong latency profiles, and incorrect failure mode analysis.

Correct Approach

Map from mechanism, not from track number. A track is in Layer 1 if it uses pattern matching. It is in Layer 2 if it uses derived feature scoring with a fixed threshold. It is in Layer 3 if it uses a trained model. It is in Layer 4 if it is stateful across requests. A track can span multiple layers if it uses multiple mechanisms.

Section Summary

What You Learned

The four-layer detection architecture — signature, heuristic, ML-based, behavioural — defines the structure that every detection programme builds toward, whether explicitly or not. Each layer has a characteristic failure mode that the next layer compensates for. The layer ordering follows compute cost: signature first (microseconds, every request), heuristic second (milliseconds, every request), ML third (tens of milliseconds, gated on Layer 2 signal), behavioural fourth (async, no request latency). The seven-track gateway is an instance of this model: Track 1's Sigma conditions, Track 3 and Track 6's per-request rule are Layer 1; Track 1's centroid gate, Track 2 and Track 7's squeezer are Layer 2; Track 1's classifiers and Track 7's adversarial classifier are Layer 3; Tracks 4, 5 and 6's per-user accumulation are Layer 4. Two Layer 3 gaps and one Layer 4 gap remain for Chapters 12 and 13.

Key Terms

Term

Signature detection (Layer 1)

Definition

Detection by exact pattern matching: regex, keyword lists, byte sequences. Fast, deterministic, low false positive rate on known patterns. Primary failure mode: obfuscation of the matched pattern.

Term

Heuristic detection (Layer 2)

Definition

Detection by derived feature scoring with fixed thresholds: entropy, embedding distance, character class ratios. Robust to surface obfuscation. Primary failure mode: adaptive adversaries who understand and satisfy the feature constraints.

Term

ML-based detection (Layer 3)

Definition

Detection by trained classifiers or anomaly detectors on learned representations. Adaptable to novel variants within training distribution. Primary failure mode: attacks outside training distribution; adversarial evasion of the classifier.

Term

Behavioral detection (Layer 4)

Definition

Detection by stateful accumulation of cross-request or cross-session signals. Only layer that catches campaign-level attack patterns. Primary failure mode: attacks designed to stay below accumulation thresholds; high alert latency.

Term

Gating strategy

Definition

Running expensive layers (ML inference) only on requests that exhibit signal from cheaper layers (Layer 2 flagging), rather than on all requests. Reduces median request latency while preserving detection coverage on suspicious traffic.
