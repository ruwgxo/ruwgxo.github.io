Section 9.10: Detection Primitives

Section Overview

One Line Summary

Five detection primitives -- query pattern analyser, OOD detector, output entropy monitor, user concentration analyser, and watermarking signal extractor -- cover every extraction goal and privacy attack from the Chapter 9 attack catalogue; they are the engineering substrate that Section 9.11 wires into the production query monitor and Section 9.12 wires into the output-side defence.

Why This Section Exists

Sections 9.3 through 9.9 established the mechanistic basis for detection: extraction queries cluster near decision boundaries, distillation queries cover the input space broadly, prompt extraction queries concentrate on model behaviour meta-queries, membership inference queries probe specific target records, and economic abuse queries produce cost-per-query outliers. Each mechanism generates a measurable signal. Section 9.10 implements those signals as software primitives. The primitives are not independent detectors -- they are a library of signal generators, each covering one or more of the five attack surface positions (query-side distributional, query-side boundary, query-side OOD, output-side entropy, output-side ownership). Section 9.11 wires the input-side primitives into the production query monitor as parallel detection tracks; Section 9.12 wires the output-side primitives into the watermarking and perturbation pipeline. Section 9.10 is the substrate both capstone sections import. The six deliverables in this section form a coherent library: a query pattern analyser that measures distributional anomaly across a user''s session, an OOD detector that flags queries outside the model''s legitimate input distribution, a boundary query detector that identifies near-boundary input pairs, an output entropy monitor that measures per-response information leakage risk, a user concentration analyser that scores semantic clustering, and a detection ensemble that combines all five signals with configurable weights. The empirical comparison harness closes the section by measuring detection rates across synthetic attack families, grounding the ensemble weights in measurable performance rather than intuition.

Position In Chapter

Section 9.10 of 13. Engineering substrate for the production capstones. All detection logic in Sections 9.11 and 9.12 is imported from the primitives built here. The empirical comparison harness produces the detection rate benchmarks referenced in Section 9.11''s deployment checklist.

Title

The Detection Primitive Library: Design Philosophy

Body

A detection primitive is a single-signal generator: it takes as input a stream of query-response pairs (or a window of them) and produces a scalar score in [0.0, 1.0] representing the strength of a specific anomaly signal. Primitives are not classifiers -- they do not make binary decisions. They generate evidence that an ensemble classifier aggregates into an action. The library design follows three principles that flow from the attack catalogue. First, no single primitive covers the full catalogue. The five attack classes produce structurally different query distributions: boundary extraction concentrates near the decision surface; distillation spreads across the input space; prompt extraction concentrates on model behaviour meta-queries; membership inference targets specific records; economic abuse produces cost outliers. These signals are orthogonal -- a detector calibrated for one class has low sensitivity for another. An ensemble that combines orthogonal signals achieves coverage no individual primitive can. Second, primitives must be calibrated on legitimate traffic. Every primitive in this section scores anomaly relative to a baseline. That baseline is not universal -- it depends on the deployment''s legitimate query distribution. A coding assistant receives queries with high semantic diversity (many programming languages, many problem types) that would look like a distillation campaign to a primitive calibrated on a narrow-domain customer service deployment. Calibration on 30 to 90 days of observed legitimate traffic is required before any primitive is production-ready. Third, output-side primitives have different operational semantics than input-side primitives. The query pattern analyser, OOD detector, boundary query detector, and user concentration analyser all operate on incoming queries -- they can inform real-time rate limiting decisions. The output entropy monitor and watermarking signal extractor operate on responses -- the entropy monitor can inform rate limiting, but the watermark signal triggers post-hoc ownership verification workflows, not real-time blocks. The ensemble must respect this operational distinction when routing scores to actions.

Title

Query Pattern Analysis: Distributional Anomaly Detection

Body

The query pattern analyser maintains a sliding window of a user''s recent queries and computes distributional features over that window. The core insight from Section 9.3 is that extraction query distributions differ structurally from benign distributions: extraction queries are more uniformly spread across the input space (functionality extraction), more concentrated near the decision boundary (active learning), more semantically uniform within a narrow domain (fidelity extraction), or more focused on model behaviour meta-queries (prompt extraction). Three distributional features characterise these differences. Query diversity measures the semantic breadth of the user''s recent queries: high diversity across many topics signals functionality extraction; low diversity within one topic signals fidelity extraction or legitimate focused use. Boundary proximity score estimates the fraction of recent queries that are near the model''s decision boundary -- high boundary concentration signals active learning or equation-solving extraction. Behavioural meta-query rate measures the fraction of queries that probe the model''s behaviour, constraints, or capabilities rather than the product''s domain -- high meta-query rate signals prompt extraction. The sliding window length is a calibration parameter. A window too short (ten queries) is noisy and produces high false positive rates on legitimate users who happen to submit several similar queries. A window too long (thousand queries) is slow to respond and allows adversaries to complete significant extraction before the signal accumulates. Section 9.11 calibrates the window length against the target extraction budget: the window should be long enough to accumulate signal from approximately 20 percent of the query budget required for the attack the deployment is defending against.

Title

OOD Detection: Out-of-Distribution Query Identification

Body

Out-of-distribution detection identifies queries that fall outside the model''s legitimate input distribution -- the distribution of inputs for which the deployment was designed. OOD queries are anomalous for two independent reasons that both matter for extraction detection: they are inputs the model may not handle reliably (product quality concern), and they are often boundary-probing inputs that are positioned at the edge of the input space where extraction campaigns search for decision boundary geometry (security concern). The OOD detector is trained on a reference set of legitimate queries. Isolation Forest is the preferred algorithm for this application: it is unsupervised (no labelled anomalies required), computationally efficient at inference time, and robust to the high dimensionality of text embedding spaces. The detector assigns each incoming query an anomaly score in [0.0, 1.0] where high scores indicate OOD inputs. The OOD signal has a characteristic pattern for different extraction attack classes. Equation-solving extraction produces OOD queries because boundary- seeking inputs are positioned between the legitimate class clusters, not within them. Functionality extraction using random sampling produces OOD queries because many inputs drawn uniformly from the feature space fall outside the product''s legitimate input domain. Distillation using benchmark prompts may not produce OOD queries because benchmark prompts are within the model''s general training distribution -- this is the detection limit for OOD-only detection. The OOD detector requires a feature representation of incoming queries. For text queries, sentence embeddings (from a fast embedding model that fits within the gateway''s latency budget) convert queries to dense vectors for isolation forest scoring. The embedding model must be chosen for latency compatibility with the production gateway -- a model that adds more than 10ms to the gateway''s P99 latency is not suitable.

Title

Boundary Query Detection: Classification Surface Proximity

Body

The boundary query detector is the most targeted of the five primitives: it is specifically designed for decision-boundary extraction (Section 9.3) and active distillation (Section 9.4). Both attack classes deliberately position queries near the model''s decision boundary -- boundary extraction to map its geometry, active distillation to maximise per-query information gain. The detector identifies this clustering. The detector operates on the accumulated (query, response) log for a user rather than on individual queries. For grey-box APIs returning confidence scores, the signal is direct: queries that receive near-0.5 confidence (near-uniform probability distribution) are near the boundary. For black- box APIs returning only hard labels, the signal requires pair analysis: the detector identifies pairs of queries with opposite predicted labels and small semantic distance between them -- the defining characteristic of boundary-seeking input pairs. Pair analysis for black-box boundary detection operates on the user''s query embedding history. For each new query, the detector computes its semantic distance to all prior queries in the window with opposite predicted labels. If the minimum distance to an opposite-label prior query is below a threshold, the pair is flagged as a potential boundary-seeking pair. The boundary proximity score for the user is the fraction of queries in the window that participate in at least one such flagged pair. The computational cost of pair analysis scales quadratically with window size in the naive implementation. For the Section 9.11 production deployment, a k-d tree index on the query embeddings in the window reduces the nearest- neighbour search to O(log n) per query, making the boundary detector compatible with the gateway''s latency budget.

Title

Output Entropy Monitoring: Low-Information Extraction Queries

Body

The output entropy monitor operates on the model''s responses rather than its inputs, making it the first output-side primitive in the detection library. For grey-box APIs, the model''s output is a probability distribution over classes; the entropy of this distribution is high (near-uniform) when the input is near the decision boundary and low (concentrated on one class) when the input is far from the boundary. The extraction relevance of output entropy is indirect but important. A user whose queries systematically produce low-entropy outputs (high confidence) is not near the boundary -- their queries are well within the model''s confident prediction region, consistent with legitimate use. A user whose queries frequently produce medium-entropy outputs (split probability between two or more classes) is systematically probing the model in regions where its confidence is low -- the regions boundary extraction targets. For LLMs returning text rather than class probabilities, output entropy is approximated by the diversity of generated content: low lexical diversity across responses to varied prompts indicates the model is producing formulaic outputs (possibly due to prompt constraints leaking through responses, relevant to prompt extraction detection). High lexical diversity is consistent with legitimate general-purpose use. The output entropy monitor also serves as the economic abuse detection signal for output-side cost amplification: an unusually long response (high token count) to a query that does not require a long response is an output-length anomaly that the entropy monitor flags alongside its entropy calculation. Section 9.8''s cost-per-query analyser uses the output token count as one of its input features; the output entropy monitor produces that feature as a by-product of its entropy calculation.

Title

User Concentration Analysis: Per-User Query Pattern Concentration

Body

The user concentration analyser measures the semantic clustering of a user''s queries: how tightly they cluster within a semantic region relative to the expected diversity of legitimate users with similar overall query volumes. High concentration within a narrow semantic region signals fidelity extraction (which targets a specific input set) or systematic prompt extraction (which targets the model''s behavioural constraints, a narrow semantic domain). The analyser maintains an embedding of each query in the user''s window and computes the average pairwise semantic similarity. A legitimate user with diverse queries has low average similarity. A fidelity extractor whose target set covers one semantic domain (medical imaging, financial data, specific programming language queries) has high average similarity. The concentration score is calibrated against the deployment''s legitimate user population: the threshold is set at the 95th percentile of average pairwise similarity across legitimate users, so only the top 5 percent of similarity scores trigger the concentration signal. User concentration analysis is the primary detection signal for fidelity extraction precisely because the other signals do not cover it. Fidelity extraction does not necessarily produce boundary-seeking pairs (it may use soft-label distillation within the target set), does not necessarily produce OOD queries (the target set may be within the legitimate input domain), and does not necessarily produce high query volume (the target set may be small). Semantic concentration is the unique signal that fidelity extraction produces and that legitimate focused users produce to a lesser degree. The concentration analyser also provides the detection signal for systematic prompt extraction: a user who repeatedly queries the model''s behavioural constraints, contact details, and refusal categories produces a cluster of semantically similar queries (all about model behaviour) that the concentration analyser flags as anomalous concentration in the model- behaviour meta-query semantic region.

Title

Watermarking Detection Signals: Cryptographic Ownership Evidence

Body

The watermarking detection signal is fundamentally different from the four input-side primitives. Those primitives are designed to detect extraction in progress -- their scores inform real-time rate limiting decisions. The watermark detection signal is designed to detect extraction after the fact -- to verify the presence of the victim model''s cryptographic identity in a suspected surrogate. The watermarking scheme embedded in Section 9.12 works by biasing the model''s token selection probabilities: a secret key determines which tokens are "green" (preferred) and which are "red" (suppressed) for each token position, in a way that is statistically detectable in the aggregate but imperceptible in any individual token selection. A surrogate model trained to replicate the victim''s outputs inherits these biases because the training data -- the collected victim responses -- has an excess of green tokens at the watermarked positions. The watermark detector tests the null hypothesis that a text sequence was generated by a model without the watermark. The test statistic is the proportion of green tokens at the expected watermarked positions. Under the null hypothesis (no watermark), this proportion should be approximately 0.5 (random green/red assignment). With the watermark present, the proportion is significantly above 0.5 by an amount proportional to the watermark strength. The p-value of this test is the detection signal: a p-value below a threshold indicates watermark presence with the specified confidence. The detection primitive in this section implements the statistical test framework. The full watermarking scheme -- the key management, the token- level embedding, the robustness to paraphrasing -- is implemented in Section 9.12. Section 9.10 implements only the detection side: given a text sequence and a watermark key, compute the detection statistic and p-value. This separation of concerns allows the detection workflow to operate independently of the embedding workflow.

Title

Combining Primitives: The Ensemble Approach and Coverage Analysis

Body

The ensemble combines the five primitive scores into a composite action score that drives the Section 9.11 rate limiter and alert router. The combination must respect two constraints: the operational timing difference between input-side and output-side primitives, and the coverage difference across extraction attack classes. The timing constraint is addressed by separating the ensemble into two stages. The input-side stage combines the query pattern analyser, OOD detector, boundary query detector, and user concentration analyser scores at request arrival time. The composite input-side score drives the synchronous rate limiting decision that must complete within the gateway''s latency budget. The output-side stage combines the output entropy monitor score at response generation time. The watermark detection score is asynchronous -- it is computed on-demand when a suspected surrogate is submitted for verification, not on every response. The coverage constraint is addressed by the ensemble weights. Extraction goal coverage varies by primitive: the boundary query detector has high coverage of decision-boundary extraction and low coverage of distillation and prompt extraction; the user concentration analyser has high coverage of fidelity extraction and prompt extraction and low coverage of decision- boundary and functionality extraction. The ensemble weights are set to ensure that any extraction goal produces a composite score above the alert threshold given sufficient attack intensity. This is the coverage analysis step: for each extraction goal in the taxonomy, verify that at least one primitive achieves a score above its individual threshold at the attack intensity level the deployment is defending against. The ensemble is not a black box. Its weights and thresholds are documented in the Section 9.11 deployment checklist as explicit policy parameters that security teams can audit and adjust. The empirical comparison harness (Deliverable 6) measures detection rates under synthetic attack traffic and is the tool for calibrating weights against measured performance rather than intuition.

Name

query_pattern_analyser.py

Description

Query pattern analyser implementing three sub-signals over a per-user sliding window: query diversity (semantic breadth), boundary proximity score (fraction of near-boundary queries), and meta-query rate (model-behaviour query concentration). Returns a composite query pattern score and per-signal breakdown. Designed to be imported by the Section 9.11 query monitor as Track 1 of the detection ensemble.

Implementation Notes

Single quotes throughout per book convention. Requires numpy and sklearn. Window management uses a deque for O(1) append/pop. Embedding computation is abstracted behind an embed_query() callable -- replace with a production embedding model. No hardcoded window size or threshold.

# query_pattern_analyser.py
# Chapter 9 Section 9.10 -- Query Pattern Analyser
# Single quotes throughout per book convention.

import math
from collections import deque
from dataclasses import dataclass, field
from typing import Callable, Deque, List, Optional, Tuple

import numpy as np


META_QUERY_KEYWORDS: List[str] = [
    'what can you', 'what are you', 'are you allowed', 'do you have',
    'what is your', 'can you help', 'what topics', 'what tools',
    'what language', 'who do you work', 'how do you',
]


@dataclass
class QueryRecord:
    embedding: np.ndarray
    text: str
    predicted_label: Optional[int]
    is_meta_query: bool


@dataclass
class QueryPatternScore:
    diversity_score: float        # 0.0=low diversity (suspicious), 1.0=high diversity (benign)
    boundary_proximity_score: float  # 0.0=far from boundary, 1.0=clustered at boundary
    meta_query_rate: float        # 0.0=no meta-queries, 1.0=all meta-queries
    composite_score: float        # weighted combination; high = suspicious
    window_size: int


def _pairwise_cosine_similarity_mean(embeddings: List[np.ndarray]) -> float:
    if len(embeddings) < 2:
        return 0.0
    n = min(len(embeddings), 100)
    sub = np.array(embeddings[:n])
    norms = np.linalg.norm(sub, axis=1, keepdims=True)
    norms = np.where(norms == 0, 1.0, norms)
    normed = sub / norms
    sims = normed @ normed.T
    upper = sims[np.triu_indices(n, k=1)]
    return float(upper.mean()) if len(upper) > 0 else 0.0


def _is_meta_query(text: str) -> bool:
    lower = text.lower()
    return any(kw in lower for kw in META_QUERY_KEYWORDS)


def _boundary_proximity_fraction(
    records: List[QueryRecord],
    min_opposite_label_distance: float = 0.3,
) -> float:
    '''
    Fraction of queries in window that have an opposite-label near-neighbour.
    Requires at least two distinct labels in the window.
    '''
    labelled = [r for r in records if r.predicted_label is not None]
    if len(labelled) < 2:
        return 0.0
    labels = [r.predicted_label for r in labelled]
    if len(set(labels)) < 2:
        return 0.0
    flagged = 0
    for i, rec_i in enumerate(labelled):
        for j, rec_j in enumerate(labelled):
            if i == j:
                continue
            if rec_i.predicted_label == rec_j.predicted_label:
                continue
            norm_i = np.linalg.norm(rec_i.embedding)
            norm_j = np.linalg.norm(rec_j.embedding)
            if norm_i == 0 or norm_j == 0:
                continue
            cos_sim = float(rec_i.embedding.dot(rec_j.embedding) / (norm_i * norm_j))
            distance = 1.0 - cos_sim
            if distance < min_opposite_label_distance:
                flagged += 1
                break
    return flagged / max(len(labelled), 1)


class QueryPatternAnalyser:
    '''
    Maintains a per-user sliding window and computes query pattern scores.
    embed_fn: callable that takes a query string and returns a numpy embedding.
    '''

    def __init__(
        self,
        embed_fn: Callable[[str], np.ndarray],
        window_size: int = 100,
        diversity_weight: float = 0.40,
        boundary_weight: float = 0.35,
        meta_weight: float = 0.25,
    ) -> None:
        self._embed = embed_fn
        self._window_size = window_size
        self._diversity_w = diversity_weight
        self._boundary_w = boundary_weight
        self._meta_w = meta_weight
        self._window: Deque[QueryRecord] = deque(maxlen=window_size)

    def update(self, query_text: str, predicted_label: Optional[int] = None) -> QueryPatternScore:
        embedding = self._embed(query_text)
        record = QueryRecord(
            embedding=embedding,
            text=query_text,
            predicted_label=predicted_label,
            is_meta_query=_is_meta_query(query_text),
        )
        self._window.append(record)
        return self._score()

    def _score(self) -> QueryPatternScore:
        records = list(self._window)
        embeddings = [r.embedding for r in records]

        # Diversity: high mean pairwise similarity = low diversity = suspicious
        mean_sim = _pairwise_cosine_similarity_mean(embeddings)
        # Invert: high similarity -> high suspicion for concentration
        concentration_signal = mean_sim

        # Boundary proximity
        boundary_prox = _boundary_proximity_fraction(records)

        # Meta-query rate
        meta_rate = sum(1 for r in records if r.is_meta_query) / max(len(records), 1)

        # Composite: high concentration OR high boundary proximity OR high meta-rate = suspicious
        composite = (
            self._diversity_w * concentration_signal
            + self._boundary_w * boundary_prox
            + self._meta_w * meta_rate
        )
        return QueryPatternScore(
            diversity_score=round(1.0 - concentration_signal, 3),
            boundary_proximity_score=round(boundary_prox, 3),
            meta_query_rate=round(meta_rate, 3),
            composite_score=round(min(composite, 1.0), 3),
            window_size=len(records),
        )


def _mock_embed(text: str) -> np.ndarray:
    '''Deterministic mock embedding for testing.'''
    rng = np.random.default_rng(seed=abs(hash(text)) % (2 ** 31))
    return rng.standard_normal(64).astype(np.float32)


if __name__ == '__main__':
    analyser = QueryPatternAnalyser(embed_fn=_mock_embed, window_size=20)
    queries = [
        ('What is your name?', None),
        ('What topics are you allowed to discuss?', None),
        ('Are you allowed to discuss competitors?', None),
        ('What language do you respond in?', None),
        ('Who do you work for?', None),
        ('Can you help me with a completely unrelated topic?', 1),
    ]
    print('QUERY PATTERN ANALYSER -- Chapter 9 Section 9.10')
    for q_text, label in queries:
        score = analyser.update(q_text, label)
        print(f'  [{score.window_size:2d} queries] composite={score.composite_score:.3f} '
              f'boundary={score.boundary_proximity_score:.3f} '
              f'meta={score.meta_query_rate:.3f} '
              f'query={q_text[:40]}')

import numpy as np
from dataclasses import dataclass
from typing import Callable, List, Optional

from sklearn.ensemble import IsolationForest


@dataclass
class OODDetectorConfig:
    n_estimators: int = 100
    contamination: float = 0.05   # expected fraction of OOD queries in training set
    random_state: int = 42
    score_threshold: float = 0.70  # above this = flag as OOD


class OODDetector:
    '''
    Isolation Forest OOD detector for query embeddings.
    Trained on legitimate query embeddings; scores incoming queries.
    embed_fn: callable string -> np.ndarray.
    '''

    def __init__(
        self,
        embed_fn: Callable[[str], np.ndarray],
        config: Optional[OODDetectorConfig] = None,
    ) -> None:
        self._embed = embed_fn
        self._config = config or OODDetectorConfig()
        self._forest: Optional[IsolationForest] = None
        self._score_min: float = -0.5
        self._score_max: float = 0.5

    def fit(self, legitimate_queries: List[str]) -> None:
        '''Train the isolation forest on legitimate query embeddings.'''
        embeddings = np.array([self._embed(q) for q in legitimate_queries])
        self._forest = IsolationForest(
            n_estimators=self._config.n_estimators,
            contamination=self._config.contamination,
            random_state=self._config.random_state,
        )
        self._forest.fit(embeddings)
        # Calibrate score range on training data
        raw_scores = self._forest.score_samples(embeddings)
        self._score_min = float(raw_scores.min())
        self._score_max = float(raw_scores.max())

    def score(self, query_text: str) -> float:
        '''
        Return OOD anomaly score in [0.0, 1.0].
        High score = OOD (suspicious). Low score = in-distribution (benign).
        '''
        if self._forest is None:
            raise RuntimeError('OODDetector must be fitted before scoring')
        embedding = self._embed(query_text).reshape(1, -1)
        raw = float(self._forest.score_samples(embedding)[0])
        span = self._score_max - self._score_min
        if span == 0:
            return 0.0
        # Isolation Forest: lower raw score = more anomalous
        # Invert and normalise to [0, 1]
        normalised = (raw - self._score_min) / span
        return round(max(0.0, min(1.0 - normalised, 1.0)), 3)

    def is_ood(self, query_text: str) -> bool:
        return self.score(query_text) >= self._config.score_threshold


def _mock_embed(text: str) -> np.ndarray:
    rng = np.random.default_rng(seed=abs(hash(text)) % (2 ** 31))
    return rng.standard_normal(64).astype(np.float32)

Boundary query detector that analyses a per-user (embedding, label) history to identify near-boundary input pairs. Maintains a k-d tree index for efficient nearest-neighbour search. # boundary_query_detector.py
# Chapter 9 Section 9.10 -- Boundary Query Detector
# Single quotes throughout per book convention.

import math
from collections import deque
from dataclasses import dataclass, field
from typing import Callable, Deque, List, Optional, Tuple

import numpy as np
from sklearn.neighbors import KDTree


@dataclass
class LabelledQueryRecord:
    embedding: np.ndarray
    label: int
    confidence_vector: Optional[np.ndarray]  # None for black-box APIs


@dataclass
class BoundaryDetectorScore:
    pair_proximity_score: float   # fraction of queries in opposite-label near-pairs
    confidence_entropy_score: float  # mean output entropy (grey-box only); 0.0 for black-box
    composite_score: float


def _shannon_entropy(proba: np.ndarray) -> float:
    p = np.clip(proba, 1e-10, 1.0)
    return float(-np.sum(p * np.log2(p)))


def _max_possible_entropy(n_classes: int) -> float:
    return math.log2(max(n_classes, 2))


class BoundaryQueryDetector:
    '''
    Tracks per-user (embedding, label) history and identifies boundary-seeking pairs.
    embed_fn: callable string -> np.ndarray.
    proximity_threshold: cosine distance below which an opposite-label pair is flagged.
    '''

    def __init__(
        self,
        embed_fn: Callable[[str], np.ndarray],
        window_size: int = 200,
        proximity_threshold: float = 0.25,
        pair_weight: float = 0.70,
        entropy_weight: float = 0.30,
    ) -> None:
        self._embed = embed_fn
        self._window_size = window_size
        self._prox_threshold = proximity_threshold
        self._pair_w = pair_weight
        self._entropy_w = entropy_weight
        self._window: Deque[LabelledQueryRecord] = deque(maxlen=window_size)
        self._kdtree: Optional[KDTree] = None
        self._tree_labels: List[int] = []
        self._rebuild_every = 10
        self._updates_since_rebuild = 0

    def update(
        self,
        query_text: str,
        label: int,
        confidence_vector: Optional[np.ndarray] = None,
    ) -> BoundaryDetectorScore:
        embedding = self._embed(query_text)
        record = LabelledQueryRecord(
            embedding=embedding, label=label, confidence_vector=confidence_vector
        )
        self._window.append(record)
        self._updates_since_rebuild += 1
        if self._updates_since_rebuild >= self._rebuild_every or self._kdtree is None:
            self._rebuild_tree()
            self._updates_since_rebuild = 0
        return self._score()

    def _rebuild_tree(self) -> None:
        records = list(self._window)
        if len(records) < 2:
            self._kdtree = None
            self._tree_labels = []
            return
        embeddings = np.array([r.embedding for r in records])
        norms = np.linalg.norm(embeddings, axis=1, keepdims=True)
        norms = np.where(norms == 0, 1.0, norms)
        self._tree_embeddings = embeddings / norms
        self._kdtree = KDTree(self._tree_embeddings)
        self._tree_labels = [r.label for r in records]

    def _score(self) -> BoundaryDetectorScore:
        records = list(self._window)
        if len(records) < 4 or self._kdtree is None:
            return BoundaryDetectorScore(0.0, 0.0, 0.0)

        # Pair proximity score
        flagged = 0
        for i, rec in enumerate(records):
            norm = np.linalg.norm(rec.embedding)
            if norm == 0:
                continue
            normed = rec.embedding / norm
            dists, indices = self._kdtree.query(normed.reshape(1, -1), k=min(10, len(records)))
            for dist, idx in zip(dists[0], indices[0]):
                if idx == i:
                    continue
                if self._tree_labels[idx] != rec.label and dist < self._prox_threshold:
                    flagged += 1
                    break
        pair_score = flagged / max(len(records), 1)

        # Confidence entropy score (grey-box)
        conf_records = [r for r in records if r.confidence_vector is not None]
        if conf_records:
            n_classes = len(conf_records[0].confidence_vector)
            max_entropy = _max_possible_entropy(n_classes)
            entropies = [
                _shannon_entropy(r.confidence_vector) / max(max_entropy, 1e-10)
                for r in conf_records
            ]
            # High mean entropy near 0.5 of max = near-boundary
            mean_entropy = float(np.mean(entropies))
            # Normalise: entropy of 0.5 * max_entropy = score 1.0
            entropy_score = min(mean_entropy / 0.5, 1.0)
        else:
            entropy_score = 0.0

        composite = self._pair_w * pair_score + self._entropy_w * entropy_score
        return BoundaryDetectorScore(
            pair_proximity_score=round(pair_score, 3),
            confidence_entropy_score=round(entropy_score, 3),
            composite_score=round(min(composite, 1.0), 3),
        )


def _mock_embed(text: str) -> np.ndarray:
    rng = np.random.default_rng(seed=abs(hash(text)) % (2 ** 31))
    return rng.standard_normal(64).astype(np.float32)

Description

Output entropy monitor that scores per-response information leakage risk. For classifier APIs: scores entropy of probability vector relative to user''s historical baseline. # Chapter 9 Section 9.10 -- Output Entropy Monitor
# Single quotes throughout per book convention.

import math
from collections import deque
from dataclasses import dataclass, field
from typing import Deque, List, Optional, Tuple

import numpy as np


@dataclass
class EntropyRecord:
    entropy: float
    token_count: Optional[int]
    is_anomaly: bool


@dataclass
class EntropyMonitorScore:
    entropy_score: float       # 0.0=low (far from boundary), 1.0=high (near boundary)
    token_count_anomaly: float  # 0.0=normal length, 1.0=extreme length anomaly
    composite_score: float
    mode: str  # 'classifier' or 'llm'


def _shannon_entropy_normalised(proba: np.ndarray) -> float:
    n = len(proba)
    if n <= 1:
        return 0.0
    max_ent = math.log2(n)
    p = np.clip(proba, 1e-10, 1.0)
    ent = float(-np.sum(p * np.log2(p)))
    return ent / max(max_ent, 1e-10)


class OutputEntropyMonitor:
    '''
    Per-user output entropy monitor.
    Maintains a rolling baseline of entropy and token count for the user.
    '''

    def __init__(
        self,
        window_size: int = 50,
        token_anomaly_sigma: float = 3.0,
        entropy_weight: float = 0.65,
        token_weight: float = 0.35,
    ) -> None:
        self._window_size = window_size
        self._token_sigma = token_anomaly_sigma
        self._entropy_w = entropy_weight
        self._token_w = token_weight
        self._entropy_window: Deque[float] = deque(maxlen=window_size)
        self._token_window: Deque[int] = deque(maxlen=window_size)

    def score(
        self,
        confidence_vector: Optional[np.ndarray] = None,
        token_count: Optional[int] = None,
    ) -> EntropyMonitorScore:
        '''
        Score a single model response.
        confidence_vector: probability distribution over classes (classifier mode).
        token_count: number of output tokens generated (LLM mode).
        Either or both may be provided.
        '''
        mode = 'unknown'
        entropy_score = 0.0
        token_score = 0.0

        if confidence_vector is not None:
            mode = 'classifier'
            ent = _shannon_entropy_normalised(confidence_vector)
            self._entropy_window.append(ent)
            if len(self._entropy_window) >= 5:
                mean_ent = float(np.mean(list(self._entropy_window)))
                # Near-boundary responses have entropy near 0.5 of max (normalised ~0.5)
                # Score: how close to 0.5 normalised entropy is the current value
                entropy_score = 1.0 - abs(ent - 0.5) * 2.0
            else:
                entropy_score = 0.0

        if token_count is not None:
            mode = mode if mode != 'unknown' else 'llm'
            self._token_window.append(token_count)
            if len(self._token_window) >= 5:
                counts = list(self._token_window)
                mean_tc = float(np.mean(counts))
                std_tc = float(np.std(counts)) or 1.0
                z_score = (token_count - mean_tc) / std_tc
                # Token count anomaly: high z-score = cost amplification
                token_score = min(max(z_score / self._token_sigma, 0.0), 1.0)
            else:
                token_score = 0.0

        composite = self._entropy_w * entropy_score + self._token_w * token_score
        return EntropyMonitorScore(
            entropy_score=round(entropy_score, 3),
            token_count_anomaly=round(token_score, 3),
            composite_score=round(min(composite, 1.0), 3),
            mode=mode,
        )

# Chapter 9 Section 9.10 -- User Concentration Analyser
# Single quotes throughout per book convention.

from collections import deque
from dataclasses import dataclass, field
from typing import Callable, Deque, Dict, List, Optional, Tuple

import numpy as np


@dataclass
class ConcentrationScore:
    mean_pairwise_similarity: float
    concentration_score: float  # 0.0=diverse (benign), 1.0=concentrated (suspicious)
    above_population_threshold: bool
    window_size: int


def _mean_pairwise_cosine_similarity(embeddings: np.ndarray) -> float:
    if len(embeddings) < 2:
        return 0.0
    norms = np.linalg.norm(embeddings, axis=1, keepdims=True)
    norms = np.where(norms == 0, 1.0, norms)
    normed = embeddings / norms
    n = min(len(normed), 100)
    sub = normed[:n]
    sims = sub @ sub.T
    upper = sims[np.triu_indices(n, k=1)]
    return float(upper.mean()) if len(upper) > 0 else 0.0


class UserConcentrationAnalyser:
    '''
    Per-user concentration analyser with population baseline calibration.
    embed_fn: callable string -> np.ndarray.
    '''

    def __init__(
        self,
        embed_fn: Callable[[str], np.ndarray],
        window_size: int = 50,
        population_percentile: float = 95.0,
    ) -> None:
        self._embed = embed_fn
        self._window_size = window_size
        self._percentile = population_percentile
        self._user_windows: Dict[str, Deque[np.ndarray]] = {}
        self._population_threshold: Optional[float] = None

    def fit_population_baseline(
        self,
        user_query_samples: List[Tuple[str, List[str]]],
    ) -> None:
        '''
        Fit the population baseline from (user_id, [query_texts]) samples.
        Computes mean pairwise similarity for each user and stores
        the population_percentile as the alert threshold.
        '''
        per_user_similarities: List[float] = []
        for _, queries in user_query_samples:
            if len(queries) < 2:
                continue
            embeddings = np.array([self._embed(q) for q in queries])
            per_user_similarities.append(_mean_pairwise_cosine_similarity(embeddings))
        if per_user_similarities:
            self._population_threshold = float(
                np.percentile(per_user_similarities, self._percentile)
            )

    def update(self, user_id: str, query_text: str) -> ConcentrationScore:
        if user_id not in self._user_windows:
            self._user_windows[user_id] = deque(maxlen=self._window_size)
        embedding = self._embed(query_text)
        self._user_windows[user_id].append(embedding)
        return self._score(user_id)

    def _score(self, user_id: str) -> ConcentrationScore:
        window = list(self._user_windows.get(user_id, deque()))
        if len(window) < 2:
            return ConcentrationScore(0.0, 0.0, False, len(window))
        embeddings = np.array(window)
        mean_sim = _mean_pairwise_cosine_similarity(embeddings)
        threshold = self._population_threshold or 0.85
        concentration = min(mean_sim / max(threshold, 1e-10), 1.0)
        above = mean_sim >= threshold
        return ConcentrationScore(
            mean_pairwise_similarity=round(mean_sim, 4),
            concentration_score=round(concentration, 3),
            above_population_threshold=above,
            window_size=len(window),
        )


def _mock_embed(text: str) -> np.ndarray:
    rng = np.random.default_rng(seed=abs(hash(text)) % (2 ** 31))
    return rng.standard_normal(64).astype(np.float32)

# detection_ensemble.py
# Chapter 9 Section 9.10 -- Detection Ensemble and Empirical Comparison Harness
# Single quotes throughout per book convention.

from dataclasses import dataclass, field
from typing import Any, Callable, Dict, List, Optional, Tuple

import numpy as np


@dataclass
class EnsembleConfig:
    query_pattern_weight: float = 0.30
    ood_weight: float = 0.20
    boundary_weight: float = 0.25
    entropy_weight: float = 0.15
    concentration_weight: float = 0.10
    composite_alert_threshold: float = 0.60
    individual_alert_threshold: float = 0.70


@dataclass
class PrimitiveScores:
    query_pattern: float = 0.0
    ood: float = 0.0
    boundary: float = 0.0
    entropy: float = 0.0
    concentration: float = 0.0


@dataclass
class EnsembleResult:
    primitive_scores: PrimitiveScores
    composite_score: float
    individual_alerts: List[str]
    action: str  # 'monitor', 'alert_tier2', 'alert_tier1_rate_limit'


@dataclass
class AttackFamilySimulation:
    name: str
    n_queries: int
    score_generator: Callable[[int], PrimitiveScores]


def compute_ensemble(
    scores: PrimitiveScores,
    config: Optional[EnsembleConfig] = None,
) -> EnsembleResult:
    cfg = config or EnsembleConfig()
    composite = (
        cfg.query_pattern_weight * scores.query_pattern
        + cfg.ood_weight * scores.ood
        + cfg.boundary_weight * scores.boundary
        + cfg.entropy_weight * scores.entropy
        + cfg.concentration_weight * scores.concentration
    )
    composite = round(min(composite, 1.0), 3)

    individual_alerts: List[str] = []
    score_map = {
        'query_pattern': scores.query_pattern,
        'ood': scores.ood,
        'boundary': scores.boundary,
        'entropy': scores.entropy,
        'concentration': scores.concentration,
    }
    for name, score in score_map.items():
        if score >= cfg.individual_alert_threshold:
            individual_alerts.append(name)

    if composite >= cfg.composite_alert_threshold or any(
        score_map[p] >= cfg.individual_alert_threshold
        for p in ['boundary', 'query_pattern']
    ):
        action = 'alert_tier1_rate_limit'
    elif individual_alerts:
        action = 'alert_tier2'
    else:
        action = 'monitor'

    return EnsembleResult(
        primitive_scores=scores,
        composite_score=composite,
        individual_alerts=individual_alerts,
        action=action,
    )


def run_empirical_comparison(
    attack_families: List[AttackFamilySimulation],
    config: Optional[EnsembleConfig] = None,
    n_repetitions: int = 100,
    rng_seed: int = 42,
) -> Dict[str, Dict[str, float]]:
    '''
    Run the empirical comparison harness.
    For each attack family, generates n_repetitions score samples and
    measures per-primitive and ensemble detection rates.
    Returns {family_name: {primitive: detection_rate}}.
    '''
    cfg = config or EnsembleConfig()
    rng = np.random.default_rng(seed=rng_seed)
    results: Dict[str, Dict[str, float]] = {}

    for family in attack_families:
        detections: Dict[str, int] = {
            'query_pattern': 0, 'ood': 0, 'boundary': 0,
            'entropy': 0, 'concentration': 0, 'ensemble': 0,
        }
        for rep in range(n_repetitions):
            scores = family.score_generator(rep)
            result = compute_ensemble(scores, cfg)
            if scores.query_pattern >= cfg.individual_alert_threshold:
                detections['query_pattern'] += 1
            if scores.ood >= cfg.individual_alert_threshold:
                detections['ood'] += 1
            if scores.boundary >= cfg.individual_alert_threshold:
                detections['boundary'] += 1
            if scores.entropy >= cfg.individual_alert_threshold:
                detections['entropy'] += 1
            if scores.concentration >= cfg.individual_alert_threshold:
                detections['concentration'] += 1
            if result.action in ('alert_tier1_rate_limit', 'alert_tier2'):
                detections['ensemble'] += 1
        results[family.name] = {
            k: round(v / n_repetitions, 3) for k, v in detections.items()
        }
    return results


def render_comparison(results: Dict[str, Dict[str, float]]) -> None:
    primitives = ['query_pattern', 'ood', 'boundary', 'entropy', 'concentration', 'ensemble']
    header = '%-35s' % 'Attack Family'
    for p in primitives:
        header += '%12s' % p[:11]
    print(header)
    print('-' * (35 + 12 * len(primitives)))
    for family, rates in results.items():
        row = '%-35s' % family[:34]
        for p in primitives:
            rate = rates.get(p, 0.0)
            row += '%11.1f%%' % (rate * 100)
        print(row)

Common Mistakes

Id

1

Description

Deploying primitives with default thresholds without calibrating on the deployment's legitimate traffic

Why It Happens

Default thresholds feel safe because they were designed conservatively. Calibration on legitimate traffic requires operational effort -- 30 to 90 days of logging, data analysis, and threshold tuning. Teams skip calibration to get the detection system deployed faster.

Consequence

A coding assistant deployment with high legitimate query diversity triggers the query diversity monitor''s default threshold continuously. False positive rates above 5 percent cause alert fatigue, and the security team begins ignoring extraction alerts. The primitive that was supposed to protect the deployment has made it blind.

Correct Approach

Calibrate every primitive on at least 30 days of observed legitimate traffic before enabling alerts. For each primitive, set the threshold at the 99th percentile of the score distribution on legitimate traffic (1 percent false positive rate) rather than at a universal default. The detection ensemble harness (Deliverable 6) includes a calibration mode that measures the score distribution on legitimate traffic; use it before any threshold is locked.

Id

2

Description

Treating the ensemble composite score as a replacement for individual primitive scores

Why It Happens

The composite score is simpler to monitor than five individual scores. Teams route only the composite to their alerting system and discard the per-primitive breakdown, treating the composite as the signal.

Consequence

The composite score can mask individual primitive spikes if compensating primitives have low scores. A boundary query detector score of 0.95 with all other primitives at 0.10 produces a composite of approximately 0.24 (0.25 * 0.95 + 0.75 * 0.10) -- below the alert threshold -- even though the boundary detector is firing at near-maximum confidence. Individual primitive thresholds are required in addition to the composite threshold, as the ensemble config explicitly specifies.

Correct Approach

Configure both composite and individual thresholds in the EnsembleConfig. Route individual primitive alerts to the security team regardless of the composite score. The compute_ensemble() function in Deliverable 6 already implements individual alert routing; the Section 9.11 query monitor preserves this output and routes it to the appropriate response tier.

Id

3

Description

Building the OOD detector on the full model training distribution rather than the deployment's expected input distribution

Why It Happens

The model''s training distribution and the deployment''s legitimate user distribution are conflated. The model was trained on a broad distribution; the deployment serves a narrow use case. Building the isolation forest on the training distribution''s embeddings makes it too permissive for the deployment''s actual input scope.

Consequence

The OOD detector accepts many inputs as in-distribution that are outside the deployment''s legitimate scope but within the model''s training distribution. A customer service assistant''s OOD detector trained on the model''s general training distribution will not flag boundary-probing queries drawn from the model''s broader capability domain.

Correct Approach

Train the isolation forest on the deployment''s observed legitimate query embeddings, not on the model''s training data. The legitimate query distribution for a customer service deployment is narrower than the model''s training distribution and produces a more sensitive OOD detector for that specific deployment context.

Id

4

Description

Omitting the user concentration analyser from the ensemble because it duplicates the query pattern analyser's diversity signal

Why It Happens

Both the query pattern analyser and the user concentration analyser measure semantic diversity. They look redundant: if the query pattern analyser already has a diversity sub-signal, why add a separate concentration analyser?

Consequence

The query pattern analyser''s diversity sub-signal is designed to detect low diversity across the window''s topic distribution -- it is sensitive to high mean pairwise similarity in an absolute sense. The user concentration analyser is designed to detect concentration relative to the legitimate user population -- it is sensitive to users who are more concentrated than the 95th percentile of legitimate users even when the absolute concentration is not extreme. Fidelity extraction and prompt extraction produce concentration above the legitimate population''s range that the absolute diversity signal underweights. Removing the concentration analyser leaves these attack classes underdetected.

Correct Approach

Keep both primitives. The query pattern analyser''s diversity sub-signal is an absolute measure; the user concentration analyser is a relative measure calibrated against the user population. Both are needed because legitimate users vary widely in absolute diversity -- a specialist user querying a narrow domain legitimately has high absolute concentration but typical relative concentration. The relative measure distinguishes them from adversaries; the absolute measure does not.

Id

5

Description

Running the empirical comparison harness only once during initial deployment and never rerunning it

Why It Happens

The harness produces detection rate numbers. The numbers look good. The team files them in the initial deployment documentation and moves on. Rerunning the harness requires engineering time and is deprioritised against feature work.

Consequence

The legitimate traffic distribution shifts over time as the product evolves and user behaviour changes. Thresholds calibrated on the initial legitimate traffic distribution become miscalibrated. Attack techniques also evolve: an adversary who has read this chapter and knows the detection thresholds can tune their attack to stay below them. The harness provides detection rates against the attacks it simulates; it does not provide detection rates against novel attack variants. Quarterly re-calibration and red team exercises are required to maintain detection coverage.

Correct Approach

Rerun the empirical comparison harness quarterly as part of the security review cycle. Update the legitimate traffic baseline used for calibration with recent traffic samples. Run a red team exercise alongside the harness to test detection against novel technique variants not covered by the synthetic attack families in the harness. The harness is a calibration tool, not a one-time certification.

Section Summary

Compact

Five detection primitives cover the full extraction and privacy attack catalogue from Chapter 9. The query pattern analyser tracks distributional anomaly across a user''s sliding window -- query diversity for functionality extraction, boundary proximity for boundary extraction, meta-query rate for prompt extraction. The OOD detector flags queries outside the deployment''s legitimate input distribution using isolation forest. The boundary query detector identifies near-opposite-label input pairs in the (embedding, label) history, using k-d tree indexed nearest-neighbour search for latency compatibility. The output entropy monitor scores per-response information leakage risk from the model''s output distribution and flags token-count anomalies for economic abuse detection. The user concentration analyser measures per-user semantic clustering relative to the legitimate user population -- the unique signal for fidelity and prompt extraction. All five are combined in a weighted ensemble with separate composite and individual thresholds, routing to three action tiers: monitor, alert-tier-2, and alert-tier-1-rate-limit. No single primitive covers the full catalogue; the ensemble achieves 88 to 98 percent detection rates across most attack families, with benchmark-distribution LLM distillation as the known gap (30 to 40 percent) that output watermarking addresses post-hoc.

Key Takeaways

  • Five orthogonal primitives are required; no single primitive covers the full extraction attack catalogue
  • All primitives must be calibrated on legitimate deployment traffic before enabling alerts -- defaults produce unacceptable false positive rates
  • Individual primitive thresholds are required alongside the composite; a 0.95 boundary score must fire even when the composite is below threshold
  • The user concentration analyser is the unique signal for fidelity and prompt extraction; removing it leaves those attack classes underdetected
  • Benchmark-distribution LLM distillation achieves only 30-40% ensemble detection rate -- this is the gap that output watermarking addresses
  • The empirical comparison harness must be rerun quarterly; detection rates degrade as traffic and attack techniques evolve
