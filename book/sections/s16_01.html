Chapter 16 · Section 1 · ~6 pages

SIEM Integration Taxonomy: From Detections to Security Operations

Section Overview

One Line Summary

A detection that never reaches a security analyst is not actioned. Section 16.01 is the map of how the Chapter 15 detector suite integrates with security operations: one detection-event schema feeding three kinds of integration -- portable Sigma rules, platform connectors for Splunk, Datadog, and Elastic, and a custom webhook with alert enrichment -- so every following section builds one integration against a shared contract rather than a one-off export.

Why This Section Exists

Part 4 has built the detector suite (Chapter 15) and deployed it on the production gateway (Chapter 14). The suite produces detections. But a detection is an internal signal until it reaches the tooling a security team actually watches, and that tooling is the SIEM. This section is the anchor for Chapter 16, mirroring the taxonomy anchors of 12.01, 13.01, 14.01, and 15.01, and it makes three commitments the rest of the chapter honours. First, there is one detection-event schema. A detector produces a DetectorResult in the Chapter 15 shape; the integration layer turns it into a platform-neutral DetectionEvent that carries the verdict, the severity, the scores, the evidence, and the request context. Every integration consumes that event and nothing else, so a detection is expressed once and delivered everywhere. Second, the integration surface has three parts: Sigma rules as portable detection logic that any platform can evaluate, platform connectors that push events into Splunk, Datadog, and Elastic, and alert enrichment that adds the Chapter 13 behavioural context, IOCs, and response actions to a raw detection. Third, the goal is automated rule deployment -- the generated Sigma rules and the connectors stay in sync with the deployed detectors rather than drifting from them. State these once here and the rest of the chapter is a deliberate build against them.

Position In Chapter

Section 16.01 is the taxonomy anchor for the six sections that follow. It defines the detection-event schema that 16.02's Sigma generator and every connector in 16.03-16.06 translate from, states the push-versus-pull model those connectors are classified under, and sets the roadmap the summary (16.07) synthesises. The detection-event schema introduced here is the single artifact every subsequent section depends on.

Prose Content

Part 1

Title

Why Detections Must Reach Security Operations

Body

The detector suite of Chapter 15 is correct, fast, and deployed. It produces a verdict on every request, with a score, a confidence, and the evidence behind the decision. And none of that matters operationally until it reaches a human who can act on it. A detection that is computed and then left inside the gateway is a tree falling in an empty forest: the work happened, but nothing follows from it. The place a security team watches -- where alerts are triaged, correlated with other signals, and turned into a response -- is the SIEM. So the last mile of the detector suite is not more detection; it is delivery. This reframes integration from an afterthought into the step that turns the suite from a signal source into an operational capability. The argument of the whole chapter follows from it. If delivery is what makes a detection useful, then the integration must speak the SIEM's language rather than the detector's: it must produce events the platform can ingest, rules the platform can evaluate, and alerts a responder can act on without reconstructing the context from scratch. The rest of this section lays out the surface that does that, and the rest of the chapter builds it.

Part 2

Title

The Integration Surface: Sigma, Connectors, Enrichment

Body

The integration surface has three parts, and they answer three different questions. Sigma rules answer 'how does the detection logic run on a platform we do not control?' Sigma is portable, platform-agnostic detection logic -- a rule expressed once in a neutral format that Splunk, Elastic, and other platforms can each compile to their own query language. Generating Sigma rules from the detectors means the detection logic deploys anywhere without being rewritten per platform, and, because it is generated rather than hand-authored, it stays in sync with the detectors instead of drifting from them. Platform connectors answer 'how do the detections themselves get into the platform?' A connector pushes detection events into a specific SIEM through its ingestion API -- Splunk's HTTP Event Collector, Datadog's Logs API, Elastic's Logstash pipelines -- mapping the shared event schema to that platform's field model so a detection becomes a searchable, alertable record there. Alert enrichment answers 'how does a raw detection become something a responder can act on?' A bare detection is an isolated event; enrichment adds the entity, session, and graph context of Chapter 13, the IOCs the detection implies, and the response actions available, so the alert arrives with the story already attached. Three parts, three questions, one detector suite behind all of them.

Part 3

Title

The Platforms and the Push-Versus-Pull Model

Body

Chapter 16 integrates four kinds of destination: Splunk, Datadog, the Elastic Stack, and a custom webhook path for anything else. The first three are the common enterprise SIEM and observability platforms, each with a dedicated connector; the fourth is the escape hatch, a documented webhook contract that lets the suite deliver to any platform without a bespoke connector. Between them they cover the realistic deployment landscape: a team is on one of the big three, or it is on something else that can receive an HTTP POST. Cutting across the platforms is a model distinction worth naming up front. In a push integration, the gateway sends events to the platform -- it owns delivery, and the event arrives with low latency the moment the detection is made. The Splunk, Datadog, Elastic, and custom-webhook connectors are all push. In a pull integration, the platform fetches or evaluates rules against events it already holds -- the Sigma path is effectively pull, because the generated rules run on the platform against data it has ingested, with no per-event delivery from the gateway. The distinction matters because it decides who owns delivery and what the latency and coupling look like, and every connector section states which model it uses so the trade-off is explicit rather than buried.

Part 4

Title

The Detection-Event Schema: The Integration Contract

Body

Everything downstream consumes one object: the detection event. A detector produces a DetectorResult in the Chapter 15 shape -- detector name, verdict, score, confidence, latency, and evidence. That is the right shape for a detector to return, but it is the wrong shape to ship to a SIEM: it has no timestamp, no request context, no severity a platform can sort on, no room for IOCs, and it carries a Python enum rather than a serialisable value. The detection-event schema closes that gap. It wraps the DetectorResult with the request context (request id, session, surface, the emitting source), a timestamp, a severity derived from the verdict and confidence, and slots for evidence, IOCs, and labels -- all as plain, serialisable data. Building the event in one place is the point. There is exactly one function that turns a DetectorResult into a DetectionEvent, and every integration starts from the event it returns, never from the raw result. That single choke point is what makes the schema a contract: the Sigma generator, the three connectors, and the enrichment pipeline all translate from the same object, so a detection is expressed once and delivered to every platform consistently. Add a field to the event and every integration sees it; change how severity is derived and every platform sorts the same new way. The severity mapping itself lives in the schema, not in each connector, precisely so the platforms cannot disagree about how urgent a detection is. The schema is the small, boring, central artifact that the rest of the chapter leans on.

Part 5

Title

Automated Rule Deployment and the Chapter Roadmap

Body

The last commitment is that the integration is automated, not manual. A detection system where an engineer hand-translates each detector into a SIEM rule has a drift problem built in: the moment a detector changes, the SIEM rule that mirrors it is stale, and the gap between what the suite detects and what the SIEM evaluates grows silently until an incident reveals it. Automated rule deployment removes that gap. The Sigma rules are generated from the detectors, so regenerating them after a detector change keeps the SIEM logic current by construction, and the connectors push live events rather than depending on a rule someone remembered to update. Keeping the SIEM in sync with the detectors is a first-class goal, not a maintenance chore. The chapter follows the surface directly. Section 16.02 builds the Sigma rule generator -- the portable logic. Sections 16.03, 16.04, and 16.05 build the three platform connectors -- Splunk via HEC, Datadog via the Logs API and metrics, and Elastic via Logstash pipelines -- each mapping the detection-event schema to its platform and each stating its integration model. Section 16.06 builds the custom webhook path for any other platform and the alert enrichment pipeline that makes the delivered detections actionable, drawing in the Chapter 13 behavioural context. Section 16.07 synthesises the integration and previews Chapter 17, where the detections now flowing into the SIEM feed the monitoring and tuning loops that improve the detectors over time. Each following section is a response to a named part of this taxonomy.

Deliverable 1

Title

The Detection-Event Schema

Filename

detection_event_schema.py

Description

The one schema every SIEM integration consumes. It carries over the Chapter 15 Section 15.01 DetectorResult, adds a Severity enum with a deliberate verdict-and-confidence mapping, and defines the DetectionEvent dataclass plus the single build_event function that turns a DetectorResult and request context into a platform-neutral, serialisable event. Every integration in the chapter starts from the event this returns.

Implementation Notes

Python 3.12, single quotes throughout per book convention, standard-library json, time, dataclasses, enum, and typing only. The DetectorResult and Evidence types are reproduced inline so the file runs standalone; in the suite they are imported from detector_api_contract.py. The severity mapping lives here, not in each connector, so every platform sorts detections identically. The __main__ block builds an event and round-trips it through JSON.

Code

# detection_event_schema.py
# Section 16.01: The Detection-Event Schema
# 20260121 | AI Security Mastery -- Chapter 16 by Raghav Dinesh
# Single quotes throughout per book convention
#
# The one schema every SIEM integration consumes. A detector produces a
# DetectorResult (Chapter 15 Section 15.01); the integration layer needs a
# platform-neutral, serialisable event carrying the verdict, the scores, the
# evidence, and the request context. This schema is that contract: a detection
# is expressed once as a DetectionEvent and delivered to every platform --
# Sigma, Splunk, Datadog, Elastic, custom -- through it.

import json
import time
from dataclasses import dataclass, field, asdict
from enum import Enum
from typing import Any, Dict, List, Optional


# --- Carried over from Chapter 15 Section 15.01 -----------------------------
# Reproduced so this file runs standalone. In the suite these are imported from
# detector_api_contract.py and every detector and integration shares them.

class Verdict(Enum):
    ALLOW = 'allow'
    FLAG = 'flag'
    BLOCK = 'block'


@dataclass
class Evidence:
    source: str
    label: str
    detail: str = ''


@dataclass
class DetectorResult:
    detector: str
    verdict: Verdict
    score: float
    confidence: float
    latency_ms: float
    evidence: List[Evidence] = field(default_factory=list)


# --- Severity: the operational urgency the SIEM sorts on --------------------
# The verdict says what the detector decided; severity says how much a responder
# should care. The mapping is deliberate and lives here, not in each connector,
# so every platform sorts detections the same way.

class Severity(Enum):
    INFO = 'info'
    LOW = 'low'
    MEDIUM = 'medium'
    HIGH = 'high'
    CRITICAL = 'critical'


_VERDICT_SEVERITY = {
    Verdict.ALLOW: Severity.INFO,
    Verdict.FLAG: Severity.MEDIUM,
    Verdict.BLOCK: Severity.HIGH,
}


def severity_for(verdict: Verdict, confidence: float) -> Severity:
    '''Map a verdict and confidence to an operational severity. A high-confidence
    block is critical; a low-confidence flag drops to low. The SIEM sorts on this.'''
    base = _VERDICT_SEVERITY[verdict]
    if verdict is Verdict.BLOCK and confidence >= 0.9:
        return Severity.CRITICAL
    if verdict is Verdict.FLAG and confidence < 0.5:
        return Severity.LOW
    return base


# --- The detection-event schema ---------------------------------------------

SCHEMA_VERSION = '1.0'


@dataclass
class DetectionEvent:
    '''The platform-neutral detection event every integration consumes. Built
    from a Chapter 15 DetectorResult plus the request context, it is the single
    contract that Sigma generation and every connector translate from.'''
    schema_version: str
    event_id: str
    timestamp: str                          # ISO 8601 UTC
    detector: str
    verdict: str                            # Verdict value
    severity: str                           # Severity value
    score: float
    confidence: float
    latency_ms: float
    surface: str                            # 'input' or 'output'
    request_id: str
    session_id: Optional[str]
    source: str                             # the gateway/service emitting the event
    evidence: List[Dict[str, str]] = field(default_factory=list)
    iocs: List[Dict[str, str]] = field(default_factory=list)
    labels: Dict[str, str] = field(default_factory=dict)

    def to_dict(self) -> Dict[str, Any]:
        return asdict(self)

    def to_json(self) -> str:
        return json.dumps(self.to_dict(), separators=(',', ':'), sort_keys=True)


def _iso_now() -> str:
    return time.strftime('%Y-%m-%dT%H:%M:%SZ', time.gmtime())


def build_event(result: DetectorResult, *, request_id: str, surface: str = 'input',
                session_id: Optional[str] = None, source: str = 'detection-gateway',
                event_id: Optional[str] = None, timestamp: Optional[str] = None,
                labels: Optional[Dict[str, str]] = None) -> DetectionEvent:
    '''Construct a DetectionEvent from a DetectorResult and request context. This
    is the one place a DetectorResult becomes a platform-neutral event; every
    integration starts from the event this returns, never from the raw result.'''
    ev = [{'source': e.source, 'label': e.label, 'detail': e.detail} for e in result.evidence]
    sev = severity_for(result.verdict, result.confidence)
    return DetectionEvent(
        schema_version=SCHEMA_VERSION,
        event_id=event_id if event_id is not None else f'{request_id}:{result.detector}',
        timestamp=timestamp if timestamp is not None else _iso_now(),
        detector=result.detector,
        verdict=result.verdict.value,
        severity=sev.value,
        score=round(result.score, 4),
        confidence=round(result.confidence, 4),
        latency_ms=round(result.latency_ms, 4),
        surface=surface,
        request_id=request_id,
        session_id=session_id,
        source=source,
        evidence=ev,
        iocs=[],
        labels=labels if labels is not None else {},
    )


if __name__ == '__main__':
    result = DetectorResult(
        detector='prompt_injection', verdict=Verdict.BLOCK, score=0.92,
        confidence=0.94, latency_ms=3.4,
        evidence=[Evidence('pattern', 'instruction_override', 'ignore previous instructions')])
    event = build_event(result, request_id='req-1001', surface='input',
                        session_id='sess-42', source='prod-gateway-1')
    print('severity :', event.severity)
    print('event_id :', event.event_id)
    parsed = json.loads(event.to_json())
    assert parsed['detector'] == 'prompt_injection'
    assert parsed['severity'] == 'critical'
    assert parsed['schema_version'] == SCHEMA_VERSION
    print('round-trip: ok')

Title

Push-Versus-Pull Integration Model Reference

Filename

integration_model_reference.py

Description

The push-versus-pull model as maintainable data: each platform classified by model and transport with a delivery note stating who owns delivery and what the latency and coupling look like. The connector sections build on this stated model rather than an implicit one.

Implementation Notes

Python 3.12, single quotes throughout per book convention, standard-library dataclasses, enum, and typing only. push_models and pull_models filter the reference so a later section can assert its connector's model. Self-checks by printing the classification and the push/pull counts.

Code

# integration_model_reference.py
# Section 16.01: Push vs Pull Integration Models
# 20260121 | AI Security Mastery -- Chapter 16 by Raghav Dinesh
# Single quotes throughout per book convention
#
# The two ways a detection reaches a SIEM: the gateway pushes events to the
# platform (HEC, Logs API, webhook), or the platform pulls them by evaluating
# rules against events it already holds. This reference states the trade-off and
# classifies each Chapter 16 connector, so the connector sections build on a
# stated model rather than an implicit one.

from dataclasses import dataclass
from enum import Enum
from typing import List


class Model(Enum):
    PUSH = 'push'
    PULL = 'pull'


@dataclass
class IntegrationModel:
    platform: str
    model: Model
    transport: str
    delivery_note: str


REFERENCE: List[IntegrationModel] = [
    IntegrationModel('Splunk', Model.PUSH, 'HTTP Event Collector (HEC)',
                     'Gateway POSTs events to the HEC token endpoint; low latency, gateway owns delivery.'),
    IntegrationModel('Datadog', Model.PUSH, 'Logs API + metrics',
                     'Gateway POSTs logs and submits metrics; near-real-time, gateway owns delivery.'),
    IntegrationModel('Elastic', Model.PUSH, 'Logstash HTTP input',
                     'Gateway POSTs to a Logstash pipeline that transforms and indexes; gateway owns delivery.'),
    IntegrationModel('Custom SIEM', Model.PUSH, 'Webhook contract',
                     'Gateway POSTs to an arbitrary endpoint on a documented contract; covers any platform.'),
    IntegrationModel('Sigma-based SIEM', Model.PULL, 'Generated Sigma rules',
                     'Platform evaluates Sigma rules against events it already ingests; portable, no bespoke connector.'),
]


def push_models() -> List[IntegrationModel]:
    return [m for m in REFERENCE if m.model is Model.PUSH]


def pull_models() -> List[IntegrationModel]:
    return [m for m in REFERENCE if m.model is Model.PULL]


if __name__ == '__main__':
    for m in REFERENCE:
        print(f'{m.platform:16} [{m.model.value:4}] {m.transport}')
    print(f'\npush: {len(push_models())}  pull: {len(pull_models())}')
    assert len(push_models()) == 4 and len(pull_models()) == 1
    print('classification ok')

Common Mistakes

Mistake 1

Description

Computing detections but never delivering them to the SIEM the security team watches

Why It Happens

The detector suite is the hard, interesting engineering, and once it produces correct verdicts the work feels done. Delivery looks like plumbing.

Consequence

The detections exist only inside the gateway. No analyst sees them, no alert fires, and the suite's correct verdicts change nothing operationally -- the detection is a tree falling in an empty forest.

Correct Approach

Treat delivery as the last mile of the suite. Integrate the detections into the SIEM where triage, correlation, and response actually happen, so a correct verdict becomes an actioned alert.

Mistake 2

Description

Writing a separate ad-hoc export for each platform instead of one shared event schema

Why It Happens

Each platform has its own API, so it seems natural to write directly to each one, shaping the payload per platform as you go.

Consequence

The detection is expressed differently for every platform, the mappings drift apart, and a change to what a detection carries has to be made in every export by hand -- the integrations disagree about the same detection.

Correct Approach

Define one detection-event schema and build it in one place. Every connector translates from the same event, so a detection is expressed once and delivered to every platform consistently.

Mistake 3

Description

Deriving severity inside each connector, so the platforms disagree about how urgent a detection is

Why It Happens

Severity feels like a presentation detail each platform can decide for itself, and it is easy to add a quick mapping wherever the connector formats its payload.

Consequence

The same detection is critical in Splunk and medium in Datadog because each connector mapped it differently, so an analyst's sense of urgency depends on which console they happen to be looking at.

Correct Approach

Derive severity once, in the schema, from the verdict and confidence. Every connector carries the severity the event already has, so the platforms sort detections the same way.

Mistake 4

Description

Hand-translating detectors into SIEM rules instead of generating and deploying them automatically

Why It Happens

Writing one SIEM rule by hand is quick, and the drift it introduces is invisible until much later.

Consequence

Every detector change leaves the hand-written SIEM rule stale, and the gap between what the suite detects and what the SIEM evaluates grows silently until an incident exposes it.

Correct Approach

Generate Sigma rules from the detectors and push live events through the connectors, so the SIEM logic stays in sync with the deployed detectors by construction rather than by memory.
