Title

The Detection-First Framework: Five Fields Per Technique

Content

how_to_use_this_section: | Section 5.7 gave you the vocabulary. This section is the practitioner's reference. For every ATLAS technique you get five fields a detection engineer needs to actually build a detection rule: (1) attack_pattern — what the adversary does in concrete terms (2) observables — signals left in your data (3) data_source — which log stream contains those signals (4) detection_logic — the condition that fires an alert (5) difficulty — low / medium / high + false-positive profile This is detection-first, not attacker-first. The goal is a detection programme covering observable behaviours, not a deep adversary simulation. detection_difficulty_taxonomy: low_difficulty: definition: "Signal is unambiguous, data source is commonly available, FP near zero without tuning." detection_approach: "Signature-based — exact match or threshold, minimal tuning." examples: - "AML.T0019 — pickle magic bytes at intake (zero FP if format check implemented)" - "AML.T0029 — token cost spike 3x above rolling average" medium_difficulty: definition: "Signal detectable but requires baseline calibration or multi-source correlation." detection_approach: "Threshold-based with baseline — calibrate per deployment, suppress known FP." examples: - "AML.T0040 — high-volume diverse API queries (FP from legitimate batch jobs)" - "AML.T0043 — near-identical consecutive queries (FP from retry logic)" high_difficulty: definition: "Requires long-window behavioural baselines, or technique occurs off-network." detection_approach: "Behavioural baseline (Chapter 13) or indirect via correlated signals." examples: - "AML.T0015 — model evasion (no signal at inference time without adversarial detector)" - "AML.T0005 — proxy model creation (entirely off-network)"

Persistence and Attack Staging Techniques

Content

group_note: | ML persistence techniques are invisible to standard accuracy benchmarks. Only proactive trigger-probe testing and canary tokens provide reliable detection. Attack staging leaves API signals during adversary verification phases — the most detectable window in an otherwise stealthy staging campaign. aml_t0018: id: "AML.T0018" name: "Backdoor ML Model" tactic: "Persistence in ML" attack_pattern: | Modify model weights to respond to a trigger pattern with adversary- controlled output. Trigger may be a visual watermark, a specific phrase, or an imperceptible perturbation. Model performs normally on standard benchmarks — backdoor is invisible without trigger-probe testing. observables: - "Behavioural regression failure on trigger-probe test suite" - "Canary token activation in model output" - "Output distribution anomaly on trigger-adjacent inputs" data_source: "Behavioural regression test log; canary monitor" detection_logic: | safety_test_failures > 0 ON current_checkpoint OR canary_trigger_fired == true difficulty: "medium" key_insight: | Invisible to standard accuracy evals. A model with 99% MMLU accuracy may carry a perfect backdoor. Trigger-probe testing and canary tokens are the only reliable detection mechanisms. fp_notes: "Regression failures from legitimate updates — maintain per-version golden baseline" aml_t0020: id: "AML.T0020" name: "Poison Training Data" tactic: "Persistence in ML" attack_pattern: | Inject malicious examples into training data: label flipping, backdoor trigger insertion, feature injection, or data availability attacks. Poisoned data persists in the training corpus, surviving retraining cycles. observables: - "Unauthorised write to training data directory or S3 training bucket" - "Label distribution anomaly (KL divergence spike) in recent batch" - "Dataset hash change since last verified snapshot" data_source: "Filesystem/IAM access log; dataset integrity monitor" detection_logic: | write_to_training_data BY identity NOT IN authorised_data_writers OR label_distribution_KL_divergence > threshold FROM baseline OR dataset_hash != last_verified_hash difficulty: "medium" fp_notes: "Legitimate data updates trigger distribution alerts — calibrate per update cadence" aml_t0042: id: "AML.T0042" name: "Verify Attack" tactic: "ML Attack Staging" attack_pattern: | Before deploying a full attack, adversary verifies payload efficacy by probing the production API with near-attack inputs. This verification phase produces a distinctive pattern: diversity drops sharply after a high-diversity recon phase as adversary narrows to one payload. observables: - "Input diversity score drops from >0.7 to <0.2 in 10-minute window" - "Burst of near-identical inputs with small systematic variations" - "Pre-attack pattern: high diversity (recon) to low diversity (verify)" data_source: "API request log — per-account input pattern time series" detection_logic: | diversity_drops FROM > 0.7 TO < 0.2 in 10min_window AND edit_distance(consecutive_inputs) < 10 AND count > 15 difficulty: "medium" fp_notes: "Retry logic and idempotent requests — suppress known retry patterns" aml_t0043: id: "AML.T0043" name: "Craft Adversarial Data" tactic: "ML Attack Staging" attack_pattern: | Generate inputs exploiting model decision boundaries: [000] Black-box: query-based perturbation (NES, SPSA, zeroth-order methods) [001] White-box: gradient-based (FGSM, PGD, C&W) — requires weight access [002] Backdoor trigger: embed trigger patterns in training examples observables: - "Consecutive inputs with l2-distance < 0.05 over many iterations (black-box)" - "Unusual rare-pattern frequency in submitted training data (backdoor)" data_source: "API request log (black-box); training data log (backdoor)" detection_logic: | consecutive_input_l2_distance < 0.05 AND count > 20 in 5min [black-box] OR rare_pattern_frequency_in_training_data > 3x_baseline [backdoor] difficulty: "medium (black-box, backdoor) / high (white-box)" fp_notes: "Temperature-based sampling retries — calibrate l2 threshold per application" aml_t0046: id: "AML.T0043" name: "Craft Adversarial Patches" tactic: "ML Attack Staging" attack_pattern: | Generate printable patch (sticker, overlay) that causes physical-world misclassification by an image classifier. Patch must be robust to printing variation, viewing angle, and lighting changes. Primarily relevant to vision systems: autonomous vehicles, surveillance, face recognition. observables: - "Images with unusual high-frequency texture in critical regions" - "Systematic rotational/scale variants of the same image submitted" data_source: "Image preprocessing pipeline log; API request log" detection_logic: | high_freq_texture_anomaly > threshold IN sign_or_face_region OR near_rotational_duplicate_submissions > 10 in 5min difficulty: "high" fp_notes: "Legitimate high-texture images — requires dedicated adversarial patch detector"

@dataclass

def _run(steps: List[ChainStep],
         rules: Dict[str, bool]) -> List[ChainStep]:
    for s in steps:
        s.detected = rules.get(s.technique_id, False)
        s.note = (f"Alert on {s.data_source}" if s.detected
                  else f"MISSED — no rule for {s.technique_id}")
    return steps

def assess_coverage(covered_ids: List[str]) -> Dict:
    covered = [t for t in TOP_10 if t["id"] in covered_ids]
    missing = [t for t in TOP_10 if t["id"] not in covered_ids]
    by_tactic: Dict[str, Dict] = {}
    for t in TOP_10:
        tac = t["tactic"]
        if tac not in by_tactic:
            by_tactic[tac] = {"covered": 0, "total": 0}
        by_tactic[tac]["total"] += 1
        if t["id"] in covered_ids:
            by_tactic[tac]["covered"] += 1
    return {
        "top10_covered": len(covered),
        "top10_total": len(TOP_10),
        "top10_pct": round(len(covered) / len(TOP_10) * 100, 1),
        "missing": [{"id": t["id"], "name": t["name"]} for t in missing],
        "per_tactic": by_tactic,
    }

Takeaway 02

AML.T0010 (supply chain) and AML.T0029 (DoS) both score 100 in the priority matrix (prevalence × detectability × impact). Both are low-difficulty, near- zero FP, and immediately implementable. Any detection programme that does not cover these two techniques has a critical gap regardless of everything else it covers.

Takeaway 03

High-difficulty techniques (AML.T0015, AML.T0005, AML.T0043) are not undetectable — they require behavioural baselines and statistical monitoring rather than signature-based rules. The correct response to "high difficulty" is not to skip the technique but to sequence it after the statistical baseline infrastructure is in place (Chapter 13).

Takeaway 04

Technique chaining is how real attacks work. The extraction campaign (T0001 → T0005 → T0040 → T0025 → T0042) is undetectable by a programme with only T0019 and T0029 rules, even though those two techniques have perfect scores. Coverage must address complete chains, not individual techniques in isolation.

Takeaway 05

Correlation rules — detecting technique A followed by technique B within a time window — dramatically increase detection fidelity for multi-step campaigns. A T0040 probe alert has a 10% false-positive rate alone; the same alert combined with a T0025 sustained query campaign on the same account has near-zero FP.

Takeaway 06

AML.T0018 (backdoor) is invisible to standard accuracy benchmarks. A model achieving 99% on MMLU may carry a perfect trigger-activated backdoor. The only reliable detection mechanisms are: (a) a trigger-probe test suite run on every checkpoint, and (b) canary tokens injected into training data. Neither is available without proactive investment.

Takeaway 07

The ATLAS coverage score (covered techniques / total techniques) is a defensible stakeholder metric. Starting from zero, implementing the top-6 priority techniques (T0019, T0029, T0056, T0035, T0053, T0020) with two to four days of engineering effort each yields approximately 20% coverage and blocks the most prevalent and immediately exploitable vectors.

Takeaway 08

The Sigma stubs generated in this section are the seed set for Chapter 11. Every stub is tagged with atlas.aml.TXXXX and owasp.LLMXX references, enabling a detection programme that is simultaneously ATLAS-aligned and OWASP-aligned — two frameworks, one set of rules.
