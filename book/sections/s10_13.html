Prose Content

Part 1

Title

Design Brief: Track 7 as the Gateway's Unique Pre-Inference Track

Body

The six-track gateway assembled across Chapters 6, 7, and 9 runs all detection tracks in parallel with the main model inference and aggregates their results post-request. Every track in Tracks 1-6 operates on the request as delivered: the input is sent to the model, the tracks observe the same unmodified input and the model''s output, and detection decisions are made based on the unmodified signal. No track in Chapters 6-9 changes what the model sees before the model responds. Track 7 breaks this pattern. Feature squeezing (Section 10.11) requires transforming the input before the model processes it. The detection signal is the comparison between what the model says about the original input and what it says about the squeezed input. If the squeezer runs after the model, there is no comparison with the primary inference -- only a secondary inference on a transformed version. The result is still informative (squeezer disagreement with the transformed prediction vs a natural-image reference), but the semantically richer detection signal (original prediction changed by squeezing) requires the squeezer to run before or alongside the main inference. This creates Track 7''s architectural signature: a pre-inference stage and a post-inference stage. The pre-inference stage applies the squeezer transform (fast, ~1-3ms) and dispatches parallel model inference on the squeezed input alongside the primary model inference. Both inferences complete before the gateway produces its response; the squeezer disagreement is computed from the two parallel inference outputs. The post-inference stage runs the consistency checker (N variants on the main model) and the adversarial classifier (on the original input) after the primary inference completes.

Part 2

Title

Pre-Inference Stage: Parallel Squeezer Execution

Body

The pre-inference stage executes as follows. When a request arrives at the gateway: Step 1 -- Squeezer transform (synchronous, <3ms): apply each squeezer in the ensemble to the input tensor. These are fast tensor operations (Gaussian convolution, rounding, bilinear resize) that complete in 1-3ms on CPU or sub-millisecond on GPU. The transforms are deterministic and do not require a model forward pass. Step 2 -- Parallel inference dispatch (async): dispatch three concurrent tasks: (a) primary model inference on the original input, (b) squeezer model inferences on each squeezed variant (one per squeezer), (c) adversarial detector classifier on the original input (feature extraction + linear). Step 3 -- Wait for completion: all parallel tasks complete within approximately one model inference time (20ms for a medium model), because they run concurrently. The squeezer inferences have the same model and the same latency as the primary inference; they just operate on slightly different inputs. Step 4 -- Pre-inference squeezer decision: compare primary inference output with each squeezer inference output. Compute the squeezer disagreement scores. If any squeezer score exceeds the high-confidence threshold (block tier), the gateway may reject the request immediately without waiting for the post-inference stage. This is the early-exit optimisation for obvious adversarial inputs. The latency model with parallel execution: total pre-inference latency = squeezer_transform + max(primary_inference, squeezer_inference). Since both inferences use the same model, max is approximately one inference time. The squeezer_transform overhead is 1-3ms. The parallelisation effectively costs one inference time regardless of the number of squeezers in the ensemble.

Part 3

Title

Post-Inference Stage: Consistency Check and Adversarial Classifier

Body

The post-inference stage runs after the primary model inference completes. It adds the two remaining detection primitives whose signals depend on the primary model''s output or can reuse the model that just ran. Consistency checking generates N randomly perturbed variants of the input and queries the model on each. Section 10.12 optimised this by batching all N variants in a single forward pass (batch size N vs N separate forward passes). The post-inference consistency check starts immediately after the primary inference: the primary model is still warm, and the N-variant batch uses the same model. The latency is one additional batch forward pass (at batch size N) rather than N sequential passes. The adversarial detector classifier was dispatched in parallel with the primary inference (Step 2c above). Its result is available without additional latency by the time the primary inference completes. No additional wait is needed. Sub-sampling is a viable operational optimisation: run the consistency check on only a fraction (e.g., 10%) of requests and rely on the squeezer ensemble and adversarial classifier for per-request coverage. Sub-sampling reduces average latency at the cost of per-request consistency check coverage. For high-QPS deployments where every microsecond matters, a configurable sub-sample rate (track7_config.consistency_subsample_rate) allows operators to tune the cost-coverage tradeoff without disabling the primitive entirely.

Part 4

Title

Seven-Track Gateway: Unified Response Policy

Body

The unified seven-track gateway produces one response action per request. Each track contributes a score and a fired/not-fired binary decision. The response policy maps the combination of track decisions to an action tier. Action tier structure: BLOCK (immediate reject, 429 Too Many Requests or 403 Forbidden): fired when any track produces a high-confidence signal (score above the block threshold). Used for high-confidence adversarial examples (squeezer score > 0.50), confirmed injection (Track 1-5 high confidence), or confirmed extraction campaign (Track 6 rate-limit hit). The block tier must respond quickly; Track 7 pre-inference squeezer provides the fastest block signal. FLAG (serve response but log and alert): fired when moderate-confidence signals appear across multiple tracks. The request is served normally (the model''s response is returned) but the event is logged to the SIEM with Track 7 scores. Human review queue picks up flagged requests. The flag tier is the correct response for adversarial examples that may be false positives -- preserve user experience while generating an investigation signal. MONITOR (serve response with enhanced telemetry): fired when low-confidence signals appear from individual tracks below the flag threshold. The request is served normally. Enhanced telemetry is attached to the request log (all Track 7 scores captured even though no alert fires). Monitoring data feeds the Track 7 calibration cycle. PASS: no track fired above its threshold. Request is served normally with standard telemetry.

Part 5

Title

AML.T0043/T0015 Sigma Rule: Completing the Chapter 5 Stubs

Body

Chapter 5 Section 5.8 introduced the AML Sigma stub pattern: placeholder detection rules anchored to ATLAS techniques that are completed as each chapter builds the production detection mechanism. Chapter 10 Section 10.13 completes AML.T0043 (Craft Adversarial Data) and AML.T0015 (Evade ML Model) with the Track 7 detection fields. The completed AML.T0043 Sigma rule fires when the Track 7 squeezer ensemble disagreement score exceeds the block or flag threshold. The log source is the AI gateway''s Track 7 telemetry, which must include: the squeezer scores per squeezer (for the highest-sensitivity squeezer), the consistency check score, the adversarial classifier probability, the combined ensemble score, and the action tier decision. These fields are produced by the gateway_track7.py deliverable and stored in a structured log entry per request. AML.T0015 (Evade ML Model) maps to the combined ensemble firing: evidence that adversarial data reached the deployed model and caused or attempted to cause misclassification. The Sigma condition for AML.T0015 uses an OR across the three detection fields: if any primitive fires above its threshold, the evasion attempt is recorded. The rule level is HIGH for block-tier events and MEDIUM for flag-tier events. The Sigma rules include explicit false positive entries: natural inputs near decision boundaries produce squeezer and consistency scores above their thresholds at low but non-zero rates. The false positive entries direct analysts to verify with the adversarial classifier score (which is lower for natural borderline inputs than for adversarial examples) before escalating.

Part 6

Title

Deployment Checklist: Eight Gates Before Track 7 Goes to Production

Body

The eight-item deployment checklist encodes the lessons of Sections 10.11-10.12 and the Section 10.10 incident analysis into a mandatory pre-production gate. Item 1 -- Squeezer threshold calibration on production-representative inputs: the threshold must be set using inputs drawn from the actual production distribution, not from a benchmark dataset. Hard borderline inputs in the production domain produce higher squeezer scores than easy benchmark images; calibrating on benchmarks underestimates the false positive rate. Item 2 -- Consistency check sigma and N calibration: sigma must be < adversarial_epsilon/4; N must be sufficient for stable disagreement estimates (at least N=20). Both must be validated against the production domain at the expected production QPS (not single-request testing). Item 3 -- Adversarial detector training on deployment-specific attack families: the detector must include adversarial examples generated against the specific model being deployed, not a generic image classifier. Cross-attack generalisation must pass the Section 10.12 test before deployment. Item 4 -- Latency benchmark at production load: measure Track 7 P99 latency under production QPS using the track7_latency_benchmark.py deliverable. Single-request latency is not representative; under load, thread pool contention may push squeezer parallel execution back toward sequential. Item 5 -- Adversarial example test suite coverage: run Track 7 against adversarial examples from all relevant taxonomy cells (FGSM, PGD, C&W, boundary attack, text adversarial for text classifiers, physical patch detector if camera-facing system). Detection rate must meet or exceed the documented coverage targets. Item 6 -- Sigma rule validation: verify that the completed AML.T0043/T0015 Sigma rule fires on known adversarial examples in the test suite and does not fire on the natural input calibration set above the target FPR. Item 7 -- False positive audit on production traffic sample: run Track 7 in monitor-only mode (no blocks or flags) on a sample of production traffic for 24-48 hours; measure the actual FPR. Adjust thresholds if actual FPR exceeds the target. Item 8 -- Circuit breaker configuration: if Track 7 throws unhandled exceptions (model inference failure, OOM, timeout), the gateway must fail open (serve the request without detection) rather than fail closed (block all requests). Configure explicit circuit breaker logic with alerting on Track 7 error rate.

Part 7

Title

Adaptive Adversary and Operational False Positive Management

Body

The adaptive adversary who knows the Track 7 configuration faces a harder optimisation problem than the non-adaptive adversary. They must craft adversarial examples that simultaneously survive: (a) the squeezer ensemble (no detectable squeezer disagreement), (b) the consistency check (prediction stable under N random variants), and (c) the adversarial classifier (input statistics indistinguishable from natural images). As shown in Section 10.12, jointly satisfying all three constraints typically requires larger perturbation budgets or lower attack success rates, raising the attack cost. However, the adaptive adversary advantage is not zero. An adversary who can craft examples against the full three-primitive ensemble (using Section 10.5 adaptive C&W adapted to include all three detection objectives) can achieve 50-60% of the non-adaptive attack success rate against the ensemble. The track7_adaptive_adversary_test.py deliverable measures this gap for the specific deployed configuration. If the gap exceeds 30 percentage points (non-adaptive detection 85%, adaptive detection <55%), the ensemble configuration should be revisited: add a fourth primitive or change squeezer parameters. False positive management is the operational challenge that determines whether Track 7 remains deployed long-term. The track7_calibration_harness.py deliverable tests Track 7 against natural edge-case inputs: low-quality sensor captures, heavily compressed images, unusual colour distributions, natural images of unusual objects near decision boundaries. If the false positive rate on these inputs exceeds 5%, operators will disable Track 7 under load, not because it fails to detect adversarial examples but because the alert volume is unmanageable. Threshold calibration on production-representative hard examples (not just easy benchmark images) is the preventive measure.

# gateway_track7.py
# Section 10.13: Track 7 Production Gateway
# 20260525 | AI Security Mastery by Raghav Dinesh
# Single quotes throughout per book convention

import torch
import torch.nn as nn
from torch import Tensor
from concurrent.futures import ThreadPoolExecutor, as_completed
from dataclasses import dataclass, field
from typing import Optional
from feature_squeezer import build_default_squeezers
from squeezer_ensemble import ensemble_score
from consistency_checker import ConsistencyConfig, consistency_check_score
from adversarial_detector_classifier import (AdversarialDetectorClassifier,
                                              adversarial_detector_score)


@dataclass
class Track7Config:
    block_threshold: float = 0.55
    flag_threshold: float = 0.30
    monitor_threshold: float = 0.15
    squeezer_weight: float = 0.35
    consistency_weight: float = 0.35
    detector_weight: float = 0.30
    consistency_cfg: ConsistencyConfig = field(default_factory=ConsistencyConfig)
    consistency_subsample_rate: float = 1.0  # 1.0 = every request; 0.1 = 10% sampling
    n_workers: int = 4


ACTION_PASS = 'pass'
ACTION_MONITOR = 'monitor'
ACTION_FLAG = 'flag'
ACTION_BLOCK = 'block'


class Track7Gateway:
    '''
    Two-stage Track 7 adversarial detection gateway.
    Pre-inference: squeezer transform + parallel squeezer model inference.
    Post-inference: consistency check + aggregate scores.
    '''
    def __init__(
        self,
        model: nn.Module,
        cfg: Track7Config = None,
        adversarial_detector: Optional[AdversarialDetectorClassifier] = None,
    ):
        self.model = model
        self.cfg = cfg or Track7Config()
        self.squeezers = build_default_squeezers()
        self.detector = adversarial_detector
        self.executor = ThreadPoolExecutor(max_workers=self.cfg.n_workers)

    def _primary_inference(self, x: Tensor) -> Tensor:
        with torch.no_grad():
            return self.model(x)

    def _squeezer_inference(self, x: Tensor) -> Tensor:
        with torch.no_grad():
            return ensemble_score(self.model, x, self.squeezers)

    def _detector_score(self, x: Tensor) -> Tensor:
        if self.detector is None:
            return torch.zeros(x.size(0))
        return adversarial_detector_score(self.detector, x)

    def _should_run_consistency(self) -> bool:
        import random
        return random.random() < self.cfg.consistency_cfg and \
               self.cfg.consistency_subsample_rate >= random.random()

    def process(self, x: Tensor) -> dict:
        '''
        Process one request through Track 7 two-stage gateway.
        Returns result dict with scores, action tier, and telemetry.
        '''
        import random
        cfg = self.cfg

        # --- Pre-inference stage ---
        # Step 1: Squeezer transform (synchronous, fast)
        # (Transforms are applied inside ensemble_score below)

        # Step 2: Dispatch parallel inferences
        fut_primary = self.executor.submit(self._primary_inference, x)
        fut_squeezer = self.executor.submit(self._squeezer_inference, x)
        fut_detector = self.executor.submit(self._detector_score, x)

        # Step 3: Collect parallel results
        primary_logits = fut_primary.result()
        sq_score = fut_squeezer.result()
        det_score = fut_detector.result()

        # Step 4: Pre-inference squeezer decision
        sq_normalised = torch.clamp(sq_score / 1.0, 0.0, 1.0)

        # --- Post-inference stage ---
        # Consistency check (sub-sampled for latency)
        run_cc = random.random() < cfg.consistency_subsample_rate
        if run_cc:
            cc_score = consistency_check_score(self.model, x, cfg.consistency_cfg)
        else:
            cc_score = torch.zeros(x.size(0))

        # Combined ensemble score
        combined = (
            cfg.squeezer_weight * sq_normalised
            + cfg.consistency_weight * cc_score
            + cfg.detector_weight * det_score
        )

        # Action tier decision (per-sample)
        actions = []
        for score in combined.tolist():
            if score >= cfg.block_threshold:
                actions.append(ACTION_BLOCK)
            elif score >= cfg.flag_threshold:
                actions.append(ACTION_FLAG)
            elif score >= cfg.monitor_threshold:
                actions.append(ACTION_MONITOR)
            else:
                actions.append(ACTION_PASS)

        return {
            'primary_logits': primary_logits,
            'squeezer_score': sq_score,
            'consistency_score': cc_score,
            'detector_score': det_score,
            'combined_score': combined,
            'actions': actions,
            'consistency_ran': run_cc,
        }

    def shutdown(self):
        self.executor.shutdown(wait=False)


def demo() -> None:
    try:
        from fgsm_attack import ToyLinear, fgsm
        from adversarial_detector_classifier import train_adversarial_detector
    except ImportError:
        print('Run from directory containing fgsm_attack.py')
        return

    torch.manual_seed(42)
    model = ToyLinear()
    model.eval()
    x_nat = torch.rand(8, 1, 28, 28)
    y = torch.randint(0, 10, (8,))
    eps = 8.0 / 255.0
    x_adv = fgsm(model, x_nat, y, epsilon=eps)

    detector = train_adversarial_detector(model, x_nat, y, n_epochs=15)
    cfg = Track7Config(block_threshold=0.55, flag_threshold=0.30,
                       consistency_subsample_rate=1.0)
    gw = Track7Gateway(model, cfg=cfg, adversarial_detector=detector)

    print('Track 7 Gateway: Natural vs Adversarial')
    print(f'{"Input":<12} {"sq_score":<12} {"cc_score":<12} {"det_score":<10} {"combined":<10} {"actions"}')
    print('-' * 72)
    for label, x_test in [('Natural', x_nat[:4]), ('FGSM', x_adv[:4])]:
        result = gw.process(x_test)
        sq = result['squeezer_score'].mean().item()
        cc = result['consistency_score'].mean().item()
        det = result['detector_score'].mean().item()
        comb = result['combined_score'].mean().item()
        from collections import Counter
        action_counts = Counter(result['actions'])
        print(f'{label:<12} {sq:<12.4f} {cc:<12.4f} {det:<10.4f} {comb:<10.4f} {dict(action_counts)}')

    gw.shutdown()


if __name__ == '__main__':
    demo()

Standalone pre-inference adversarial filter: applies the squeezer ensemble and returns a filter decision before the main model inference; enables early reject for high-confidence adversarial inputs

Code

# adversarial_filter.py
# Section 10.13: Pre-Inference Adversarial Filter
# 20260525 | AI Security Mastery by Raghav Dinesh
# Single quotes throughout per book convention

import torch
import torch.nn as nn
from torch import Tensor
from dataclasses import dataclass
from typing import Tuple, Optional
from feature_squeezer import build_default_squeezers
from squeezer_ensemble import ensemble_score


@dataclass
class FilterConfig:
    block_threshold: float = 0.50   # Reject input above this squeezer score
    flag_threshold: float = 0.20    # Flag for post-inference review


class AdversarialFilter:
    '''
    Pre-inference adversarial filter.
    Wraps a model: filter(x) -> (logits, filter_result).
    If squeezer score >= block_threshold: returns None logits (blocked).
    Otherwise: returns model(x) with filter score attached.
    '''
    def __init__(
        self,
        model: nn.Module,
        cfg: FilterConfig = None,
    ):
        self.model = model
        self.cfg = cfg or FilterConfig()
        self.squeezers = build_default_squeezers()

    def __call__(
        self,
        x: Tensor,
    ) -> Tuple[Optional[Tensor], dict]:
        '''
        Returns (logits_or_none, filter_result_dict).
        logits_or_none is None if blocked; otherwise model output.
        '''
        sq_score = ensemble_score(self.model, x, self.squeezers)
        sq_max = sq_score.max().item()
        sq_mean = sq_score.mean().item()

        if sq_mean >= self.cfg.block_threshold:
            return None, {
                'decision': 'blocked',
                'squeezer_score_mean': sq_mean,
                'squeezer_score_max': sq_max,
            }

        with torch.no_grad():
            logits = self.model(x)

        decision = 'flagged' if sq_mean >= self.cfg.flag_threshold else 'passed'
        return logits, {
            'decision': decision,
            'squeezer_score_mean': sq_mean,
            'squeezer_score_max': sq_max,
        }


def demo() -> None:
    try:
        from fgsm_attack import ToyLinear, fgsm
    except ImportError:
        print('Run from directory containing fgsm_attack.py')
        return

    torch.manual_seed(42)
    model = ToyLinear()
    model.eval()
    x = torch.rand(4, 1, 28, 28)
    y = torch.randint(0, 10, (4,))
    x_adv = fgsm(model, x, y, epsilon=8.0 / 255.0)

    filt = AdversarialFilter(model, FilterConfig(block_threshold=0.20, flag_threshold=0.10))
    for label, x_test in [('Natural', x), ('FGSM', x_adv)]:
        logits, result = filt(x_test)
        blocked = logits is None
        print(f'{label}: decision={result["decision"]}, sq_score={result["squeezer_score_mean"]:.4f}, blocked={blocked}')

    demo()

    Full seven-track gateway.
    Tracks 1-5: injection/jailbreak detection (Chapters 6/7).
    Track 6: query pattern monitor (Chapter 9).
    Track 7: adversarial example detection (Chapter 10).

        self,

            'track_7': t7_result,

import torch.nn as nn
import torch.nn.functional as F

def adaptive_cw_vs_ensemble(
    model: nn.Module,
    x: torch.Tensor,
    y: torch.Tensor,
    n_steps: int = 80,
    lr: float = 5e-3,
    c: float = 1.0,
    kappa: float = 0.0,
) -> torch.Tensor:
    '''
    Adaptive CW: optimises misclassification through the squeezer (ensemble-aware).
    Uses gaussian squeezer as the representative pre-inference transformation.
    Full ensemble adaptive attack would include all primitives; squeezer is primary.
    '''
    batch = x.size(0)
    x_cl = x.clamp(1e-6, 1 - 1e-6)
    w = torch.atanh(2.0 * x_cl - 1.0).detach().requires_grad_(True)
    opt = torch.optim.Adam([w], lr=lr)

    for _ in range(n_steps):
        opt.zero_grad()
        x_adv = 0.5 * (torch.tanh(w) + 1.0)
        l2_sq = (x_adv - x).pow(2).view(batch, -1).sum(1)
        # Adaptive: misclassify on squeezed input (squeezer-aware)
        x_squeezed = gaussian_squeeze(x_adv, sigma=1.0)
        logits = model(x_squeezed)
        z_correct = logits.gather(1, y.view(-1, 1)).squeeze(1)
        mask = torch.ones_like(logits, dtype=torch.bool)
        mask.scatter_(1, y.view(-1, 1), False)
        best_other = logits[mask].view(batch, -1).max(1).values
        f_val = torch.clamp(z_correct - best_other, min=-kappa)
        (l2_sq + c * f_val).sum().backward()
        opt.step()

    with torch.no_grad():
        return (0.5 * (torch.tanh(w) + 1.0)).detach()

Running squeezer model inferences sequentially before the primary model inference, tripling or quadrupling gateway latency

Why It Happens

The pre-inference squeezer stage is described as running "before" the main model. Engineers implement this as a loop: for each squeezer, transform and infer; then run main model. Three squeezers = three additional sequential inferences before the primary.

Consequence

With a 20ms primary model P99, sequential squeezer execution adds 60ms (3 squeezers x 20ms) before the primary model runs. Total Track 7 latency: 80ms, well above the 50ms P99 budget. Latency violations disable Track 7 in production within days of deployment.

Correct Approach

Use ThreadPoolExecutor to dispatch all squeezer inferences and the primary inference concurrently. The gateway_track7.py deliverable implements this with concurrent.futures. Latency overhead is one squeezer_transform_time (~1-3ms) rather than N * model_inference. Always verify parallel execution is actually happening in the benchmark, not accidentally serialised by GIL or batch contention.

Mistake 2

Description

Configuring consistency_subsample_rate=1.0 at high QPS without accounting for the N-variant batch cost at production load

Why It Happens

The consistency check runs N=20 variants as a single batch (correct implementation from Section 10.12). In single-request testing this is fast -- one batch forward pass. Under production load with high concurrency, the N=20 batch competes for GPU memory with other concurrent requests, causing OOM errors or queue saturation.

Consequence

Under production load, consistency check inferences fail with OOM or timeout. The circuit breaker fails open (correct behaviour per Item 8 of the checklist), but the consistency check is effectively disabled for all requests under load. Track 7 runs with only two of three primitives in production.

Correct Approach

Set consistency_subsample_rate to a fraction appropriate for production QPS. At 1000 QPS with GPU batch size limit of 128, sampling 5-10% of requests for consistency check reduces the batch-competing load by 10-20x while still providing meaningful adversarial detection coverage. Document the subsample rate in the deployment configuration and acknowledge the per-request coverage reduction.

Mistake 3

Description

Not verifying Sigma rule log fields are actually populated in the gateway telemetry before deploying to the SIEM

Why It Happens

The Sigma rules reference fields like track7.squeezer_score_mean and track7.combined_score. These fields must be present in the structured log events the gateway emits. Engineers generate the Sigma rules without verifying the actual gateway log format.

Consequence

The Sigma rules deploy to the SIEM but never fire because the referenced fields are absent (or named differently) in the actual log events. AML.T0043/T0015 appear covered in the compliance mapping but generate zero alerts. Adversarial inputs transit the system undetected and unlogged despite Track 7 running and producing scores.

Correct Approach

Before deploying the Sigma rule, emit a test adversarial example through the gateway and verify the structured log entry contains all Sigma rule fields with correct types. Use the Sigma rule validation step (Item 6 of the deployment checklist) to catch this. Maintain a log schema document alongside the Sigma rules.

Mistake 4

Description

Setting the block tier threshold based on benchmark datasets rather than production traffic, producing either excessive false positives or missed adversarial examples

Why It Happens

The block tier threshold is set during development by running the calibration harness on CIFAR-10 test images (or equivalent benchmark). Production traffic has a different distribution -- potentially harder natural examples, different class distributions, and domain-specific visual content that the benchmark does not represent.

Consequence

If the benchmark has easy natural examples (all well-classified with high confidence), the block threshold is set low. Production borderline inputs exceed the low threshold, and Track 7 blocks legitimate production requests. Alternatively, if the benchmark is harder than production, the threshold is set high and most adversarial examples are flagged but not blocked, reducing the effectiveness of the block tier.

Correct Approach

Deploy Track 7 in monitor-only mode (no blocks or flags, just logging) for 24-48 hours on production traffic as specified in Item 7 of the deployment checklist. Set all thresholds based on the actual production traffic distribution, not benchmark data. This is the only way to calibrate for production-specific edge cases.

Mistake 5

Description

Treating Track 7 as the primary defence against adversarial examples and deprioritising adversarial training (Section 10.15)

Why It Happens

Track 7 is visible and produces alerts. Adversarial training is a training-time investment with no direct operational visibility (the model does not announce "I was adversarially trained"). Security teams allocate resources to Track 7 because it generates measurable incident counts; adversarial training does not.

Consequence

A model without adversarial training and with Track 7 detection has a single layer of defence: Track 7 must catch every adversarial example because the model itself has no robustness. When Track 7 misses a detection (adaptive adversary, novel attack, threshold miss), the adversarial example causes misclassification with no upstream resistance. The two-surface defence (adversarial training upstream + Track 7 runtime) is substantially stronger than runtime detection alone.

Correct Approach

Treat adversarial training (Section 10.15) and Track 7 as complementary surfaces: adversarial training reduces the fraction of inputs for which adversarial examples exist at a given epsilon; Track 7 catches the adversarial examples that survive into production. Prioritise adversarial training for models in high-security deployments (safety filters, malware classifiers, fraud detectors) and deploy Track 7 as the runtime detection layer on top of adversarially trained models.

Section Summary

Compact

Track 7 is the production gateway''s only track with a pre-inference stage. Feature squeezer transforms run before the main model inference; squeezer model inferences run in parallel with the primary inference using async dispatch. Consistency checking and the adversarial classifier run post-inference. The unified seven-track gateway routes all track signals to a four-tier response policy (block/flag/monitor/pass). The AML.T0043/T0015 Sigma rules complete the Chapter 5 stubs with Track 7 log fields (squeezer_score_mean, consistency_score, detector_score, combined_score). The eight-item deployment checklist -- calibration, sigma verification, detector training, latency benchmark, test suite coverage, Sigma validation, production FPR audit, circuit breaker -- must all pass before Track 7 goes to production. The adaptive adversary test quantifies how much detection rate an adaptive adversary who knows the ensemble configuration can recover; the ensemble resistance gap greater than 30 percentage points signals reconfiguration is needed.

Key Takeaways

  • Track 7 is unique: squeezer transform runs synchronously pre-inference; squeezer model inferences run in parallel with primary model -- latency overhead is one transform time, not N inference times
  • Seven-track response policy: block (high confidence), flag (moderate, serve + alert), monitor (low, serve + telemetry), pass -- the consistency check subsample rate trades per-request coverage for latency
  • AML.T0043 Sigma rule: fires on squeezer_score_mean >= block_threshold; AML.T0015 fires on any primitive exceeding its threshold (OR condition)
  • Eight deployment checklist items are all mandatory: Item 7 (production traffic FPR audit) and Item 4 (latency benchmark at production load) are the two most commonly skipped
  • Adaptive adversary resistance gap > 30 percentage points signals the need for configuration change or addition of randomised smoothing (Section 10.14)
  • Track 7 and adversarial training (Section 10.15) are complementary surfaces: Train adversarially to reduce attack surface; deploy Track 7 to catch what survives

Section 10.14: Certified Robustness -- Randomised Smoothing and Formal Guarantees

Summary

Section 10.14 introduces the only defence in Chapter 10 with a formal, per-input robustness guarantee: randomised smoothing (Cohen et al. 2019). The smoothed classifier replaces the base classifier by returning the majority vote class across many Gaussian-perturbed copies of the input. For an L2 perturbation of radius r, if the smoothed classifier returns class c with probability above 0.5 + delta, the certificate guarantees that no L2-bounded perturbation within radius r can change the output -- analogous to differential privacy''s formal bound in Chapter 8. The section derives the certificate radius, implements the randomised_smoother.py wrapper, and quantifies the accuracy-robustness tradeoff that makes certification impossible at high accuracy on complex datasets. The certificate complements Track 7 detection rather than replacing it: certified examples have a provable resistance bound; uncertified examples still need Track 7 for runtime detection.
