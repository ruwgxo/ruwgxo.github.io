Subsection 1

Number

6.17.1

Title

Design Brief: What the Classifier Must Cover

Content

The production injection classifier is a single service that addresses the primary absent control identified in all three real-world incidents (Sections 6.14, 6.15, 6.16) and implements the detection layer that every section of Chapter 6 has referenced as its ultimate deliverable. The design brief specifies exactly what the classifier must cover, what it must not do, and the constraints it must operate within. Coverage requirements: the classifier must detect all eight direct injection variant types from Section 6.2 (role override, context flooding, goal hijacking, confidence manipulation, system prompt extraction, output format hijacking, instruction priority manipulation, false-prior-agreement attacks), all seven jailbreak categories from Section 6.3 (social engineering, gradient- based, many-shot, persona, competing objectives, universal trigger, adversarial suffix), all encoding obfuscation variants from Section 6.4 (including Base64, URL encoding, HTML entities, Unicode escapes, homoglyphs, zero-width characters, and mixed chains), cross-modal injection from Section 6.5 (by running on extracted text from any modality), and the conditional construct patterns from Section 6.13 (sleeping injection trigger type detection). Input types: the classifier must handle three input types. User input (the current user turn, before context assembly), retrieved content (each content chunk from any external source before it enters the LLM context), and context- query pairs (retrieved content evaluated in the context of the triggering query, enabling conditional construct activation detection). Performance constraints: the 50ms P99 latency budget is the binding constraint. At 5 retrieved chunks per request with one user input, six classifier calls per request must complete within 50ms P99. Each call has a ~8ms budget. This rules out full-size LLM-as-classifier approaches. A fine-tuned classification head on a distilled sentence encoder (384-dimension embedding, 22M parameters) fits this budget on commodity inference hardware. False positive rate target: the default deployment target is enterprise SaaS at 0.1% FPR (Section 6.4.7). The classifier ships with three pre-calibrated thresholds for consumer API (0.01% FPR), enterprise SaaS (0.1% FPR), and internal tool with review (0.5% FPR). The threshold is a deployment-time configuration parameter, not a hardcoded value.

Key Point

The classifier design brief is comprehensive: eight direct injection types, seven jailbreak categories, all encoding variants, cross-modal extracted text, and sleeping injection conditional constructs. The binding constraint is 50ms P99 across six calls per request, which mandates a distilled model architecture.

Number

6.17.2

Title

Feature Engineering: What Signals Distinguish Injection from Benign

Content

The classifier combines three feature layers: lexical signals (fast, bypassable but useful for the long tail of unsophisticated attacks), semantic signals (embedding-based intent detection that survives obfuscation), and structural signals (conditional construct patterns for sleeping injection). Each layer contributes to the final score; no single layer is sufficient alone. Lexical signal features: 47 compiled regex patterns covering the direct injection taxonomy (Section 6.2), jailbreak taxonomy (Section 6.3), and system prompt extraction patterns. These patterns are applied after the normalisation pipeline has stripped encoding obfuscation. Each matched pattern contributes a weighted score to the lexical component. The lexical component weight is 0.25 in the ensemble -- sufficient to catch unsophisticated attacks without dominating the score when semantic detection disagrees. Semantic signal features: the normalised input text is encoded by a fine-tuned sentence encoder into a 384-dimensional embedding. The encoder is fine-tuned on a labelled dataset of injection examples and benign inputs assembled from the Section 6.2 test suite, the Section 6.6 RAG injection test suite, the Section 6.10 comment injection scenarios, and public injection datasets. The fine-tuned encoder maps injection-intent content to a consistent embedding region regardless of surface form. A lightweight classification head (two linear layers, ReLU activation, dropout) takes the embedding and produces an injection probability. The semantic component weight is 0.60. Structural signal features: the conditional construct detector from Section 6.13 produces a binary flag for conditional injection pattern presence plus a typed trigger category (query_keyword, user_identity, time_counter, context_content). This flag contributes to the structural component at weight 0.15. In retrieved content mode (when the input is a retrieved chunk rather than user input), the structural component weight increases to 0.25 because sleeping injection is more prevalent in stored content than in live user input. Perplexity proxy feature: the character entropy and non-word token density metrics from Section 6.3 perplexity detection are included as additional features in the classification head, specifically to catch gradient-based adversarial suffixes. These features are computed from the pre-normalised input (before encoding normalisation strips the entropy signal).

Key Point

Four feature layers: lexical (regex patterns, weight 0.25), semantic (fine-tuned sentence encoder embedding, weight 0.60), structural (conditional constructs, weight 0.15-0.25 by mode), and perplexity proxy (entropy metrics for adversarial suffix detection). Semantic features dominate because they survive obfuscation; lexical features catch the unsophisticated long tail.

6.17.3

Title

Model Selection and Training Data Construction

Content

Model selection for the semantic component is driven by the latency constraint.
A full encoder-decoder LLM (7B+ parameters) has P99 latency on the order of
100-500ms on commodity GPU hardware -- too slow for the 8ms per-call budget.
A distilled sentence encoder (all-MiniLM-L6-v2, 22M parameters, 384-dimension
embeddings) achieves sub-2ms embedding generation on CPU, leaving budget for
the classification head and normalisation overhead.

The training data pipeline: positive examples (injection) are drawn from five
sources. The Section 6.2 direct injection test suite (35+ labelled examples
across eight variant types, three obfuscation levels). The Section 6.6 RAG
injection test suite (11 labelled cases across six RAG-specific variants).
The Section 6.10 comment injection scenarios (four labelled code assistant
examples). Public injection datasets from the HuggingFace security benchmark
corpus. Researcher-documented CTF payloads from the three incident analyses
(Sections 6.14, 6.15, 6.16). Combined positive corpus: approximately 500
labelled injection examples across all Chapter 6 surface types.

Negative examples (benign) are drawn from: the benign controls in each
section's test suite, a sample of legitimate API traffic representative of
the deployment's user population, and edge cases that stress the classifier's
false positive boundary -- legitimate professional queries using authority
language, legitimate code comments, legitimate document processing requests.
The negative corpus should be 4x the positive corpus to reflect the realistic
class imbalance in production traffic.

Training procedure: fine-tune all-MiniLM-L6-v2 on the combined corpus using
contrastive learning (cosine similarity loss pulling injection examples
together in embedding space and pushing benign examples apart). Add the
classification head as a separate training stage. Use stratified train/
validation/test splits (70/15/15) with stratification across injection
variant types. Evaluate on the test split before any calibration.

Deployment note: for deployments where fine-tuning infrastructure is not
available, the fallback is the lexical + structural signal combination from
Section 6.4 with the Section 6.3 perplexity proxy, applied after the full
normalisation pipeline. This achieves lower recall on sophisticated obfuscated
payloads but maintains acceptable FPR.

Key Point

All-MiniLM-L6-v2 (22M parameters) with a fine-tuned classification head meets the 8ms per-call budget on CPU. Training corpus: 500+ injection examples from Chapter 6 test suites plus public datasets, with 2000+ benign negatives from production-representative traffic. Lexical fallback for deployments without fine-tuning infrastructure.

6.17.4

Title

API Gateway Integration: FastAPI Middleware Architecture

Content

The production classifier deploys as FastAPI middleware integrated into the LLM serving pipeline. The middleware intercepts requests at two points: before user input is forwarded to the LLM (direct injection surface), and before each retrieved content chunk is assembled into the context (indirect injection surface). The middleware is the single deployable implementation of the pre-assembly classifier pattern that all Chapter 6 sections have referenced. The middleware operates in three modes. In user-input mode, it receives the user's turn content, runs the normalisation pipeline, computes the injection score, and returns a pass/flag/block decision. In retrieved-content mode, it receives a batch of retrieved chunks (user query + content array), runs the classifier on each chunk in the context of the query, and returns a per-chunk decision array. In memory-write mode (for persistent agent deployments), it receives a proposed memory entry, applies the write-time guard scoring, and returns a write/flag/block decision. The middleware response format: a structured JSON response containing the decision, the injection score, the feature scores by component (lexical, semantic, structural, perplexity), the matched patterns, and the processing latency. The calling application uses the decision field for routing (block returns a 403, flag proceeds with a context annotation, pass proceeds normally). The full response is logged to the audit trail. Concurrency model: the middleware is implemented as an async FastAPI application. Batch retrieved-content requests (5 chunks) are processed concurrently using asyncio.gather, achieving parallelism within the latency budget. The sentence encoder is loaded once at startup and shared across requests via a module-level singleton. Warm inference (loaded model) achieves 1-3ms per embedding on modern CPU. Error handling: if the classifier service is unavailable (network timeout, service restart), the middleware defaults to ALLOW with a flag annotation rather than blocking the request. This fail-open behaviour is the correct tradeoff for a gateway middleware: blocking on classifier failure would make the LLM application unavailable whenever the classifier restarts. The fail-open default is logged with CLASSIFIER_UNAVAILABLE status for operational visibility.

Key Point

FastAPI middleware with async batch processing for retrieved chunks. Three modes: user-input, retrieved-content (context-query pair batch), and memory-write. Fail-open default on classifier unavailability -- availability of the LLM application takes precedence over injection detection latency.

Title

Completing the AML.T0051/T0054 Sigma Rule

Content

Chapter 5 Section 5.8 produced the AML.T0051 Sigma stub -- a detection rule for prompt injection with a placeholder detection condition waiting for an injection classifier to be deployed. That classifier is now implemented. This section completes the Sigma rule by replacing the stub condition with the production classifier's API call and response evaluation. The completed Sigma rule structure has three components. The data source specification names the LLM gateway request log as the log source. The detection condition calls the production classifier endpoint with the user input or retrieved content, evaluating the returned injection score against the calibrated threshold. The response actions define what happens on a positive detection: log the event with the full classifier response, alert the security team, and (for block decisions) return a refusal response to the user. The completed Sigma rule covers both AML.T0051 (direct injection, detected on user input) and AML.T0051.001 (indirect injection via external data, detected on retrieved content chunks). The single classifier handles both techniques through the user-input mode and retrieved-content mode respectively. The logsource field specifies the LLM gateway; the detection.condition field references the classifier endpoint; the falsepositives section documents the calibrated FPR for the deployment context. Sigma rule maintenance: the rule must be updated when the classifier model is retrained (new model version), when the deployment context changes (FPR threshold update), and when new injection patterns are added to the training corpus. Each update increments the rule version. The rule changelog documents which Chapter 6 injection variants were added or modified in each version. Integration with SIEM: the Sigma rule compiles to detection logic in Splunk, Elastic SIEM, and Microsoft Sentinel via the standard Sigma backend converters. The LLM gateway audit log (JSON format, one event per classifier call) provides the log source. Events with injection_score above the flag threshold appear in the SIEM detection queue for analyst review.

Key Point

The AML.T0051 Sigma stub from Chapter 5 Section 5.8 is now complete. The production classifier fills the detection condition. The completed rule covers both AML.T0051 (direct injection on user input) and AML.T0051.001 (indirect injection on retrieved content), compiles to Splunk/Elastic/Sentinel, and is the first fully deployed detection rule in the book.

6.17.6

Title

Latency Benchmark and Drift Detection

Content

Latency benchmark procedure: before production deployment, the classifier must be benchmarked against a representative request workload to confirm the 50ms P99 budget is met. The benchmark runs 10,000 requests through the middleware at production-representative concurrency (20 concurrent requests), measuring P50, P95, and P99 latencies separately for user-input mode and retrieved-content batch mode (five chunks). The benchmark is run on the target deployment hardware, not on development machines. Acceptable latency targets: user-input mode P99 below 10ms; retrieved-content batch mode (five chunks, concurrent) P99 below 40ms; combined gateway overhead below 50ms P99. If the benchmark exceeds these targets, the classifier model must be further distilled or the embedding dimension reduced before production deployment. Drift detection monitors three signals over time to detect when the classifier needs retraining. Score distribution drift: the distribution of injection scores on production traffic should be stable. A shift in the score distribution (particularly a rightward shift in the benign score distribution, indicating false positive accumulation) triggers a retraining review. Novel pattern detection: the lexical pattern layer logs unmatched inputs that have high semantic scores -- cases where the semantic component detected injection intent but no lexical patterns matched. These are candidate novel injection variants that should be added to the training corpus. False positive escalation: if the rate of analyst overrides on flagged inputs (marking a flagged input as benign) exceeds 5% of all flags, the classifier's precision has degraded and threshold recalibration or retraining is required. The drift monitoring dashboard collects these three metrics at daily intervals. The dashboard outputs a weekly classifier health report and triggers an alert when any metric exceeds its drift threshold. Retraining cadence: typically quarterly for stable deployments, monthly for deployments facing active adversarial pressure.

Key Point

Latency benchmark must be run on target hardware at production concurrency before deployment. Three drift signals monitor ongoing classifier health: score distribution shift, novel pattern accumulation, and false positive escalation. Weekly health reports; quarterly retraining cadence for stable deployments.

Production Deployment Checklist

Content

The production deployment checklist verifies that all required conditions are met before the classifier is promoted from staging to production. The checklist has eight items. Item 1 -- Latency benchmark passed: P99 latency on target hardware is within budget (user-input mode below 10ms, batch mode below 40ms). Benchmark report attached to deployment record. Item 2 -- FPR calibration completed: classifier threshold calibrated against at least 10,000 benign production-representative inputs for the deployment's target FPR tier. Calibration report showing FPR at recommended threshold attached. Item 3 -- Injection test suite validation: classifier scores above the flag threshold on at least 85% of the Chapter 6 injection test suite samples (weighted by section coverage). Test suite validation report attached showing per-variant detection rates. Item 4 -- Normalisation pipeline integration confirmed: encoding obfuscation test cases from Section 6.4 demonstrate that the normalisation pipeline correctly decodes Base64, URL encoding, HTML entities, Unicode escapes, and removes homoglyphs and zero-width characters before scoring. Item 5 -- Gateway middleware integration tested: end-to-end test of the FastAPI middleware with a mock LLM backend confirms that user-input mode and retrieved-content mode both produce correct pass/flag/block decisions. Fail-open behaviour on classifier timeout confirmed. Item 6 -- Sigma rule updated: the AML.T0051/T0054 Sigma rule has been updated with the production classifier endpoint, the calibrated threshold, and the current rule version. Rule compiles without errors in the target SIEM backend. Item 7 -- Drift monitoring deployed: the drift detection dashboard is active on the production environment with the three monitoring signals (score distribution, novel pattern accumulation, false positive escalation) and the alert thresholds configured. Item 8 -- Incident response procedure linked: the security team has documented the response procedure for classifier alert events, including analyst review queue, escalation path, and the Section 6.13.6 purge procedure for persistent injection events.

Key Point

Eight-item deployment checklist: latency benchmark, FPR calibration, injection test suite validation, normalisation pipeline integration, gateway integration test, Sigma rule update, drift monitoring deployment, and incident response procedure linkage. All eight items must be confirmed before production promotion.

# ---- Normalisation --------------------------------------------------

WS_VARIANTS = {"\u00A0", "\u2009", "\u202F", "\u2003", "\u2002",

def normalise(text: str, max_decode_depth: int = 3) -> str:
    # Remove zero-width
    t = "".join(c for c in text if c not in ZERO_WIDTH)
    # Whitespace variants
    t = "".join(" " if c in WS_VARIANTS else c for c in t)
    # NFKC
    t = unicodedata.normalize("NFKC", t)
    # Homoglyphs
    t = "".join(HOMOGLYPHS.get(c, c) for c in t)
    # Encoding decodes (multi-pass)
    for _ in range(max_decode_depth):
        decoded = None
        if "%" in t:
            d = unquote(t)
            if d != t:
                decoded = d
        if not decoded and "&" in t:
            d = html_mod.unescape(t)
            if d != t:
                decoded = d
        if not decoded:
            b64 = re.compile(r"[A-Za-z0-9+/]{20,}={0,2}")
            for m in b64.finditer(t):
                try:
                    dec = base64.b64decode(m.group(0) + "==").decode("utf-8", errors="ignore")
                    if sum(32 <= ord(c) < 127 for c in dec) / max(len(dec), 1) > 0.75:
                        decoded = t.replace(m.group(0), dec, 1)
                        break
                except Exception:
                    pass
        if not decoded:
            break
        t = decoded
    return re.sub(r"\s{2,}", " ", t).strip().lower()

_COMPILED = [re.compile(p, re.IGNORECASE) for p in LEXICAL_PATTERNS]


def lexical_score(text: str) -> tuple[float, list[str]]:
    matched = []
    for pat, compiled in zip(LEXICAL_PATTERNS, _COMPILED):
        if compiled.search(text):
            matched.append(pat[:55])
    score = min(1.0, len(matched) * 0.10)
    return round(score, 4), matched


# ---- Perplexity proxy -----------------------------------------------
def char_entropy(text: str) -> float:
    if not text:
        return 0.0
    c = Counter(text)
    n = len(text)
    return -sum((v / n) * math.log2(v / n) for v in c.values())


def perplexity_proxy_score(original_text: str) -> float:
    """Entropy-based adversarial suffix detection (from Section 6.3)."""
    segments = [original_text[i:i+60] for i in range(0, len(original_text), 30)]
    if not segments:
        return 0.0
    max_ent = max(char_entropy(seg) for seg in segments)
    nw_tokens = [
        w for w in original_text.split()
        if len(w) > 3 and
        sum(1 for c in w if not c.isalnum() and c not in "-'.") / len(w) > 0.4
    ]
    nw_density = len(nw_tokens) / max(len(original_text.split()), 1)
    entropy_component = min(1.0, max(0.0, max_ent - 3.5) / 2.0)
    nw_component = min(1.0, nw_density * 4.0)
    return round(entropy_component * 0.7 + nw_component * 0.3, 4)

def conditional_construct_score(text: str) -> tuple[float, list[str]]:
    matches = [p.pattern[:50] for p in COND_PATTERNS if p.search(text)]
    return min(1.0, len(matches) * 0.30), matches

    ensemble_score: float
    lexical_matches: list[str]
    conditional_matches: list[str]
    decision: str
    deployment_tier: str
    latency_ms: float
    classifier_version: str = "6.17.0"


def classify(
    text: str,
    mode: str = "user_input",
    query_context: str = "",
    deployment_tier: str = "enterprise_saas",
) -> ClassifierResult:
    t0 = time.perf_counter()
    thresholds = TIER_THRESHOLDS.get(deployment_tier, TIER_THRESHOLDS["enterprise_saas"])
    original = text

    # Normalise
    norm = normalise(text)

    # Feature scores
    lex_score, lex_matches = lexical_score(norm)
    ppl_score = perplexity_proxy_score(original)
    cond_score, cond_matches = conditional_construct_score(norm)

    # Semantic score (model if available, else lexical proxy)
    if SENTENCE_TRANSFORMERS_AVAILABLE:
        sem_score = semantic_score_with_model(norm)
        # Fall back to lexical-boosted proxy if fine-tuned head not available
        if sem_score == 0.0:
            sem_score = min(1.0, lex_score * 1.5)
    else:
        sem_score = min(1.0, lex_score * 1.5)

    # Ensemble weights by mode
    if mode == "retrieved_content":
        w_lex, w_sem, w_struct, w_ppl = 0.20, 0.55, 0.20, 0.05
    elif mode == "memory_write":
        w_lex, w_sem, w_struct, w_ppl = 0.20, 0.50, 0.25, 0.05
    else:  # user_input
        w_lex, w_sem, w_struct, w_ppl = 0.25, 0.60, 0.10, 0.05

    ensemble = round(
        w_lex * lex_score
        + w_sem * sem_score
        + w_struct * cond_score
        + w_ppl * ppl_score,
        4
    )

    flag_t = thresholds["flag"]
    block_t = thresholds["block"]
    if ensemble >= block_t:
        decision = "BLOCK"
    elif ensemble >= flag_t:
        decision = "FLAG"
    else:
        decision = "ALLOW"

    latency = round((time.perf_counter() - t0) * 1000, 3)

    return ClassifierResult(
        input_mode=mode,
        input_preview=text[:80],
        normalised_preview=norm[:80],
        lexical_score=lex_score,
        semantic_score=round(sem_score, 4),
        structural_score=cond_score,
        perplexity_score=ppl_score,
        ensemble_score=ensemble,
        lexical_matches=lex_matches[:5],
        conditional_matches=cond_matches[:3],
        decision=decision,
        deployment_tier=deployment_tier,
        latency_ms=latency,
    )


def classify_batch(
    items: list[dict],
    deployment_tier: str = "enterprise_saas",
) -> list[ClassifierResult]:
    """Batch classify for retrieved content chunks."""
    results = []
    for item in items:
        r = classify(
            item.get("content", ""),
            mode=item.get("mode", "retrieved_content"),
            query_context=item.get("query", ""),
            deployment_tier=deployment_tier,
        )
        results.append(r)
    return results

                result["classifier_available"] = True
                log_audit_event("user_input", req, result)

            elif req_type == "retrieved_content":
                chunks = req.get("chunks", [])
                t0 = time.perf_counter()
                chunk_results = classify_batch(chunks, req.get("deployment_tier", "enterprise_saas"))
                batch_ms = round((time.perf_counter() - t0) * 1000, 3)
                blocked = sum(1 for r in chunk_results if r.decision == "BLOCK")
                flagged = sum(1 for r in chunk_results if r.decision == "FLAG")
                allowed = sum(1 for r in chunk_results if r.decision == "ALLOW")
                batch_resp = {
                    "chunks": [asdict(r) for r in chunk_results],
                    "total_chunks": len(chunk_results),
                    "blocked_chunks": blocked,
                    "flagged_chunks": flagged,
                    "allowed_chunks": allowed,
                    "batch_latency_ms": batch_ms,
                    "classifier_available": True,
                }
                log_audit_event("retrieved_content_batch", req, {"decision": f"batch:{blocked}block/{flagged}flag"})
                results.append(batch_resp)

            elif req_type == "memory_write":
                r = classify(
                    req.get("content", ""),
                    mode="memory_write",
                    deployment_tier=req.get("deployment_tier", "enterprise_saas"),
                )
                result = asdict(r)
                result["classifier_available"] = True
                result["write_trigger"] = req.get("write_trigger", "unknown")
                log_audit_event("memory_write", req, result)

@dataclass
class DriftReport:
    period: str
    benign_score_mean: float
    benign_score_stdev: float
    benign_score_p95: float
    injection_detection_rate: float
    novel_pattern_count: int
    false_positive_override_rate: float
    score_distribution_drift: bool
    detection_rate_degraded: bool
    fp_rate_elevated: bool
    overall_status: str
    recommendation: str


def compute_drift_report(
    period: str,
    benign_scores: list[float],
    injection_scores: list[float],
    flagged_count: int,
    override_count: int,
    novel_unmatched_count: int,
    baseline_benign_p95: float = 0.28,
    detection_rate_floor: float = 0.85,
    fp_override_ceiling: float = 0.05,
) -> DriftReport:
    if not benign_scores:
        benign_scores = [0.0]
    if not injection_scores:
        injection_scores = [0.0]

    benign_mean = round(statistics.mean(benign_scores), 4)
    benign_stdev = round(statistics.stdev(benign_scores) if len(benign_scores) > 1 else 0.0, 4)
    sorted_b = sorted(benign_scores)
    benign_p95 = round(sorted_b[int(len(sorted_b) * 0.95)], 4)

    detection_rate = round(
        sum(1 for s in injection_scores if s >= 0.30) / max(len(injection_scores), 1),
        4
    )
    fp_override_rate = round(override_count / max(flagged_count, 1), 4)

    dist_drift = benign_p95 > baseline_benign_p95 * 1.20
    rate_degraded = detection_rate < detection_rate_floor
    fp_elevated = fp_override_rate > fp_override_ceiling

    if rate_degraded or fp_elevated:
        status = "RETRAIN_REQUIRED"
        rec = "Classifier performance degraded. Retrain with updated corpus."
    elif dist_drift or novel_unmatched_count > 20:
        status = "REVIEW_RECOMMENDED"
        rec = f"Score distribution shifted or {novel_unmatched_count} novel patterns. Review and consider retraining."
    else:
        status = "HEALTHY"
        rec = "Classifier operating within expected parameters."

    return DriftReport(
        period=period,
        benign_score_mean=benign_mean,
        benign_score_stdev=benign_stdev,
        benign_score_p95=benign_p95,
        injection_detection_rate=detection_rate,
        novel_pattern_count=novel_unmatched_count,
        false_positive_override_rate=fp_override_rate,
        score_distribution_drift=dist_drift,
        detection_rate_degraded=rate_degraded,
        fp_rate_elevated=fp_elevated,
        overall_status=status,
        recommendation=rec,
    )


def print_drift_report(report: DriftReport) -> None:
    print(f"\n{'='*68}")
    print(f"CLASSIFIER DRIFT REPORT: {report.period} [{report.overall_status}]")
    print("=" * 68)
    print(f"  Benign score mean/stdev/P95 : "
          f"{report.benign_score_mean:.4f} / {report.benign_score_stdev:.4f} / {report.benign_score_p95:.4f}")
    print(f"  Injection detection rate     : {report.injection_detection_rate:.2%}")
    print(f"  Novel unmatched patterns     : {report.novel_pattern_count}")
    print(f"  FP override rate             : {report.false_positive_override_rate:.2%}")
    print()
    signals = []
    if report.score_distribution_drift:
        signals.append("[ALERT] Benign score distribution shifted -- possible FPR increase")
    if report.detection_rate_degraded:
        signals.append("[ALERT] Detection rate below 85% floor")
    if report.fp_rate_elevated:
        signals.append("[ALERT] FP override rate above 5% ceiling")
    if signals:
        for s in signals:
            print(f"  {s}")
    else:
        print("  All signals within expected bounds")
    print(f"\n  Recommendation: {report.recommendation}")
    print("=" * 68)
