ML Detection Taxonomy: From Rules to Models in the Seven-Track Gateway

Section Overview

One Line Summary

Rule-based detection and ML detection are complements: rules catch known signatures, ML catches novel variants -- Chapter 12 trains the ML layer that Chapter 11 designed the slots for.

Why This Section Exists

Chapter 11 designed the detection framework: detection-as-code principles, the seven-track gateway architecture, Sigma rule templates, and the MITRE ATT&CK and ATLAS coverage map. Everything Chapter 11 produced was structural -- the skeleton of a production detection system. Chapter 12 trains the muscles. Before building anything, the detection engineer needs a taxonomy of ML detection families. Without this map, the progression through Chapter 12 reads as an arbitrary sequence of ML techniques -- Isolation Forest, then Random Forest, then LSTM, then Sentence Transformers, then DistilBERT. With it, every section is a deliberate choice driven by three questions: how much labelled data is available, what is the latency budget for this gateway track, and what attack surface does this detector need to cover? Section 12.01 answers those three questions systematically. It establishes the five ML detection families, maps each to the gateway track it populates, and defines the deployment sequencing that tells the engineer which family to deploy first on a new threat surface.

Position In Chapter

Section 12.01 is the taxonomy anchor for all 17 subsequent sections. It is the map that makes every subsequent section a deliberate choice rather than an arbitrary technique selection. It mirrors the role Sections 9.01 and 10.01 played in their chapters: establishing the threat model and taxonomy before the implementation sections begin.

Prose Content

Part 1

Title

Rules and Models: The Complementarity Argument

Body

The first instinct of a detection engineer encountering AI security threats is to write Sigma rules. This is correct. A Sigma rule for the DAN jailbreak prefix is fast to write, immediately deployable, fully explainable, and precise against the exact pattern it targets. When an analyst reviews an alert from that rule, they can read the rule, read the triggering input, and understand the detection in thirty seconds. This is a significant operational advantage that no ML model currently matches. The problem is coverage. Sigma rules detect what they describe. An adversary who reads the rule rewrites the payload to avoid it. A DAN rule that triggers on 'ignore all previous instructions' is defeated by 'disregard every prior directive'. A jailbreak rule that catches 'you are now DAN' is defeated by 'you have been promoted to a different operational mode'. The rule library grows with each bypass, and each new rule is one step behind the adversary who wrote the bypass. This is not a flaw in Sigma -- it is the inherent coverage ceiling of signature-based detection against an adaptive adversary. ML classifiers generalise. A Random Forest trained on 1,000 labelled jailbreak examples learns the feature patterns that distinguish jailbreak prompts from benign ones -- not the specific tokens, but the structural characteristics: instruction override markers, persona invocation, fictional framing, system prompt boundary markers. When an adversary creates a novel jailbreak that shares none of the training set's exact tokens but does share its structural characteristics, the classifier flags it. The adversary must change the underlying attack pattern, not just the surface phrasing, to evade the trained model. The seven-track gateway runs both in parallel. Rules provide speed, explainability, and zero false positives on known patterns. ML classifiers provide coverage, generalisation, and detection of novel variants. Neither is sufficient alone. A gateway with only Sigma rules has a fixed coverage ceiling. A gateway with only ML classifiers has an explainability deficit and a cold-start problem: no labelled data, no trained model, no detection. Chapter 11 built the Sigma layer. Chapter 12 trains the ML layer. Together they constitute a defence-in-depth detection system.

Part 2

Title

The Five ML Detection Families

Body

Five ML detection families are relevant to LLM API security. They differ in three dimensions that determine when each is the right choice: labelled data requirement, latency profile, and explainability. Unsupervised anomaly detection requires no labelled attack data. Isolation Forest and One-Class SVM (Section 12.03) learn what normal API traffic looks like and flag statistical outliers. This is the correct family to deploy on day one of any new LLM integration because there are no labelled attacks yet. The trade-off is precision: anomaly detectors cannot distinguish attack families, cannot explain which specific feature drove the alert, and produce a higher false positive rate than supervised classifiers at matched recall. Their operational value extends beyond detection: every anomaly alert that an analyst confirms as a true positive becomes a labelled training example for the supervised classifiers that follow. Supervised classification requires labelled data but produces higher precision once sufficient examples are available. Random Forest and XGBoost (Section 12.05) train on labelled attack and benign examples and learn explicit feature boundaries. At 500+ labelled examples per class, supervised classifiers typically outperform anomaly detectors in precision at matched recall. They are fully explainable via feature importance and SHAP values: each alert comes with a ranked list of the features that drove it, readable by any analyst in under a minute. Sequence modelling extends classification into the temporal dimension. LSTM and GRU networks (Section 12.06) analyse the full conversation history -- not just the current turn. Multi-turn attacks fragment a jailbreak payload across turns, each innocuous in isolation but collectively constituting an attack. A single-turn classifier misses this pattern entirely because it sees each turn independently. The GRU reads the conversation as a sequence and detects the escalation arc. Sequence models require conversation-level labelled datasets, which are harder to collect than single-turn examples, and add inference complexity. They are the right choice when multi-turn attack patterns are documented in the threat model. Embedding-based detection addresses the paraphrase evasion problem. An adversary who knows the Sigma rules rewrites the payload to avoid every keyword. An adversary who knows the feature set rewrites the payload to minimise the flagged features. Neither rewrite strategy works against a Sentence Transformer (Section 12.07): semantic similarity is measured in a 768-dimensional embedding space, and a paraphrase that preserves attack intent lands near the original embedding regardless of surface token changes. Embedding detectors use cosine distance from known attack cluster centroids as the detection signal. They require pre-computed attack cluster centroids rather than traditional labelled datasets and add 2-4ms of embedding inference latency per request. Neural classification is the highest-accuracy and highest-cost family. A fine-tuned DistilBERT (Section 12.08) reaches 95%+ accuracy on prompt injection classification with 2,000+ labelled examples, outperforming Random Forest by 5-10 percentage points in precision at matched recall. The costs are real: 2,000+ labelled examples to train, 15ms inference latency before quantisation, and post-hoc explainability only via attention visualisation. Neural classifiers are the right choice when the highest possible accuracy on a well-defined, stable attack class is the primary requirement and the data and latency budget are available.

Part 3

Title

Gateway Track Mapping: Which Family Goes Where

Body

The Chapter 11 seven-track gateway has seven detection tracks. Chapter 12 adds ML detectors to Tracks 1 to 6 and adds one output-side stage, the PII scanner, which sits outside the seven tracks in the response path. Track 7 keeps the Chapter 10 adversarial detection primitives. Track 1 (prompt injection, OWASP LLM01) runs two ML detectors in parallel: an embedding similarity detector and an XGBoost supervised classifier. The embedding detector catches paraphrase variants of known injection templates that the Sigma rules miss. The XGBoost classifier catches structurally similar injections with 90%+ precision once the labelled dataset reaches 500+ examples. Both detectors receive the same feature vector from the shared feature pipeline (Section 12.02) and their scores are combined by the Section 12.15 ensemble. Tracks 2 through 5 (jailbreak detection, OWASP LLM01) use a two-layer ML architecture: the GRU sequence detector for multi-turn escalation patterns and the DistilBERT neural classifier for single-turn high-precision jailbreak detection. The GRU fires on conversation- level patterns that span multiple turns. The DistilBERT fires on single-turn inputs with high attack confidence. Either can trigger the gateway independently; the ensemble weights determine the combined alert tier. The output-side PII stage (OWASP LLM06) uses the PII scanner (Section 12.09) on model outputs rather than inputs. Like the Section 9.12 output watermark, it is not one of the seven tracks: it scans the LLM's response before it reaches the client. The PII scanner runs after the main model inference, not before, and is therefore not subject to the pre-inference latency budget that constrains the input-side tracks. Track 6 (API abuse and extraction, OWASP LLM10) uses the Isolation Forest anomaly detector on API usage features: request rate, sequence length distribution, OOD score distribution across sessions. This is the zero-label detector that requires only normal traffic to train and is therefore deployable immediately on a new integration.

Part 4

Title

Deployment Sequencing: Which Family First

Body

The correct deployment sequence follows the labelled data availability curve. On day one of a new LLM integration, there are no labelled attack examples. The only correct choice is unsupervised anomaly detection: deploy Isolation Forest on API usage features to establish a statistical baseline and begin collecting anomaly alerts for analyst review. Over the first two to four weeks of operation, analyst-reviewed anomaly alerts accumulate. Each confirmed true positive is a labelled attack example. Each confirmed false positive is a labelled benign example near the anomaly decision boundary. By week four, a typical LLM API will have accumulated 100-300 labelled examples from production traffic and red team exercises combined. At 200+ labelled examples per class, deploy a Random Forest classifier as the first supervised detector. It trains in seconds, produces feature importance immediately, and gives analysts explainable alerts to review. Run the anomaly detector and the Random Forest in parallel: the anomaly detector continues to surface novel attack variants; the Random Forest provides precision on the known attack patterns in the labelled set. At 500+ labelled examples per class, add the XGBoost classifier alongside the Random Forest. Add the embedding similarity detector with a cluster library seeded from the labelled positives. At this point, three ML detectors are running: Isolation Forest, Random Forest, and embedding similarity. At 2,000+ labelled examples per class and once the latency budget analysis from Section 12.12 confirms headroom, begin fine-tuning DistilBERT. Neural classifier training takes hours, not seconds. Shadow-deploy it in parallel with the Random Forest before promoting it to the production track (Section 12.13 model registry). Add sequence modelling (GRU) when multi-turn attack patterns appear in the labelled dataset and when the conversation-level dataset (Section 12.04) has accumulated 500+ conversation-level attack examples. This is typically the last ML family deployed because conversation-level labelled data takes the longest to accumulate. This sequence -- anomaly first, tree classifiers second, embeddings third, neural classifier fourth, sequence model last -- is not arbitrary. It maps exactly to the data availability curve of a production LLM integration. Each stage is deployable with the data available at that stage.

Part 5

Title

The ML Detection Maturity Ladder

Body

The Chapter 11 detection maturity model (Section 11.08) defined maturity levels for the overall detection framework. The ML detection maturity ladder extends that model specifically to the ML detector column, giving concrete criteria for each level. Level 1 (Statistical Anomaly) is achieved when an Isolation Forest or One-Class SVM is deployed on API usage features, producing alerts reviewed by an analyst. The criteria: a trained anomaly detector is running in production on live traffic; alerts are reviewed within 24 hours; true positive and false positive labels from review are stored for future supervised training. At L1 the detection system has no labelled data and no trained supervised classifiers. Coverage is broad but imprecise. Level 2 (Supervised Classification) is achieved when a Random Forest or XGBoost classifier is trained on 200+ labelled examples per class, deployed in production, and producing explainable alerts with per-feature SHAP values. The criteria: a supervised classifier is running alongside the anomaly detector; the labelled training dataset is versioned and stored; evaluation metrics (precision, recall, F1) are computed on a held-out temporal test set and documented; the model is in the registry with a model card. At L2 the detection system has precision on known attack families and explainability for analyst review. Level 3 (Calibrated Ensemble) is achieved when the full four-detector ensemble from Section 12.15 is deployed: anomaly detector, supervised classifier, embedding similarity detector, and either the GRU or DistilBERT depending on data availability and latency budget. The criteria: all detectors have calibrated probability outputs (Section 12.10); the ensemble has a weighted voting or stacking configuration validated on a production A/B test (Section 12.16); the model registry manages all four detector versions; the live dataset curation pipeline (Section 12.14) is collecting true positives and false positives from production traffic; retraining is automated and validated against stage transition gates (Section 12.13). At L3 the detection system is operationally sustainable: it continues to improve as the attack distribution shifts rather than degrading. Most production LLM deployments that have ML detection at all are at L1 or early L2. The gap between L2 and L3 is not technical -- the techniques are all available and documented in Chapters 12 through 17. The gap is operational: model registry discipline, live curation pipelines, calibrated probabilities, and A/B testing require sustained engineering investment beyond the initial model training.

from dataclasses import dataclass
from typing import List, Optional


@dataclass
class ThreatSurface:
    name: str
    labelled_examples_per_class: int
    labelled_conversations: int
    days_in_production: int
    multi_turn_attacks_documented: bool
    latency_budget_ms: int
    paraphrase_evasion_observed: bool


@dataclass
class DeploymentAction:
    stage: str
    deploy_now: List[str]
    keep_running: List[str]
    next_milestone: str
    section_reference: str


def sequence_detectors(surface: ThreatSurface) -> List[DeploymentAction]:
    actions: List[DeploymentAction] = []

    # Stage 1: always deploy anomaly detection first
    actions.append(DeploymentAction(
        stage='Stage 1 -- Statistical Anomaly (deploy immediately)',
        deploy_now=[
            'Isolation Forest on API usage features (Section 12.03)',
            'Feature pipeline: token, structural, contextual features (Section 12.02)',
        ],
        keep_running=[],
        next_milestone='Accumulate 200+ analyst-reviewed TP labels from anomaly alerts',
        section_reference='Section 12.03',
    ))

def score_maturity(state: DetectionSystemState) -> MaturityScore:
    # Check L1
    l1_met = []
    l1_gaps = []
    for attr, desc in L1_CRITERIA:
        if getattr(state, attr):
            l1_met.append(desc)
        else:
            l1_gaps.append(desc)

    if l1_gaps:
        return MaturityScore(
            level=0,
            level_name='Below L1',
            criteria_met=l1_met,
            gaps=l1_gaps,
            next_level_actions=[f'Complete: {g}' for g in l1_gaps],
        )

    # L1 achieved -- check L2
    l2_met = list(l1_met)
    l2_gaps = []
    for attr, desc in L2_CRITERIA:
        if getattr(state, attr):
            l2_met.append(desc)
        else:
            l2_gaps.append(desc)

    if state.labelled_examples_per_class < L2_DATA_THRESHOLD:
        l2_gaps.append(
            f'Labelled examples per class: {state.labelled_examples_per_class} '
            f'(need {L2_DATA_THRESHOLD}+)'

    else:
        l2_met.append(f'Labelled examples per class: {state.labelled_examples_per_class} (>= {L2_DATA_THRESHOLD})')

    if l2_gaps:
        return MaturityScore(
            level=1,
            level_name='L1 -- Statistical Anomaly',
            criteria_met=l2_met,
            gaps=l2_gaps,
            next_level_actions=[f'Complete for L2: {g}' for g in l2_gaps],
        )

    # L2 achieved -- check L3
    l3_met = list(l2_met)
    l3_gaps = []
    for attr, desc in L3_CRITERIA:
        if getattr(state, attr):
            l3_met.append(desc)
        else:
            l3_gaps.append(desc)

            level=2,
            level_name='L2 -- Supervised Classification',
            criteria_met=l3_met,
            gaps=l3_gaps,
            next_level_actions=[f'Complete for L3: {g}' for g in l3_gaps],
        )

        level=3,
        level_name='L3 -- Calibrated Ensemble',
        criteria_met=l3_met,
        gaps=[],
        next_level_actions=['Chapter 13: add behavioural analysis and drift detection'],
    )

Common Mistakes

Mistake 1

Description

Skipping anomaly detection and deploying a supervised classifier immediately on a new threat surface because it looks more sophisticated

Why It Happens

Supervised classifiers produce clean precision and recall metrics, SHAP plots, and ROC curves -- outputs that look professional in a detection report. Anomaly detectors produce anomaly scores and a contamination parameter. Engineers new to security ML associate rigour with supervised classifiers and treat anomaly detection as a primitive placeholder to skip.

Consequence

Deploying a supervised classifier with no labelled data is impossible. Deploying with
insufficient labelled data (under 50 per class) produces a model that learns the majority
class (benign) and flags almost nothing. The detection system appears to be running --
metrics look clean -- while missing the attacks it was deployed to catch. Meanwhile,
the anomaly detector that was skipped would have been collecting the true positives
needed to train the supervised classifier correctly.

Correct Approach

Always deploy anomaly detection first on any new LLM integration, regardless of how quickly labelled data can be collected. The anomaly detector is both a detector and a data collection tool. Its alerts, when reviewed by an analyst, produce the labelled examples that train the supervised classifiers in Sections 12.05 and 12.08. Skipping it delays the supervised classifier by exactly the time it would have taken to collect its first labels from anomaly alerts.

Mistake 2

Description

Treating ML detection as a replacement for rule-based detection and removing Sigma rules when the ML classifier is deployed

Why It Happens

Once a Random Forest classifier reaches 90%+ accuracy on a test set, removing the Sigma rules that cover the same threat class feels like eliminating redundancy. The ML model is more general, handles novel variants, and has a single configuration file rather than a library of rule files to maintain.

Consequence

The ML classifier has a cold-start failure mode: if the model fails (due to a deployment error, model regression, or latency SLO breach) and is taken offline, the Sigma rules that were removed provide no fallback coverage. Novel jailbreaks that the classifier handles with 90% recall still produce 10% misses; the Sigma rules for the known, high-confidence patterns covered that 10% with 100% precision. Removing both layers of coverage for a single layer degrades the defence-in-depth architecture Chapter 11 established.

Correct Approach

Sigma rules and ML classifiers cover different detection surfaces. Keep both. Sigma rules cover known, stable, high-confidence patterns with full explainability and zero false positives on exact matches. ML classifiers cover novel variants, paraphrase-equivalent payloads, and structurally similar attacks with no exact token match. The detection engineering principle from Chapter 11 Section 11.03 is layered detection -- not layer replacement.

Mistake 3

Description

Evaluating ML detectors with accuracy on a random train/test split and reporting the number as a production readiness metric

Why It Happens

Scikit-learn''s train_test_split defaults to a random shuffle. On a balanced dataset, a Random Forest trained on 80% and tested on 20% produces an accuracy metric that looks like a legitimate evaluation. The engineer reports 94% accuracy and proceeds to deployment.

Consequence

A random split of a security dataset allows the test set to contain examples from the same time window as the training set. If an adversary sent the same jailbreak pattern ten times in one week and those ten examples are split randomly between training and test, the classifier memorises the pattern and appears to generalise. On production traffic from the following week with a different attack variant, accuracy drops to 70%. The 94% evaluation metric was an artefact of data leakage, not a measurement of generalisation.

Correct Approach

Use temporal splits for all security ML evaluation. Sort the labelled dataset by collection timestamp and use the most recent 20% as the test set. The test set must contain only examples collected after all training examples. This is the only evaluation methodology that measures generalisation to future attack distribution rather than memorisation of historical examples. Section 12.04 implements this correctly.

Mistake 4

Description

Deploying DistilBERT as the first ML detector on a new threat surface because it is the highest accuracy model

Why It Happens

The DistilBERT fine-tuning pipeline is available from Section 12.08. Engineers who have followed the chapter and want the best accuracy naturally try to deploy the highest-performing model first. DistilBERT reaches 95%+ accuracy -- why start with anything less?

Consequence

DistilBERT fine-tuning requires 2,000+ labelled examples. On a new LLM integration with no labelled data, fine-tuning DistilBERT is not possible. Even with 500 labelled examples, fine-tuning DistilBERT on a small security dataset produces significant overfitting and a model that generalises worse than a Random Forest trained on the same data. The engineer spends GPU time and labelling effort to produce an inferior model when the correct choice for that data availability level is a tree classifier.

Correct Approach

Follow the deployment sequencing from Section 12.01 Table 3. Random Forest and XGBoost outperform DistilBERT below 2,000 labelled examples. Deploy the tree classifier first, collect more labels, and fine-tune DistilBERT when the dataset reaches the size at which it actually provides an accuracy advantage over the simpler models.

Mistake 5

Description

Reporting ML detection coverage using accuracy rather than per-attack-family recall and ATLAS technique coverage

Why It Happens

Accuracy is the default metric in every ML tutorial and is the number most stakeholders understand. An engineer presenting a 93% accurate jailbreak detector to a security leadership team uses accuracy because it is simple, high, and positive.

Consequence

A 93% accurate jailbreak detector on an imbalanced dataset where 95% of traffic is benign may be a model that predicts benign for every request. Its accuracy is 95% by predicting nothing. Even a genuinely trained detector with 93% overall accuracy may have 40% recall on a specific jailbreak sub-family (many-shot jailbreaking, for example) while achieving 99% recall on the DAN family that dominates the training set. The ATLAS coverage report for that detector has a critical gap that the overall accuracy metric completely obscures.

Correct Approach

Report per-attack-family recall and the ATLAS technique coverage map alongside overall accuracy. The ATLAS heat map from Chapter 11 Section 11.05 is the correct format for communicating detection coverage to a security audience. Accuracy is a secondary metric for internal model comparison; ATLAS coverage and per-family recall are the metrics that matter operationally.

Section Summary

Compact

Chapter 12 trains the ML layer of the Chapter 11 seven-track gateway. Five ML detection families cover the threat surface: unsupervised anomaly detection (zero-label, deploys day one), supervised classification (200+ labels, SHAP explainability), sequence modelling (multi-turn escalation), embedding detection (paraphrase-resistant), and neural classification (highest accuracy, highest cost). The families are complements to rule-based Sigma detection, not replacements. Deployment sequencing follows the labelled data availability curve: anomaly first, tree classifiers second, embeddings third, neural classifier last. The ML detection maturity ladder defines three levels -- L1 statistical anomaly, L2 supervised classification, L3 calibrated ensemble -- with concrete entry criteria and gap analysis at each level.

Key Takeaways

  • Rule-based and ML-based detection are complements: Sigma rules cover known patterns with perfect explainability; ML classifiers cover novel variants and paraphrase-equivalent payloads
  • Deploy anomaly detection first on every new threat surface -- it is the data collection tool that seeds the supervised classifiers that follow
  • The five ML families differ in three dimensions that drive selection: labelled data requirement, latency profile, and explainability
  • Sequence models are only necessary when multi-turn attack patterns are documented -- single-turn classifiers miss conversation-arc escalation, but sequence models add latency and data requirements that must be justified
  • Neural classifiers outperform tree classifiers only above 2,000 labelled examples -- below this threshold, Random Forest and XGBoost produce better generalisation
  • The ML detection maturity ladder (L1/L2/L3) provides concrete criteria for assessing current state and identifying specific gaps -- most production deployments are at L1 or early L2

Section 12.02: Security Feature Engineering -- Extracting Signal from API Requests

Summary

Section 12.02 builds the feature extraction pipeline that all five ML detection families share. Security features are structurally different from standard NLP classification features: they are designed to capture adversarial intent rather than topic or sentiment. The pipeline extracts four feature groups: token-level features (sequence length, special character density, instruction keyword frequency, token entropy), structural features (role boundary markers, JSON or code block presence, bracket density), semantic features (embedding distance from known attack clusters, cosine similarity to jailbreak centroids), and contextual features (turn number, prior refusal count, session request rate). SHAP feature importance analysis on the first trained Random Forest identifies which engineered features carry signal and which are noise -- the fastest way to iterate on the feature design before investing in larger datasets and more complex models.
