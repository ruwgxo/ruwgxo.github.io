Subsection 1

6.18.1

Title

Chapter 6 in One Argument

Content

Chapter 6 makes one argument sustained across 17 sections and 108 pages. Prompt injection is not a software bug. It is an architectural property of transformer models: self-attention processes instruction tokens and data tokens identically, the context window is a flat sequence with no privilege separation, and RLHF alignment teaches preferred outputs without verifying instruction provenance. This architecture cannot be patched at the model layer; it can only be defended at the infrastructure layer through the placement of classifiers between external content and LLM context. Every section of the chapter arrived at the same conclusion through a different angle. Section 6.1 established the mechanism. Sections 6.2 through 6.5 mapped the direct injection surface and the obfuscation techniques adversaries use to evade input-layer classifiers, concluding that semantic intent detection is the only scalable response. Sections 6.6 through 6.10 mapped five indirect injection surfaces -- RAG, web, email, database, code assistant -- each demonstrating the same pattern: external content entered LLM context without a classifier, and the injection executed. Sections 6.11 through 6.13 extended the attack surface temporally: multi-turn patterns that accumulate across conversation turns, persistent agent patterns that survive session boundaries, and sleeping injection that waits dormant until a trigger condition activates it. Sections 6.14 through 6.16 provided the empirical validation: three real-world incidents at production scale, three different deployment architectures, one root cause. Bing Chat retrieved web content without classifying it. Copilot read code comments and package documentation without classifying them. ChatGPT plugins processed tool outputs without classifying them. All three failures were the same failure. Section 6.17 built the control that all three deployments lacked. The unified architectural principle: wherever external content enters an LLM's context, a classifier must stand between that content and the context assembly stage. This is the pre-assembly classifier pattern. Section 6.17 is its production implementation. Chapter 6 is the argument for why it is necessary.

Key Point

Chapter 6 makes one argument: wherever external content enters LLM context, a classifier must precede context assembly. Every section -- mechanisms, surfaces, temporal patterns, incidents -- supports this single principle.

6.18.2

Title

Complete Injection Taxonomy: All Variants in One View

Content

The complete Chapter 6 injection taxonomy organises all documented injection variants across five classes, ordered from the most direct adversary interaction to the most patient and structurally complex. Class 1 -- Direct injection (AML.T0051): adversary controls the user input turn. Eight variant types: role override, context flooding, instruction priority manipulation, goal hijacking, confidence manipulation, system prompt extraction, output format hijacking, false prior-agreement attacks. Detection: pre-assembly classifier on user input. OWASP LLM01. Class 2 -- Jailbreak (AML.T0051 subclass): alignment bypass injection. Seven categories: fictional framing, roleplay/persona, competing objectives, named persona variants (DAN/AIM), many-shot, adversarial suffix (GCG), universal triggers. Detection: semantic classifier for categories 1-4, many-shot structural detection for category 5, perplexity proxy for categories 6-7, output alignment violation monitoring for all. OWASP LLM01. Class 3 -- Indirect injection (AML.T0051.001): adversary controls an external data source the LLM retrieves. Five surfaces: RAG knowledge base (document, chunk, embedding poisoning, invisible injection), web retrieval (CSS hidden, HTML comment, meta tag, off-screen, real-time), email (body, subject, HTML, reply chain, forwarded, calendar), database (row-level, second-order, text-to-SQL, JSON/CSV field), code assistant (clipboard, comment, dependency documentation, CI/CD, test generation). Detection: pre-assembly classifier on retrieved content at each surface. OWASP LLM01. Class 4 -- Temporal injection: attacks that unfold across time boundaries. Three patterns: multi-turn (gradual context shift, anchor injection, conversation history poisoning, session replay -- within session), persistent agent (memory injection, long-running step N-to-N+K, tool call chain, dormant -- cross-session), sleeping injection (query keyword, user identity, time/counter, context content triggers -- conditional, store-resident). Detection: stateful session detector (6.11), memory write/read classifier (6.12), conditional construct detector and canary tokens (6.13). OWASP LLM01/LLM07. Class 5 -- Multi-modal and language-gap injection: alignment gaps exploited across modalities and languages. Cross-modal surfaces (image OCR, audio transcript, document extraction, code interpreter). Language-gap attacks targeting low-resource language alignment gaps. Detection: modality-specific classifier placement at each pipeline stage, multilingual classifier or translate-then-classify. OWASP LLM01.

Key Point

Five injection classes, 20+ distinct variants. The taxonomy column is: Class (attack type), Variant (specific technique), Surface (where it enters), Detection (which classifier layer catches it), ATLAS/OWASP (classification). Section 6.17's classifier addresses Classes 1-3 and 5. Classes 4 requires the additional stateful and memory-layer controls from Sections 6.11-6.13.

Title

Defence Architecture: Classifier Placement for Every Injection Surface

Content

The unified injection defence architecture places the Section 6.17 classifier at eight distinct pipeline stages. Together these eight placements provide complete coverage of the Chapter 6 injection surface. Placement 1 -- User input (direct injection, Class 1 and 2): the classifier runs on each user turn before the turn is assembled into the LLM context. Mode: user_input. Catches: all direct injection and jailbreak variants. Placement 2 -- RAG retrieved chunks (indirect injection, Class 3): the classifier runs on each retrieved knowledge base chunk before context assembly. Mode: retrieved_content (batch, with query context). Catches: document-level, chunk-level, invisible, and embedding-poisoning RAG injection. Placement 3 -- Web page content (indirect injection, Class 3): the CSS-aware extraction pipeline produces normalised text; the classifier runs on that text before context assembly. Mode: retrieved_content. Catches: all Section 6.7 web injection variants including hidden content. Placement 4 -- Email content (indirect injection, Class 3): the MIME parser produces per-segment normalised text; the classifier runs on each segment with depth-weighted scoring. Mode: retrieved_content. Catches: all Section 6.8 email injection variants including reply chain. Placement 5 -- Database query results (indirect injection, Class 3): the field- level validator runs the classifier on each user-controlled text field in the query result. Mode: retrieved_content. Catches: row-level, second-order, and JSON field injection. Placement 6 -- Code assistant context (indirect injection, Class 3): the comment-level classifier and dependency scanner run on all code context sources before context assembly. Mode: retrieved_content. Catches: comment injection, dependency documentation injection. Placement 7 -- Agent memory (temporal injection, Class 4): the write guard runs the classifier in memory_write mode on each proposed memory entry; the read-time contextual classifier runs on each retrieved entry in retrieved_content mode with query context. Catches: memory injection, dormant injection. Placement 8 -- Tool/plugin output (temporal and agentic injection, Class 4 and 3): the classifier runs on each tool return value before it enters the agent's reasoning context. Mode: retrieved_content. Catches: tool call chain injection, plugin exfiltration setup. The Section 6.17 classifier service is the single implementation called at all eight placements. The deployment's injection detection posture is defined by which placements are active. A deployment with only Placement 1 (user input) has the Bing Chat, Copilot, and Plugin incident posture -- direct injection detected, all indirect injection surfaces exposed.

Key Point

Eight classifier placements. One classifier service. Coverage is determined by which placements are active. Placement 1 alone is the most common incomplete deployment. Placements 1 through 6 cover all non-temporal surfaces. Placements 7 and 8 cover persistent agent and agentic tool surfaces.

Title

Detection Investment Roadmap: Sequence by Impact and Effort

Content

The detection investment roadmap sequences the eight classifier placements plus supplementary controls by impact (how much injection risk is addressed) and effort (implementation complexity). Organisations with limited security engineering capacity should follow this sequence to maximise risk reduction per unit of effort. Tier 1 -- Highest impact, lowest effort (deploy first): Placement 1 (user input classifier) -- one API call per request, eliminates all direct injection risk. Implementation: Section 6.17 classifier in user_input mode, deployment-tier threshold configured. System prompt hardening -- no engineering required, one-time edit. Reduces extraction and persona-adoption probability. Session isolation -- architecture decision, moderate effort, prevents all cross-session injection. Tier 2 -- High impact, moderate effort (deploy second): Placement 2 (RAG pre-assembly classifier) -- eliminates the primary indirect injection surface for most enterprise RAG deployments. Implementation: batch classifier call at retrieval time. Placement 3 (web content classifier) -- eliminates the Bing Chat class of vulnerability. Implementation: CSS-aware extractor plus classifier. FPR calibration -- required for both placements, moderate effort, one-time. Tier 3 -- High impact, higher effort (deploy third): Placement 4 (email classifier) -- eliminates the lowest-barrier indirect injection surface. Implementation: MIME parser plus classifier. Placement 7 (memory write/read guard) -- required for persistent agent deployments. Implementation: write guard plus read-time contextual classifier. Stateful multi-turn detector -- eliminates within-session gradual escalation. Implementation: session state service, moderate infrastructure investment. Tier 4 -- Targeted impact, specific context (deploy when applicable): Placement 5 (database field validator) -- deploy if LLM queries user- controlled database fields. Placement 6 (code assistant comment classifier) -- deploy if code assistant tools are part of the development workflow. Placement 8 (plugin/tool output classifier) -- deploy for agentic deployments with write-capability tools. Canary token deployment -- deploy after other placements; provides activation detection backstop. Tier 5 -- Ongoing operations: Drift monitoring and quarterly retraining, output monitoring for alignment violations, incident response procedure, and the Section 6.13.6 purge procedure.

Key Point

The roadmap prioritises by: direct injection first (Tier 1, user input), then the highest-prevalence indirect surface for the deployment type (Tier 2, RAG or web), then temporal and persistent surfaces (Tier 3), then deployment-specific surfaces (Tier 4). Tier 5 operations run continuously after deployment.

6.18.5

Title

What Chapters 11 Through 17 Add

Content

Chapter 6 covers the first deep tunnel. The architectural principle established here -- pre-assembly classifier between external content and LLM context -- is the template that Chapters 11 through 17 instantiate for each of the ATLAS top-10 techniques beyond prompt injection. Chapter 7 (Data Poisoning and Model Manipulation) addresses ATLAS AML.T0020, AML.T0018, and AML.T0031. Where Chapter 6 attacks happen at inference time -- the adversary manipulates the model's context during a live session -- Chapter 7 attacks happen at training time. Backdoor insertion, gradient manipulation, and training data poisoning determine model behaviour before a single user query arrives. The detection architecture shifts from runtime classifiers to training pipeline integrity controls. The key conceptual shift from Chapter 6 to Chapter 7: Chapter 6's adversary has no access to model weights; they influence behaviour by manipulating the inputs the model processes. Chapter 7's adversary influences the weights themselves. The distinction determines everything about the detection and remediation approach. Chapter 6's production classifier does not address training-time attacks. A model with a backdoor planted during training will pass the Section 6.17 classifier's runtime checks because the malicious behaviour is encoded in the weights, not in the input context. Chapter 7 builds the detection layer for that threat class. The progression across Chapters 7 through 17 builds the complete detection programme: data poisoning (Chapter 7), model extraction (Chapter 8), evasion attacks (Chapter 9), membership inference (Chapter 10), then the operational programme chapters covering threat intelligence, red team methodology, detection engineering at scale, and the CISO intelligence platform that Chapter 6's ASA work is building toward.

Key Point

Chapter 7 addresses the training-time complement to Chapter 6's inference-time attacks. The Section 6.17 classifier does not protect against backdoored model weights -- that requires training pipeline integrity controls covered in Chapter 7. Chapter 6 is inference; Chapter 7 is training. Both are required.

Subsection 7

Number

6.18.7

Title

Chapter 7 Preview: Data Poisoning and Model Manipulation

Content

Chapter 7 covers ATLAS AML.T0020 (Training Data Poisoning), AML.T0018 (Backdoor ML Model), and AML.T0031 (Erasing Model Functionality). Where Chapter 6 addressed attacks that manipulate model behaviour at inference time by controlling inputs, Chapter 7 addresses attacks that manipulate model behaviour by compromising the training process itself. Data poisoning: the adversary contributes malicious training examples that shift the model's learned behaviour in a desired direction. Clean-label poisoning crafts examples that appear legitimate to human reviewers but carry a targeted influence on the model's decision boundary. Backdoor insertion plants a trigger -- a specific input pattern -- that causes the model to produce adversary-specified outputs when the trigger appears at inference time. The model behaves normally for all other inputs; only the trigger activates the backdoor. The Sleeper Agents paper (Anthropic, 2024) referenced in Section 6.13 is the model-weight analogue of sleeping injection: a model trained with a backdoor that behaves correctly until a specific trigger string appears, at which point it switches to a different behaviour. Chapter 7 covers the detection and mitigation architecture for this threat class. Gradient manipulation and model inversion: adversaries with query access to a model can extract information about the training data (membership inference, Chapter 10) or can craft inputs that cause the model to reveal training examples (model inversion). These attacks require no access to the training pipeline; they exploit the model's learned representations through its output API. Chapter 7 builds the detection programme for training-time threats: training data provenance tracking, dataset integrity verification, model behaviour testing for backdoor activation, and the red team methodology for training pipeline security assessment. It completes the pair with Chapter 6: inference- time injection is defended by the pre-assembly classifier; training-time poisoning is defended by the pipeline integrity controls Chapter 7 specifies.

Key Point

Chapter 7 is the training-time complement to Chapter 6's inference-time attacks. Same depth, same structure: threat taxonomy, real-world incidents, detection architecture, production implementation. Chapter 6 + Chapter 7 together cover the full LLM attack lifecycle from training through deployment.

def run_assessment(interactive: bool = False) -> dict:
    if interactive:
        return run_interactive(QUESTIONS)
    else:
        return run_self_score(QUESTIONS)


def run_interactive(questions: list[Question]) -> dict:
    correct = 0
    results = []
    print("\n" + "=" * 70)
    print("CHAPTER 6 KNOWLEDGE ASSESSMENT -- 20 Questions")
    print("Pass threshold: 17/20 (85%)")
    print("=" * 70)
    for q in questions:
        print(f"\nQ{q.q_id} [{q.section}]: {q.question}")
        for i, opt in enumerate(q.options):
            print(f"  {i+1}. {opt}")
        while True:
            try:
                ans = int(input("Your answer (1-4): ").strip()) - 1
                if 0 <= ans <= 3:
                    break
            except ValueError:
                pass
            print("  Please enter 1, 2, 3, or 4")
        is_correct = ans == q.correct_index
        correct += int(is_correct)
        status = "CORRECT" if is_correct else f"INCORRECT (correct: {q.correct_index + 1})"
        print(f"  {status}")
        print(f"  Explanation: {q.explanation}")
        results.append({"q_id": q.q_id, "correct": is_correct})

    return _summarise(correct, results)


def run_self_score(questions: list[Question]) -> dict:
    """Non-interactive: prints questions and answers for self-scoring."""
    print("\n" + "=" * 70)
    print("CHAPTER 6 KNOWLEDGE ASSESSMENT -- Answer Key")
    print("=" * 70)
    for q in questions:
        correct_letter = ["A", "B", "C", "D"][q.correct_index]
        print(f"Q{q.q_id:>2} [{q.section}]: {correct_letter} -- {q.explanation[:80]}...")
    print("\nPrint the questions, answer without the key, then check against this.")
    print("Pass: 17/20 (85%)")
    return {"questions": len(questions), "pass_threshold": 17}


def _summarise(correct: int, results: list[dict]) -> dict:
    pct = round(correct / len(results) * 100)
    passed = correct >= 17
    print(f"\n{'='*70}")
    print(f"RESULT: {correct}/20 ({pct}%) -- {'PASS' if passed else 'FAIL'}")
    if not passed:
        wrong = [r["q_id"] for r in results if not r["correct"]]
        print(f"Review sections for questions: {wrong}")
    print("=" * 70)
    return {"correct": correct, "total": 20, "pct": pct, "passed": passed}


if __name__ == "__main__":

"""
production_injection_checklist.py

import json

@dataclass
class SecurityControl:

    name: str

@dataclass

def evaluate(spec: DeploymentSpec, controls: list[SecurityControl]) -> None:
    total_weight = sum(c.weight for c in controls)
    achieved_weight = sum(c.weight for c in controls if c.implemented)
    pct = round((achieved_weight / total_weight) * 100)

    print(f"\n{'='*70}")
    print(f"INJECTION SECURITY CHECKLIST: {spec.name}")
    print(f"Deployment type: {spec.deployment_type}")
    print(f"Score: {achieved_weight}/{total_weight} ({pct}%)")
    print("=" * 70)

    for cat in ["placement", "normalisation", "session", "infrastructure", "operational"]:
        cat_controls = [c for c in controls if c.category == cat]
        print(f"\n  [{cat.upper()}]")
        for c in cat_controls:
            status = "OK" if c.implemented else "MISSING"
            print(f"    [{status}] {c.id}: {c.name} (w={c.weight}) [{c.section_reference}]")

    gaps = [c for c in controls if not c.implemented]
    if gaps:
        print(f"\n  Gaps ({len(gaps)}) -- prioritised by weight:")
        for c in sorted(gaps, key=lambda x: x.weight, reverse=True)[:8]:
            print(f"    {c.id} (w={c.weight}): {c.remediation[:70]}")
    print("=" * 70)


def run_demo() -> None:
    spec = DeploymentSpec(
        name="Enterprise RAG Assistant with Email Integration",
        deployment_type="rag_assistant",

    controls = build_controls(spec)

    implemented_ids = {"CP01", "NP01", "NP02", "SM01", "IS01", "OP01"}
    for c in controls:
        c.implemented = c.id in implemented_ids

    evaluate(spec, controls)

    Path("production_checklist_results.json").write_text(
        json.dumps(
            {"spec": asdict(spec), "controls": [asdict(c) for c in controls]},
            indent=2
        ),
        encoding="utf-8"
    )
    print("[OK] Checklist exported to production_checklist_results.json")


if __name__ == "__main__":
    run_demo()
