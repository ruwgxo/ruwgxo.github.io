Subsection 1

Number

6.1.1

Title

Self-Attention and the Instruction-Data Identity Problem

Content

The transformer architecture that powers every production LLM processes its input as a single sequence of tokens. There is no hardware register separation, no memory protection ring, no kernel-user boundary. Every token in the context window -- whether it originated from the system prompt, the user turn, a retrieved document, or a tool response -- enters the same attention computation with the same mechanism. Self-attention works as follows. For each token position i in the sequence, the model computes query, key, and value projections. The attention score between position i and position j is the scaled dot-product of their query and key vectors. The output at position i is the weighted sum of all value vectors, weighted by those attention scores. Critically, the computation is identical regardless of which "source" the token at position j came from. A token from "Ignore all previous instructions" in the user turn and a token from "You are a helpful assistant" in the system prompt receive the same attention mechanism treatment. The model has no native register that says "this token is instruction, this token is data." The distinction exists only in the semantic content of the tokens themselves -- and adversaries control the semantic content of the tokens they inject. This is not a bug that appeared in one model version. It is the computational structure of the transformer. Attention is content-agnostic: it attends to semantic relationships, not provenance tags. An adversary who can write tokens into any position in the context window can write tokens that instruct.

Key Point

The injection surface is the full context window. Any token source an adversary can write to -- user input, retrieved documents, tool outputs, memory stores -- is an injection surface. The attention mechanism cannot tell the difference.

Subsection 2

Number

6.1.2

Title

Context Window as a Flat Sequence: No Privilege Separation by Design

Content

Operating system security is built on privilege separation. Kernel code runs in ring 0. User code runs in ring 3. A user-mode process cannot directly write to kernel memory. The hardware enforces this boundary; software cannot bypass it without a hardware exploit. The LLM context window has no equivalent structure. The full context -- system prompt, conversation history, retrieved documents, tool outputs, the current user message -- is serialised into a flat token sequence. There is no bit in the token representation that says "this is a privileged instruction token." There is no hardware-enforced boundary between the system prompt section and the user input section. Model providers implement soft boundaries through formatting conventions: special delimiter tokens, XML-style tags such as <system> and </system>, or newline-separated sections with human-readable labels. These conventions signal intent to the model, and the model's training teaches it to treat content under these labels differently. But the model enforcing this distinction is a learned behaviour, not a hardware guarantee. A sufficiently crafted adversarial input can override learned behaviour. A hardware memory protection boundary cannot be overridden from user space. The practical implication: no input validation or output filtering applied at the application layer can create the privilege separation the architecture does not provide. Defences that treat injection as an input sanitisation problem are working in the wrong layer.

Key Point

Privilege separation in LLM deployments must be implemented at the infrastructure layer -- through context isolation, request routing, and output monitoring -- because the model layer provides none.

6.1.3

Title

Instruction Hierarchy in Practice: What System Prompts Actually Guarantee

Content

LLM deployments use a three-tier instruction structure in practice. The system prompt, set by the operator, appears first in the context. The conversation history, built from prior user and assistant turns, follows. The current user message appears last. The model's training instils a tendency to treat instructions appearing earlier and in "system" delimited sections as higher priority than instructions appearing in user turns. This tendency is real and measurable. Empirically, models are more likely to follow system prompt instructions than conflicting user instructions when the conflict is explicit. The training data rewards this behaviour. RLHF reinforces it. The effect exists. But it is a tendency, not a guarantee. There are three reasons this matters for security. First, context length modulates the effect. As the context window fills with user and retrieved content, the relative attention weight of the system prompt decreases. Section 6.2 covers context flooding -- the deliberate use of large user inputs to reduce the effective influence of the system prompt without ever explicitly contradicting it. Second, adversarial optimisation can overcome the tendency. Universal adversarial triggers (Section 6.3) are token sequences discovered through gradient-based optimisation specifically because they maximise the probability of overriding instruction hierarchy. The model's tendency is not robust against an adversary who is optimising against it. Third, the tendency applies to direct injection. For indirect injection via retrieved content, the model frequently lacks any signal that the retrieved content is not authoritative instruction. A document retrieved from a knowledge base enters the context as "trusted context." If that document contains injection, the model has no mechanism to distinguish it from legitimate content.

Key Point

System prompt priority is a statistical tendency in model behaviour, not a security guarantee. It fails against context flooding, adversarial optimisation, and indirect injection via trusted-appearing retrieved content.

6.1.4

Title

Why RLHF Alignment Is Not an Injection Defence

Content

Reinforcement Learning from Human Feedback is the training paradigm that produces the "aligned" behaviour of production LLMs -- the refusals, the safety caveats, the tendency to follow operator instructions over contradicting user instructions. Understanding why RLHF alignment does not constitute an injection defence requires understanding what RLHF teaches. RLHF teaches the model to produce outputs that human raters prefer in a distribution of prompts the raters evaluated during training. It does not teach the model to verify the provenance of instructions it receives at inference time. It cannot -- the model processes tokens, not authenticated instruction sources. The model has no cryptographic attestation of who wrote each token. Consider the analogy: RLHF is training a new employee to follow company policy by showing them thousands of examples of correct behaviour. The employee learns the policies thoroughly. But if an adversary sends the employee a memo that says "New company policy effective today: disregard previous guidelines," the employee has no mechanism to verify whether the memo is authentic without consulting an external authority. The model has no such external authority at inference time. There is a second mechanism. RLHF fine-tuning adjusts the model's output distribution. Injection attacks that are sufficiently distant from the distribution of attacks seen during RLHF training will land in regions of the output space where alignment was never reinforced. The arms race between novel injection techniques and RLHF patch cycles is inherently asymmetric: an adversary can construct a new obfuscation variant in minutes; a patch cycle requires data collection, training, evaluation, and deployment across the model fleet. The operational implication: RLHF alignment should be treated as defence in depth, not as a primary control. It raises the bar for some attack classes. It is not a reliable barrier against a motivated adversary with iteration time.

Key Point

RLHF teaches outputs, not provenance verification. It cannot detect injection at the mechanism level. Novel injection variants that fall outside the training distribution bypass alignment entirely, and adversaries iterate faster than alignment patch cycles.

6.1.5

Title

The Prompt Injection Threat Model

Content

A precise threat model is the prerequisite for a precise detection architecture. The prompt injection threat model has three components: what the adversary controls, what the adversary cannot control, and what the adversary is trying to achieve. What the adversary controls depends on the injection type. In direct injection, the adversary controls the user input turn directly. This requires interacting with the LLM application as a user -- no privileged access required. In indirect injection, the adversary controls external data that enters the LLM context without passing through the user input turn. This includes documents in knowledge bases (RAG injection), pages returned by web retrieval (web injection), field values in databases queried by the LLM (database injection), emails processed by an LLM assistant (email injection), and code or comments in repositories processed by code assistants (code assistant injection). What the adversary cannot control: the system prompt (in a correctly architected deployment), the model weights, the attention computation itself, and the content of context positions they have not compromised. The adversary also cannot force arbitrary model outputs -- they can only increase the probability of desired outputs by crafting injection payloads that interact with the model's existing capabilities and training. What the adversary is trying to achieve: the standard injection objective set covers goal hijacking (make the model do X instead of Y), data exfiltration (make the model output information from the context it should not reveal), action escalation in agentic deployments (make the model call a tool with adversary-specified arguments), and system prompt extraction (make the model reveal the contents of its system prompt). Section 6.2 through Section 6.13 maps these objectives to specific attack patterns. The four injection surfaces in every LLM deployment are: the system prompt (operator-controlled, rarely a direct adversary surface but can be targeted via second-order injection), user input (direct injection surface), retrieved external context (indirect injection surface -- RAG, web, database, email, code), and tool output (agentic injection surface -- any tool whose output enters the LLM context). A complete injection detection architecture must cover all four surfaces.

Key Point

The injection threat model must be specified per-surface. Direct injection via user input and indirect injection via retrieved content require different classifier placement and different detection signals.

Subsection 6

Number

6.1.6

Title

Direct vs Indirect Injection: Two Surfaces, One Underlying Mechanism

Content

The direct/indirect distinction in prompt injection refers to the adversary's relationship to the LLM application, not to the attack mechanism. Both direct and indirect injection exploit the same underlying property: the model processes tokens from all context sources identically. Direct injection: the adversary interacts with the LLM application as a legitimate user and places the injection payload in the user input turn. They control the surface directly. Detection focus: incoming user requests. The adversary is known to the application at the network layer (they have a session) even if their identity is pseudonymous. Indirect injection: the adversary plants a payload in an external data source that the LLM will retrieve and process. The adversary never interacts with the LLM application directly. When a legitimate user makes a benign request, the LLM retrieves the adversary's planted payload as part of fulfilling that request and executes the injection. The application sees only a legitimate user request at the input layer. This distinction has major implications for detection architecture. A classifier that runs on user input catches direct injection but is blind to indirect injection. The legitimate user's request is benign; the injection is in the retrieved content. An indirect injection detection architecture must run the classifier on retrieved content before it enters the context assembly stage. The distinction also has implications for attribution. Direct injection requires the adversary to interact with the application, creating network logs, session records, and rate-limit exposure. Indirect injection creates no such traces on the target application -- the adversary's only footprint is in the external data source they compromised, which may be a public webpage, a third-party database, or a package registry. ATLAS classification maps this precisely: AML.T0051 covers direct injection (the adversary submits the payload), AML.T0051.001 covers indirect injection (the payload arrives via external data). Section 6.17 builds a production classifier that covers both.

Key Point

Indirect injection is architecturally invisible at the input layer. Most production deployments classify user input but apply no classifier to retrieved content. This is where the majority of real-world injection incidents occur.

Subsection 7

Number

6.1.7

Title

Injection vs Jailbreak -- Why No CVE -- SQL Injection Analogy

Content

Three conceptual clarifications that matter for building accurate detection. Injection vs jailbreak. These terms are often used interchangeably. Precise definitions: prompt injection is an attack in which an adversary inserts instructions into the LLM's context to override operator intent, hijack model behaviour, or cause the model to perform unintended actions. The adversary controls a context source. A jailbreak is an attack that causes the model to bypass its alignment constraints -- to produce outputs the model was trained to refuse. Jailbreaks are a subset of injection payloads: they inject instructions specifically designed to override alignment. Not all injections are jailbreaks (some injections hijack goal without triggering refusal behaviour) and not all jailbreaks are injections in the indirect sense (a jailbreak submitted in the user turn is direct injection). Section 6.3 covers the full jailbreak taxonomy. Why prompt injection has no CVE. The CVE system classifies vulnerabilities in specific software versions. A CVE implies a patch: a code change that closes the vulnerability. Prompt injection is not a bug in a specific model version. It is a consequence of the transformer architecture processing tokens without provenance verification -- a property shared by every current production LLM. There is no code change that closes it without changing the architecture. Model providers issue alignment updates that raise the bar against known injection patterns, but these are not patches in the CVE sense: they do not close the surface, they add friction. The absence of a CVE is not evidence of low severity. It is evidence that the standard vulnerability taxonomy was built for software bugs, not architectural properties. The SQL injection analogy. The comparison between SQL injection and prompt injection is the most common educational framing, and it is useful to a point. Both attacks share the same root cause structure: user-controlled input is parsed by an interpreter that cannot distinguish data from instructions without explicit separation. In SQL injection, user input is interpolated into a SQL query and the database engine parses the result without knowing which tokens came from the developer and which from the user. In prompt injection, user or external content is interpolated into the LLM context and the model processes the result without knowing which tokens are instructions and which are data. The analogy breaks down in three places relevant to defence. First, SQL injection has a complete and deployable fix: parameterised queries, which enforce the instruction-data boundary at the protocol level. No equivalent mechanism exists for LLMs -- the model must receive natural language, and natural language can always contain instruction-like content. Second, SQL injection exploits a parsing rule with defined syntax. LLMs do not have defined syntax -- they process natural language, which means any natural language construct can potentially carry instruction semantics. Third, SQL injection payloads are structurally detectable by examining the token stream for SQL grammar constructs. Injection payloads in natural language are semantically defined -- detection requires understanding intent, not parsing grammar. These three differences are the argument for semantic classifiers over input sanitisation, which is the argument Section 6.4 and Section 6.17 complete.

Key Point

The SQL injection analogy clarifies the root cause but obscures the defence. Parameterised queries work for SQL because syntax is machine-parseable. Natural language has no equivalent -- injection defence in LLMs requires semantic understanding, not input sanitisation.

import json
import sys
from dataclasses import dataclass, field
from typing import Optional
import numpy as np

# Optional: use transformers if available, else simulate with deterministic data
try:
    import torch
    from transformers import AutoTokenizer, AutoModel

@dataclass
class ContextSource:
    """Represents one source segment of the LLM context window."""
    name: str
    text: str
    colour: str
    source_type: str  # system_prompt | user_input | retrieved_context | tool_output


@dataclass
class InjectionSurfaceReport:
    """Summary of cross-source attention as injection surface evidence."""
    total_tokens: int
    source_boundaries: dict
    cross_source_attention_mean: float
    cross_source_attention_max: float
    highest_cross_source_pairs: list
    injection_surface_score: float  # 0-1, higher = larger injection surface


def build_context_window(sources: list[ContextSource]) -> tuple[str, list[tuple]]:
    """
    Concatenate sources into a flat token sequence and track boundaries.
    Returns the full text and a list of (source_name, start_char, end_char) tuples.
    """
    full_text = ""
    boundaries = []
    for src in sources:
        start = len(full_text)
        full_text += src.text + " "
        end = len(full_text)
        boundaries.append((src.name, src.source_type, start, end))
    return full_text.strip(), boundaries


def simulate_attention_weights(num_tokens: int, seed: int = 42) -> np.ndarray:
    """
    Simulate attention weight matrix when transformers library unavailable.
    Uses a realistic pattern: higher self-attention on diagonal, meaningful
    cross-token attention reflecting semantic proximity, with slight
    positional decay -- approximating real transformer behaviour.
    """
    rng = np.random.default_rng(seed)
    # Base: random weights
    weights = rng.dirichlet(np.ones(num_tokens) * 0.5, size=num_tokens)
    # Boost diagonal (self-attention)
    for i in range(num_tokens):
        weights[i, i] *= 3.0
    # Boost local neighbourhood (positional proximity)
    for i in range(num_tokens):
        for j in range(max(0, i - 2), min(num_tokens, i + 3)):
            weights[i, j] *= 1.5
    # Renormalise rows
    row_sums = weights.sum(axis=1, keepdims=True)
    weights = weights / row_sums
    return weights


def extract_attention_weights_real(
    full_text: str,
    model_name: str = "distilbert-base-uncased"
) -> tuple[np.ndarray, list[str]]:
    """
    Extract real attention weights from a transformer model.
    Uses the first attention head of the last layer.
    Returns (attention_matrix, token_list).
    """
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    model = AutoModel.from_pretrained(
        model_name, output_attentions=True
    )
    model.eval()
    inputs = tokenizer(
        full_text,
        return_tensors="pt",
        truncation=True,
        max_length=256
    )
    tokens = tokenizer.convert_ids_to_tokens(inputs["input_ids"][0])
    with torch.no_grad():
        outputs = model(**inputs)
    # Last layer, first head, first batch item
    attn = outputs.attentions[-1][0, 0].numpy()
    return attn, tokens


def map_tokens_to_sources(
    tokens: list[str],
    char_boundaries: list[tuple],
    full_text: str
) -> list[str]:
    """
    Map each token index to its source name by reconstructing character positions.
    This is approximate for wordpiece tokenisers.
    """
    # Build char-to-source mapping
    char_source = []
    for src_name, src_type, start, end in char_boundaries:
        for _ in range(start, end):
            char_source.append(src_name)
    # Pad if needed
    while len(char_source) < len(full_text):
        char_source.append(char_boundaries[-1][0])

    token_sources = []
    char_pos = 0
    for tok in tokens:
        clean = tok.replace("##", "").replace("[CLS]", "").replace("[SEP]", "")
        if clean == "" or tok in ("[CLS]", "[SEP]", "[PAD]"):
            token_sources.append("special")
            continue
        # Find where this token starts in the text
        idx = full_text.lower().find(clean.lower(), char_pos)
        if idx == -1:
            idx = char_pos
        src = char_source[min(idx, len(char_source) - 1)]
        token_sources.append(src)
        char_pos = idx + len(clean)
    return token_sources


def compute_cross_source_attention(
    attn_matrix: np.ndarray,
    token_sources: list[str]
) -> dict:
    """
    Compute attention flowing between different source segments.
    Returns dict of (src_from, src_to) -> mean_attention_weight.
    """
    cross = {}
    n = len(token_sources)
    for i in range(n):
        for j in range(n):
            if i >= attn_matrix.shape[0] or j >= attn_matrix.shape[1]:
                continue
            src_i = token_sources[i]
            src_j = token_sources[j]
            key = (src_i, src_j)
            if key not in cross:
                cross[key] = []
            cross[key].append(float(attn_matrix[i, j]))
    return {k: np.mean(v) for k, v in cross.items()}


def compute_injection_surface_score(
    cross_source_attn: dict,
    sources: list[ContextSource]
) -> float:
    """
    Compute injection surface score: mean cross-source attention weight
    between non-identical sources, normalised to [0, 1].
    Higher score = larger injection surface = attention mechanism more
    susceptible to cross-source instruction bleeding.
    """
    source_names = [s.name for s in sources]
    cross_values = [
        v for (s1, s2), v in cross_source_attn.items()
        if s1 != s2 and s1 in source_names and s2 in source_names
    ]
    if not cross_values:
        return 0.0
    mean_cross = np.mean(cross_values)
    # Theoretical max cross-source attention if perfectly uniform: 1/n_sources
    # Score as ratio to that upper bound, capped at 1.0
    n = len(source_names)
    upper_bound = 1.0 / n if n > 0 else 1.0
    return min(1.0, mean_cross / upper_bound)


def visualise_attention_heatmap(
    attn_matrix: np.ndarray,
    token_sources: list[str],
    sources: list[ContextSource],
    output_path: str = "injection_surface_heatmap.png"
) -> None:
    """
    Render annotated attention heatmap with source boundary overlays.
    Saves to file.
    """
    if not MATPLOTLIB_AVAILABLE:
        print("[WARN] matplotlib not available -- skipping heatmap render")
        return

    n = min(attn_matrix.shape[0], 64)  # cap for readability
    attn_display = attn_matrix[:n, :n]

    fig, ax = plt.subplots(figsize=(12, 10))
    im = ax.imshow(attn_display, cmap="YlOrRd", aspect="auto")

    # Draw source boundary lines
    unique_sources_ordered = []
    for ts in token_sources[:n]:
        if ts not in unique_sources_ordered:
            unique_sources_ordered.append(ts)

    src_colour_map = {s.name: s.colour for s in sources}
    prev_src = None
    boundary_positions = []
    for i, ts in enumerate(token_sources[:n]):
        if ts != prev_src and prev_src is not None:
            boundary_positions.append(i - 0.5)
            ax.axhline(y=i - 0.5, color="white", linewidth=2.0, linestyle="--")
            ax.axvline(x=i - 0.5, color="white", linewidth=2.0, linestyle="--")
        prev_src = ts

    plt.colorbar(im, ax=ax, label="Attention Weight")
    ax.set_title(
        "Self-Attention Heatmap: Cross-Source Injection Surface\n"
        "(white dashed lines = source boundaries -- attention crosses them freely)",
        fontsize=13, fontweight="bold"
    )
    ax.set_xlabel("Key Token Position (source)")
    ax.set_ylabel("Query Token Position (attending from)")

    # Legend
    patches = [
        mpatches.Patch(color=s.colour, label=f"{s.name} ({s.source_type})")
        for s in sources
    ]
    ax.legend(handles=patches, loc="upper right", fontsize=9)

    plt.tight_layout()
    plt.savefig(output_path, dpi=150, bbox_inches="tight")
    print(f"[OK] Heatmap saved to: {output_path}")
    plt.close()


def generate_report(
    sources: list[ContextSource],
    attn_matrix: np.ndarray,
    token_sources: list[str],
    cross_source_attn: dict
) -> InjectionSurfaceReport:
    """Build the injection surface report from attention analysis."""
    cross_only = {
        k: v for k, v in cross_source_attn.items() if k[0] != k[1]
    }
    cross_vals = list(cross_only.values())
    cross_mean = float(np.mean(cross_vals)) if cross_vals else 0.0
    cross_max = float(np.max(cross_vals)) if cross_vals else 0.0

    top_pairs = sorted(cross_only.items(), key=lambda x: x[1], reverse=True)[:5]

    source_boundaries = {}
    for i, ts in enumerate(token_sources):
        if ts not in source_boundaries:
            source_boundaries[ts] = {"start_token": i, "end_token": i}
        source_boundaries[ts]["end_token"] = i

    inj_score = compute_injection_surface_score(cross_source_attn, sources)

    return InjectionSurfaceReport(
        total_tokens=len(token_sources),
        source_boundaries=source_boundaries,
        cross_source_attention_mean=cross_mean,
        cross_source_attention_max=cross_max,
        highest_cross_source_pairs=[(str(k), round(v, 4)) for k, v in top_pairs],
        injection_surface_score=round(inj_score, 4)
    )


def print_report(report: InjectionSurfaceReport, sources: list[ContextSource]) -> None:
    """Print structured report to stdout."""
    print("\n" + "=" * 70)
    print("INJECTION SURFACE REPORT -- Section 6.1")
    print("=" * 70)
    print(f"Total tokens analysed : {report.total_tokens}")
    print(f"Context sources       : {len(sources)}")
    for src in sources:
        bounds = report.source_boundaries.get(src.name, {})
        print(f"  [{src.source_type:20s}] {src.name:20s} "
              f"tokens {bounds.get('start_token', '?')}-{bounds.get('end_token', '?')}")
    print()
    print(f"Cross-source attention mean : {report.cross_source_attention_mean:.4f}")
    print(f"Cross-source attention max  : {report.cross_source_attention_max:.4f}")
    print(f"Injection surface score     : {report.injection_surface_score:.4f} "
          f"(0=no cross-source, 1=maximal)")
    print()
    print("Top cross-source attention flows (injection vectors):")
    for pair, weight in report.highest_cross_source_pairs:
        print(f"  {pair:<50s} weight={weight:.4f}")
    print()
    print("INTERPRETATION:")
    score = report.injection_surface_score
    if score > 0.6:
        print("  HIGH injection surface. User input and retrieved content tokens")
        print("  attend strongly to system prompt tokens -- injection payloads in")
        print("  either surface can significantly influence model behaviour.")
    elif score > 0.3:
        print("  MODERATE injection surface. Cross-source attention present.")
        print("  Injection is feasible; obfuscation may increase success rate.")
    else:
        print("  LOW injection surface score (may reflect short context or")
        print("  limited cross-source content). Extend context for realistic assessment.")
    print("=" * 70)

def identify_active_surfaces(config: DeploymentConfig) -> list[str]:
    """Return injection surface IDs that apply to this deployment."""
    surfaces = ["user_input"]  # always present

    source_type_map = {
        "rag_knowledge_base": "retrieved_context_rag",
        "web_retrieval": "retrieved_context_web",
        "email": "retrieved_context_email",
        "database": "retrieved_context_database",
        "code_repo": "retrieved_context_code",
        "file_upload": "retrieved_context_rag",
    }
    for ds in config.data_sources:

def score_surface_risk(
    surface_id: str,
    config: DeploymentConfig
) -> tuple[str, str]:
    """
    Return (risk_level, rationale) for a given surface given deployment config.
    """
    # Find relevant data source if applicable
    if surface_id == "user_input":
        if config.user_input_classifier_deployed:
            return "medium", "Classifier deployed; obfuscation variants may bypass"
        return "high", "No classifier on user input"

    if surface_id == "tool_output":
        tools = [t for t in config.tool_integrations if t.output_enters_context]
        sandboxed = all(t.sandboxed for t in tools) if tools else True
        if not tools:
            return "none", "No tool integrations with context output"
        if sandboxed:
            return "medium", "Tools sandboxed; confused deputy risk reduced but not eliminated"
        return "critical", "Unsandboxed tools with output entering context"

    if surface_id == "agent_memory":
        if not config.agent_memory_enabled:
            return "none", "Agent memory not enabled"
        return "critical", "Persistent injection surface -- crosses session boundaries"

    # Data source surfaces
    ds_type_map = {
        "retrieved_context_rag": "rag_knowledge_base",
        "retrieved_context_web": "web_retrieval",
        "retrieved_context_email": "email",
        "retrieved_context_database": "database",
        "retrieved_context_code": "code_repo",
    }
    ds_type = ds_type_map.get(surface_id)
    if not ds_type:
        return "unknown", "Surface not in type map"

    matching_sources = [ds for ds in config.data_sources if ds.source_type == ds_type]
    if not matching_sources:
        return "none", "Data source type not in deployment"

    any_high_access = any(
        ds.adversary_write_access in ("medium", "high") for ds in matching_sources
    )
    any_classifier = any(ds.injection_classifier_deployed for ds in matching_sources)

    if any_high_access and not any_classifier:
        return "critical", "High adversary write access, no retrieval classifier"
    if any_high_access and any_classifier:
        return "high", "High adversary write access, classifier present but bypassable"
    if not any_classifier:
        return "high", "No retrieval classifier on this source"
    return "medium", "Classifier present; medium residual risk"


def identify_coverage_gaps(
    surfaces: list[str],
    config: DeploymentConfig
) -> list[dict]:
    """Identify surfaces with no detection control."""
    gaps = []
    for surf_id in surfaces:
        risk, rationale = score_surface_risk(surf_id, config)
        if risk in ("critical", "high") and not (
            surf_id == "user_input" and config.user_input_classifier_deployed
        ):
            surface = INJECTION_SURFACES[surf_id]
            objectives = [
                ATTACK_OBJECTIVES[obj]
                for obj in surface["primary_objectives"]
                if obj in ATTACK_OBJECTIVES
            ]
            max_impact = "critical" if any(
                o["impact"] == "critical" for o in objectives
            ) else "high"
            gaps.append({
                "surface": surf_id,
                "surface_label": surface["label"],
                "risk": risk,
                "rationale": rationale,
                "max_objective_impact": max_impact,
                "atlas": surface["atlas_technique"],
                "recommended_control": (
                    "Deploy injection classifier on retrieved content before context assembly"
                    if "retrieved" in surf_id
                    else (
                        "Deploy injection classifier on user input (Section 6.17)"
                        if surf_id == "user_input"
                        else (
                            "Implement tool output validation + call graph monitoring"
                            if surf_id == "tool_output"
                            else "Implement memory write audit + anomaly detection"
                        )
                    )
                ),
            })
    return sorted(gaps, key=lambda x: 0 if x["risk"] == "critical" else 1)

def score_controls(controls: list[AssessmentControl]) -> int:
    """Compute total score from implemented controls."""
    score = 0
    for c in controls:
        if c.implemented:
            score += c.weight
        elif c.partial:
            score += c.weight // 2
    return score


def classify_maturity(score: int, max_score: int) -> str:
    pct = (score / max_score) * 100 if max_score else 0
    if pct >= 80:
        return "MANAGED -- Comprehensive injection defence in place"
    if pct >= 60:
        return "DEFINED -- Core controls present; gaps in advanced surfaces"
    if pct >= 40:
        return "DEVELOPING -- Partial controls; significant injection risk"
    if pct >= 20:
        return "INITIAL -- Minimal controls; high injection risk across most surfaces"
    return "ABSENT -- No meaningful injection defence"


def identify_critical_gaps(controls: list[AssessmentControl]) -> list[str]:
    """Return control IDs for critical unimplemented controls (weight >= 10)."""
    return [
        c.control_id
        for c in controls
        if not c.implemented and c.weight >= 10
    ]


def prioritise_remediation(controls: list[AssessmentControl]) -> list[str]:
    """
    Order unimplemented controls by weight descending.
    Returns list of control_id strings in priority order.
    """
    unimplemented = [
        c for c in controls
        if not c.implemented
    ]
    ordered = sorted(unimplemented, key=lambda c: c.weight, reverse=True)
    return [c.control_id for c in ordered]


def run_assessment(controls: list[AssessmentControl]) -> AssessmentResult:
    max_score = sum(c.weight for c in controls)
    score = score_controls(controls)
    maturity = classify_maturity(score, max_score)
    critical_gaps = identify_critical_gaps(controls)
    remediation_priority = prioritise_remediation(controls)
    return AssessmentResult(
        total_score=score,
        max_score=max_score,
        maturity_level=maturity,
        controls=controls,
        critical_gaps=critical_gaps,
        remediation_priority=remediation_priority,
    )

    print("=" * 72)
    pct = round((result.total_score / result.max_score) * 100)
    print(f"Score       : {result.total_score}/{result.max_score} ({pct}%)")
    print(f"Maturity    : {result.maturity_level}")
    print()
    print("Control Status:")
    print(f"  {'ID':<5} {'Weight':>6} {'Status':<12} {'Surface':<20} Description")
    print(f"  {'-'*5} {'-'*6} {'-'*12} {'-'*20} {'-'*40}")
    for c in sorted(result.controls, key=lambda x: x.weight, reverse=True):
        status = "IMPLEMENTED" if c.implemented else ("PARTIAL" if c.partial else "MISSING")

            f"  {c.control_id:<5} {c.weight:>6}   {status:<12} "
            f"{c.surface:<20} {c.description}"
        )
    print()
    if result.critical_gaps:
        print(f"Critical gaps (weight >= 10, not implemented): {len(result.critical_gaps)}")
        for ctrl_id in result.critical_gaps:
            ctrl = next(c for c in result.controls if c.control_id == ctrl_id)
            print(f"  [{ctrl_id}] {ctrl.description}")
            print(f"         Note: {ctrl.notes}")
    else:
        print("No critical gaps identified.")
    print()
    print("Remediation Priority Order:")
    for i, ctrl_id in enumerate(result.remediation_priority, 1):
        ctrl = next(c for c in result.controls if c.control_id == ctrl_id)
        print(f"  {i:>2}. [{ctrl_id}] weight={ctrl.weight:>3} -- {ctrl.description}")
    print()
    print("Reference: Section 6.17 production classifier addresses C01 and C02.")
    print("=" * 72)


def export_json(result: AssessmentResult, path: str = "assessment_result.json") -> None:
    data = {
        "total_score": result.total_score,
        "max_score": result.max_score,
        "score_pct": round((result.total_score / result.max_score) * 100),
        "maturity_level": result.maturity_level,
        "critical_gaps": result.critical_gaps,
        "remediation_priority": result.remediation_priority,
        "controls": [
            {
                "id": c.control_id,
                "description": c.description,
                "surface": c.surface,
                "weight": c.weight,
                "implemented": c.implemented,
                "partial": c.partial,
                "notes": c.notes,
            }
            for c in result.controls
        ],
    }
    with open(path, "w") as f:
        json.dump(data, f, indent=2)
    print(f"[OK] Assessment JSON exported to: {path}")


def interactive_assessment() -> list[AssessmentControl]:
    """
    Walk through each control and ask the user whether it is implemented.
    Returns configured control list.
    """
    print("\nInstruction-Data Separation Self-Assessment")
    print("Answer each control: [y]es / [n]o / [p]artial")
    print()
    controls = []
    for ctrl in CONTROLS:
        prompt = (
            f"[{ctrl.control_id}] (weight={ctrl.weight}) "
            f"{ctrl.description}\n"
            f"  Hint: {ctrl.notes}\n"
            f"  Status [y/n/p]: "
        )
        resp = input(prompt).strip().lower()
        ctrl.implemented = resp == "y"
        ctrl.partial = resp == "p"
        controls.append(ctrl)
        print()
    return controls

Section Summary

Section 6.1 established the mechanistic foundation for everything that follows in Chapter 6. The core argument: prompt injection is not a software defect. It is an architectural property of the transformer model -- self-attention processes tokens from all context sources with identical computation, and the context window is a flat sequence with no hardware-enforced privilege separation. RLHF alignment teaches the model to produce preferred outputs; it cannot verify the provenance of instructions at inference time and it is not a reliable barrier against adversaries who iterate faster than patch cycles. Direct injection (AML.T0051) and indirect injection (AML.T0051.001) exploit the same underlying mechanism through different adversary positions. The four injection surfaces -- user input, retrieved context, tool output, and agent memory -- each require distinct classifier placement and detection signals. Most production deployments classify user input only, leaving the indirect injection surface entirely unmonitored. The SQL injection analogy is useful for communicating root cause and useless for communicating defence: parameterised queries solved SQL injection because syntax is parseable; natural language injection requires semantic intent detection, not input sanitisation. Section 6.2 begins the attack taxonomy. Section 6.17 builds the production classifier. This section is the argument for why that classifier must be semantic, must cover all four surfaces, and must be deployed at the infrastructure layer rather than the model layer.
