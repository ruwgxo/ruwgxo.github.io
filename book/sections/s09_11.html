Section 9.11: Production Query Monitoring and Rate Limiting

Section Overview

One Line Summary

The input-side capstone wires the Section 9.10 detection library into a production query monitor as Track 6 of the Chapter 6/7 gateway, pairs it with a four-dimension adaptive rate limiter, adds a cross-user collusion detector for distributed campaigns, completes the AML.T0040/T0024 Sigma rule, and closes the input-side half of OWASP LLM10.

Why This Section Exists

Section 9.10 built five detection primitives and showed they achieve 88 to 98 percent detection rates against most extraction attack families. Those rates exist on paper until the primitives are wired into production infrastructure. Section 9.11 does that wiring. Three integration challenges must be solved. First, the primitives require per-user state that persists across requests -- a stateful layer that the Chapter 6 and 7 gateway did not need. Second, detection without action is observation, not defence: the rate limiter must translate primitive scores into enforcement decisions that impose real query budget costs on adversaries. Third, per-user monitoring is bypassable by distributed campaigns: an adversary who splits their query budget across ten accounts can evade any per-user threshold. A cross-user collusion detector closes this gap. The section also completes the AML.T0040/T0024 Sigma rule. Chapter 5 Section 5.8 introduced the AML stub pattern -- a skeleton Sigma rule for ATLAS techniques that is populated with specific detection logic when a production control is built. Section 9.11 is where that population happens for the two ATLAS techniques that anchor Chapter 9. The architectural position is Track 6 in the Chapter 6/7 unified gateway ensemble. Tracks 1 through 5 (injection classifier, OOD detector, semantic consistency checker, jailbreak ensemble, pattern analyser) from Chapters 6 and 7 run unchanged. Track 6 runs in parallel, using the same asynchronous dispatch pattern, within the same 50ms P99 latency budget. The monitor is stateful; the other five tracks are stateless. This is the only structural difference from the Chapter 6/7 architecture.

Position In Chapter

Section 9.11 of 13. Input-side production capstone. Pairs with Section 9.12 (output-side capstone) to close OWASP LLM10. The Sigma rule completed here is the formal compliance artefact for AML.T0040 and AML.T0024 detection.

Title

The Input-Side Capstone: Design Brief and Architectural Position

Body

The Chapter 6 production injection classifier was the first gateway component. Chapter 7 extended it to a parallel ensemble of five tracks, each processing every incoming request asynchronously within the 50ms P99 latency budget. Section 9.11 adds Track 6: query monitoring with per-user state tracking. The design brief for Track 6 has four requirements that distinguish it from Tracks 1 through 5. First, it is stateful: it maintains a rolling window of query statistics per user that persists across requests, sessions, and days. The other five tracks are stateless -- they read a request and return a score without memory of prior requests. Track 6 reads a request, updates a per-user state store, and returns a score derived from the accumulated state. Second, it is extraction-aware: the rate limiting policy it drives is calibrated against extraction query budgets (the Section 9.2 budget-fidelity curves) rather than infrastructure throughput capacity. A rate limit set purely for infrastructure protection may allow complete extraction within normal usage volumes; a rate limit calibrated against extraction economics imposes real adversary cost at the relevant query count. Third, it is cross-user aware: distributed campaigns that split query budgets across multiple accounts are invisible to per-user state tracking. The cross-user correlator is a separate component that runs at lower frequency than the per-request monitor and examines semantic similarity patterns across user accounts within a time window. Fourth, it is the Sigma rule target: the AML.T0040/T0024 Sigma rule is a formal detection specification that requires a concrete observable (the query monitor''s alert events) to be actionable. Completing the Sigma rule means the query monitor produces alert events in a format the SIEM can ingest and correlate with other intelligence.

Title

Track 6 Integration: Parallel Query Monitoring in the Gateway Ensemble

Body

The Chapter 6/7 gateway dispatches each incoming request to five parallel workers, collects their scores within the latency budget, and applies the ensemble routing decision. Track 6 joins as a sixth parallel worker using the same dispatch and collection mechanism. The integration has one structural asymmetry: Track 6 requires a write to the per-user state store on every request, whereas Tracks 1 through 5 are read-only with respect to external state. This write must be non-blocking from the gateway''s perspective: if the state store write fails or times out, the gateway must fall back to stateless operation (using only Tracks 1 through 5) rather than failing the request. The write is fire-and-forget from the latency-critical path; the state is eventually consistent across requests. Track 6''s score is computed from the state read, not the state write. On each request, Track 6 first reads the current per-user state (the rolling window of query embeddings, labels, and cost entries), computes the five primitive scores from Section 9.10, combines them into the ensemble score, and returns that score to the gateway dispatcher. The state write updates the window with the current request''s data and is dispatched asynchronously after the score is returned. This read-then-write pattern means Track 6''s score reflects the state as of the previous request, not the current one. The one-request lag is acceptable: extraction detection operates on distributions across many queries, not on individual queries, and a one-query lag does not meaningfully reduce detection sensitivity. The latency budget constraint is met by pre-computing embeddings during Track 6''s async processing and caching them in the state store. The embedding computation (typically 5 to 15ms for a short sentence encoder) happens in a background worker, not on the critical path. Track 6''s on- path work is state read (< 2ms from an in-memory store), primitive scoring from pre-computed embeddings (< 5ms), and ensemble score computation (< 1ms). Total Track 6 latency on the critical path is under 10ms, well within the 50ms P99 budget shared with Tracks 1 through 5.

Title

query_monitor.py: Per-User State Architecture and Signal Integration

Body

The production query monitor is the orchestrating component that integrates per-user state management with the Section 9.10 detection primitives. Its responsibilities are: maintaining per-user state stores (sliding window of embeddings, labels, costs, and metadata), orchestrating the five primitive computations from Section 9.10, routing the ensemble result to the rate limiter, and emitting structured alert events. The per-user state store is a dictionary keyed by user ID, where each entry contains the sliding windows required by the five primitives: an embedding deque for the query pattern analyser and user concentration analyser, an (embedding, label) deque for the boundary query detector, a cost history deque for the output entropy monitor''s token count tracking, and a timestamp log for rate limit window computation. For production deployments, this in-memory state is backed by a distributed cache (Redis or equivalent) with a configurable TTL. The TTL determines how long inactivity resets the per-user window: a seven-day TTL means a user who is inactive for a week starts with a fresh window. The TTL is a security parameter: a shorter TTL makes extraction detection more fragile against patient adversaries who space queries to reset their window. The monitor emits structured alert events when the ensemble score exceeds the composite threshold or when any individual primitive exceeds its individual threshold. Each alert event contains: the user ID, the timestamp, the primitive scores breakdown, the composite score, the recommended action, and a trace ID linking to the specific request that triggered the alert. This structure is the input to the Sigma rule detector and the incident response playbook.

Title

rate_limiter.py: Adaptive Extraction-Aware Policy Framework

Body

The adaptive rate limiter translates detection scores into enforcement decisions across four independent policy dimensions. Each dimension bounds a different adversary strategy: requests per minute bounds rate-limit exhaustion and high-frequency campaigns; tokens per minute bounds total compute consumption; cost per hour bounds denial-of-wallet; input tokens per request bounds context padding. The extraction-aware calibration distinguishes this rate limiter from infrastructure-oriented rate limiters. For the requests-per-minute dimension, the calibration target is the query count required to complete the cheapest relevant extraction attack at the deployment''s specific model architecture. For a linear classifier deployment (Section 9.3 equation-solving), the relevant budget is O(d × log(1/ε)) queries; the per-user daily limit should force the adversary to spread this budget across multiple days, increasing the cross-session detection window. For an LLM deployment, the relevant budget is the soft-label distillation budget from Section 9.4; the daily limit should make a 50,000-query campaign take at least thirty days per account, giving the cross-user correlator time to identify distributed campaigns. Rate limit decisions are tiered rather than binary. The limiter has three action tiers: normal (no restriction), soft limit (reduced throughput, alert emitted), and hard limit (request rejected, alert escalated). The transition from normal to soft limit occurs when the ensemble score exceeds the tier-2 threshold (0.40 by default). The transition from soft to hard limit occurs when the ensemble score exceeds the tier-1 threshold (0.60) or when any individual boundary or query-pattern primitive exceeds its individual threshold (0.70). The tiered response reduces false positive impact on legitimate users: a user who briefly triggers the soft limit is throttled but not blocked. The rate limiter maintains a per-user leaky bucket state for each of the four dimensions. The leaky bucket refills at the configured rate and is decremented on each request by the request''s token count, cost, or input length as appropriate. When any bucket is empty, the limiter applies the corresponding tier''s enforcement action.

Title

cross_user_correlator.py: Distributed Campaign Detection

Body

The cross-user correlator runs as a background job at a lower frequency than the per-request query monitor -- typically once per hour. It analyses the query logs across all users within a configurable time window and identifies patterns that suggest coordinated extraction campaigns. The correlation mechanism has two signals. The first is semantic similarity clustering: if multiple users submit queries with high pairwise semantic similarity within a short time window, and those queries are individually anomalous on the OOD or boundary proximity dimensions, the correlation flags a potential distributed extraction campaign. Legitimate coordinated use (a team of users working on the same product query) produces high semantic similarity but typically scores low on the OOD and boundary dimensions. The second signal is temporal synchronisation: if multiple users submit queries at a rate that, when summed, substantially exceeds what the per-user limits allow individually, and the timing pattern suggests deliberate coordination (queries arriving in regular intervals from multiple accounts at the same rate), the correlator flags the pattern as rate-limit-aware distributed execution. The correlator output is a campaign risk score for each cluster of potentially coordinated users, a list of the user IDs in the cluster, the time window of the suspected campaign, and a recommended action (increase monitoring frequency for all accounts in the cluster, apply shared rate limits across the cluster, or escalate to manual review). The privacy implication of cross-user correlation is real and must be documented in the deployment''s privacy impact assessment: correlating query patterns across user accounts means the system processes data about multiple users jointly and can infer relationships between accounts that the users may not have disclosed. The correlator should operate only on anonymised embeddings (not raw query text) and should not retain cross-user correlation outputs beyond the investigation window.

Title

The AML.T0040/T0024 Sigma Rule: Completing the Detection Coverage

Body

MITRE ATLAS AML.T0040 (ML Model Inference API Access) and AML.T0024 (Exfiltration via ML Inference API) are the two ATLAS sub-techniques that Chapter 9 covers. A Sigma rule for these techniques enables SIEM platforms to ingest the query monitor''s alert events and correlate them with other threat intelligence. The Chapter 5 Section 5.8 AML stub pattern established the skeleton: a Sigma rule with title, status, description, ATLAS technique references, and a detection field populated with a placeholder. Section 9.11 populates the detection field with the specific log schema emitted by the query monitor''s alert events. The Sigma rule detects on three conditions combined with an OR logic: first, a query monitor alert event with composite score above the tier-1 threshold; second, a boundary query detector individual alert; and third, a cross-user correlator campaign alert for a cluster of three or more accounts within a 24-hour window. These three conditions correspond to the three most reliable signals in the detection primitive taxonomy: the ensemble (broadest coverage), the boundary detector (highest specificity for decision-boundary extraction), and cross-user clustering (coverage for distributed campaigns that evade per-user detection). The rule''s timeframe is set to fifteen minutes for real-time SIEM alerting. False positive reduction is achieved by requiring that the triggering event has either a composite score above 0.60 (not merely above the tier-2 soft limit of 0.40) or a boundary detector score above 0.70, or a cross-user cluster of three or more accounts. This three-tier specificity filter prevents the rule from generating high alert volume on marginal anomalies.

Title

Latency Budget Management: 50ms P99 Across All Tracks

Body

The latency budget constraint -- that the full six-track gateway ensemble must complete within 50ms at the P99 percentile -- drives architectural decisions throughout Section 9.11. Track 6 adds the highest latency risk because it requires state reads, primitive computations, and a state write that the other five tracks do not. The latency decomposition for Track 6 has four components. State read from an in-memory cache: 1 to 2ms. Primitive scoring from pre-computed embeddings: boundary query detector with k-d tree index (3 to 8ms), query pattern analyser on a 100-entry window (2 to 4ms), OOD detector isolation forest scoring (1 to 3ms), output entropy monitor (< 1ms), user concentration analyser (2 to 4ms). Ensemble combination (< 1ms). State write dispatched asynchronously (not on critical path). Total Track 6 critical-path latency: 10 to 20ms at P99. The critical-path embedding computation is pre-empted by a background worker. When a request arrives, the gateway dispatches it to all six tracks simultaneously. While Tracks 1 through 5 process the request content, Track 6 starts a background job to compute the request''s embedding and update the state store. The current request''s embedding is not available in the state for this request''s score -- it will be available from the next request onward. This is the acceptable one-request lag described in Part 2. Embedding precomputation for Track 6 uses a lightweight sentence encoder (a 6 to 22 million parameter model with sub-5ms inference on CPU) rather than the full model. The embedding quality is sufficient for the distributional anomaly detection the primitives require; it does not need to match the full model''s semantic precision. The latency benchmark in Deliverable 5 measures the full six-track gateway latency under simulated load to verify that the P99 target is met before production deployment.

Title

Deployment Checklist and Operational Considerations

Body

Eight pre-production verification items cover the query monitor''s production readiness. They are derived from the lessons learned in Section 9.9 and the calibration requirements of Section 9.10. Item 1: per-user state store is deployed and accessible within the latency budget. Verification: issue 100 sequential state reads and writes; confirm P99 round-trip under 2ms. Item 2: embedding model is loaded in the background worker and producing embeddings within the latency target. Verification: issue 100 embedding requests; confirm P99 under 5ms. Item 3: primitive thresholds are calibrated on at least 30 days of legitimate traffic. Verification: the calibration report from Section 9.10''s empirical harness shows false positive rate under 1 percent on held-out legitimate traffic. Item 4: rate limit policy dimensions are calibrated against the deployment''s specific extraction budget economics. Verification: for the model architecture in scope, compute the minimum query count for the cheapest relevant extraction technique; confirm the daily per-user limit forces that budget across at least ten days. Item 5: cross-user correlator is running at the configured frequency and producing output to the alert log. Verification: inject a synthetic three- account correlated campaign into the test environment; confirm the correlator flags the campaign within two correlation cycles. Item 6: alert events are routed to the SIEM in the Sigma rule''s expected log schema. Verification: trigger a test alert; confirm SIEM ingestion and rule match within 15 minutes. Item 7: the AML.T0040/T0024 Sigma rule is loaded in the SIEM and generating alerts against synthetic test events. Item 8: a false positive escalation path exists for legitimate high-volume users who are rate-limited. Verification: the rate limit appeals process is documented, the responsible team is identified, and the appeals SLA is defined. Two operational considerations warrant explicit documentation. False positive management is the primary operational challenge: a miscalibrated threshold produces alerts on legitimate users, generating analyst fatigue and business escalation. The rate limit''s tiered response (throttle before block) reduces the customer impact of false positives. The appeals process in Item 8 is the human-in-the-loop safety valve. Legitimate high-volume users (researchers, enterprise evaluation pipelines, automated testing) may trigger the volume and diversity signals legitimately. The deployment checklist should identify known high-volume users and configure custom per-user policy tiers that raise their throughput limits while tightening their boundary proximity and concentration thresholds.

# query_monitor.py
# Chapter 9 Section 9.11 -- Production Query Monitor (Track 6)
# Single quotes throughout per book convention.

import time
from dataclasses import dataclass, field, asdict
from typing import Any, Callable, Dict, List, Optional

import numpy as np

from detection_ensemble import (
    EnsembleConfig, PrimitiveScores, compute_ensemble, EnsembleResult,
)


@dataclass
class MonitorConfig:
    window_size: int = 100
    state_ttl_seconds: int = 604800  # 7 days
    embed_dim: int = 64
    composite_alert_threshold: float = 0.60
    boundary_individual_threshold: float = 0.70
    ensemble_config: EnsembleConfig = field(default_factory=EnsembleConfig)


@dataclass
class UserState:
    user_id: str
    query_embeddings: List[np.ndarray] = field(default_factory=list)
    query_labels: List[Optional[int]] = field(default_factory=list)
    query_texts: List[str] = field(default_factory=list)
    cost_history: List[float] = field(default_factory=list)
    last_updated: float = field(default_factory=time.time)


@dataclass
class AlertEvent:
    event_id: str
    user_id: str
    timestamp: float
    composite_score: float
    primitive_scores: Dict[str, float]
    individual_alerts: List[str]
    action: str
    trace_id: str
    atlas_techniques: List[str] = field(
        default_factory=lambda: ['AML.T0040', 'AML.T0024']
    )


class InMemoryStateStore:
    '''
    In-memory per-user state store with TTL eviction.
    Replace with a Redis adapter for production deployment.
    '''

    def __init__(self, ttl_seconds: int = 604800) -> None:
        self._store: Dict[str, UserState] = {}
        self._ttl = ttl_seconds

    def get(self, user_id: str) -> Optional[UserState]:
        state = self._store.get(user_id)
        if state is None:
            return None
        if time.time() - state.last_updated > self._ttl:
            del self._store[user_id]
            return None
        return state

    def set(self, user_id: str, state: UserState) -> None:
        state.last_updated = time.time()
        self._store[user_id] = state

    def evict_expired(self) -> int:
        now = time.time()
        expired = [uid for uid, s in self._store.items()
                   if now - s.last_updated > self._ttl]
        for uid in expired:
            del self._store[uid]
        return len(expired)


class QueryMonitor:
    '''
    Production query monitor. Track 6 in the Chapter 6/7 gateway ensemble.
    embed_fn: callable str -> np.ndarray (should be < 5ms P99).
    '''

    def __init__(
        self,
        embed_fn: Callable[[str], np.ndarray],
        config: Optional[MonitorConfig] = None,
        state_store: Optional[InMemoryStateStore] = None,
    ) -> None:
        self._embed = embed_fn
        self._cfg = config or MonitorConfig()
        self._store = state_store or InMemoryStateStore(self._cfg.state_ttl_seconds)
        self._alert_log: List[AlertEvent] = []

    def process_request(
        self,
        user_id: str,
        query_text: str,
        predicted_label: Optional[int] = None,
        confidence_vector: Optional[np.ndarray] = None,
        token_count: Optional[int] = None,
        cost_usd: Optional[float] = None,
        trace_id: str = '',
    ) -> EnsembleResult:
        '''
        Process one request and return the ensemble detection result.
        Updates per-user state asynchronously (in this implementation, synchronously
        for simplicity; in production, the state write is dispatched to a background worker).
        '''
        # Read current state
        state = self._store.get(user_id) or UserState(user_id=user_id)

        # Score from existing state (one-request lag is acceptable)
        scores = self._score_from_state(state, confidence_vector, token_count)
        result = compute_ensemble(scores, self._cfg.ensemble_config)

        # Emit alert if warranted
        if result.action != 'monitor':
            alert = AlertEvent(
                event_id=f'alert_{user_id}_{int(time.time() * 1000)}',
                user_id=user_id,
                timestamp=time.time(),
                composite_score=result.composite_score,
                primitive_scores={
                    'query_pattern': scores.query_pattern,
                    'ood': scores.ood,
                    'boundary': scores.boundary,
                    'entropy': scores.entropy,
                    'concentration': scores.concentration,
                },
                individual_alerts=result.individual_alerts,
                action=result.action,
                trace_id=trace_id,
            )
            self._alert_log.append(alert)

        # Update state (async in production; sync here for demonstration)
        embedding = self._embed(query_text)
        window = self._cfg.window_size
        state.query_embeddings = (state.query_embeddings + [embedding])[-window:]
        state.query_labels = (state.query_labels + [predicted_label])[-window:]
        state.query_texts = (state.query_texts + [query_text])[-window:]
        if cost_usd is not None:
            state.cost_history = (state.cost_history + [cost_usd])[-window:]
        self._store.set(user_id, state)

        return result

    def _score_from_state(
        self,
        state: UserState,
        confidence_vector: Optional[np.ndarray],
        token_count: Optional[int],
    ) -> PrimitiveScores:
        n = len(state.query_embeddings)
        if n < 3:
            return PrimitiveScores()

        embeddings = np.array(state.query_embeddings)
        norms = np.linalg.norm(embeddings, axis=1, keepdims=True)
        norms = np.where(norms == 0, 1.0, norms)
        normed = embeddings / norms

        # Query pattern: diversity + boundary proximity + meta-query rate
        sims = normed @ normed.T
        upper_idx = np.triu_indices(min(n, 50), k=1)
        mean_sim = float(sims[:50, :50][upper_idx].mean()) if n >= 2 else 0.0
        meta_count = sum(
            1 for t in state.query_texts
            if any(kw in t.lower() for kw in ['what can you', 'what are you', 'are you allowed'])
        )
        meta_rate = meta_count / max(n, 1)
        qp_score = min(0.5 * mean_sim + 0.3 * meta_rate, 1.0)

        # OOD: simplified proxy -- fraction of embeddings with norm outlier
        norms_flat = np.linalg.norm(embeddings, axis=1)
        norm_mean = float(norms_flat.mean())
        norm_std = float(norms_flat.std()) or 1.0
        ood_score = float(np.mean(np.abs(norms_flat - norm_mean) / norm_std > 2.0))

        # Boundary: opposite-label near-pairs
        labels = state.query_labels
        boundary_score = 0.0
        if len(set(l for l in labels if l is not None)) >= 2:
            flagged = 0
            labelled_emb = [(normed[i], labels[i]) for i in range(n) if labels[i] is not None]
            for i, (e_i, l_i) in enumerate(labelled_emb):
                for e_j, l_j in labelled_emb:
                    if l_i != l_j:
                        dist = float(1.0 - np.dot(e_i, e_j))
                        if dist < 0.30:
                            flagged += 1
                            break
            boundary_score = flagged / max(len(labelled_emb), 1)

        # Entropy (output-side)
        entropy_score = 0.0
        if confidence_vector is not None:
            p = np.clip(confidence_vector, 1e-10, 1.0)
            ent = float(-np.sum(p * np.log2(p)))
            max_ent = float(np.log2(len(p)))
            entropy_score = 1.0 - abs(ent / max(max_ent, 1e-10) - 0.5) * 2.0

        # Concentration: mean pairwise similarity
        concentration_score = round(min(mean_sim / 0.85, 1.0), 3)

        return PrimitiveScores(
            query_pattern=round(min(qp_score, 1.0), 3),
            ood=round(min(ood_score, 1.0), 3),
            boundary=round(min(boundary_score, 1.0), 3),
            entropy=round(min(entropy_score, 1.0), 3),
            concentration=concentration_score,
        )

    def get_alert_log(self) -> List[AlertEvent]:
        return list(self._alert_log)

class AdaptiveRateLimiter:
    '''
    Four-dimension adaptive rate limiter with per-user leaky bucket state.
    Tightens limits dynamically when the query monitor''s ensemble score is elevated.
    '''

    def __init__(self, policy: Optional[RateLimitPolicy] = None) -> None:
        self._policy = policy or DEFAULT_POLICY
        # {user_id: {dimension_name: BucketState}}
        self._buckets: Dict[str, Dict[str, BucketState]] = {}

    def _get_bucket(self, user_id: str, dim: DimensionPolicy) -> BucketState:
        if user_id not in self._buckets:
            self._buckets[user_id] = {}
        if dim.name not in self._buckets[user_id]:
            self._buckets[user_id][dim.name] = BucketState(level=0.0)
        return self._buckets[user_id][dim.name]

    def _refill(self, bucket: BucketState, dim: DimensionPolicy) -> None:
        if dim.refill_rate == 0.0:
            return
        now = time.time()
        elapsed = now - bucket.last_refill_time
        refilled = elapsed * dim.refill_rate
        bucket.level = max(0.0, bucket.level - refilled)
        bucket.last_refill_time = now

    def check_and_consume(
        self,
        user_id: str,
        request_count: float = 1.0,
        token_count: float = 0.0,
        cost_usd: float = 0.0,
        input_token_count: float = 0.0,
        ensemble_score: float = 0.0,
    ) -> RateLimitDecision:
        '''
        Check all dimensions and consume budget if allowed.
        Returns the enforcement decision.
        ensemble_score: from query monitor; tightens limits if elevated.
        '''
        tighten = ensemble_score >= 0.40
        factor = self._policy.tighten_factor if tighten else 1.0

        units_map = {
            'requests': request_count,
            'tokens': token_count,
            'usd': cost_usd,
            'input_tokens': input_token_count,
        }

        # Check all dimensions; find the most restrictive decision
        worst_action = 'allow'
        worst_dimension = None

        for dim in self._policy.dimensions:
            bucket = self._get_bucket(user_id, dim)
            self._refill(bucket, dim)
            consumption = units_map.get(dim.units, 0.0)
            if consumption == 0.0:
                continue

            effective_hard = dim.hard_limit * factor
            effective_soft = dim.soft_limit * factor

            new_level = bucket.level + consumption

            if new_level > effective_hard:
                worst_action = 'reject'
                worst_dimension = dim.name
                break
            elif new_level > effective_soft:
                if worst_action != 'reject':
                    worst_action = 'throttle'
                    worst_dimension = dim.name

        # Only consume budget if not rejecting
        if worst_action != 'reject':
            for dim in self._policy.dimensions:
                consumption = units_map.get(dim.units, 0.0)
                if consumption > 0.0:
                    self._get_bucket(user_id, dim).level += consumption

        return RateLimitDecision(
            action=worst_action,
            triggered_dimension=worst_dimension,
            user_id=user_id,
            policy_name=self._policy.name,
        )

def _mean_pairwise_similarity(embeddings: List[np.ndarray]) -> float:
    if len(embeddings) < 2:
        return 0.0
    mat = np.array(embeddings)
    norms = np.linalg.norm(mat, axis=1, keepdims=True)
    norms = np.where(norms == 0, 1.0, norms)
    normed = mat / norms
    sims = normed @ normed.T
    n = len(embeddings)
    upper = sims[np.triu_indices(n, k=1)]
    return float(upper.mean()) if len(upper) > 0 else 0.0


def _temporal_sync_score(timestamps_per_user: List[List[float]]) -> float:
    '''
    Score temporal synchronisation: how regular are inter-query intervals
    across users? Low CV of collective intervals = high synchronisation.
    '''
    all_intervals: List[float] = []
    for ts_list in timestamps_per_user:
        sorted_ts = sorted(ts_list)
        for i in range(1, len(sorted_ts)):
            all_intervals.append(sorted_ts[i] - sorted_ts[i - 1])
    if len(all_intervals) < 3:
        return 0.0
    mean_interval = float(np.mean(all_intervals))
    std_interval = float(np.std(all_intervals))
    cv = std_interval / max(mean_interval, 1e-10)
    # Low CV = high regularity = high synchronisation score
    return round(max(0.0, 1.0 - cv), 3)


class CrossUserCorrelator:
    '''
    Correlates query patterns across users to detect distributed campaigns.
    Privacy note: operates on anonymised embeddings; does not process raw text.
    '''

    def __init__(self, config: Optional[CorrelatorConfig] = None) -> None:
        self._cfg = config or CorrelatorConfig()
        self._campaign_counter = 0

    def correlate(
        self,
        user_summaries: List[UserQuerySummary],
    ) -> List[CampaignAlert]:
        if len(user_summaries) < self._cfg.min_cluster_size:
            return []
        now = time.time()
        window_start = now - self._cfg.time_window_hours * 3600.0

        # Filter to users with recent activity
        active = [
            s for s in user_summaries
            if s.recent_timestamps and max(s.recent_timestamps) >= window_start
        ]
        if len(active) < self._cfg.min_cluster_size:
            return []

        # Build representative embedding per user (mean of recent embeddings)
        user_reps: List[Tuple[str, np.ndarray]] = []
        for s in active:
            if s.recent_embeddings:
                rep = np.mean(np.array(s.recent_embeddings), axis=0)
                user_reps.append((s.user_id, rep))

        if len(user_reps) < self._cfg.min_cluster_size:
            return []

        # Find clusters above similarity threshold
        alerts: List[CampaignAlert] = []
        visited: Set[str] = set()

        for i, (uid_i, emb_i) in enumerate(user_reps):
            if uid_i in visited:
                continue
            cluster_ids = [uid_i]
            cluster_embeddings = [emb_i]

            for j, (uid_j, emb_j) in enumerate(user_reps):
                if i == j or uid_j in visited:
                    continue
                norm_i = np.linalg.norm(emb_i)
                norm_j = np.linalg.norm(emb_j)
                if norm_i == 0 or norm_j == 0:
                    continue
                sim = float(np.dot(emb_i, emb_j) / (norm_i * norm_j))
                if sim >= self._cfg.similarity_threshold:
                    # Check that at least one member has elevated OOD or boundary score
                    summary_i = next((s for s in active if s.user_id == uid_i), None)
                    summary_j = next((s for s in active if s.user_id == uid_j), None)
                    if (summary_i and summary_i.mean_ood_score >= self._cfg.min_ood_score_for_similarity_flag) or \
                       (summary_j and summary_j.mean_ood_score >= self._cfg.min_ood_score_for_similarity_flag):
                        cluster_ids.append(uid_j)
                        cluster_embeddings.append(emb_j)

            if len(cluster_ids) < self._cfg.min_cluster_size:
                continue

            for uid in cluster_ids:
                visited.add(uid)

            mean_sim = _mean_pairwise_similarity(cluster_embeddings)
            cluster_ts = [
                s.recent_timestamps for s in active if s.user_id in cluster_ids
            ]
            temporal_score = _temporal_sync_score(cluster_ts)
            composite = round(
                self._cfg.similarity_weight * mean_sim
                + self._cfg.temporal_weight * temporal_score,
                3,
            )
            action = 'alert_tier1' if composite >= 0.70 else 'alert_tier2'
            self._campaign_counter += 1
            alerts.append(CampaignAlert(
                campaign_id=f'campaign_{self._campaign_counter:04d}',
                user_ids=cluster_ids,
                time_window_start=window_start,
                time_window_end=now,
                mean_cluster_similarity=round(mean_sim, 3),
                temporal_synchronisation_score=temporal_score,
                composite_campaign_score=composite,
                recommended_action=action,
            ))
        return alerts

def _percentile(values: List[float], p: float) -> float:
    if not values:
        return 0.0
    sorted_v = sorted(values)
    idx = (len(sorted_v) - 1) * p / 100.0
    lo = int(idx)
    hi = min(lo + 1, len(sorted_v) - 1)
    return sorted_v[lo] + (idx - lo) * (sorted_v[hi] - sorted_v[lo])

Common Mistakes

Id

1

Description

Making the state store write synchronous on the critical path

Why It Happens

Writing the updated per-user state feels like it should happen before the response is returned -- otherwise the state is inconsistent. The simplest implementation puts the write in the same synchronous flow as the score computation.

Consequence

A slow state store (network latency to Redis, lock contention under high load) adds its latency directly to the gateway''s P99. A state store that is occasionally slow adds tail latency spikes. At high traffic, the write serialises requests from the same user and creates a latency bottleneck that would not exist with async writes.

Correct Approach

Dispatch the state write asynchronously after the score is returned. Accept the one-request lag in the state: the detection signal operates on distributions across many queries, and a one-request lag does not meaningfully reduce sensitivity. The query_monitor.py implementation notes this design; in production, the write is dispatched to a background task queue.

Id

2

Description

Setting the same rate limit policy for all users regardless of their demonstrated query patterns

Why It Happens

Universal policies are simpler to operate and audit. Different policies for different users create management complexity and raise fairness concerns. The default policy is applied universally.

Consequence

Legitimate high-volume users (enterprise evaluation pipelines, research teams) are throttled at the same limits as adversaries. High-value customers experience degraded service and escalate. The operations team manually exempts known high-volume users, creating an ad-hoc whitelist that bypasses the rate limiter entirely for exempted accounts -- including potentially adversarial accounts that obtain enterprise status.

Correct Approach

Configure per-user policy tiers based on demonstrated query patterns and business relationship. Enterprise users may have higher throughput limits but tighter boundary proximity and concentration thresholds: more requests are allowed, but extraction-specific signals trigger at lower scores. The rate_limit_policy_templates.py calibrate_policy() function supports per-deployment calibration; extend it with per-user tier support for production deployments with diverse user populations.

Running the cross-user correlator at per-request frequency

Why It Happens

The per-request monitor runs on every request. The cross-user correlator seems like it should also run on every request to provide real-time distributed campaign detection.

Consequence

Cross-user correlation at per-request frequency requires O(n^2) pairwise comparison across all active users on every request -- computationally infeasible at scale. A deployment with 10,000 active users would require 100 million similarity computations per request. The correlator overwhelms available compute and either fails or is disabled.

Correct Approach

Run the cross-user correlator as a background job at a frequency calibrated to the target detection latency. Hourly runs provide detection within one hour of a distributed campaign starting -- sufficient given that a distributed campaign designed to evade per-user detection will take days to complete. The cross_user_correlator.py implementation is designed for batch execution, not per-request execution.

Treating the Sigma rule as a one-time compliance artefact rather than a living detection specification

Why It Happens

The Sigma rule is generated once, loaded into the SIEM, and filed in the compliance documentation. It appears in the annual security review as evidence of ATLAS technique coverage. Nobody updates it when the query monitor''s alert schema changes or when new extraction techniques are discovered.

Not documenting the privacy implications of cross-user correlation in the deployment's privacy impact assessment

Why It Happens

The cross-user correlator is a security control. Privacy impact assessments (PIAs) are associated with product features that process user data for product purposes, not security controls. The security team implements the correlator without engaging the privacy team.

Consequence

The correlator processes query embeddings across multiple user accounts jointly -- a form of cross-user data analysis that most privacy frameworks require to be disclosed in the privacy notice and assessed in a PIA. Section 9.11 closed the input-side half of OWASP LLM10. Section 9.12 closes the output-side half. Output watermarking embeds a cryptographic signal in every response using token-level probability shaping with a secret key; the statistical detection test identifies the victim''s signature in suspected surrogate outputs. Output perturbation applies calibrated noise to reduce per-query extraction information -- particularly for soft-label classifier outputs and prompt-derived verbatim phrases. Adaptive perturbation applies higher noise to high-risk responses and lower noise to low-risk responses to preserve product utility. The combined watermarking plus perturbation architecture closes the benchmark-distribution LLM distillation detection gap that the Section 9.10 ensemble leaves at 30 to 40 percent. Together with Section 9.11, it completes the OWASP LLM10 coverage and brings cumulative Chapter 9 coverage to LLM01 plus LLM03 plus LLM10.
