Cost Optimisation: Sampling, Caching, and Batching

Section Overview

One Line Summary

A detection system with no cost discipline is switched off when the bill arrives, so cost optimisation is a survival requirement: sampling runs expensive analytics on a representative subset, caching reuses results for repeated inputs, and batching amortises per-call overhead -- applied where the cost-versus-coverage trade-off is safe, so the security-critical inline checks still run on every request while the expensive tiers stay affordable.

Why This Section Exists

The dashboard of Section 14.09 surfaced the cost of the gateway -- per million requests, per detector, per tier -- but showing a cost is not controlling it. This section controls it, and it is the last production concern from the 14.01 taxonomy. The consequence of neglect here is uniquely blunt: a gateway that is fast, scalable, resilient, and observable but too expensive is switched off when the bill arrives, and a switched-off detection system provides exactly no security. Cost is therefore not a nice-to-have to optimise if time permits; it is a survival requirement, on the same footing as latency and availability. This section works through the cost drivers -- inference calls, compute for the tiers, storage for state -- and applies three levers to bring them under control. Sampling runs expensive detection on a representative subset rather than every request. Caching reuses results for repeated or similar inputs. Batching amortises per-call overhead across many requests. The governing constraint throughout is the cost-versus-coverage trade-off, and getting it right is a security decision as much as a cost one: sampling trades coverage for cost, which is safe for analytics that estimate an aggregate signal and catastrophic for a security-critical check that must act on every request. So the section draws a hard line -- the inline security-critical detectors run on every request and are never sampled, while the expensive analytics that tolerate a representative subset are -- and it attributes cost per detector and per tier so the optimisation is targeted where it pays. The result is a gateway kept affordable without weakening the coverage that matters.

Prose Content

Part 1

Title

Cost Is a Survival Requirement

Body

Every concern in this chapter so far has been about making the gateway work: place it, make it fast, scale it, keep it resilient, make it observable and operable. Cost is different in kind. A gateway can be excellent on every other axis and still fail on this one, and when it fails on cost the failure is total, because the response to an unaffordable system is not to tune it but to turn it off. A detection system that is switched off provides no security whatsoever, so cost neglect is a security failure delivered by way of a finance decision. This gives cost the same status as latency and availability rather than a lower one. In Section 14.04, a detector too slow to keep was shown to provide no protection because it gets removed; the argument here is identical in shape. A detection tier too expensive to keep provides no protection because it gets removed, and the removal is just as final. The bill is a hard constraint the way the latency budget is a hard constraint: exceed it persistently and the system does not degrade gracefully, it gets shut down. Cost optimisation is therefore not an efficiency exercise to do if there is time -- it is a survival requirement, and it belongs in the deployment engineering alongside the concerns that are more obviously about keeping the system alive. The good news is that most of the cost of a detection gateway is concentrated and addressable. The expensive work is not spread evenly across every request; it is concentrated in a few heavy detectors on the slower tiers, and those are exactly the ones where cost can be reduced without touching the security-critical coverage. The task of this section is to find where the cost actually is, apply the right lever to each place, and do it all while keeping the checks that must run on every request running on every request. That begins with understanding what drives the cost in the first place.

Part 2

Title

The Cost Drivers and Where They Fall

Body

A detection gateway spends money in three ways, and knowing which one dominates where is what tells you which lever to reach for. The three drivers are inference cost -- the model calls a detector makes; compute cost -- the CPU and processing the tiers consume; and storage cost -- holding the state a detector needs. They do not fall evenly across the tiers, and the unevenness is the whole point. The inline tier is dominated by inference volume. Its detectors run on every single request, so even a cheap per-call cost, multiplied by the full request rate, becomes the largest contributor for that tier. Its state is minimal -- it reads precomputed summaries rather than holding much -- so storage is negligible, and its compute is the modest cost of signature and heuristic checks. The lever that fits an inference-volume-dominated tier is caching, because caching cuts the number of expensive calls on repeated inputs without cutting coverage, which is the only kind of reduction the inline tier can accept. The batch tier is the opposite. It runs heavy analytics over a large historical corpus, so it is dominated by compute -- large data-parallel jobs -- and storage -- the corpus at rest. Its volume in requests is low because it runs periodically, not per request, but each run is expensive. The levers that fit a compute-and-storage-dominated tier are sampling and batching: sampling reduces how much of the expensive analytics runs, and batching amortises the per-job overhead across the corpus. The near-real-time tier sits between them, with moderate compute over recent-window state. The cost driver table for this section maps each tier to its dominant driver, because applying one lever everywhere -- caching a batch job, or trying to sample an inline security check -- is how optimisation efforts get spent in the wrong place.

Part 3

Title

The Cost-Versus-Coverage Trade-Off

Body

Of the three levers, two are free of any coverage cost and one is not, and this asymmetry organises the whole section. Caching and batching reduce cost without reducing coverage. A cache hit returns the same verdict the detector would have computed, just without recomputing it, so caching changes what it costs to check a repeated input, not whether it is checked. Batching runs the same detections it always would, just grouped to share the per-call overhead, so it changes the overhead per detection, not the set of detections. Because neither touches coverage, caching and batching are safe to apply wherever they help. Sampling is the exception, and it is the lever that requires judgement, because sampling reduces cost precisely by reducing coverage. To sample is to run a detector on some requests and not others, which by definition means some requests go unchecked by that detector. Whether that is acceptable depends entirely on what the detector is for, and this is where cost optimisation becomes a security decision. The test is simple to state: does the detector need per-request coverage, or does it estimate a signal that a representative subset carries just as well? For a security-critical check the answer is that coverage is the whole point. An injection classifier exists to block the injection on this request; a sampled-out request is a request whose injection is never checked, which is an unblocked attack. Sampling such a detector does not weaken a statistic, it opens a hole, and an attacker who learns the sampling rate knows exactly how often the check is absent. For an analytics detector the answer is different. A coordinated-network analysis looks for an aggregate pattern across many entities, and a population baseline is by nature a statistical estimate; both are computed from a sample already, so running them on a representative subset carries the signal at a fraction of the cost with no meaningful loss. The rule of thumb is exact: if a missed call means a missed attack, never sample; if a missed call only slightly weakens a statistical estimate, sampling is safe.

Part 4

Title

The Inline Checks Run on Every Request

Body

The cost-versus-coverage test resolves, for a detection gateway, into a hard placement rule for sampling, and it is worth stating on its own because it is the line that must not be crossed under cost pressure. The inline security-critical checks -- injection, jailbreak, output PII -- run on every request and are never sampled. The expensive analytics on the near-real-time and batch tiers, which tolerate a representative subset, are where sampling is applied. This rule aligns cost optimisation with the architecture the chapter has built rather than cutting against it. The inline tier was already the tier of small-state, per-request, security-critical detection, kept fast enough to run on every request within the latency budget. That it also runs on every request for coverage reasons is the same fact from a different angle: these are the checks whose value is that no request escapes them. The near-real-time and batch tiers were already the tiers of large-state, aggregate, analytical detection, kept off the hot path. That they also tolerate sampling is, again, the same fact -- their value is a signal estimated over many requests, which a subset carries. The sampling placement falls exactly along the tier boundary the state-latency coupling drew, because the property that made a detector belong on a tier is the same property that decides whether it can be sampled. The cost optimiser deliverable for this section enforces this in code: a detector marked security-critical cannot be given a sampling rate below one, and attempting it is an error rather than a tuning option. Caching may still reduce the cost of the inline checks on repeated inputs -- that is a coverage-free saving -- but their coverage is fixed at every request. The saving from the inline tier is therefore modest and comes only from caching, while the large savings come from the batch tier where sampling and batching apply. This is the correct shape: cost is reduced most where it is safe to reduce it, and not at all where reducing it would open a security hole.

Part 5

Title

Sampling, Caching, and Batching in Practice

Body

With the placement settled, the three levers combine to bring the cost down. Their effects compose in a definite order on the tiers where all three apply. Sampling comes first and reduces the number of calls a detector makes, and it applies only to the non-critical analytics. Caching then removes a further fraction of the calls that remain, since a cache hit costs nothing to recompute. Batching finally reduces the per-call overhead on the calls that do run, by grouping them so the fixed cost of a call is shared across many. The cost optimiser applies them in this order and attributes the resulting cost per detector, so the effect of each lever is visible rather than lumped together. The composition is what makes the savings large on the expensive tiers. A batch analytics detector sampled to a tenth of requests, then batched to remove most of its per-call overhead, costs a small fraction of its baseline, and because it was the most expensive detector to begin with, that fraction is where most of the total saving comes from. The near-real-time session scorer, sampled to a quarter and batched, saves similarly. The inline checks, sampled not at all, save only what caching removes on repeated inputs -- a modest but real reduction that never costs coverage. The cost analysis and optimisation report deliverable pulls this together at the level a budget owner cares about: the baseline and optimised spend per tier, the total per million requests, and the projected monthly spend at production volume. Attribution is the point of the report. Without it, an optimisation effort is guesswork -- someone shaves cost off whatever is easiest to reach, which is rarely where the money is. With it, the report shows plainly that the batch tier dominates the bill and the inline tier does not, so the effort goes where it pays and the security-critical coverage is left untouched because touching it would save little and cost much.

Part 6

Title

Cost Controlled, and the Concerns Complete

Body

With sampling placed safely, caching and batching applied where they help, and cost attributed per detector and per tier, the gateway is affordable, and affordability is what keeps it alive. The cost that the 14.09 dashboard measures is now bounded and targeted: reduced most on the expensive analytics tiers where the cost-versus-coverage trade-off is safe, reduced modestly on the inline tier through caching alone, and never reduced by weakening a security-critical check. The gateway costs what a budget owner can sustain, without a coverage hole hidden inside the saving. It is worth holding onto the security framing one last time, because cost is the concern where it is easiest to lose. Every lever in this section was evaluated first for whether it costs coverage, and the one that does -- sampling -- was confined to the detectors that can spare it. A cost optimisation that quietly sampled an inline check would show a lovely saving on the report and a hole in the defence that no cost metric would ever reveal. Keeping the saving honest means keeping the coverage of the security-critical checks at every request, which this section does by construction. Cost was the last of the production concerns named in the Section 14.01 taxonomy. With it controlled, the full set is complete: placement chose where detection sits and where it hooks in; latency and scaling made it fast per request and sufficient in aggregate; failure policy and high availability made it resilient; observability and the dashboard made it operable; and cost optimisation made it affordable. Each concern has been engineered on its own. What remains is to put them together, because a gateway is not the sum of eight separate mechanisms but one service in which they all operate at once on the same request. Section 14.11 is that assembly: the production detection gateway capstone, where the architecture pattern, integration points, latency budget, scaling, failure policy, circuit breakers, observability, and cost optimisation come together into a single running service that meets its latency, availability, and cost targets together.

Deliverables

Deliverable 1

Title

Cost Optimiser: Sampling, Caching, and Batching

Filename

cost_optimizer.py

Description

Applies sampling, caching, and batching to the detectors with per-detector cost attribution, enforcing that a security-critical detector cannot be sampled below full coverage -- attempting it raises an error -- so the inline checks keep every-request coverage while the expensive analytics are sampled and batched for most of the saving.

Implementation Notes

Python 3.12, single quotes throughout per book convention, no external dependencies, prints per-detector baseline and optimised cost with the saving, and raises if a security-critical detector is sampled.

Code

# cost_optimizer.py
# Section 14.10: Sampling, Caching, and Batching for the Near-Real-Time and Batch Tiers
# 20260121 | AI Security Mastery -- Chapter 14 by Raghav Dinesh
# Single quotes throughout per book convention

from dataclasses import dataclass, field
from typing import Dict, List, Optional


@dataclass
class DetectorCost:
    name: str
    tier: str
    security_critical: bool     # if True, must run on every request -- never sampled
    cost_per_call_usd: float
    calls_per_million: int      # baseline: how many calls per million requests


@dataclass
class Optimisation:
    sampling_rate: float        # 1.0 = every request; < 1.0 only for non-critical
    cache_hit_rate: float       # fraction of calls served from cache
    batch_overhead_saving: float  # fraction of per-call overhead removed by batching


# Baseline detectors across the tiers.
DETECTORS: List[DetectorCost] = [
    DetectorCost('Injection classifier', 'inline', True, 0.000020, 1_000_000),
    DetectorCost('Jailbreak classifier', 'inline', True, 0.000018, 1_000_000),
    DetectorCost('Output PII scanner', 'inline', True, 0.000012, 1_000_000),
    DetectorCost('Session behaviour scorer', 'near_real_time', False, 0.000090, 1_000_000),
    DetectorCost('Coordinated-network', 'batch', False, 0.000600, 1_000_000),
    DetectorCost('Population baselining', 'batch', False, 0.000450, 1_000_000),
]

# Optimisations. Security-critical inline detectors are NOT sampled (rate stays 1.0).
OPTIMISATIONS: Dict[str, Optimisation] = {
    'Injection classifier': Optimisation(1.0, 0.35, 0.0),
    'Jailbreak classifier': Optimisation(1.0, 0.35, 0.0),
    'Output PII scanner': Optimisation(1.0, 0.10, 0.0),
    'Session behaviour scorer': Optimisation(0.25, 0.0, 0.40),
    'Coordinated-network': Optimisation(0.10, 0.0, 0.60),
    'Population baselining': Optimisation(0.10, 0.0, 0.60),
}


def optimised_cost(det: DetectorCost, opt: Optimisation) -> float:
    '''Cost per million requests after sampling, caching, and batching.

    Sampling reduces the number of calls (only for non-critical detectors).
    Caching removes a fraction of the remaining calls (cache hits cost nothing).
    Batching removes a fraction of per-call overhead on the calls that do run.
    A security-critical detector has sampling_rate 1.0, so its coverage is untouched.
    '''
    if det.security_critical and opt.sampling_rate < 1.0:
        raise ValueError(f'{det.name} is security-critical and must run on every request; sampling < 1.0 is forbidden')
    effective_calls = det.calls_per_million * opt.sampling_rate
    after_cache = effective_calls * (1.0 - opt.cache_hit_rate)
    effective_cost_per_call = det.cost_per_call_usd * (1.0 - opt.batch_overhead_saving)
    return after_cache * effective_cost_per_call


def baseline_cost(det: DetectorCost) -> float:
    return det.calls_per_million * det.cost_per_call_usd


def report() -> None:
    print('=' * 92)
    print('COST OPTIMISER: SAMPLING, CACHING, BATCHING (with per-detector attribution)')
    print('Security-critical inline checks run on every request; only analytics are sampled')
    print('=' * 92)
    header = ('Detector'.ljust(28) + 'Tier'.ljust(16) + 'Baseline $'.ljust(12)
              + 'Optimised $'.ljust(13) + 'Saved')
    print(header)
    print('-' * 92)
    total_base = 0.0
    total_opt = 0.0
    for det in DETECTORS:
        opt = OPTIMISATIONS[det.name]
        base = baseline_cost(det)
        new = optimised_cost(det, opt)
        total_base += base
        total_opt += new
        saved_pct = 100.0 * (base - new) / base if base else 0.0
        flag = '  [critical -- full coverage]' if det.security_critical else ''
        print(det.name.ljust(28) + det.tier.ljust(16)
              + f'${base:.2f}'.ljust(12) + f'${new:.2f}'.ljust(13)
              + f'{saved_pct:.0f}%{flag}')
    print('-' * 92)
    total_saved = 100.0 * (total_base - total_opt) / total_base if total_base else 0.0
    total_label = 'TOTAL / million req'.ljust(28) + ''.ljust(16)
    print(total_label + f'${total_base:.2f}'.ljust(12) + f'${total_opt:.2f}'.ljust(13) + f'{total_saved:.0f}%')
    print()
    print('The inline security-critical detectors keep full coverage -- caching cuts their')
    print('cost only on repeated inputs, never their coverage. The expensive batch analytics')
    print('are sampled to a representative subset and batched, where the cost-versus-coverage')
    print('trade-off is safe, which is where most of the saving comes from.')


if __name__ == '__main__':
    report()

from dataclasses import dataclass, field
from typing import Dict, List


@dataclass
class TierSpend:
    tier: str
    baseline_usd_per_million: float
    optimised_usd_per_million: float

    def saved_usd(self) -> float:
        return self.baseline_usd_per_million - self.optimised_usd_per_million

    def saved_pct(self) -> float:
        if self.baseline_usd_per_million == 0:
            return 0.0
        return 100.0 * self.saved_usd() / self.baseline_usd_per_million


@dataclass
class CostReport:
    monthly_requests_millions: float
    tiers: List[TierSpend]

    def total_baseline(self) -> float:
        return sum(t.baseline_usd_per_million for t in self.tiers)

    def total_optimised(self) -> float:
        return sum(t.optimised_usd_per_million for t in self.tiers)

    def monthly_baseline(self) -> float:
        return self.total_baseline() * self.monthly_requests_millions

    def monthly_optimised(self) -> float:
        return self.total_optimised() * self.monthly_requests_millions


def build_report() -> CostReport:
    return CostReport(
        monthly_requests_millions=4200.0,
        tiers=[
            TierSpend('Inline', 50.00, 35.50),
            TierSpend('Near-real-time', 90.00, 13.50),
            TierSpend('Batch', 1050.00, 42.00),
        ],
    )


def print_report(report: CostReport) -> None:
    print('=' * 88)
    print('COST ANALYSIS AND OPTIMISATION REPORT')
    print(f'Volume: {report.monthly_requests_millions:.0f} million requests/month')
    print('=' * 88)
    print()
    header = 'Tier'.ljust(18) + 'Baseline $/M'.ljust(15) + 'Optimised $/M'.ljust(16) + 'Saved'
    print(header)
    print('-' * 88)
    for t in report.tiers:
        print(t.tier.ljust(18) + f'${t.baseline_usd_per_million:.2f}'.ljust(15)
              + f'${t.optimised_usd_per_million:.2f}'.ljust(16) + f'{t.saved_pct():.0f}%')
    print('-' * 88)
    tb = report.total_baseline()
    to = report.total_optimised()
    tot_pct = 100.0 * (tb - to) / tb if tb else 0.0
    print('TOTAL / million'.ljust(18) + f'${tb:.2f}'.ljust(15) + f'${to:.2f}'.ljust(16) + f'{tot_pct:.0f}%')
    print()
    print('PROJECTED MONTHLY SPEND')
    print('-' * 88)
    mb = report.monthly_baseline()
    mo = report.monthly_optimised()
    print(f'  Baseline : ${mb:,.0f} / month')
    print(f'  Optimised: ${mo:,.0f} / month')
    print(f'  Saved    : ${mb - mo:,.0f} / month ({100.0 * (mb - mo) / mb:.0f}%)')
    print()
    print('The report attributes cost per tier so the optimisation is targeted where it pays.')
    print('Most of the saving is in the batch tier, whose expensive analytics are safely')
    print('sampled and batched, while the inline tier keeps full security coverage and saves')
    print('only through caching. Cost attribution is what shows where a bill is actually going.')


if __name__ == '__main__':
    print_report(build_report())

Common Mistakes

Mistake 1

Description

Treating cost optimisation as an efficiency nice-to-have rather than a survival requirement

Why It Happens

Cost does not break the system the way a latency breach or an outage does -- the gateway keeps working -- so cost feels like something to tidy up later once the real engineering is done.

Consequence

The gateway runs correctly but expensively until a finance review declares it unaffordable, and the response to an unaffordable system is to switch it off, so a detection system that worked perfectly provides no security because it no longer runs.

Correct Approach

Treat cost as a hard constraint on the same footing as latency and availability: a detection tier too expensive to keep provides no protection, so bound the cost deliberately as part of deployment engineering, not as an afterthought.

Mistake 2

Description

Sampling a security-critical inline check to save cost

Why It Happens

Sampling is the most powerful cost lever, and the inline checks run on every request so they look like an obvious place to cut, especially when the cost report shows them running constantly.

Consequence

A sampled-out request is one whose injection, jailbreak, or PII leak is never checked, so sampling opens a coverage hole that is an unblocked attack, and an attacker who learns the sampling rate knows exactly how often the check is absent -- a security failure that no cost metric reveals.

Correct Approach

Never sample a security-critical check: the inline injection, jailbreak, and output-PII detectors run on every request, and cost is reduced there only through caching, which cuts recomputation without cutting coverage.

Mistake 3

Description

Applying one optimisation lever everywhere regardless of the tier dominant cost driver

Why It Happens

One lever is simpler to reason about, and whichever technique a team is comfortable with gets reached for by default, without checking what actually drives the cost on each tier.

Consequence

Effort is spent caching a batch job that runs periodically and has few repeated inputs, or trying to batch an inline per-request check, so the optimisation lands where it does little while the dominant driver on each tier goes unaddressed.

Correct Approach

Identify the dominant cost driver per tier and apply the lever that fits it: caching for the inference-volume inline tier, sampling and batching for the compute-and-storage batch tier, rather than one lever everywhere.

Mistake 4

Description

Optimising without cost attribution, so effort goes to the cheapest things

Why It Happens

Without a per-detector and per-tier breakdown, the visible cost is a single aggregate number, and optimisation naturally starts with whatever is easiest to change rather than whatever costs the most.

Consequence

A team shaves cost off cheap, easy-to-reach detectors while the batch tier that dominates the bill is never touched, so a great deal of effort produces a small saving and the actual cost driver is left running at full price.

Correct Approach

Attribute cost per detector and per tier first, so the optimisation is targeted at where the money actually goes -- usually the expensive analytics tiers -- and the cheap inline checks are left alone because saving there is small and risks coverage.

Mistake 5

Description

Assuming caching and batching carry the same coverage risk as sampling

Why It Happens

All three are grouped together as cost levers, so it is easy to treat them as equally risky and either apply sampling too freely or avoid caching and batching out of the same caution sampling deserves.

Consequence

Either the coverage-free savings of caching and batching are left on the table out of misplaced caution, or sampling is treated as equally safe and applied where it opens a coverage hole, both of which come from not distinguishing the levers.

Correct Approach

Distinguish the levers by their coverage cost: caching and batching reduce cost without reducing coverage and are safe anywhere they help, while sampling reduces coverage and is confined to detectors that a representative subset serves.

Section Summary

Compact

A detection system with no cost discipline is switched off when the bill arrives, and a switched-off system provides no security, so cost optimisation is a survival requirement on the same footing as latency and availability, not an efficiency nice-to-have. The gateway spends money through three drivers -- inference calls, compute for the tiers, and storage for state -- which fall unevenly: the inline tier is dominated by inference volume because it runs on every request, and the batch tier by compute and storage over a large corpus. Three levers reduce the cost. Caching reuses results for repeated inputs and batching amortises per-call overhead, both reducing cost without reducing coverage, so they are safe anywhere they help. Sampling runs a detector on a representative subset, which reduces cost by reducing coverage, so it is governed by the cost-versus-coverage trade-off: if a missed call means a missed attack, never sample; if it only slightly weakens a statistical estimate, sampling is safe. This draws a hard line -- the inline security-critical checks run on every request and are never sampled, while the expensive analytics that tolerate a representative subset are -- and the line falls exactly along the state-latency tier boundary. The cost optimiser enforces that a security-critical detector cannot be sampled, and cost is attributed per detector and per tier so optimisation targets where the money actually goes: most saving comes from the expensive batch tier through safe sampling and batching, while the inline tier keeps full coverage and saves only through caching. Cost was the last production concern; with it controlled, Section 14.11 assembles all the concerns into the running gateway.

Key Takeaways

  • A detection system with no cost discipline is switched off when the bill arrives, so cost is a survival requirement on the same footing as latency and availability
  • The three cost drivers -- inference, compute, storage -- fall unevenly, with the inline tier dominated by inference volume and the batch tier by compute and storage, and the dominant driver determines the lever
  • Caching and batching reduce cost without reducing coverage, so they are safe anywhere; sampling reduces coverage and is governed by the cost-versus-coverage trade-off
  • The inline security-critical checks run on every request and are never sampled, while the expensive analytics that a representative subset serves are sampled -- the line falling along the state-latency tier boundary
  • Cost is attributed per detector and per tier so optimisation targets where the money actually goes, which is the expensive batch tier, not the cheap inline checks
  • The saving is honest only if the security-critical coverage stays at every request, so the optimiser forbids sampling those checks by construction -- and cost was the last production concern before the capstone assembly
