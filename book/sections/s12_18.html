Section 12.18: Chapter 12 Summary

Section Overview

One Line Summary

Chapter 12 built the ML detection layer of the security gateway: five detector families, a four-detector ensemble, and the operational infrastructure that keeps it accurate, fast, and current in production.

Why This Section Exists

Chapter 12 spanned seventeen content sections that each built one component of an ML-based detection system. Read in isolation, each section is a technique -- an anomaly detector, a calibration method, a model registry. Read together, they are a single architecture: a production ML detection layer that extends the Chapter 11 signature-based gateway with classifiers that catch the novel attack variants signatures miss. This summary synthesises the seventeen sections into that architecture. It revisits the five detection families and the four-detector ensemble, the feature pipeline shared across the detectors, the calibration and inference optimisation that make the ensemble deployable, the model registry and live curation that keep it from decaying, and the production gateway capstone that integrates everything. It consolidates the chapter's central thesis -- that ML detection complements rather than replaces signature detection -- and it sets up Chapter 13, where the per-request detection decisions made by this gateway are lifted to session-level behavioural analysis. The summary is the map of the territory the chapter covered, the reference for the decisions a practitioner makes when building an ML detection system, and the bridge to the behavioural analysis that the per-request classifiers cannot perform alone.

Position In Chapter

Section 12.18 closes Chapter 12. It synthesises Sections 12.1 through 12.17 and previews Chapter 13 (Behavioural Analysis and Monitoring). It is the final section of the chapter and the transition point from the per-request ML detection layer to the session-level behavioural layer that Chapter 13 builds on top of it.

Title

Sections 12.1 and 12.2 in Review: Taxonomy and Feature Engineering

Body

Chapter 12 opened by establishing what ML-based detection is and is not. Section 12.1 built the
taxonomy of five detection families -- unsupervised anomaly detection, supervised classification,
sequence modelling, embedding-based semantic detection, and neural classification -- and the
maturity ladder that places a detection programme on the path from no ML (L1) through the full
ensemble (L3). The taxonomy is the map: it tells a practitioner which family fits which attack
class and which families are worth the operational cost at each maturity level.

Section 12.2 built the feature engineering that every supervised detector depends on. The five
feature groups -- token, structural, semantic, contextual, and API-level -- convert a raw request
into the SecurityFeatureVector that the classifiers consume. The section introduced the
training-serving skew risk that Section 12.11 later addressed in production, and it established
SHAP as the explainability method that makes a classifier's decision attributable to specific
features. The feature engineering is the foundation: a detector is only as good as the features
it sees, and the shared feature design is what lets the detectors be combined coherently.

Title

Sections 12.3 and 12.4 in Review: Anomaly Detection and Dataset Curation

Body

Section 12.3 built the first detector, the one that needs no labels. The Isolation Forest and One-Class SVM learn the benign distribution and flag deviations, catching novel attacks on day one before any labelled data exists. The anomaly-to-label pipeline turned the anomaly alerts into the seed labelled data for the supervised detectors, establishing the bootstrap that lets the detection programme start with zero labels and grow its dataset from production. Section 12.4 built the dataset curation that the supervised detectors train on. The four data sources, the temporal split that prevents future-leakage, the SMOTE and class-weighting that handle the severe class imbalance of security data, and the inter-annotator agreement that ensures label quality together produce the training dataset. The temporal-split discipline established here propagated through the whole chapter: every detector, every calibration, and every meta-learner trains on the temporal split, never a random one, because a random split inflates the metrics with future-leakage.

Title

Sections 12.5 through 12.9 in Review: The Four Trained Detectors and the PII Scanner

Body

Sections 12.5 through 12.8 built the four supervised detectors. Section 12.5 built the Random Forest and XGBoost supervised classifiers and the shared security_evaluator.py that every subsequent detector section imported. Section 12.6 built the LSTM and GRU sequence models that catch multi-turn escalation -- the attacks that build across conversation turns, which single-message detectors cannot see. Section 12.7 built the embedding-based semantic detector that catches paraphrase variants by similarity to known attacks. Section 12.8 built the DistilBERT neural classifier, the highest-precision supervised detector, with the model card that became the registry gate condition. Section 12.9 built the PII scanner, the chapter's only output-side detector. It scans the model response, not the user request, addressing the OWASP LLM06 leakage that no input-side detector can catch. The three-layer ensemble -- regex, NER, and Presidio with context scoring -- distinguishes real PII from the fictional and example data that a model legitimately generates. The PII scanner's output-side position is why it runs separately from the four-detector input-side ensemble.

Title

Sections 12.10 through 12.12 in Review: Calibration, Feature Pipeline, and Inference Optimisation

Body

Sections 12.10 through 12.12 built the layer that turns the trained detectors into deployable production components. Section 12.10 built the calibration -- Platt scaling and isotonic regression -- that makes the detector scores reliable probabilities on a common scale, the prerequisite for combining them in the ensemble, and the threshold tuning that sets each detector's operating point from the analyst capacity rather than the default 0.5. Section 12.11 built the production feature pipeline that makes the Section 12.2 feature design real: sub-5ms extraction, training-serving parity through a single canonical pipeline and the same ONNX embedding model at training and serving, and feature schema versioning that rejects mismatched requests. Section 12.12 built the inference optimisation that fits the four-detector ensemble within the 50ms P99 budget: INT8 quantisation, async parallel scoring that makes the ensemble latency the maximum rather than the sum of the detector latencies, early exit, and model warm-up. Together these three sections are why the ensemble runs in production rather than only in a notebook.

Title

Sections 12.13 and 12.14 in Review: Model Registry and Live Dataset Curation

Body

Sections 12.13 and 12.14 built the infrastructure that keeps the detection system from decaying. Section 12.13 built the model registry -- the control plane that makes every detector update safe and reversible. The Staging-Production-Archived stage model, the stage transition gates that enforce the calibration, latency, accuracy, and model-card checks, the shadow mode and canary promotion that validate a candidate on live traffic, and the model lineage that satisfies the audit requirement together make model deployment a governed operation rather than a manual incident. Section 12.14 built the live dataset curation that closes the active learning loop. Uncertainty sampling focuses the scarce analyst annotation on the boundary cases that improve the model most; the composite retraining trigger combines data quantity and drift signal; the data flywheel turns production traffic into the fresh labelled data that keeps the detectors current as adversaries adapt. Together, the registry and the curation are the difference between a one-time detector deployment and a self-improving detection system that does not decay.

Title

Sections 12.15 and 12.16 in Review: The Four-Detector Ensemble and Benchmarking

Body

Section 12.15 built the four-detector ensemble, the chapter's primary production deliverable. The Isolation Forest, the supervised classifiers, the GRU, and the embedding detector are combined by weighted voting or a stacking meta-learner into a single decision whose coverage and precision exceed any individual detector through complementarity. The coverage complementarity analysis and the confidence correlation matrix verify that the detectors cover different attack families and make independent errors -- the two properties that make the ensemble valuable. The three-tier alert routing aligns the ensemble output with the analyst capacity. Section 12.16 built the benchmarking and A/B testing that back every model promotion with evidence. The cross-detector benchmark compares the configurations on the same temporal test set; the A/B testing framework validates a candidate on production traffic with statistical significance and guardrail metrics; the sample size calculator ensures the test runs long enough to detect the effect; the online-offline divergence quantifies the gap between the benchmark and production reality. Together they turn anecdotal accuracy claims into statistically significant production evidence.

Section 12.17 in Review: The Production ML Gateway Capstone

Body

Section 12.17 integrated everything into the production ML gateway. The four input-side detectors are distributed across the seven gateway tracks by coverage profile and combined by the ensemble; the PII scanner runs as an output-side stage outside the seven tracks; the feature pipeline and inference optimisation keep the integrated gateway within the 50ms P99 budget. The ML layer extends the Chapter 11 signature layer rather than replacing it, providing defence-in-depth where the two layers cover each other's gaps and fail independently. The capstone addressed the production realities that the isolated sections did not. Graceful degradation sheds the highest-latency detectors first under load, falling back toward signature-only rather than breaching the SLO. The deployment checklist enforces the registry gate conditions as a hard gate before any detector handles traffic. The ATLAS AML.T0040 Sigma rule detects the meta-attack -- adversaries probing the classifier decision boundaries to craft evasions. The monitoring dashboard makes the ML layer observable. The capstone is where the ML detection layer became a deployable, observable, defensible production system.

Title

Integration: How Chapter 12 Extends the Chapter 11 Gateway

Body

Chapter 12 did not build a standalone detection system -- it built a detection layer that plugs into the Chapter 11 seven-track gateway. The integration is the chapter's architectural through-line: each ML detector is assigned to the gateway tracks its coverage profile fits, running in parallel with the signature rules already on those tracks. Track 1 (injection) gains the embedding detector and XGBoost; Tracks 2-5 (jailbreak) gain the GRU and DistilBERT; a new output-side stage gains the PII scanner; Track 6 (extraction) gains the Isolation Forest; Track 7 (adversarial) gains the Chapter 10 detectors. The integration principle is complementarity at the track level. The signature layer provides fast, precise, interpretable detection of known attacks and the baseline that never goes blind. The ML layer provides coverage of the novel variants the signatures miss, at the cost of higher latency and lower interpretability, managed by the calibration, ensemble, inference optimisation, and monitoring built across the chapter. The integrated gateway is more robust than either layer alone because the layers cover each others gaps and fail independently -- if the ML layer is shed under load, the signatures continue; if a novel attack evades the signatures, the ML layer covers it.

Title

Cross-Chapter Arc: Rules Plus Classifiers Equals Defence-in-Depth

Body

Chapter 11 built the rules; Chapter 12 built the classifiers. Together they close the detection layer of Part 3 of the book. The cross-chapter arc is the maturation of the detection system from a pure signature-based gateway to a hybrid gateway with both a fast, precise signature layer and a coverage-broad ML layer. Neither layer alone is sufficient: signatures miss novel variants, ML detectors are slower and less interpretable, and a sophisticated adversary can probe either. The two together provide defence-in-depth. This arc reflects the central thesis of Chapter 12: ML detection is not a replacement for signature detection but a complement. The chapters that follow build on this hybrid detection foundation. Chapter 13 lifts the per-request decisions to session-level behavioural analysis. Chapter 14 scales the deployment. Chapter 17 monitors and tunes the system over time. The detection system the book builds is the hybrid gateway, and Chapter 12 is the chapter that added its ML half.

Title

Five Cross-Cutting Threads

Body

Five threads ran through the whole chapter and are worth isolating. First, the temporal split: every detector, calibration, and meta-learner trains on the temporal split, never a random one, because the random split inflates metrics with future-leakage that production does not enjoy. Second, calibration as a prerequisite: uncalibrated scores cannot be combined, cannot be uncertainty-sampled, and cannot be interpreted, so the Section 12.10 calibration underpins the ensemble, the curation, and the explainability. Third, the latency budget as a security constraint: a detector that breaches the 50ms SLO is disabled under load, so the inference optimisation and graceful degradation are not performance niceties but security requirements. Fourth, the operational sustainability: the registry, curation, and monitoring are what separate a sustainable detection system from a decaying snapshot, and a detector without them will fall behind the attack distribution. Fifth, defence-in-depth: the ML layer complements the signature layer, the ensemble complements the individual detectors, and the output-side PII scanner complements the input-side detectors -- redundant coverage that fails independently.

Title

Chapter 13 Preview: Behavioural Analysis and Monitoring

Body

Chapter 12 trained classifiers that evaluate individual API requests. Each detector, the ensemble, and the gateway make a per-request decision: is this request an attack. This is the foundation of detection, but it is not the whole. Some attacks are invisible at the per-request level and visible only across a session or a user's history: a slow extraction campaign where each query is individually benign, a coordinated probing where each request is near-the-boundary, an account takeover where the behavioural pattern shifts. Chapter 13 lifts the analysis from the request to the session and the user. It builds behavioural baselines that capture what a normal user session looks like, drift detection that flags when a user's behaviour deviates from baseline, rate-based detection that the per-request classifiers cannot see, and user behaviour profiling that builds entity-level risk scores across sessions. It also covers model behavioural monitoring -- detecting when the LLM's output distribution shifts in ways that indicate injection success rather than surface-level injection attempts. By the end of Chapter 13, the detection system covers the full arc from individual request analysis (Chapter 12) to session-level behavioural analysis (Chapter 13), ready for Chapter 14's production deployment at scale.

# operational_sustainability_checklist.py

from __future__ import annotations

from dataclasses import dataclass
from typing import Dict, List


@dataclass
class SustainabilityRequirement:
    name: str
    section: str
    present: bool
    without_it: str


def assess_sustainability(
    has_registry: bool,
    has_curation: bool,
    has_retraining_trigger: bool,
    has_canary: bool,
) -> List[SustainabilityRequirement]:
    return [
        SustainabilityRequirement('Model registry', '12.13', has_registry,
                                  'Rollback is manual; regressions reach production'),
        SustainabilityRequirement('Live dataset curation', '12.14', has_curation,
                                  'Detectors decay as the attack distribution shifts'),
        SustainabilityRequirement('Retraining trigger', '12.14', has_retraining_trigger,
                                  'Retrain too often (waste) or too rarely (decay)'),
        SustainabilityRequirement('Canary promotion', '12.13', has_canary,
                                  'A regressed model affects all traffic immediately'),
    ]


def print_assessment(requirements: List[SustainabilityRequirement]) -> bool:
    print('Operational Sustainability Assessment')
    print('=' * 60)
    all_present = True
    for r in requirements:
        status = 'PRESENT' if r.present else 'MISSING'
        print(f'  [{status:>7}] {r.name} ({r.section})')
        if not r.present:
            all_present = False
            print(f'            Without it: {r.without_it}')
    print('-' * 60)
    verdict = 'SUSTAINABLE' if all_present else 'WILL DECAY'
    print(f'  Verdict: {verdict}')
    return all_present


if __name__ == '__main__':
    # A system missing curation and the retraining trigger will decay
    reqs = assess_sustainability(
        has_registry=True, has_curation=False,
        has_retraining_trigger=False, has_canary=True,
    )
    print_assessment(reqs)

from __future__ import annotations

from dataclasses import dataclass
from typing import List


@dataclass
class SecurityControl:
    category: str
    control: str
    section: str


SECURITY_CHECKLIST: List[SecurityControl] = [
    SecurityControl('Detection coverage', 'All seven tracks have signature + ML coverage', '12.17'),
    SecurityControl('Detection coverage', 'No single-detector track without monitoring', '12.15'),
    SecurityControl('Calibration', 'Every detector ECE below threshold', '12.10'),
    SecurityControl('Calibration', 'Thresholds set from analyst capacity, not 0.5', '12.10'),
    SecurityControl('Latency', 'Gateway P99 within 50ms validated under load', '12.12'),
    SecurityControl('Latency', 'Graceful degradation policy configured', '12.17'),
    SecurityControl('Feature integrity', 'Training-serving parity tests passing', '12.11'),
    SecurityControl('Feature integrity', 'Feature schema versioning enforced', '12.11'),
    SecurityControl('Governance', 'Model registry with stage gates active', '12.13'),
    SecurityControl('Governance', 'Shadow mode and canary validated', '12.13'),
    SecurityControl('Sustainability', 'Live curation and retraining trigger active', '12.14'),
    SecurityControl('Meta-attack', 'AML.T0040 boundary-probing detection deployed', '12.17'),
    SecurityControl('Observability', 'Monitoring dashboard and alerting configured', '12.17'),
    SecurityControl('Privacy', 'PII anonymisation before annotation queue', '12.14'),
]


def print_security_checklist(controls: List[SecurityControl] = None) -> None:
    controls = controls or SECURITY_CHECKLIST
    print('Seven-Track ML Gateway Security Checklist')
    print('=' * 66)
    current_category = None
    for c in controls:
        if c.category != current_category:
            print(f'\n[{c.category}]')
            current_category = c.category
        print(f'    [ ] {c.control}  (Section {c.section})')


if __name__ == '__main__':
    print_security_checklist()

from __future__ import annotations

from dataclasses import dataclass
from typing import List


@dataclass
class IntegrationStage:
    layer: str
    chapter: str
    produces: str


INTEGRATION_FLOW: List[IntegrationStage] = [
    IntegrationStage('Per-request ML classification', 'Chapter 12',
                     'Per-request attack decision (block/flag/monitor) + detector scores'),
    IntegrationStage('Decision logging', 'Chapter 12 -> 13',
                     'Stream of per-request decisions tagged with session and source'),
    IntegrationStage('Session aggregation', 'Chapter 13',
                     'Per-session behavioural features from the decision stream'),
    IntegrationStage('Behavioural baseline', 'Chapter 13',
                     'What a normal session looks like per user/entity'),
    IntegrationStage('Drift and rate detection', 'Chapter 13',
                     'Deviations from baseline; rate-based patterns per-request misses'),
    IntegrationStage('Entity risk scoring', 'Chapter 13',
                     'Cross-session entity-level risk scores'),
]


def render_integration(flow: List[IntegrationStage] = None) -> str:
    flow = flow or INTEGRATION_FLOW
    lines = ['Chapter 12 -> Chapter 13 Integration', '=' * 64]
    for i, stage in enumerate(flow):
        connector = '   |' if i < len(flow) - 1 else ''
        lines.append(f'\n[{stage.chapter}] {stage.layer}')
        lines.append(f'    produces: {stage.produces}')
        if connector:
            lines.append(connector)
            lines.append('   v')
    lines.append('\n' + '=' * 64)
    lines.append('Chapter 12 makes the per-request decision; Chapter 13 lifts')
    lines.append('the decisions to session-level and entity-level behavioural analysis.')
    return '\n'.join(lines)


if __name__ == '__main__':
    print(render_integration())

Common Mistakes

Id

1

Description

Treating the individual detectors as the deliverable rather than the integrated system

Why It Happens

Each detector section produced a working detector, so a practitioner concludes that building the detectors is the goal. The integration -- the ensemble, the calibration, the operational infrastructure -- is seen as secondary to the detectors themselves.

Consequence

A collection of individually good detectors without the integration is not a detection system. Uncalibrated, they cannot be combined; without the registry, they cannot be updated safely; without the curation, they decay. The detectors are necessary but not sufficient; the integration is what makes them a system.

Correct Approach

Treat the integrated system as the deliverable: the ensemble that combines the detectors, the calibration that makes the combination coherent, the inference optimisation that makes it deployable, and the operational infrastructure that keeps it current. The detectors are components; the system is the integration.

Id

2

Description

Building the detection system without the operational infrastructure, producing a decaying snapshot

Why It Happens

The detectors work and the ensemble is accurate on the test set, so the system is considered complete. The model registry, live curation, and monitoring are deferred as infrastructure to add later, once the detection is proven.

Consequence

Without the operational infrastructure, the detection system is a point-in-time snapshot that decays as adversaries adapt. There is no safe way to update it, no fresh data to retrain on, and no visibility into its degradation. Within months, the accurate detectors have fallen behind the attack distribution with no mechanism to recover.

Correct Approach

Build the operational infrastructure as part of the detection system, not as an afterthought. The registry, curation, retraining trigger, and monitoring are what make the system sustainable. A detection system without them is not finished -- it is a snapshot that will decay.

3

Description

Ignoring calibration and deploying detectors at the default 0.5 threshold

Why It Happens

The detectors output scores between 0 and 1 that look like probabilities, and 0.5 is the obvious decision boundary. Calibration is seen as a refinement, and the default threshold is carried through from training to deployment.

Consequence

The uncalibrated scores cannot be combined in the ensemble coherently, and the default 0.5 threshold produces an alert volume that may flood or starve the analyst queue. Both failures stem from skipping the calibration and threshold tuning that translate model scores into actionable decisions.

Correct Approach

Calibrate every detector and set its threshold from the analyst capacity, per Section 12.10. Calibration is a prerequisite for the ensemble, the uncertainty sampling, and the score interpretation, not an optional refinement.

4

Description

Deploying without latency profiling, discovering the SLO breach under production load

Why It Happens

The detectors are individually fast in development, and the latency is not profiled under load. The system is deployed on the assumption that individually fast detectors compose into a fast system.

Consequence

Under production load, the sequential or unoptimised composition of the detectors breaches the 50ms P99 SLO, and the detection layer is disabled to recover the latency, leaving the system unprotected. The latency was a security constraint that was not validated.

Correct Approach

Profile the latency under representative load before deployment, per Section 12.12, and use the async parallel scoring, quantisation, and graceful degradation that fit the ensemble within the budget. The latency budget is a security constraint, not a performance nicety.

5

Description

Not versioning models, making rollback a manual recovery and the audit impossible

Why It Happens

Models are deployed by copying files, and versioning is seen as overhead. The system works without it until a rollback or an audit is needed.

Consequence

When a model regresses, the rollback is a manual recovery that fails if the previous state was not preserved. When a decision is challenged, the audit cannot identify which model made it or what it was trained on. Both failures stem from the absence of model versioning.

Correct Approach

Use the model registry from Section 12.13 to version every model with its full lineage. Versioning makes rollback a single operation and the audit possible -- it is the control plane that makes every model update safe and every decision traceable.

Section Summary

Compact

Chapter 12 built the ML detection layer of the security gateway across seventeen sections. It established the five detection families (anomaly, supervised, sequence, semantic, neural) and the feature engineering shared across them; built the four input-side detectors and the output-side PII scanner; added the calibration, feature pipeline, and inference optimisation that make the detectors deployable within the 50ms budget; built the model registry and live curation that keep the system from decaying; combined the detectors in the four-detector ensemble; validated everything with benchmarking and A/B testing; and integrated it all into the production ML gateway capstone. The central thesis is that ML detection complements rather than replaces signature detection: the two layers cover each other's gaps and fail independently, providing defence-in-depth. The chapter's deliverable is not the individual detectors but the integrated system -- the ensemble plus the operational infrastructure -- and a detection system without the registry, curation, and monitoring is a decaying snapshot rather than a sustainable defence. Chapter 13 lifts the per-request decisions this gateway makes to session-level and entity-level behavioural analysis.

Key Takeaways

  • The Chapter 12 deliverable is the integrated detection system, not the individual detectors: the ensemble combines them, the calibration makes the combination coherent, and the operational infrastructure keeps it current
  • Five detection families cover the attack surface: anomaly (novel attacks), supervised (known families), sequence (multi-turn), semantic (paraphrase), and neural (highest precision), with the PII scanner covering output-side leakage
  • The operational infrastructure -- registry, curation, retraining trigger, monitoring -- is what separates a sustainable detection system from a decaying snapshot; a detector without it falls behind the attack distribution
  • ML detection complements signature detection rather than replacing it: the signatures catch known attacks fast and precisely, the ML detectors cover the novel variants, and the two fail independently for defence-in-depth
  • Calibration and the latency budget are not refinements but requirements: uncalibrated scores cannot be combined, and a detector that breaches the SLO is disabled under load
  • Chapter 12 makes the per-request decision; Chapter 13 lifts it to session-level behavioural analysis that the per-request classifiers cannot perform, completing the arc from request analysis to behavioural analysis

Chapter 13: Behavioural Analysis and Monitoring

Preview

Chapter 12 trained classifiers that evaluate individual API requests. Chapter 13 lifts the analysis to the session and user level: behavioural baselines that capture what a normal user session looks like, drift detection that flags when a user's behaviour deviates from baseline, rate-based detection patterns that the Chapter 12 classifiers cannot see because they operate per-request, and user behaviour profiling that builds entity-level risk scores across sessions. Chapter 13 also covers model behavioural monitoring: detecting when the LLM's output distribution shifts in ways that indicate prompt injection success rather than surface-level injection attempts. By the end of Chapter 13, the detection system covers the full arc from individual request analysis (Chapter 12) to session-level behavioural analysis (Chapter 13), ready for Chapter 14's production deployment at scale.
