Security Feature Engineering: Extracting Signal from API Requests

Section Overview

One Line Summary

Security feature engineering starts with the adversary goal: what signal at the feature level separates an attack from a legitimate request -- get this right once and every classifier in Chapter 12 benefits.

Why This Section Exists

Every ML classifier in Chapter 12 -- Isolation Forest, Random Forest, XGBoost, GRU, Sentence Transformer, DistilBERT -- consumes features. The features are not free: they must be designed, extracted, and served within the latency budget of the production gateway. A well-designed feature set enables a Random Forest to reach 90%+ accuracy with 500 labelled examples. A naive feature set -- raw text passed directly to a bag-of-words vectoriser -- requires 10x the data and still misses the structural attack signals that simple engineered features catch immediately. Section 12.02 builds the shared feature extraction pipeline that all five detection families use. It is an infrastructure section: after this section, every subsequent classifier section can focus on the model architecture rather than re-engineering features from scratch. The four feature groups -- token-level, structural, semantic, and contextual -- each capture a distinct signal class that the others do not. Together they give the classifiers enough coverage of the adversarial attack surface to detect novel variants, not just known examples.

Position In Chapter

Section 12.02 is the shared infrastructure that all subsequent classifier sections depend on. It immediately follows the taxonomy (Section 12.01) and precedes every training section. The feature pipeline built here is referenced explicitly in Sections 12.03 through 12.17. It is the single highest-leverage investment in Chapter 12: good features compound across every model; bad features degrade every model.

Prose Content

Part 1

Title

Why Security Features Are Different

Body

Standard NLP classification features are designed to capture topic, sentiment, or intent as a reader would perceive them. A spam classifier uses word frequency, sender reputation, and link density. A sentiment classifier uses emotional language markers, negation patterns, and adjective polarity. The features are semantic: they describe what the text means. Security feature engineering for LLM API detection starts from a different question: what signal at the feature level separates an attack from a legitimate request at the structural and behavioural level, independent of the specific words used? This matters because adversaries adapt. An attacker who knows the spam classifier's top features stops using the flagged words. An attacker who knows the jailbreak classifier's top semantic features rewrites the payload to reduce semantic similarity to known jailbreaks. But an attacker who knows that the classifier flags role boundary markers cannot simply rewrite around that feature without fundamentally changing the attack structure -- because the role boundary marker is the attack mechanism, not just a surface indicator. This is the core principle of security feature engineering: features that describe the attack mechanism are more robust to adversarial adaptation than features that describe the surface presentation. A prompt injection attack requires an instruction override signal. That signal manifests in structural features: the presence of 'ignore', 'disregard', or 'forget' near the beginning of a user turn; a role label (system:, assistant:) inside a user-role message; a markdown code block containing what appears to be a system prompt. These structural features describe the injection mechanism. Rewriting the surface wording does not eliminate the structural feature; it still registers. The second principle is that attack features span multiple signal classes. A jailbreak prompt may be semantically close to a known jailbreak (semantic feature), contain a persona invocation token (structural feature), be longer than 95% of benign requests (token-level feature), and arrive in the third turn of a conversation that has already seen one refusal (contextual feature). No single feature class captures the full attack signal. The flat feature vector that combines all five groups gives the classifier a richer representation than any single group alone, enabling it to generalise across attack families with different surface presentations.

Part 2

Title

Token-Level Features: Signal in the Raw Text

Body

Token-level features are computed directly from the raw text of the request without requiring a neural model or session context. They are the fastest features to compute -- sub-millisecond for all token-level features combined -- and the most robust to inference infrastructure failures. They capture attack signals that manifest in the statistical properties of the text rather than its specific tokens. Sequence length is a reliable first-order feature. Jailbreak prompts are typically longer than benign requests: they require setup (establishing the persona, describing the alternative mode), payload (the actual instruction override), and often a closing confirmation request. The median jailbreak prompt in the JailbreakChat.com corpus is 3.2x longer than the median benign request to a consumer LLM API. Sequence length is not a sufficient feature -- short injections exist -- but it is a strong prior that the classifier uses as a base rate adjustment. Special character density measures the ratio of non-alphanumeric characters to total tokens. Injection payloads frequently use special characters for structure: backticks for code blocks, brackets for emphasis, angle brackets for pseudo-tags, forward slashes for role labels. A legitimately composed user request rarely exceeds 8% special character density; injection payloads average 15-22%. The feature is computed as len([c for c in text if not c.isalnum() and not c.isspace()]) / max(len(text), 1). Instruction keyword frequency counts the occurrence of high-signal instruction verbs relative to total token count: 'ignore', 'disregard', 'forget', 'pretend', 'roleplay', 'act as', 'you are now', 'your new instructions'. These terms are the surface manifestation of the instruction override mechanism. Their frequency relative to text length is more informative than raw count: a long document that mentions 'ignore' once in a different context is different from a 30-token prompt that opens with 'ignore all previous'. Token entropy measures the information density of the text using the Shannon entropy of the character or token distribution. Low-entropy texts (repetitive, formulaic) are associated with automated attack generation. High-entropy texts that exceed the normal distribution for human-written prompts may indicate obfuscated payloads (Base64 encoded instructions, Unicode homoglyph substitution) that Chapter 6 Section 6.04 documented as token smuggling techniques.

Part 3

Title

Structural Features: Signal in the Architecture of the Request

Body

Structural features capture how the request is constructed rather than what it says. They are computed by parsing the text for structural markers and are typically the highest- signal feature group for prompt injection detection -- higher than semantic embedding features -- because structural markers directly indicate the attack mechanism rather than its surface content. Role boundary markers are the most diagnostic structural feature for prompt injection. An injection attack that attempts to override the system prompt frequently includes explicit role labels inside the user-turn content: 'System:', 'SYSTEM:', '[SYSTEM]', 'Assistant:', '<assistant>', or markdown headers that mimic system prompt formatting. The presence of any role label pattern inside a user-role message is a strong injection signal. Detection is a boolean feature with near-zero false positive rate on legitimate traffic: human users almost never write 'System:' in a conversational message. Code block presence and density counts the number of markdown triple-backtick code blocks and their cumulative character length relative to total message length. Indirect injection attacks embedded in documents, web pages, and email content (Chapter 6 Sections 6.06 through 6.10) frequently use code block formatting to present instructions in a context that the LLM treats as authoritative. A user message that is more than 60% code block content by character length is statistically anomalous in benign traffic and common in indirect injection payloads. Bracket and quotation density measures the ratio of bracket characters (square, curly, angle, parenthetical) and quotation marks to total characters. Structured injection templates use brackets extensively to demarcate sections, pseudo-tags, and role labels. A request with a bracket density above the 95th percentile of the benign training distribution is worth flagging for ensemble scoring even if no other feature triggers. Instruction imperative count is a syntactic feature that counts the number of imperative verb constructions in the text: sentences that begin with a verb in base form addressed to the model ('Write', 'Tell', 'Explain', 'Ignore', 'Respond only in'). The ratio of imperative constructions to total sentences is elevated in injection and jailbreak prompts relative to conversational requests. The feature is extracted with a lightweight POS tagger -- spaCy's small English model adds 2-3ms but the feature is high signal for instruction-dense payloads.

Part 4

Title

Semantic Features: Signal in the Meaning

Body

Semantic features capture the meaning of the request in a continuous embedding space. They are computed from a Sentence Transformer model and enable the classifier to detect paraphrase-equivalent attacks that share no surface tokens with known examples. The computational cost is 2-4ms for MiniLM-L6 via ONNX Runtime -- affordable within the 50ms gateway budget but meaningful relative to the sub-millisecond token and structural features. Cosine distance to jailbreak cluster centroids is the primary semantic feature. During the dataset curation phase (Section 12.04), confirmed jailbreak examples are embedded with MiniLM-L6 and clustered with HDBSCAN into semantically coherent families: DAN-style persona jailbreaks, fictional framing jailbreaks, instruction hierarchy attacks, and so on. The centroid of each cluster is stored in the attack cluster library (Section 12.07). At inference time, the request embedding is compared to all cluster centroids and the minimum cosine distance across all centroids is computed as a scalar feature. A small minimum distance (below 0.25) indicates semantic proximity to a known attack family. Cosine distance to the benign centroid is the complement: a request that is semantically distant from all known attack clusters but also semantically distant from the benign centroid may be a novel attack variant with no existing cluster. This out-of-distribution signal is the semantic analogue of the Isolation Forest anomaly score -- it flags inputs that are unusual relative to both known attack families and known benign traffic. Embedding magnitude (L2 norm of the request embedding) is a lightweight additional feature that captures the density of the semantic representation. Injection payloads that combine multiple unrelated instructions into a single request often produce lower- magnitude embeddings than coherent natural language text because the mixed semantic content does not project strongly in any single direction of the embedding space.

Part 5

Title

Contextual and API-Level Features: Signal Across the Session

Body

Contextual features capture the request's position in the user's session history. They are the only feature group that requires cross-request state: they depend on what happened in earlier turns of the conversation or earlier requests in the session. This makes them the most expensive feature group to serve -- they require a Redis session cache or equivalent to avoid reconstructing the conversation history on every request -- but they are uniquely powerful for detecting multi-turn attack patterns that single-turn features cannot see. Turn number in conversation is the simplest contextual feature: the ordinal position of the current request in the conversation. Multi-turn jailbreak attacks (Chapter 7 Section 7.07) typically begin with innocuous early turns to establish rapport and context before introducing the attack payload in a later turn. A high-confidence attack signal that arrives in turn 5 of a conversation is more likely to be a deliberate gradual escalation than an isolated impulsive request. Prior refusal count is the count of turns in the current conversation where the model responded with a refusal or safety deflection. An adversary who is actively probing the model's boundaries will accumulate refusals as they test different approaches. A session with 3+ refusals before the current request is a strong signal that the user is engaged in systematic boundary testing rather than legitimate use. This feature requires the conversation history to be stored in the session cache and the model's responses to be monitored for refusal patterns -- a non-trivial integration that Chapter 14 Production Deployment covers. Session request rate is the number of requests per minute in the current session. Automated jailbreak generation (Chapter 7 Section 7.12) and model extraction campaigns (Chapter 9) both produce elevated request rates relative to human-paced conversation. A session request rate above the 99th percentile of the benign training distribution is an independent anomaly signal that combines multiplicatively with attack-content signals. API-level features capture the configuration of the API call itself rather than the content. Temperature setting is a useful signal: jailbreak researchers frequently set high temperature (0.9-1.0) when probing model boundaries to increase response variance. The streaming flag distinguishes interactive from automated clients. Model name selection (using a more powerful model than the default for a given endpoint) may indicate a sophisticated user with specific capability requirements. These features are extracted from the API request headers and parameters rather than the message content and add zero latency to the pipeline.

Part 6

Title

Feature Correlation, Importance, and Distribution Shift

Body

Once the five feature groups are implemented, three analytical tasks complete the feature engineering phase before any model is trained: correlation analysis, importance analysis, and distribution shift monitoring. Feature correlation analysis computes pairwise Pearson or Spearman correlation across all features on the labelled training dataset. Features with pairwise correlation above 0.85 are collinear: they carry largely the same signal, and including both wastes model capacity and can inflate feature importance scores for the correlated pair. Collinear feature pairs are resolved by keeping the faster-to-compute feature and dropping the redundant one. For example, sequence length and instruction keyword count are correlated (longer prompts have more keywords) but sequence length computes in microseconds while keyword count requires a scan of the keyword list. When the correlation is high, sequence length is the correct feature to keep. SHAP feature importance analysis runs after the first supervised classifier is trained on the feature set (Section 12.05). SHAP TreeExplainer decomposes each prediction into additive feature contributions and aggregates them into a global feature importance ranking. The ranking reveals whether the feature set is measuring the right signal: the top SHAP features should correspond to structural and behavioural attack mechanisms, not surface artifacts. If 'sequence_length' and 'token_count' dominate the SHAP ranking and the structural features (role_boundary_marker, code_block_density) rank low, the feature set is measuring request length rather than attack structure -- a signal that is easy for an adversary to manipulate by padding a short injection payload with benign text. Feature distribution shift monitoring tracks the distributions of each feature in live traffic against their distributions in the training dataset. An attack distribution that is shifting -- because adversaries have adapted their tactics -- will manifest as a distributional change in the features that were most predictive of the old attack patterns. The monitoring uses the Kolmogorov-Smirnov test per feature, comparing the training distribution to a rolling window of live traffic. A KS statistic above 0.15 on any of the top-10 SHAP features triggers an investigation and potentially a retraining trigger (Section 12.14).

# security_feature_extractor.py
# Section 12.02: Security Feature Engineering
# 20260606 | AI Security Mastery -- Chapter 12 by Raghav Dinesh
# Single quotes throughout per book convention

from __future__ import annotations

import re
import math
from dataclasses import dataclass, field, asdict
from typing import Dict, List, Optional, Tuple

import numpy as np

# ---------------------------------------------------------------------------
# Feature schema version -- bump whenever a feature is added, removed, or
# renamed. Every trained model is tagged with the schema version used at
# training time. Requests arriving at inference time are rejected if their
# computed schema version does not match the model's tagged version.
# ---------------------------------------------------------------------------
FEATURE_SCHEMA_VERSION = '1.0.0'

# ---------------------------------------------------------------------------
# Instruction keywords: surface-level attack verb vocabulary.
# These are high-signal for prompt injection and jailbreak detection.
# Do NOT expand this list without re-running SHAP importance analysis.
# ---------------------------------------------------------------------------
INSTRUCTION_KEYWORDS: List[str] = [
    'ignore', 'disregard', 'forget', 'override', 'bypass',
    'pretend', 'roleplay', 'act as', 'you are now', 'your new',
    'from now on', 'new persona', 'switch to', 'hypothetically',
    'in this scenario', 'for educational purposes',
]

# ---------------------------------------------------------------------------
# Role boundary patterns: structural markers for prompt injection.
# Presence of any pattern inside a user-role message is a strong signal.
# ---------------------------------------------------------------------------
ROLE_BOUNDARY_PATTERNS: List[re.Pattern] = [
    re.compile(r'(?i)\bsystem\s*:', re.MULTILINE),
    re.compile(r'(?i)\bassistant\s*:', re.MULTILINE),
    re.compile(r'(?i)<\s*system\s*>', re.MULTILINE),
    re.compile(r'(?i)\[system\]', re.MULTILINE),
    re.compile(r'(?i)###\s*system', re.MULTILINE),
    re.compile(r'(?i)###\s*instruction', re.MULTILINE),
]


@dataclass
class APIRequestContext:
    '''Represents one API request and its session context.'''
    message_text: str
    role: str = 'user'
    turn_number: int = 1
    prior_refusal_count: int = 0
    session_requests_per_minute: float = 0.0
    temperature: float = 0.7
    streaming: bool = False
    model_name: str = 'default'
    endpoint: str = '/v1/chat/completions'
    # Pre-computed embedding: pass if already computed upstream to avoid
    # double inference. None triggers on-demand extraction.
    embedding: Optional[np.ndarray] = None
    # Pre-computed attack cluster centroids: list of (cluster_name, centroid_vector)
    attack_centroids: List[Tuple[str, np.ndarray]] = field(default_factory=list)
    benign_centroid: Optional[np.ndarray] = None


@dataclass
class SecurityFeatureVector:
    '''Flat feature vector produced by extract_features(). All fields are floats.'''

    # --- Token-level ---
    sequence_length: float = 0.0
    word_count: float = 0.0
    special_char_density: float = 0.0
    instruction_keyword_freq: float = 0.0
    token_entropy: float = 0.0
    uppercase_ratio: float = 0.0

    # --- Structural ---
    role_boundary_marker: float = 0.0      # boolean as float: 0 or 1
    code_block_count: float = 0.0
    code_block_density: float = 0.0
    bracket_density: float = 0.0
    quotation_density: float = 0.0

    # --- Semantic ---
    centroid_cosine_dist_min: float = 1.0  # distance to nearest attack centroid
    benign_cosine_dist: float = 1.0        # distance to benign centroid
    embedding_l2_norm: float = 0.0

    # --- Contextual ---
    turn_number: float = 1.0
    prior_refusal_count: float = 0.0
    session_request_rate: float = 0.0

    # --- API-level ---
    temperature: float = 0.7
    streaming_flag: float = 0.0            # boolean as float
    is_default_model: float = 1.0          # boolean as float

    schema_version: str = FEATURE_SCHEMA_VERSION

    def to_array(self) -> np.ndarray:
        '''Returns the feature vector as a numpy array (excludes schema_version).'''
        d = asdict(self)
        d.pop('schema_version')
        return np.array(list(d.values()), dtype=np.float32)

    def feature_names(self) -> List[str]:
        d = asdict(self)
        d.pop('schema_version')
        return list(d.keys())


# ---------------------------------------------------------------------------
# Token-level extraction
# ---------------------------------------------------------------------------

def _compute_token_entropy(text: str) -> float:
    '''Shannon entropy over character distribution.'''
    if not text:
        return 0.0
    freq: Dict[str, int] = {}
    for c in text:
        freq[c] = freq.get(c, 0) + 1
    n = len(text)
    return -sum((f / n) * math.log2(f / n) for f in freq.values() if f > 0)


def extract_token_features(text: str) -> Dict[str, float]:
    words = text.split()
    n_chars = max(len(text), 1)
    special_chars = sum(1 for c in text if not c.isalnum() and not c.isspace())
    text_lower = text.lower()
    keyword_hits = sum(1 for kw in INSTRUCTION_KEYWORDS if kw in text_lower)
    return {
        'sequence_length': float(n_chars),
        'word_count': float(len(words)),
        'special_char_density': special_chars / n_chars,
        'instruction_keyword_freq': keyword_hits / max(len(words), 1),
        'token_entropy': _compute_token_entropy(text),
        'uppercase_ratio': sum(1 for c in text if c.isupper()) / n_chars,
    }


# ---------------------------------------------------------------------------
# Structural extraction
# ---------------------------------------------------------------------------

def extract_structural_features(text: str) -> Dict[str, float]:
    n_chars = max(len(text), 1)

    role_hit = float(any(p.search(text) for p in ROLE_BOUNDARY_PATTERNS))

    code_blocks = re.findall(r'```[\s\S]*?```', text)
    code_chars = sum(len(b) for b in code_blocks)

    brackets = sum(1 for c in text if c in '[]{}()<>')
    quotes = sum(1 for c in text if c in '"\'`')

    return {
        'role_boundary_marker': role_hit,
        'code_block_count': float(len(code_blocks)),
        'code_block_density': code_chars / n_chars,
        'bracket_density': brackets / n_chars,
        'quotation_density': quotes / n_chars,
    }


# ---------------------------------------------------------------------------
# Semantic extraction
# ---------------------------------------------------------------------------

def _cosine_distance(a: np.ndarray, b: np.ndarray) -> float:
    norm_a = np.linalg.norm(a)
    norm_b = np.linalg.norm(b)
    if norm_a == 0 or norm_b == 0:
        return 1.0
    return float(1.0 - np.dot(a, b) / (norm_a * norm_b))


def extract_semantic_features(
    embedding: Optional[np.ndarray],
    attack_centroids: List[Tuple[str, np.ndarray]],
    benign_centroid: Optional[np.ndarray],
) -> Dict[str, float]:
    if embedding is None:
        return {
            'centroid_cosine_dist_min': 1.0,
            'benign_cosine_dist': 1.0,
            'embedding_l2_norm': 0.0,
        }

    min_dist = 1.0
    if attack_centroids:
        dists = [_cosine_distance(embedding, c) for _, c in attack_centroids]
        min_dist = min(dists)

    benign_dist = (
        _cosine_distance(embedding, benign_centroid)
        if benign_centroid is not None
        else 1.0
    )

    return {
        'centroid_cosine_dist_min': min_dist,
        'benign_cosine_dist': benign_dist,
        'embedding_l2_norm': float(np.linalg.norm(embedding)),
    }


# ---------------------------------------------------------------------------
# Contextual extraction
# ---------------------------------------------------------------------------

def extract_contextual_features(ctx: APIRequestContext) -> Dict[str, float]:
    return {
        'turn_number': float(ctx.turn_number),
        'prior_refusal_count': float(ctx.prior_refusal_count),
        'session_request_rate': float(ctx.session_requests_per_minute),
    }


# ---------------------------------------------------------------------------
# API-level extraction
# ---------------------------------------------------------------------------

def extract_api_features(ctx: APIRequestContext) -> Dict[str, float]:
    return {
        'temperature': float(ctx.temperature),
        'streaming_flag': float(ctx.streaming),
        'is_default_model': float(ctx.model_name == 'default'),
    }


# ---------------------------------------------------------------------------
# Unified extractor
# ---------------------------------------------------------------------------

def extract_features(ctx: APIRequestContext) -> SecurityFeatureVector:
    '''
    Extract all five feature groups from a single API request context.
    Returns a SecurityFeatureVector with schema_version tagged.

    The feature vector is consumed by all five ML detection families:
      - Isolation Forest (Section 12.03): uses to_array()
      - Random Forest / XGBoost (Section 12.05): uses to_array()
      - GRU (Section 12.06): uses per-turn vectors accumulated into sequence
      - Embedding detector (Section 12.07): uses centroid_cosine_dist_min directly
      - DistilBERT (Section 12.08): uses full feature vector as additional features
    '''
    tok = extract_token_features(ctx.message_text)
    struct = extract_structural_features(ctx.message_text)
    sem = extract_semantic_features(ctx.embedding, ctx.attack_centroids, ctx.benign_centroid)
    cont = extract_contextual_features(ctx)
    api = extract_api_features(ctx)

    return SecurityFeatureVector(
        # token
        sequence_length=tok['sequence_length'],
        word_count=tok['word_count'],
        special_char_density=tok['special_char_density'],

# feature_importance_analyser.py
# Section 12.02: SHAP Feature Importance Analysis for Security Classifiers
# 20260606 | AI Security Mastery -- Chapter 12 by Raghav Dinesh
# Single quotes throughout per book convention

from __future__ import annotations

from typing import Any, Dict, List, Tuple

import numpy as np
import shap
import matplotlib.pyplot as plt


# Features that should rank in the top 10 for a well-designed security classifier.
# If none of these appear in the top 10, the feature set is measuring the wrong signal.
STRUCTURAL_FEATURES = {
    'role_boundary_marker',
    'code_block_density',
    'code_block_count',
    'bracket_density',
}

SURFACE_FEATURES = {
    'sequence_length',
    'word_count',
    'token_entropy',
}


def compute_shap_values(
    model: Any,
    X: np.ndarray,
    feature_names: List[str],
) -> Tuple[shap.TreeExplainer, np.ndarray]:
    '''
    Compute SHAP values for a trained tree model (RandomForest or XGBoost).
    Returns the explainer and the SHAP value matrix (n_samples x n_features).
    '''
    explainer = shap.TreeExplainer(model)
    shap_values = explainer.shap_values(X)
    # For binary classification, shap_values is a list [class_0, class_1].
    # Take class 1 (attack class).
    if isinstance(shap_values, list):
        shap_values = shap_values[1]
    return explainer, shap_values


def global_importance_ranking(
    shap_values: np.ndarray,
    feature_names: List[str],
    top_n: int = 15,
) -> List[Tuple[str, float]]:
    '''
    Returns top_n features ranked by mean absolute SHAP value across all samples.
    '''
    mean_abs = np.abs(shap_values).mean(axis=0)
    ranked = sorted(
        zip(feature_names, mean_abs),
        key=lambda x: x[1],
        reverse=True,
    )
    return ranked[:top_n]


def plot_global_importance(
    shap_values: np.ndarray,
    X: np.ndarray,
    feature_names: List[str],
    save_path: str = 'shap_importance.png',
    top_n: int = 15,
) -> None:
    shap.summary_plot(
        shap_values,
        X,
        feature_names=feature_names,
        max_display=top_n,
        show=False,
    )
    plt.tight_layout()
    plt.savefig(save_path, dpi=150, bbox_inches='tight')
    plt.close()
    print(f'Saved SHAP summary plot: {save_path}')


def security_audit_report(
    ranking: List[Tuple[str, float]],
) -> Dict[str, Any]:
    '''
    Audits the SHAP importance ranking against the security feature design principles.
    Returns a dict with audit findings and a pass/fail verdict.
    '''
    top_10_names = {name for name, _ in ranking[:10]}
    structural_in_top_10 = STRUCTURAL_FEATURES & top_10_names
    surface_dominating = (
        len(SURFACE_FEATURES & set(name for name, _ in ranking[:3])) >= 2
    )
    structural_outranks_surface = False
    if structural_in_top_10:
        best_structural_rank = min(
            i for i, (name, _) in enumerate(ranking)
            if name in STRUCTURAL_FEATURES
        )
        best_surface_rank = min(
            (i for i, (name, _) in enumerate(ranking) if name in SURFACE_FEATURES),
            default=len(ranking),
        )
        structural_outranks_surface = best_structural_rank < best_surface_rank

    findings = []
    if not structural_in_top_10:
        findings.append(
            'WARN: No structural features in top 10. '
            'Classifier may be detecting length/token artifacts rather than attack mechanism.'
        )
    if surface_dominating:
        findings.append(
            'WARN: Surface features (sequence_length, word_count) dominate top 3. '
            'Easy for adversary to evade by padding payload with benign text.'
        )
    if structural_outranks_surface:
        findings.append(
            'OK: Structural features outrank surface features. '
            'Feature set is targeting attack mechanism.'
        )

    passed = bool(structural_in_top_10) and not surface_dominating
    return {
        'passed': passed,
        'structural_features_in_top_10': sorted(structural_in_top_10),
        'surface_dominating_top_3': surface_dominating,
        'structural_outranks_surface': structural_outranks_surface,
        'findings': findings,
    }


def print_importance_report(
    ranking: List[Tuple[str, float]],
    audit: Dict[str, Any],
) -> None:
    print('SHAP Feature Importance Ranking')
    print('=' * 50)
    for rank, (name, importance) in enumerate(ranking, 1):
        tag = ''
        if name in STRUCTURAL_FEATURES:
            tag = ' [STRUCTURAL]'
        elif name in SURFACE_FEATURES:
            tag = ' [SURFACE]'
        bar = '#' * min(int(importance * 200), 40)
        print(f'  {rank:>2}. {name:<35} {importance:.4f}  {bar}{tag}')

    print()
    print('Security Audit:')
    verdict = 'PASS' if audit['passed'] else 'FAIL'
    print(f'  Verdict: {verdict}')
    for finding in audit['findings']:
        print(f'  {finding}')

# feature_correlation_matrix.py
# Section 12.02: Feature Correlation Analysis for Security Feature Set
# 20260606 | AI Security Mastery -- Chapter 12 by Raghav Dinesh
# Single quotes throughout per book convention

from __future__ import annotations

from typing import List, Tuple

import numpy as np
import matplotlib.pyplot as plt
from scipy.stats import pearsonr, spearmanr

# Approximate computation cost rank per feature (lower = cheaper).
# Used to decide which feature to keep when a collinear pair is found.
FEATURE_COST_RANK = {
    'sequence_length': 1,
    'word_count': 1,
    'special_char_density': 2,
    'instruction_keyword_freq': 3,
    'token_entropy': 4,
    'uppercase_ratio': 2,
    'role_boundary_marker': 3,
    'code_block_count': 3,
    'code_block_density': 3,
    'bracket_density': 2,
    'quotation_density': 2,
    'centroid_cosine_dist_min': 10,
    'benign_cosine_dist': 10,
    'embedding_l2_norm': 10,
    'turn_number': 1,
    'prior_refusal_count': 1,
    'session_request_rate': 1,
    'temperature': 1,
    'streaming_flag': 1,
    'is_default_model': 1,
}

COLLINEAR_THRESHOLD = 0.85


def compute_correlation_matrix(
    X: np.ndarray,
    feature_names: List[str],
    method: str = 'pearson',
) -> np.ndarray:
    n = X.shape[1]
    corr = np.zeros((n, n))
    for i in range(n):
        for j in range(n):
            if i == j:
                corr[i, j] = 1.0
            elif i < j:
                if method == 'pearson':
                    r, _ = pearsonr(X[:, i], X[:, j])
                else:
                    r, _ = spearmanr(X[:, i], X[:, j])
                corr[i, j] = corr[j, i] = r
    return corr


def find_collinear_pairs(
    corr: np.ndarray,
    feature_names: List[str],
    threshold: float = COLLINEAR_THRESHOLD,
) -> List[Tuple[str, str, float, str]]:
    '''
    Returns list of (feature_a, feature_b, correlation, recommendation).
    Recommendation is which feature to DROP based on FEATURE_COST_RANK.
    '''
    pairs = []
    n = corr.shape[0]
    for i in range(n):
        for j in range(i + 1, n):
            r = abs(corr[i, j])
            if r >= threshold:
                fa, fb = feature_names[i], feature_names[j]
                cost_a = FEATURE_COST_RANK.get(fa, 5)
                cost_b = FEATURE_COST_RANK.get(fb, 5)
                # Drop the more expensive feature; keep the cheaper one.
                drop = fb if cost_b >= cost_a else fa
                pairs.append((fa, fb, corr[i, j], f'drop {drop}'))
    return pairs


def plot_correlation_heatmap(
    corr: np.ndarray,
    feature_names: List[str],
    save_path: str = 'feature_correlation.png',
) -> None:
    fig, ax = plt.subplots(figsize=(14, 12))
    im = ax.imshow(np.abs(corr), cmap='RdYlGn_r', vmin=0, vmax=1)
    ax.set_xticks(range(len(feature_names)))
    ax.set_yticks(range(len(feature_names)))
    ax.set_xticklabels(feature_names, rotation=45, ha='right', fontsize=7)
    ax.set_yticklabels(feature_names, fontsize=7)
    plt.colorbar(im, ax=ax, label='|Pearson r|')
    ax.set_title('Security Feature Correlation Matrix (|r|)', fontsize=12)
    plt.tight_layout()
    plt.savefig(save_path, dpi=150, bbox_inches='tight')
    plt.close()
    print(f'Saved: {save_path}')


def print_collinear_report(
    pairs: List[Tuple[str, str, float, str]],
) -> None:
    if not pairs:
        print('No collinear feature pairs found (threshold: {:.2f}).'.format(COLLINEAR_THRESHOLD))
        return
    print(f'Collinear feature pairs (|r| >= {COLLINEAR_THRESHOLD}):')
    for fa, fb, r, rec in pairs:
        print(f'  {fa} -- {fb}  |r|={abs(r):.3f}  -> {rec}')

# feature_distribution_monitor.py
# Section 12.02: Feature Distribution Shift Monitoring
# 20260606 | AI Security Mastery -- Chapter 12 by Raghav Dinesh
# Single quotes throughout per book convention

from __future__ import annotations

from dataclasses import dataclass
from typing import Dict, List, Optional, Tuple

import numpy as np
from scipy.stats import ks_2samp

KS_THRESHOLDS = {
    'monitor': 0.05,
    'investigate': 0.10,
    'alert': 0.15,
}


@dataclass
class FeatureShiftResult:
    feature_name: str
    ks_statistic: float
    p_value: float
    tier: str        # 'ok', 'monitor', 'investigate', 'alert'
    action: str


def _classify_tier(ks: float) -> Tuple[str, str]:
    if ks >= KS_THRESHOLDS['alert']:
        return ('alert', 'Trigger retraining pipeline within 24h; escalate to analyst')
    elif ks >= KS_THRESHOLDS['investigate']:
        return ('investigate', 'Investigate within 48h; check labelled dataset recency')
    elif ks >= KS_THRESHOLDS['monitor']:
        return ('monitor', 'Log and track trend')
    else:
        return ('ok', 'No action required')


def monitor_feature_distributions(
    training_X: np.ndarray,
    live_X: np.ndarray,
    feature_names: List[str],
    top_shap_features: Optional[List[str]] = None,
) -> List[FeatureShiftResult]:
    '''
    Runs KS test for each feature comparing training vs live distributions.
    If top_shap_features is provided, alerts on those features are escalated.
    '''
    results = []
    for i, name in enumerate(feature_names):
        ks_stat, p_val = ks_2samp(training_X[:, i], live_X[:, i])
        tier, action = _classify_tier(ks_stat)

        # Escalate if this is a high-importance feature
        if top_shap_features and name in top_shap_features and tier == 'investigate':
            tier = 'alert'
            action = (
                'High-SHAP feature shift detected. '
                'Trigger retraining pipeline within 24h.'
            )

        results.append(FeatureShiftResult(
            feature_name=name,
            ks_statistic=ks_stat,
            p_value=p_val,
            tier=tier,
            action=action,
        ))

    return results


def print_shift_report(
    results: List[FeatureShiftResult],
    show_ok: bool = False,
) -> bool:
    '''
    Prints the distribution shift report.
    Returns True if any feature is in 'alert' tier (retraining trigger).
    '''
    tier_order = {'alert': 0, 'investigate': 1, 'monitor': 2, 'ok': 3}
    results_sorted = sorted(results, key=lambda r: tier_order[r.tier])

    print('Feature Distribution Shift Report')
    print('=' * 60)
    alert_triggered = False
    for r in results_sorted:
        if r.tier == 'ok' and not show_ok:
            continue
        tier_label = r.tier.upper()
        print(f'  [{tier_label:<11}] {r.feature_name:<35} KS={r.ks_statistic:.4f}  p={r.p_value:.4f}')
        print(f'               Action: {r.action}')
        if r.tier == 'alert':
            alert_triggered = True

    if alert_triggered:
        print('\n*** RETRAINING TRIGGER: one or more features exceeded KS=0.15 ***')
        print('    Connect to Section 12.14 dataset_curator.py retraining_trigger()')

    return alert_triggered

Common Mistakes

Mistake 1

Description

Using raw TF-IDF bag-of-words as the only feature representation and skipping the structural and contextual feature groups

Why It Happens

TF-IDF is the default feature extraction technique in most NLP tutorials and produces a feature vector that can be plugged into any scikit-learn classifier in three lines. Engineers who learned ML from standard NLP courses apply this pattern to security classification without questioning whether topic-frequency features are appropriate for adversarial intent detection.

Consequence

A TF-IDF classifier trained on jailbreak examples learns the vocabulary of the training set: 'DAN', 'unrestricted', 'ignore', 'pretend'. An adversary who reads the JailbreakChat.com database -- the same source used to train the classifier -- rewrites their payload to avoid the flagged vocabulary. The classifier's precision collapses against novel phrasings while the structural attack mechanism (role boundary override, instruction hierarchy manipulation) remains unchanged and undetected.

Correct Approach

Implement the five feature groups from Section 12.02. Structural features (role_boundary_marker, code_block_density) target the attack mechanism rather than the surface vocabulary and survive adversarial paraphrase. Run SHAP importance analysis after the first classifier is trained to verify that structural features outrank surface token features in the global ranking.

Mistake 2

Description

Computing semantic embeddings differently at training time versus inference time, producing training-serving skew

Why It Happens

During dataset construction (Section 12.04), embeddings are computed in batch mode using the sentence-transformers library on a GPU. During inference, the production pipeline uses ONNX Runtime with a quantised model on CPU. The two paths produce numerically different embeddings for the same text -- small differences, but enough to shift cosine distances systematically against the thresholds calibrated on training data.

Consequence

The cosine distance features (centroid_cosine_dist_min, benign_cosine_dist) computed at inference time do not match the distributions those features had at training time. The classifier's precision on the centroid distance feature degrades silently. No error is raised; the classifier continues to produce predictions. Feature distribution monitoring (deliverable_4) detects this as a shift in the semantic feature distributions, but only if it was deployed. Without the monitor, the skew is invisible.

Correct Approach

Use the same inference path at training and serving time. The production feature pipeline (Section 12.11) uses ONNX Runtime MiniLM-L6 throughout -- both during dataset construction and during live inference. Never use different embedding model versions or inference backends at training and serving time without re-validating the centroid distance distributions against the new backend.

Mistake 3

Description

Omitting contextual features because they require a Redis session cache, treating the infrastructure cost as too high

Why It Happens

Contextual features (prior_refusal_count, session_request_rate, turn_number) require cross-request state: the session cache must store prior conversation history and aggregate session-level metrics. Engineers who are building a prototype or MVP defer this infrastructure as too complex for the initial version and never add it.

Consequence

Multi-turn attack patterns -- gradual jailbreak erosion, payload splitting across turns, boundary probing through accumulated refusals -- are completely invisible to the classifier. The SHAP importance analysis will show prior_refusal_count as missing from the feature set, and any multi-turn attack that fragments the payload across innocuous individual turns will evade the classifier entirely regardless of how accurate it is on single-turn examples.

Correct Approach

Implement the Redis session cache before training the first classifier. The cache implementation in Section 12.11 is straightforward: a Redis hash per session ID with a TTL, storing turn count, refusal count, and session start timestamp. The infrastructure cost is low relative to the detection improvement from contextual features on multi-turn attacks. Deferring it produces a classifier that looks accurate on single-turn test sets but misses the most sophisticated attack patterns in production.

Mistake 4

Description

Not versioning the feature schema and deploying a model trained on an older feature set against a new pipeline

Why It Happens

A new feature is added to the pipeline (e.g., imperative_count from a spaCy POS tagger), the pipeline is deployed to production, and the existing trained classifier is left in place. The classifier was trained on a 19-feature vector; the pipeline now produces a 20-feature vector. The mismatch is silent: scikit-learn's predict() may accept the wrong- dimension input with a shape broadcast, or clip the extra feature, without raising an error.

Consequence

The classifier receives a feature vector that does not match the schema it was trained on. Its predictions become unreliable in ways that are difficult to diagnose: some features are mapped to wrong columns, extra features are ignored or cause index errors, and the model's calibrated thresholds are no longer valid for the mismatched feature distribution. Detection coverage degrades silently.

Correct Approach

Tag every trained model with FEATURE_SCHEMA_VERSION at training time (the constant in security_feature_extractor.py). At inference time, verify that the live pipeline's schema version matches the model's tagged version before passing the feature vector to predict(). Reject mismatched requests with a logged error rather than silently producing wrong predictions. Section 12.13 model registry enforces this as a stage transition gate.

Mistake 5

Description

Expanding the INSTRUCTION_KEYWORDS list without re-running SHAP analysis, accumulating low-signal keywords that add noise

Why It Happens

Threat intelligence reports document new jailbreak phrasings. The engineer adds new terms to INSTRUCTION_KEYWORDS to keep the keyword list current. Over time the list grows from 15 to 80 terms. The instruction_keyword_freq feature now measures a broader and noisier signal: many of the new terms appear in legitimate technical documentation and support conversations, not only in attacks.

Consequence

The instruction_keyword_freq feature's precision degrades as low-signal keywords introduce false positives. The SHAP importance of the feature drops relative to structural features because its signal is now diluted. The classifier's false positive rate increases for technical and educational queries that happen to use terms in the expanded keyword list ('pretend', 'act as', 'hypothetically') in legitimate contexts.

Correct Approach

Treat INSTRUCTION_KEYWORDS as a curated list, not a growing append-only list. After any addition, run SHAP importance analysis on the retrained classifier and verify that instruction_keyword_freq still outranks noise features. If precision on the benign test set degrades after adding a keyword, remove it. The list in Section 12.02 is a starting point; prune it for your specific deployment context.

Section Summary

Compact

Security feature engineering extracts signal from four groups: token-level (sequence length, special character density, instruction keyword frequency, token entropy), structural (role boundary markers, code block density, bracket density), semantic (cosine distance to attack cluster centroids, benign centroid distance, embedding norm), and contextual (turn number, prior refusal count, session request rate), plus API-level features (temperature, streaming flag, model name). Structural features are the highest- signal group for prompt injection because they target the attack mechanism rather than the surface vocabulary -- they survive adversarial paraphrase. The shared feature pipeline is used by all five ML detection families in Chapter 12. Feature schema versioning, SHAP importance auditing, correlation analysis, and distribution shift monitoring are the four operational disciplines that keep the feature set accurate and the classifier predictions reliable as the attack distribution shifts.

Key Takeaways

  • Start feature design from the adversary goal: features that describe the attack mechanism (role boundary markers, instruction override structure) are more robust to adversarial adaptation than features that describe the surface presentation (keyword frequency, text length)
  • Structural features often carry more signal than semantic features for prompt injection: the role boundary marker is the injection mechanism, not just a surface indicator -- it cannot be removed without changing the attack
  • The training-serving skew problem is the most dangerous silent failure mode in security ML: compute features with exactly the same code at training and inference time, and version the feature schema alongside every trained model
  • Contextual features (prior refusal count, session escalation rate) are the only features that capture multi-turn attack patterns -- defer the Redis session cache and these features become unavailable, making the classifier blind to gradual jailbreak erosion
  • SHAP importance analysis is an auditing tool, not just an explainability tool: if sequence_length dominates the top-3 SHAP features, the classifier is detecting length anomaly rather than attack structure and is easily evaded by payload padding
  • Feature distribution monitoring with KS tests per feature is the earliest warning signal of model performance degradation: a KS statistic above 0.15 on any top-SHAP feature indicates adversary adaptation before accuracy metrics show the problem

Section 12.03: Anomaly Detection -- Isolation Forest and One-Class SVM for Zero-Label Threat Discovery

Summary

Section 12.03 trains the first ML detector: Isolation Forest and One-Class SVM on the security feature vector from Section 12.02. Both algorithms require only normal (benign) API traffic -- no labelled attack examples. Isolation Forest randomly partitions the feature space and scores each request by how quickly it is isolated: anomalous requests are isolated in fewer partitions than normal ones. One-Class SVM draws a maximum-margin boundary around the normal class in kernel space and flags requests outside the boundary. The section covers contamination fraction calibration (using held-out attack examples to tune the anomaly threshold), the anomaly-to-labelled-dataset pipeline (routing high- confidence anomaly alerts to an annotation queue that seeds the Section 12.05 supervised classifier), and the fundamental limitation that anomaly detectors acknowledge: they cannot distinguish attack families, produce higher false positive rates than supervised classifiers, and offer no per-feature explanation. They are the correct first detector precisely because these limitations are acceptable when no labelled data exists.
