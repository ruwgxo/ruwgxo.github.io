Section Overview

One Line Summary

OWASP LLM Top 10 is a vulnerability catalogue, not a detection specification — auditing the seven-track gateway against all ten categories reveals four categories with strong coverage, three with partial coverage, and three that are structural gaps requiring output-side monitoring, supply chain controls, or out-of-scope trust calibration that no detection rule can address.

Why This Section Exists

The ATLAS coverage heat map from Section 11.05 measures detection coverage against adversarial ML techniques. But a CISO or compliance team asking "are we covered against the OWASP LLM Top 10?" is working from a different taxonomy — one that security practitioners, procurement teams, and auditors are far more likely to reference than ATLAS technique IDs. This section bridges the gap. It audits the seven-track gateway against each of the ten OWASP LLM vulnerability categories in turn, scores coverage using the same three-tier model from Section 11.05, identifies the specific detection tracks responsible for coverage, names the residual gaps, and maps each gap to the chapter and section that closes it. The output is a single matrix that answers the CISO question precisely and that can be presented alongside the ATLAS heat map without needing to explain the ATLAS taxonomy first. The audit also surfaces three structural properties of the OWASP LLM Top 10 that detection engineers must understand: several categories are training-time or build-time concerns where runtime detection is structurally impossible; one category (LLM09) is a trust miscalibration problem outside the scope of technical detection entirely; and the most common gap in gateway-first architectures — output-side coverage — is confirmed as a gap in the current gateway, pointing to the output validation layer that Chapter 14 builds.

Position In Chapter

Section 11.11 is the compliance-layer coverage audit. It applies the measurement machinery from Sections 11.04 and 11.05 to the OWASP LLM taxonomy rather than the ATLAS taxonomy, producing a complementary coverage view aimed at the business and compliance audience. Sections 11.12 and 11.13 return to the technical detection engineering track.

Prose Content

Part 1 Owasp As Catalogue

Heading

OWASP LLM Top 10 as a Vulnerability Catalogue, Not a Detection Specification

Body

The OWASP LLM Top 10 is a vulnerability catalogue. It lists ten categories of vulnerability that LLM-based applications are susceptible to, with descriptions, attack scenarios, and mitigation guidance. It does not specify detection rules, log fields, thresholds, or monitoring architectures. The catalogue says "prompt injection is a vulnerability in LLM applications" — it does not say "fire a rule when cosine similarity to the known-bad embedding centroid exceeds 0.85." This distinction matters for detection engineers because each OWASP LLM category requires a bespoke detection approach, and some categories have no viable runtime detection approach at all: Runtime-detectable categories: LLM01 (Prompt Injection), LLM04 (Model Denial of Service), LLM07 (Insecure Plugin Design), LLM10 (Model Theft). These produce observable signals in the inference API logs that detection rules can match against. The seven-track gateway has meaningful coverage of all four. Build-time or training-time detectable only: LLM03 (Training Data Poisoning), LLM05 (Supply Chain Vulnerabilities). These vulnerabilities are introduced before the model reaches the inference gateway. By the time a request arrives at the gateway, the poisoning has already happened. Runtime detection can catch some downstream effects of poisoning (model behaving strangely on specific inputs) but cannot detect the poisoning event itself. These categories require build-time controls: dataset auditing, model provenance verification, and reproducible training pipelines. Partial runtime detectability: LLM02 (Insecure Output Handling), LLM06 (Sensitive Information Disclosure), LLM08 (Excessive Agency). Each of these has a runtime- detectable component — the output that contains the vulnerability is observable after inference — but the current gateway is input-side only. The gateway inspects the prompt before inference; it does not inspect the model response after inference. Building an output validation layer (Chapter 14) is the remediation for all three. Out of scope for technical detection: LLM09 (Overreliance). This category is about user trust miscalibration — users treating model outputs as factually reliable without appropriate scepticism. No detection rule can observe user trust. This is a UX, training, and documentation concern, not a detection engineering concern.

Part 2 Llm01

Heading

LLM01 — Prompt Injection: Strong Coverage with Residual L3 Gap

Body

LLM01 Prompt Injection covers both direct injection (adversarial instructions embedded in the user prompt) and indirect injection (adversarial instructions embedded in content retrieved from external sources and passed to the model as context). It is the highest-profile OWASP LLM vulnerability and the one the seven-track gateway addresses most directly. Gateway coverage: strong partial (score 1 moving toward 2 with Chapter 12). Tracks covering LLM01: Track 1 (injection and jailbreak keywords at L1, the centroid-similarity gate at L2, the injection and semantic jailbreak classifiers at L3), Track 2 (perplexity, L2, catches optimised adversarial suffixes), Track 3 (shot count, L1, catches many-shot jailbreaks), and Tracks 4 and 5 (per-session trajectory and coherence scoring, L4, catch multi-turn erosion and payload splitting). Direct injection coverage: strong. Track 1's keyword rule blocks known-prefix direct injection; its centroid gate catches semantically similar variants that evade the keywords; its classifiers catch role-switch jailbreaks that are a form of direct injection. Residual gap: highly obfuscated direct injection (encoded, fragmented, or novel framing) that falls outside the classifiers' training data evades all of these. Chapter 12 intent classifier closes this gap. Indirect injection coverage: weak. Indirect injection arrives via retrieved context (RAG pipeline outputs, tool call results, web content injected into the system prompt). The gateway operates on the prompt as it arrives from the application; it does not have visibility into which parts of the prompt were retrieved from external sources versus authored by the user. Distinguishing user-authored prompt content from retrieved content requires the application to tag retrieved spans in the prompt metadata — a field the gateway can then inspect separately. Without that tagging, indirect injection is detectable only if the injected instruction matches Track 1's keyword or centroid patterns, which is not reliable against a targeted adversary who has crafted the injected content to evade detection. Indirect injection is the most significant residual gap in LLM01 coverage and is not fully closed by any Chapter 12 or 13 deliverable — it requires application- level architectural changes (source tagging in prompt metadata) that are beyond the detection framework scope.

Part 3 Llm02 Llm06

Heading

LLM02 and LLM06 — The Output-Side Gap

Body

LLM02 Insecure Output Handling covers vulnerabilities arising from downstream processing of model outputs without sanitisation: XSS via unsanitised LLM output in web contexts, code injection via model-generated code executed without sandbox, command injection via model-generated shell commands passed to an OS interface, and SQL injection via model-generated queries passed to a database. LLM06 Sensitive Information Disclosure covers the model inadvertently reproducing training data or confidential context: PII from training data appearing in model responses, confidential system prompt content reflected in user-facing output, and membership inference-style disclosure where model response patterns reveal whether specific data was in the training set. Both categories share the same structural gap: the seven-track gateway is input-side only. It inspects the prompt before inference and makes a block/flag/pass decision. After inference, the model response flows directly to the application with no gateway inspection. The gateway never sees the output. For LLM02: a model that generates a response containing a JavaScript payload does not produce any detectable signal at the prompt level. The adversary''s injection that caused the unsafe output generation may have been subtle enough to evade input- side detection; the output itself is the evidence that detection failed. For LLM06: a model that reproduces PII from its training data or reflects system prompt content does not produce any detectable signal at the prompt level either — the disclosure is in the response, not the request. The remediation for both is an output validation layer: a post-inference inspection stage that runs Sigma rules and Python detectors against the model response before returning it to the application. Chapter 14 builds this output validation layer. It includes a PII scanner (regex plus NER-based), a code injection pattern matcher, a system prompt reflection detector, and a response entropy monitor. Until Chapter 14 is integrated, LLM02 and LLM06 remain at score 0 for the gateway — honest, documented, and addressed in the roadmap.

Part 4 Llm03 Llm05

Heading

LLM03 and LLM05 — Training-Time and Supply Chain Gaps

Body

LLM03 Training Data Poisoning covers the corruption of training or fine-tuning data to induce model misbehaviour: backdoor insertion via trigger-label manipulation, targeted capability degradation by poisoning specific output classes, and broad model corruption via large-scale label noise injection. LLM05 Supply Chain Vulnerabilities covers compromises in the model development and deployment pipeline: compromised pre-trained base models from public model hubs, poisoned training datasets from public data repositories, vulnerable ML framework dependencies (compromised libraries), and hardware-level compromises in model training infrastructure. Both categories are training-time or build-time concerns. By the time a model reaches the inference gateway, a supply chain compromise has already occurred. The gateway cannot inspect model weights, training history, or provenance metadata from the inference API — it sees only the prompt and the response. LLM03 runtime coverage: the Chapter 8 poisoning monitor (upstream of the gateway, not one of its seven tracks) provides L1 coverage of the training data ingestion process — anomalous label distributions in training API calls. But this detection covers the training pipeline, not the inference gateway. The model in production at inference time may already be poisoned; the poisoning monitor cannot detect that fact from inference traffic alone. The score for LLM03 at the inference gateway is 0 for the poisoned-model-in-production scenario, with a partial score only for the training-pipeline monitoring component. LLM05 runtime coverage: none. Supply chain verification — checking model file hashes against known-good registries, verifying that model weights match the expected provenance, validating ML framework dependency integrity — is a build-time and deployment-time control. No inference-time Sigma rule can detect a compromised pre-trained model by observing query-response pairs alone (without a baseline of expected behaviour for every possible input, which is not tractable). The remediation for LLM03 is build-time: dataset auditing, reproducible training pipelines with audit logs, and differential privacy training to limit the influence of any single training example. The remediation for LLM05 is supply chain security: model hash verification at deployment, software composition analysis for ML dependencies, and model provenance metadata enforced by the deployment pipeline. Chapter 8 covers these controls; they are not detection rules but preventive controls.

Part 5 Llm04 Llm07 Llm08 Llm10

Heading

LLM04, LLM07, LLM08, LLM10 — Partial and Specific Coverage

Body

LLM04 Model Denial of Service covers resource exhaustion attacks against LLM inference: excessively long prompts consuming token budget, recursive self-referential prompts causing model overthinking, and high-volume API abuse flooding the inference infrastructure. Gateway coverage: partial (score 1). Track 6 rate detection catches high-volume API abuse from a single session. Token budget monitoring is partially implemented via the token_count field. Residual gap: coordinated low-and-slow DoS from many users below the per-user rate threshold — a distributed denial pattern that Track 6''s per-user rate limiter cannot see. LLM07 Insecure Plugin Design covers vulnerabilities arising when LLM applications call external tools, APIs, or plugins with adversarially influenced parameters: prompt injection via tool output (indirect injection where the tool result contains adversarial instructions), over-privileged tool permissions, and insufficient validation of tool input/output. Gateway coverage: partial (score 1). Track 1 (and Track 3, which runs on the assembled context) catches injection patterns in prompt context including tool outputs, if the tool output is included in the prompt text that the gateway inspects. Residual gap: tool outputs that are processed by the application directly without passing through the gateway prompt — common in agentic architectures where the application routes tool outputs to model context without re-inspection. LLM08 Excessive Agency covers LLM-based agents that take autonomous actions beyond their intended scope: executing system commands, modifying files, calling APIs, or making financial transactions based on model outputs without sufficient authorisation. Gateway coverage: none (score 0). Excessive agency is an output-side and action-side concern. The gateway inspects the prompt; it does not inspect what downstream systems do with model outputs. No input-side detection rule can observe excessive agency — it requires monitoring of the actions the model causes, not the prompts that prompt it. Chapter 14 previews a scope monitor that tracks tool call permissions against a defined scope policy; until then, LLM08 is an acknowledged gap. LLM10 Model Theft covers extraction of model weights, functionality, or proprietary training data through systematic API querying: black-box model extraction (Track 6), knowledge distillation attacks, and membership inference. Gateway coverage: good (score 1, approaching 2). Track 6 covers systematic API-based extraction via query rate and variance monitoring, and the Section 9.12 output watermark supports post-hoc ownership claims against a distilled surrogate. The gap is distributed extraction across unlinked accounts (Chapter 13 remediation) and membership inference patterns (future track). LLM10 is the best-covered OWASP LLM category in the gateway after LLM01.

Part 6 Llm09

Heading

LLM09 — Overreliance: Out of Technical Detection Scope

Body

LLM09 Overreliance covers users treating LLM outputs as authoritative facts without appropriate scepticism: accepting hallucinated citations as real, relying on model legal or medical advice without expert review, and trusting model-generated code without security testing. The vulnerability is user behaviour and product design, not a technical attack vector. No detection rule can observe user trust. A Sigma rule cannot fire on "user believed the model output without verification." An FPR metric cannot be computed for a signal that does not exist in any log field. LLM09 is outside the scope of detection engineering entirely. The mitigations for LLM09 are product design controls: disclaimer labels on model outputs, confidence score display in the UI, application-level output validation for high-stakes use cases (medical, legal, financial), and user training on appropriate LLM use patterns. These controls reduce user overreliance without producing any detectable signal in gateway logs. In the coverage matrix, LLM09 receives the same notation as intentional ATLAS gaps: it is not scored 0 (which implies an actionable gap) but is flagged as "out of scope for technical detection — addressed by product design controls." This prevents it from appearing in the detection engineering backlog alongside genuinely actionable gaps.

Part 7 Gap Roadmap

Heading

Gap Closure Roadmap: OWASP LLM Gaps to Chapter Remediations

Body

The OWASP LLM coverage matrix produces six actionable gaps (excluding LLM09 which is out of scope and LLM03/LLM05 which are build-time-only). Ordered by priority: Gap 1: LLM01 indirect injection (score 0 for indirect injection component). Requires application-level source tagging in prompt metadata. Not fully closed by any single chapter deliverable — requires architectural collaboration with the application team. Detection engineering contribution: a Sigma rule for the retrieved_context field once source tagging is implemented (Section 11.10 workflow applies when the field becomes available). Gap 2: LLM02 Insecure Output Handling (score 0). Chapter 14 output validation layer: post-inference Sigma rules for code injection patterns, XSS payload patterns in response text, and command injection patterns in shell-executable response fields. Gap 3: LLM06 Sensitive Information Disclosure (score 0). Chapter 14 output validation layer: PII scanner (regex plus NER), system prompt reflection detector, response entropy monitor for training data reconstruction patterns. Chapter 15 adds membership inference monitoring. Gap 4: LLM08 Excessive Agency (score 0). Chapter 14 scope monitor: tracks tool call permissions against a defined scope policy, fires when a model-caused action exceeds the scope defined in the system prompt or the application policy document. Gap 5: LLM04 distributed DoS (partial, score 1). Chapter 13 cross-user correlation adds fleet-level request volume monitoring that catches low-and-slow distributed denial from many users below the per-user threshold. Gap 6: LLM10 distributed extraction (partial, score 1). Chapter 13 cross-user correlation, same deliverable as Gap 5. LLM07 indirect injection via tool output (partial, score 1): closed when the application-level source tagging from Gap 1 is implemented. No standalone chapter deliverable can close this gap independently.

def score_label(score: int, gap_type: GapType | None) -> str:
    if score == -1:
        return 'N/A (scope)'
    if score == 2:
        return '2 — Full'
    if score == 1:
        if gap_type == GapType.BUILD_TIME_ONLY:
            return '1* — Pipeline'
        return '1 — Partial'
    if score == 0:
        if gap_type == GapType.BUILD_TIME_ONLY:
            return '0* — Build-time'
        return '0 — Gap'
    return '?'

def score_symbol(score: int, gap_type: GapType | None) -> str:
    if score == -1:
        return '◈'
    if score == 2:
        return '✓'
    if score == 1:
        return '◑'
    return '✗'

Common Mistakes

Id

CM11.11.1

Mistake

Treating OWASP LLM score 0 for LLM03 and LLM05 as a detection engineering failure

Why It Happens

The matrix shows two zero-score categories. In a coverage measurement context, score 0 reads as a failure. Programme stakeholders ask why the detection team has not addressed these categories.

Why It Matters

LLM03 (Training Data Poisoning) and LLM05 (Supply Chain Vulnerabilities) are build-time concerns. No runtime detection rule can detect a poisoned model or a compromised ML dependency at inference time. Adding them to the detection backlog generates work that cannot be completed and erodes confidence in the programme''s engineering judgement.

Correct Approach

Distinguish build-time from runtime gaps explicitly in every presentation of the matrix. Use the "0* — Build-time" notation (not a plain "0") and include a one- sentence explanation in the CISO report: "These categories are addressed by build-time controls (dataset auditing, model provenance verification) — not by runtime detection rules." Point to Chapter 8 for the implemented controls.

Id

CM11.11.2

Mistake

Declaring LLM01 fully covered (score 2) after deploying Tracks 1 to 5

Why It Happens

Five tracks covering prompt injection looks comprehensive. Keyword rules, a centroid gate, two classifiers, perplexity, shot counting and multi-turn scoring together seem to address all injection variants.

Why It Matters

Indirect injection — adversarial instructions embedded in tool outputs, RAG retrieved context, or web content injected into the system prompt — is not detected by any of the input-side tracks unless the injected content happens to match Track 1's keyword or centroid patterns. A targeted adversary crafting indirect injection content specifically to evade those patterns will succeed. Declaring LLM01 fully covered misrepresents the coverage posture and delays the application-architecture work needed to close the indirect injection gap.

Correct Approach

Maintain LLM01 at score 1 until both direct injection and indirect injection are covered. Score the direct and indirect components separately in the OWASP notes field if the matrix tooling supports sub-category scoring.

Id

CM11.11.3

Mistake

Assuming that input-side gateway coverage addresses LLM02, LLM06, and LLM08

Why It Happens

The gateway blocks bad prompts. Practitioners assume that blocking the bad input also prevents the bad output. In many cases this is true — if the injection is blocked, the unsafe output is not generated. But it is not universally true.

Why It Matters

Sophisticated injection attacks that evade input-side detection will produce unsafe outputs (LLM02) or disclosure outputs (LLM06) that the gateway never sees. Agentic systems may cause excessive agency actions (LLM08) in response to prompts that passed all input-side checks but were subtly adversarial. The output-side gap is the gap that produces the highest-consequence incidents: the attack that passed all gateway checks and then exfiltrated PII or executed arbitrary code.

Correct Approach

Treat the output-side gap as a first-class programme priority. The three score-0 actionable categories (LLM02, LLM06, LLM08) all require the Chapter 14 output validation layer. Present this to leadership as: "The current gateway protects the model from bad inputs; we do not yet protect downstream systems from bad outputs. Chapter 14 builds that protection."

Id

CM11.11.4

Mistake

Including LLM09 in the detection engineering backlog and assigning resource to close it

Why It Happens

LLM09 appears on the list of ten vulnerabilities. It has a score in the matrix. Programme managers who are not deeply familiar with the categories include it in the detection backlog and ask for a detection engineering sprint to address it.

Why It Matters

LLM09 (Overreliance) is a user behaviour and product design concern. No detection rule can observe user trust. Assigning detection engineering resource to LLM09 diverts effort from the three actionable score-0 categories (LLM02, LLM06, LLM08) that have viable detection approaches and produce measurable coverage improvements.

Correct Approach

In every presentation of the OWASP matrix, explicitly label LLM09 as "Out of scope for technical detection — addressed by product design team." Route LLM09 to the product engineering backlog, not the detection engineering backlog. The owasp_llm_coverage_matrix.py --ciso-report output includes this routing explicitly.

CM11.11.5

Mistake

Reporting OWASP LLM coverage without the ATLAS coverage heat map in the same report

Why It Happens

OWASP LLM Top 10 is more accessible to non-technical stakeholders than ATLAS technique IDs. Programmes may default to OWASP-only reporting for the CISO audience and ATLAS-only reporting for the detection team, creating two separate coverage pictures that are never reconciled.

Why It Matters

The OWASP matrix and the ATLAS heat map are complementary, not alternative, coverage views. A programme with full OWASP LLM01 coverage may still have ATLAS gaps in specific injection sub-techniques. A programme with ATLAS AML.T0051 coverage at score 2 may still score LLM01 at score 1 because indirect injection is not addressed. Reporting only one view gives an incomplete picture regardless of the audience.

Correct Approach

Present both views in the quarterly programme review: the ATLAS heat map for the detection team and the OWASP matrix for the CISO and compliance audience. Show the crosswalk table (table_3_owasp_atlas_crosswalk) to any stakeholder who asks how the two taxonomies relate. The owasp_llm_coverage_matrix.py --ciso-report output is designed to accompany the Navigator heat map, not replace it.

Section Summary

What You Learned

OWASP LLM Top 10 is a vulnerability catalogue that requires a bespoke detection approach per category and contains three structural non-detection categories: build-time-only (LLM03, LLM05), output-side-only (LLM02, LLM06, LLM08), and out-of-scope (LLM09). The seven-track gateway achieves score 1 on four categories (LLM01, LLM04, LLM07, LLM10), score 0 on three actionable categories (LLM02, LLM06, LLM08), build-time-only status for two categories (LLM03, LLM05), and out-of-scope status for one (LLM09). The most significant programme gap is the output-side: the gateway is input-side only and Chapter 14 is the remediation for all three output-side score-0 categories simultaneously. The OWASP matrix and the ATLAS heat map are complementary views; both are required for a complete coverage picture.

Key Terms

Term

OWASP LLM Top 10

Definition

A vulnerability catalogue of the ten most significant security risks in LLM-based applications. Not a detection specification: each category requires bespoke detection approaches; some are not detectable at runtime at all.

Term

Build-time-only gap

Definition

An OWASP or ATLAS coverage gap where the vulnerability is introduced before inference and cannot be detected by runtime rules. Addressed by build-time controls (dataset auditing, model provenance verification, supply chain security). Distinct from actionable gaps where runtime detection is viable but not yet built.

Term

Output-side gap

Definition

An OWASP coverage gap where the detectable signal is in the model response, not the request. The seven-track gateway is input-side only; output-side gaps require a post-inference output validation layer (Chapter 14).

Term

Indirect injection

Definition

A form of LLM01 prompt injection where adversarial instructions are embedded in content retrieved from external sources (RAG outputs, tool call results, web content) and injected into the model context. Not detectable by input-side rules unless application-level source tagging identifies retrieved spans in the prompt.

Term

OWASP-ATLAS crosswalk

Definition

A mapping between OWASP LLM Top 10 categories and MITRE ATLAS technique IDs. Enables detection rules tagged with owasp.llm.NN to also carry the correct atlas.aml.tXXXX tag, ensuring both coverage matrices read the same rule set.
