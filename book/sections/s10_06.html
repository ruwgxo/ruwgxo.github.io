Black-Box Adversarial Attacks: Boundary Attack and Natural Evolution Strategies

Section Overview

One Line Summary

Boundary Attack walks from a misclassified image toward the natural input using only hard-label oracle calls; NES estimates gradient direction from antithetic query pairs under soft-label conditions -- both operate in the same API space Chapter 9 established for extraction.

Why This Section Exists

White-box attacks (Sections 10.3-10.5) require gradient access that most production APIs do not expose. The realistic adversary against a commercial classifier or LLM safety filter has only what the API returns: a class label, a confidence score, or a binary pass/fail. Section 10.6 establishes the two attack families that work under these conditions: decision-based attacks (Boundary Attack, hard-label only) and score-based attacks (NES, probabilities required). Both connect directly to Chapter 9: the API access conditions that enabled Chapter 9 extraction campaigns also enable Chapter 10 black-box adversarial evasion. The query monitor Track 6 built for extraction partially detects black-box adversarial probing for the same reason.

Position In Chapter

Section 10.6 opens the black-box attack tier of the Chapter 10 taxonomy. It establishes the query budget baselines that Section 10.7 (transfer attacks) reduces to near-zero, and the detection signal overlap with Track 6 that Section 10.13 must account for in the gateway architecture.

Prose Content

Part 1

Title

The Black-Box Threat Model: Same API, Different Goal

Body

Chapters 9 and 10 share an attack surface. Chapter 9 described the adversary who sends thousands of queries to a model API to reconstruct decision boundaries or train a surrogate. Section 10.6 describes an adversary who sends thousands of queries to that same API to produce a single adversarial example -- one perturbed input that the model misclassifies. The API configuration is identical; the adversary goal is different. This shared surface has two implications. First, the same Chapter 9 query monitor (Track 6) that flags extraction campaigns produces partial detection signals for black-box adversarial probing. Both activities concentrate queries near the decision boundary -- extraction to map it, black-box adversarial attacks to cross it. Second, an adversary who already completed a Chapter 9 extraction campaign does not need the black-box attacks in this section: they have a surrogate model for white-box access and can use transfer attacks (Section 10.7) at near-zero additional victim query cost. Black-box attacks are for adversaries who have not extracted the model -- their query budget is their only leverage. Production API configurations determine which attack family is applicable. Hard-label APIs return only the top-1 predicted class: the adversary has a binary oracle (is the input classified as the target class or not?). Soft-label APIs return class probabilities: the adversary has a scalar score for each class. Decision-based attacks (Boundary Attack) require only hard-label access. Score-based attacks (NES) require soft-label access and are more query-efficient because each query carries more information (a probability distribution rather than a single class index).

Part 2

Title

Two Black-Box Families: Score-Based and Decision-Based

Body

The binary between score-based and decision-based attacks maps precisely to what information the API exposes per query. Score-based (soft-label) attacks receive class probabilities or logit values from the model. This includes the confidence score of the correct class, the relative ordering of all classes, and the margin between the top class and the second class. NES (this section), Square Attack, and SPSA all fall in this category. The scalar loss signal per query enables efficient gradient estimation: two queries at (x + sigma*u) and (x - sigma*u) produce a scalar estimate of the gradient projection in the direction u. Score-based attacks are more query-efficient than decision-based attacks because they extract a continuous signal rather than a binary one. Decision-based (hard-label) attacks receive only the top-1 class prediction. This is the strictest API condition and the most common in production deployments: many commercial classifiers return only the classification result, not the underlying confidence. The Boundary Attack and HopSkipJump fall in this category. With only a binary oracle (adversarial or not), the adversary must sample the boundary rather than follow a gradient direction. This requires more queries but works against a wider range of deployments. The two families have different detection signatures. Score-based attacks produce uniform query distributions -- each query is drawn from approximately the same distribution (inputs near x with small sigma-scaled perturbations). Decision-based attacks produce query patterns that spiral toward the natural image from an initially very different starting point -- the queries are not concentrated near x initially but converge toward it over time.

Part 3

Title

Boundary Attack: Starting from the Wrong Side of the Decision Boundary

Body

The Boundary Attack (Brendel, Rauber, Bethge 2018) is built on a non-obvious insight: instead of asking "how do I push x to the wrong side of the decision boundary?", ask "how do I start from the wrong side of the boundary and walk toward x while staying adversarial?" Every classification model has a decision boundary that separates the space of inputs that produce one class from inputs that produce another. An adversarial example is any point on the adversary''s side of that boundary that is close to the natural input x. The Boundary Attack finds such a point by: (1) initialising from a point that is already adversarial (typically a sample from a different class or a random noise image that the model misclassifies), and (2) iteratively walking toward x along the decision boundary, reducing the L2 distance from x while maintaining the adversarial classification. This reframing has a critical property: it requires no gradient access. The walk along the boundary is a random walk guided entirely by the binary oracle response -- is the current point adversarial or not? Each step of the walk either proposes a move closer to x (radial step) or a move along the boundary (orthogonal step) and checks whether the resulting point is still adversarial. No probability score, no gradient, no model internals are needed. This makes the Boundary Attack applicable to any system where the adversary can observe the final classification decision -- including physical systems accessed via camera or sensor rather than API.

Part 4

Title

Boundary Attack Algorithm: Orthogonal Step and Radial Step

Body

Each iteration of the Boundary Attack performs two operations. The notation uses x_orig for the original natural image, x_adv for the current adversarial point on the boundary, and delta = x_adv - x_orig for the perturbation vector. The orthogonal step proposes a perturbation in a direction perpendicular to delta. Sample a random noise vector u, project out the component along delta to get u_perp = u - (u·delta / ||delta||²)·delta, normalise u_perp to unit length, and propose x_test = x_adv + step_size * ||delta|| * u_perp. If x_test is adversarial (oracle returns adversarial), accept it. Otherwise discard and try a smaller orthogonal step. The orthogonal step explores the boundary surface without changing the L2 distance to x_orig. The radial step proposes a move toward x_orig. Propose x_radial = x_adv + radial_size * (x_orig - x_adv) = lerp(x_adv, x_orig, radial_size). If x_radial is adversarial, accept it -- the adversarial example is now closer to the natural image. If not, discard -- the step would cross the boundary into correctly-classified space. The radial step reduces L2 distance when it succeeds. The convergence metric is the L2 distance ||x_adv - x_orig||_2 over iterations. A well- tuned Boundary Attack shows a monotonically decreasing L2 curve, reaching a plateau where further reduction is not achievable at the current oracle query rate. Typical configurations run 1,000 to 25,000 oracle calls per adversarial example. The step sizes (orthogonal and radial) are typically set as fractions of the current L2 distance, producing adaptive refinement as the example approaches the boundary more tightly.

Part 5

Title

NES: Gradient Direction Estimation from Antithetic Query Pairs

Body

Natural Evolution Strategies adapts an evolutionary algorithm framework to the problem of gradient estimation from oracle queries. The core idea is: query the model at pairs of points symmetric around x, and estimate the gradient direction from the score difference. For a score function f (e.g., the logit of the best wrong class minus the logit of the correct class), the NES gradient estimate uses antithetic sampling. Sample k random directions u_1, ..., u_k uniformly on the unit sphere. For each direction u_i, query the model at x + sigma*u_i and x - sigma*u_i (the antithetic pair), obtaining scores f(x + sigma*u_i) and f(x - sigma*u_i). The gradient estimate is: g_hat = (1/k) * sum_i [(f(x + sigma*u_i) - f(x - sigma*u_i)) / (2*sigma)] * u_i. This is a finite-difference approximation of the gradient projected onto the randomly sampled directions. The antithetic pairing is critical for efficiency: a single pair (x + sigma*u, x - sigma*u) provides an unbiased estimate of the gradient projection in direction u using 2 queries. Independent sampling (x + sigma*u and x + sigma*v for independent u, v) would require 2k queries for the same variance-reduction as k antithetic pairs, doubling the query budget. Once the gradient estimate g_hat is available, NES takes a step using the same gradient-sign primitive as FGSM: x_{t+1} = clip(x_t + alpha * sign(g_hat), 0, 1) for L-infinity attacks, or x_{t+1} = clip(x_t + alpha * g_hat / ||g_hat||, 0, 1) for L2 attacks. The NES attack is therefore "FGSM with estimated gradient" applied iteratively, placing it conceptually between FGSM (one exact gradient step) and PGD (k exact gradient steps) in terms of attack structure. The query cost per step is 2k queries; with 40 optimisation steps and k=25 directions, the total query budget is 2000 queries per adversarial example.

Part 6

Title

Query Budget Analysis and the Practical Threat Model

Body

The query budget frames the economic reality of black-box adversarial attacks. Each query costs money (API billing), time (rate limits), or detectability risk (query pattern anomaly). The adversary must decide whether their attack goal is worth the query budget required. For the Boundary Attack, the convergence curve shows L2 distance decreasing rapidly in the first few hundred queries and plateauing around 1,000-10,000 queries. Reaching a tight L2 norm (comparable to FGSM at epsilon=8/255) requires 10,000-100,000 queries. At commercial API pricing (roughly $0.001-0.01 per query for a standard vision classifier), this is $10-1,000 per adversarial example -- affordable for a motivated adversary targeting a high-value system, but too expensive for mass evasion of commodity classifiers. NES is more query-efficient at matched perturbation quality. With 2k=50 queries per gradient step and 40 steps, NES requires approximately 2,000 queries per adversarial example for L2 perturbation sizes comparable to FGSM at epsilon=8/255 on standard classifiers. At 40 steps with 50 queries each, NES is 200x more expensive than FGSM (1 query) and 50x more expensive than PGD-40 (40 queries). The query efficiency advantage of NES over Boundary Attack comes at the cost of requiring soft-label API access. The practical threat model for production defenders: a motivated adversary targeting a specific system (malware evasion, fraud bypass, content moderation evasion) will pay the query budget for one or a small number of high-value adversarial examples. An adversary attempting to generate adversarial examples at scale (to process thousands of malicious files through a classifier) will find black-box attacks economically infeasible and will prefer white-box access via a surrogate (Chapter 9 extraction then Section 10.7 transfer).

Part 7

Title

Detection Connection: Shared Signal Surface with Track 6

Body

Track 6 (Section 9.11) monitors the query distribution of a user session to detect extraction campaigns. The detection signal is: are queries concentrating near the decision boundary? Are OOD query rates anomalous? Is the entropy of the query distribution low (indicating the adversary is probing a specific region)? Boundary Attack queries produce a distinctive distribution. Early queries are far from x_orig (the attack starts from a misclassified image that may look nothing like the natural image). Later queries converge toward x_orig from a specific direction. The distribution shifts over time from uniformly distributed noise to concentrated near the natural image. A per-session query distribution monitor that tracks centroid drift would detect this convergence pattern. NES queries are easier to detect at the session level: they arrive in pairs (x + sigma*u and x - sigma*u) that are symmetric around a central point. The query centroids are clustered tightly around the current attack point x_t, and the cluster radius is sigma. Multiple NES steps produce a sequence of clusters, each close to the previous one, drifting toward the adversarial region. This structured query pattern is statistically distinguishable from benign query distributions. The gap between Track 6 and Track 7 detection is the single-query case. Track 6 requires a multi-query campaign footprint to fire. An adversary who spent their query budget offline (generating adversarial examples against a distillation surrogate via Chapter 9) and submits only the final adversarial example to the production API leaves no campaign footprint for Track 6. Track 7 must detect that single submission through input preprocessing (squeezer) and prediction stability analysis (consistency check) alone. Section 10.13 wires both tracks together: Track 6 handles the campaign detection and Track 7 handles the final-submission detection.

Boundary Attack Implementation

Filename

boundary_attack.py

Description

Decision-based Boundary Attack with hard-label oracle, adversarial initialisation, orthogonal step to stay near the boundary, and radial step to reduce L2 distance to the natural image

Implementation Notes

Python 3.12, single quotes throughout per book convention. Requires: torch. Import ToyLinear from fgsm_attack.py for demonstration. Hard-label oracle: returns bool per sample (adversarial or not). Batch size 1 internally; wrap for batch processing in production.

Code

# boundary_attack.py
# Section 10.6: Boundary Attack -- Decision-Based Black-Box Adversarial Attack
# 20260523 | AI Security Mastery by Raghav Dinesh
# Single quotes throughout per book convention
# Reference: Brendel, Rauber, Bethge 2018 "Decision-Based Adversarial Attacks"

import torch
import torch.nn as nn
from torch import Tensor
from typing import Optional


def hard_label_oracle(
    model: nn.Module,
    x: Tensor,
    y_true: Tensor,
    targeted: bool = False,
    y_target: Optional[Tensor] = None,
) -> Tensor:
    '''Returns boolean tensor: True where x is adversarial.'''
    with torch.no_grad():
        preds = model(x).argmax(dim=1)
    if targeted:
        return preds == y_target
    return preds != y_true


def find_adversarial_init(
    model: nn.Module,
    x: Tensor,
    y_true: Tensor,
    targeted: bool = False,
    y_target: Optional[Tensor] = None,
    max_tries: int = 100,
) -> Tensor:
    '''
    Find a starting point that is already adversarial.
    Try random images; fall back to inverted input.
    Starting adversarial is a hard requirement for Boundary Attack.
    '''
    for _ in range(max_tries):
        x_init = torch.rand_like(x)
        if hard_label_oracle(model, x_init, y_true, targeted, y_target).all():
            return x_init
    # Fallback: interpolate toward inverted input until adversarial
    x_inv = torch.clamp(1.0 - x, 0.0, 1.0)
    for alpha in [0.99, 0.9, 0.75, 0.5, 0.25]:
        x_cand = alpha * x_inv + (1.0 - alpha) * x
        if hard_label_oracle(model, x_cand, y_true, targeted, y_target).all():
            return x_cand
    return x_inv  # last resort; likely adversarial for most random-weight models


def orthogonal_step(
    x_adv: Tensor,
    x_orig: Tensor,
    step_frac: float,
) -> Tensor:
    '''
    Propose a step orthogonal to the perturbation direction (delta).
    step_frac: step size as fraction of current L2 distance to x_orig.
    '''
    delta = x_adv - x_orig
    l2 = delta.norm(p=2) + 1e-8
    # Sample random direction and orthogonalise w.r.t. delta
    u = torch.randn_like(x_orig)
    u_flat = u.view(-1)
    delta_flat = delta.view(-1)
    # Gram-Schmidt: remove component along delta
    u_perp = u - (u_flat.dot(delta_flat) / (l2 ** 2)) * delta
    u_perp = u_perp / (u_perp.norm() + 1e-8)
    return torch.clamp(x_adv + step_frac * l2 * u_perp, 0.0, 1.0)


def boundary_attack(
    model: nn.Module,
    x_orig: Tensor,
    y_true: Tensor,
    targeted: bool = False,
    y_target: Optional[Tensor] = None,
    n_steps: int = 1000,
    orthogonal_step_frac: float = 0.04,
    radial_step_frac: float = 0.02,
    verbose: bool = False,
) -> Tensor:
    '''
    Boundary Attack (Brendel et al. 2018).
    Starts from adversarial initialisation; walks toward x_orig along decision boundary.
    Each step: orthogonal perturbation (stays adversarial) + radial step (reduces L2).
    Requires only hard-label oracle; no gradients, no probabilities.

    Returns adversarial example with minimum L2 distance to x_orig found.
    '''
    assert x_orig.dim() == 4 and x_orig.size(0) == 1, 'Batch size 1 only for boundary_attack'

    # Initialise from adversarial starting point
    x_adv = find_adversarial_init(model, x_orig, y_true, targeted, y_target)

    query_count = 0
    l2_history = []

    for step in range(n_steps):
        l2_current = (x_adv - x_orig).norm(p=2).item()
        l2_history.append(l2_current)

        # --- Orthogonal step ---
        x_orth = orthogonal_step(x_adv, x_orig, orthogonal_step_frac)
        query_count += 1
        if hard_label_oracle(model, x_orth, y_true, targeted, y_target).all():
            x_adv = x_orth

        # --- Radial step: move toward x_orig ---
        x_radial = x_adv + radial_step_frac * (x_orig - x_adv)
        x_radial = torch.clamp(x_radial, 0.0, 1.0)
        query_count += 1
        if hard_label_oracle(model, x_radial, y_true, targeted, y_target).all():
            x_adv = x_radial

        if verbose and step % 200 == 0:
            l2 = (x_adv - x_orig).norm(p=2).item()
            print(f'  step {step:>5}: L2={l2:.4f}, queries={query_count}')

    return x_adv.detach(), query_count, l2_history

NES Attack Implementation

nes_attack.py

Description

Natural Evolution Strategies score-based black-box attack with antithetic sampling, gradient estimation from query pairs, and FGSM-style step on estimated gradient direction

Implementation Notes

Python 3.12, single quotes throughout per book convention. Requires: torch. Import ToyLinear from fgsm_attack.py for demonstration. Requires soft-label (probability) output from model. Antithetic sampling halves the query budget vs independent sampling at matched variance.

Code

# nes_attack.py
# Section 10.6: NES -- Natural Evolution Strategies Black-Box Attack
# 20260523 | AI Security Mastery by Raghav Dinesh
# Single quotes throughout per book convention

import torch
import torch.nn as nn
from torch import Tensor
from typing import Optional


def untargeted_score(
    model: nn.Module,
    x: Tensor,
    y_true: Tensor,
) -> Tensor:
    '''
    Score for untargeted attack: best_wrong_logit - correct_logit.
    Positive when misclassified; we want to maximise this.
    Requires soft-label output (logits); no argmax.
    '''
    logits = model(x)
    batch = logits.size(0)
    n_classes = logits.size(1)
    correct = logits.gather(1, y_true.view(-1, 1)).squeeze(1)
    mask = torch.ones_like(logits, dtype=torch.bool)
    mask.scatter_(1, y_true.view(-1, 1), False)
    best_other = logits[mask].view(batch, n_classes - 1).max(dim=1).values
    return best_other - correct


def nes_gradient_estimate(
    model: nn.Module,
    x: Tensor,
    y_true: Tensor,
    sigma: float = 0.01,
    n_samples: int = 50,
    targeted: bool = False,
    y_target: Optional[Tensor] = None,
) -> Tensor:
    '''
    NES gradient estimate using antithetic sampling.
    For each of k=n_samples//2 random directions u_i on the unit sphere:
      query model at x + sigma*u_i and x - sigma*u_i (antithetic pair)
      gradient contribution: (score_pos - score_neg) / (2*sigma) * u_i
    Returns average gradient estimate g_hat.
    Total queries: n_samples (= 2 * k antithetic pairs).
    '''
    assert n_samples % 2 == 0, 'n_samples must be even for antithetic pairing'
    batch = x.size(0)
    grad_est = torch.zeros_like(x)
    n_pairs = n_samples // 2

    for _ in range(n_pairs):
        # Sample unit sphere direction
        u = torch.randn_like(x)
        u_flat = u.view(batch, -1)
        u_norm = u_flat.norm(p=2, dim=1, keepdim=True).view(batch, *([1] * (x.dim() - 1)))
        u = u / (u_norm + 1e-8)

        x_pos = torch.clamp(x + sigma * u, 0.0, 1.0)
        x_neg = torch.clamp(x - sigma * u, 0.0, 1.0)

        with torch.no_grad():
            if targeted:
                # For targeted: score = target_logit - best_other (want to maximise)
                def tgt_score(xin):
                    logits = model(xin)
                    n_cls = logits.size(1)
                    tgt = logits.gather(1, y_target.view(-1, 1)).squeeze(1)
                    mask = torch.ones_like(logits, dtype=torch.bool)
                    mask.scatter_(1, y_target.view(-1, 1), False)
                    best_o = logits[mask].view(batch, n_cls - 1).max(dim=1).values
                    return tgt - best_o
                score_pos = tgt_score(x_pos)
                score_neg = tgt_score(x_neg)
            else:
                score_pos = untargeted_score(model, x_pos, y_true)
                score_neg = untargeted_score(model, x_neg, y_true)

        diff = (score_pos - score_neg).view(batch, *([1] * (x.dim() - 1)))
        grad_est = grad_est + diff * u / (2.0 * sigma)

    return grad_est / n_pairs


def nes_attack(
    model: nn.Module,
    x: Tensor,
    y: Tensor,
    targeted: bool = False,
    y_target: Optional[Tensor] = None,
    epsilon: float = 8.0 / 255.0,
    alpha: float = 2.0 / 255.0,
    n_steps: int = 40,
    sigma: float = 0.01,
    n_samples: int = 50,
    clip_min: float = 0.0,
    clip_max: float = 1.0,
) -> tuple:
    '''
    NES attack: FGSM-style step on estimated gradient, iterated n_steps times.
    L-infinity constraint via delta projection from original x.
    Total queries: n_steps * n_samples.

    Returns (x_adv, total_query_count).
    '''
    x = x.detach()
    x_adv = x.clone()
    total_queries = 0

    for step in range(n_steps):
        g_hat = nes_gradient_estimate(
            model, x_adv, y,
            sigma=sigma, n_samples=n_samples,
            targeted=targeted, y_target=y_target,
        )
        total_queries += n_samples

        direction = 1.0 if not targeted else 1.0  # always ascend on score
        # FGSM-style step on estimated gradient sign
        x_step = x_adv + direction * alpha * g_hat.sign()

        # L-inf projection from original x
        delta = torch.clamp(x_step - x, -epsilon, epsilon)
        x_adv = torch.clamp(x + delta, clip_min, clip_max)

    return x_adv.detach(), total_queries

    try:

def analyse_boundary_convergence(model, x, y, n_steps=1000) -> dict:
    '''Run Boundary Attack and record L2 at each step.'''
    x_adv, queries, l2_history = boundary_attack(
        model, x, y, n_steps=n_steps, verbose=False,
    )
    final_l2 = (x_adv - x).norm(p=2).item()
    with torch.no_grad():
        success = (model(x_adv).argmax(1) != y).item()
    return {
        'l2_history': l2_history,
        'final_l2': final_l2,
        'total_queries': queries,
        'success': success,
    }


def analyse_nes_convergence(model, x, y, n_steps=40, n_samples=50,
                            epsilon=8.0/255.0) -> dict:
    '''Run NES and record L2 at each step (approximated from alpha steps).'''
    x_orig = x.clone()
    x_adv = x.clone()
    l2_history = []
    total_queries = 0

    from nes_attack import nes_gradient_estimate, untargeted_score

    for step in range(n_steps):
        g_hat = nes_gradient_estimate(model, x_adv, y, sigma=0.01, n_samples=n_samples)
        total_queries += n_samples
        x_step = x_adv + (2.0 / 255.0) * g_hat.sign()

        x_adv = torch.clamp(x_orig + delta, 0.0, 1.0)
        l2_history.append((x_adv - x_orig).norm(p=2).item())

    with torch.no_grad():
        success = (model(x_adv).argmax(1) != y).all().item()
    return {
        'l2_history': l2_history,
        'final_l2': (x_adv - x_orig).norm(p=2).item(),
        'total_queries': total_queries,
        'success': success,
    }

import torch

import matplotlib.pyplot as plt
from typing import List


def simulate_nes_query_stream(x_orig: torch.Tensor, n_steps: int = 40,
                              n_samples: int = 50, sigma: float = 0.01) -> List[torch.Tensor]:
    '''
    Simulate the NES query stream without running the actual model.
    Returns the sequence of query inputs (centre point + antithetic pairs).
    Useful for analysing query distribution without attack execution.
    '''
    queries = []
    x_t = x_orig.clone()
    for step in range(n_steps):
        for _ in range(n_samples // 2):
            u = torch.randn_like(x_t)
            u = u / (u.view(-1).norm() + 1e-8)
            queries.append(torch.clamp(x_t + sigma * u, 0.0, 1.0))
            queries.append(torch.clamp(x_t - sigma * u, 0.0, 1.0))
        # Simulate small step in a random direction (placeholder for actual gradient step)
        x_t = torch.clamp(x_t + 0.005 * torch.randn_like(x_t), 0.0, 1.0)
    return queries


def simulate_boundary_query_stream(x_orig: torch.Tensor, n_steps: int = 500,
                                   init_scale: float = 1.0) -> List[torch.Tensor]:
    '''
    Simulate Boundary Attack query stream: starts far from x_orig, converges toward it.
    Returns the sequence of query inputs.
    '''
    queries = []
    # Start far from x_orig (uniform random image)
    x_t = torch.rand_like(x_orig) * init_scale
    for step in range(n_steps):
        # Orthogonal query
        delta = x_t - x_orig
        l2 = delta.norm(p=2)
        u = torch.randn_like(x_t)
        u = u / (u.view(-1).norm() + 1e-8)
        queries.append(torch.clamp(x_t + 0.04 * l2 * u, 0.0, 1.0))
        # Radial query (toward x_orig)
        x_t = torch.clamp(x_t + 0.02 * (x_orig - x_t), 0.0, 1.0)
        queries.append(x_t.clone())
    return queries


def compute_query_distribution_stats(queries: List[torch.Tensor],
                                     x_orig: torch.Tensor) -> dict:
    '''Compute statistics of a query stream relative to the natural image.'''
    l2_dists = [
        (q - x_orig).view(-1).norm(p=2).item()
        for q in queries
    ]
    flat_queries = torch.stack([q.view(-1) for q in queries])
    centroid = flat_queries.mean(0)
    centroid_drift = (centroid - x_orig.view(-1)).norm(p=2).item()
    std_of_l2 = float(np.std(l2_dists))
    return {
        'mean_l2': float(np.mean(l2_dists)),
        'min_l2': float(np.min(l2_dists)),
        'max_l2': float(np.max(l2_dists)),
        'std_l2': std_of_l2,
        'centroid_drift': centroid_drift,
        'n_queries': len(queries),
    }


def print_detection_report(stats: dict, attack_name: str) -> None:

    for k, v in stats.items():
        print(f'  {k:<22}: {v:.4f}' if isinstance(v, float) else f'  {k:<22}: {v}')

Common Mistakes

Mistake 1

Description

Initialising Boundary Attack from the original input x_orig (which is correctly classified) rather than from a point that is already adversarial

Why It Happens

The attack is described as "walking toward x_orig" so engineers initialise x_adv = x_orig and try to walk from there. But x_orig is correctly classified -- it is on the correct side of the decision boundary. There is no boundary to walk along from x_orig itself.

Consequence

Every oracle query from x_orig returns "not adversarial". The orthogonal and radial steps are accepted only when they produce a misclassified input by chance. The attack degenerates into random search and almost never converges to an adversarial example. Attack success rate is near-zero; L2 distance barely decreases from the initial value.

Correct Approach

Initialise from a point that is already adversarial: a random noise image, an image from a different class, or an interpolation between x_orig and an inverted image that the model misclassifies. The find_adversarial_init function in boundary_attack.py handles all fallback cases. Always assert that the initialisation oracle returns True before starting the walk.

Mistake 2

Description

Skipping the oracle check after the orthogonal step and accepting every proposed step unconditionally

Why It Happens

The oracle check adds one forward pass per step. Engineers optimising for speed remove the per-step oracle call and accept all proposed steps, expecting the attack to "mostly" stay adversarial.

Consequence

The walk drifts across the decision boundary into correctly-classified territory. Once on the correct side, all subsequent steps are non-adversarial and the walk cannot recover. The returned adversarial example is either the original x_orig (if the walk drifted all the way back) or a correctly-classified intermediate point. Attack success rate drops to near-zero after a small number of steps.

Correct Approach

Always check the oracle after every proposed step (both orthogonal and radial) before accepting. The oracle call is the fundamental operation of the Boundary Attack -- removing it removes the boundary constraint entirely. The boundary_attack.py deliverable enforces this by making hard_label_oracle a required function call in the step loop.

Mistake 3

Description

Using too large sigma in NES gradient estimation, producing a noisy gradient estimate that causes the attack to diverge

Why It Happens

Sigma controls the width of the perturbation used for gradient estimation. A large sigma seems like it would provide more signal per query. Engineers set sigma=0.1 or sigma=0.5 and observe that the attack runs without error but produces poor adversarial examples.

Consequence

At large sigma, the finite-difference approximation (f(x+sigma*u) - f(x-sigma*u)) / (2*sigma) estimates the gradient over a large region of the input space rather than locally at x. For nonlinear classifiers, this produces a badly noisy gradient estimate that points in the wrong direction. The NES steps move away from the adversarial region rather than toward it, and the attack oscillates without converging.

Correct Approach

Start with sigma=0.01 (1% of the normalised input range) for image classifiers. If gradient estimation is still noisy (convergence curve oscillates), reduce to sigma=0.001. If queries are too expensive, increase n_samples (antithetic pairs) before increasing sigma. Monitor the gradient estimate variance: (g_hat * g_hat).mean() should decrease across steps for a well-tuned sigma.

Mistake 4

Description

Using independent sampling instead of antithetic sampling in NES, doubling the query budget for the same gradient estimate quality

Why It Happens

Independent sampling (k forward passes with k random directions) is conceptually simpler than antithetic sampling (k/2 pairs where each pair uses u and -u). Engineers implement the simpler version and do not realise they are spending 2x the query budget for the same variance reduction.

Consequence

The query budget is doubled: 100 independent queries provide the same gradient estimate variance as 50 antithetic pairs. At 2000 total queries for a 40-step attack, independent sampling requires 4000 queries for equivalent quality. In commercial API settings where queries cost money or trigger rate limits, this 2x overhead is operationally significant.

Correct Approach

Always use antithetic sampling: for each random direction u, query at (x + sigma*u) and (x - sigma*u) and compute the score difference. The nes_attack.py deliverable enforces antithetic sampling by iterating over n_samples//2 pairs. Assert n_samples % 2 == 0 at function entry to prevent accidental independent sampling.

Mistake 5

Description

Concluding that Track 6 alone covers black-box adversarial detection because it covers extraction -- missing the single-query submission gap

Why It Happens

Track 6 detects systematic black-box adversarial probing campaigns (boundary convergence, NES symmetric pairs) because these require many queries. Engineers extend this observation and conclude that all black-box adversarial attacks are covered by Track 6.

Consequence

The single-query submission case is uncovered. An adversary who runs black-box probing offline (against a local copy or a distillation surrogate) and submits only the final adversarial example to the production API leaves no campaign footprint for Track 6. Track 6 fires on campaigns; it does not fire on individual adversarial example submissions. Track 7 (feature squeezing, consistency checking) is the only layer that can detect these single submissions. Removing Track 7 because "Track 6 covers black-box attacks" creates a complete blind spot for the single-submission threat.

Correct Approach

Treat Track 6 and Track 7 as complementary, non-overlapping for the single-submission case. Track 6 covers campaign-level detection; Track 7 covers per-input detection. The Section 10.13 gateway wires both tracks in parallel: a campaign triggers Track 6; a single adversarial submission triggers Track 7 (or neither, if the example evades both -- which motivates the three-primitive Track 7 ensemble).

Section Summary

Compact

Black-box adversarial attacks work under the same API conditions as Chapter 9 extraction. Decision-based attacks (Boundary Attack) require only a hard-label oracle and walk from an adversarial initialisation toward the natural image along the decision boundary using orthogonal and radial steps. Score-based attacks (NES) estimate the gradient direction from antithetic query pairs (x + sigma*u and x - sigma*u) and take FGSM-style steps on the estimated gradient. Query budgets are 10,000-100,000 for Boundary Attack and 1,000-10,000 for NES vs 1-200 for white-box attacks. Track 6 partially detects black-box adversarial campaigns because boundary- proximity queries generate the same distribution anomalies as extraction. The gap: a single adversarial example submission has no campaign footprint; Track 7 is the only detection layer for that case.

Key Takeaways

  • Boundary Attack: start adversarial (mandatory); orthogonal step explores boundary; radial step reduces L2 to x_orig; hard-label oracle only
  • NES: antithetic pairs halve query budget vs independent sampling; gradient estimate = (f(x+su) - f(x-su))/(2s) * u averaged over k pairs
  • Query budget asymmetry: white-box (1-200 queries) vs NES (1k-10k) vs Boundary (10k-100k) vs transfer post-extraction (~0 victim queries)
  • Track 6 covers black-box adversarial campaigns (multi-query footprint); Track 7 covers single adversarial example submissions (no footprint)
  • The adversary who completed Chapter 9 extraction does not need black-box attacks -- the transfer attack (Section 10.7) is cheaper at ~0 additional victim queries
