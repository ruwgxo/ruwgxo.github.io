Section Overview

One Line Summary

False positive management is the operational discipline that separates a detection programme that works from one that erodes — per-rule FPR targets, ROC-calibrated thresholds, structured exception management, and entity baselining are the four tools that keep the SOC queue actionable as the rule portfolio scales.

Why This Section Exists

Section 11.08 established that FPR management is currently at L1 for the seven-track gateway: no per-rule targets, no automated alerting, no systematic disposition collection. It also established that L3 FPR management is on the critical path to L3 composite maturity — the minimum bar for production. This section builds the tooling and the operational procedures that move FPR management from L1 to L3. The motivation is not abstract. A gateway with uncalibrated heuristic thresholds in Tracks 1, 2 and 7 will produce false positive rates that are, at best, unknown and, at worst, high enough to trigger the alert fatigue death spiral within weeks of production deployment. Track 1''s centroid-similarity threshold of 0.85 was chosen to work on the Chapter 6 examples; it was not calibrated against production traffic. Track 7''s squeezer threshold of 0.70 was chosen similarly. These are educated starting points, not calibrated operating points. Section 11.09 calibrates them from data.

Position In Chapter

Section 11.09 closes the FPR management debt opened in Section 11.01 and advances the FPR management dimension from L1 to L3. Its output — per-rule FPR targets and the false_positive_manager.py monitoring infrastructure — feeds both the maturity assessor (Section 11.08) and the detection engineering workflow (Section 11.10). The threshold calibration harness also closes the ''thresholds without calibration'' debt item from the Section 11.01 inventory.

Part 1 Fp Sources

Heading

Sources of False Positives in AI Gateway Detection

Body

Every detection rule in the seven-track gateway has a characteristic false positive source. Understanding the source is the prerequisite to suppressing the false positive without reducing true positive coverage. The three primary sources for AI gateway detection rules: Source 1 — Near-boundary legitimate inputs. The most common source. Track 1's centroid-similarity gate (threshold 0.85) fires on legitimate prompts that happen to be semantically close to the known-bad embedding centroid — not because they are adversarial, but because the user''s legitimate vocabulary overlaps with injection terminology. A technical writer asking about system prompt design for their own application uses language that scores 0.82–0.88 on the similarity gate. Track 7 (squeezer disagreement, threshold 0.70) fires on unusual-but-legitimate inputs with high feature entropy: mathematical proofs, mixed-language prompts, and specialised domain notation all produce squeezer scores in the 0.65–0.75 range without being adversarial. These are near-boundary inputs: genuinely unusual, genuinely close to the detection threshold, but not adversarial. Source 2 — Legitimate automation. Track 6 (the query monitor's extraction rate threshold 100 requests per session) fires on production batch inference jobs, automated regression testing pipelines, and integration test suites that use templated low-variance queries at high volume. The query pattern of a legitimate batch job and the query pattern of a model extraction attack are structurally similar: both involve many queries with low diversity. The difference is intent and source — but intent is not directly observable at the gateway. Source 3 — Benign obfuscated prompts. Track 1's injection keyword rule fires on legitimate prompts that contain injection-adjacent vocabulary in a non-adversarial context. A security instructor demonstrating injection attacks uses the exact keywords that Track 1 fires on. A prompt engineering guide that discusses system prompt override patterns for legitimate customisation purposes contains language that Track 1 flags. A code generation prompt that asks the model to write a parser for injection detection rules contains injection keywords. These are benign obfuscated prompts only in the sense that they look adversarial to the rule without being adversarial. Each source requires a different mitigation: near-boundary inputs require threshold calibration; legitimate automation requires exception management; benign obfuscated prompts require contextual refinement (adding context field conditions to the rule) or user-specific exceptions. Applying the wrong mitigation produces either residual false positives or unintentional coverage reduction.

Part 2 Death Spiral

Heading

The Alert Fatigue Death Spiral

Body

Alert fatigue is not a psychological phenomenon. It is a system failure with a predictable sequence. Understanding the sequence identifies the two intervention points where the spiral can be broken. Step 1: High FPR rules produce alert volume that exceeds analyst capacity. A rule with a 15% false positive rate on production traffic generating 10,000 requests per day produces 1,500 false positive alerts per day. If the analyst team has capacity for 200 alert investigations per day, the queue fills in eight hours and the backlog grows permanently. Step 2: Analysts adopt triage heuristics to cope with the backlog. They learn which rules produce mostly noise and stop investigating those alerts carefully. The triage heuristic is not documented; it lives in analyst memory. New analysts do not know the heuristic. Step 3: True positives from high-FPR rules are missed. An actual injection attack fires the same rule that produces 1,500 false positives per day. The alert enters the queue. The analyst reviews the rule ID, recognises it as noisy, and downgrades the investigation priority. The attack proceeds. Step 4: The missed true positive produces a security incident. Post-incident review finds that an alert fired and was not investigated. The conclusion is typically that the rule was too sensitive, producing noise that masked the real signal. The remediation action is to raise the threshold — reducing sensitivity. Step 5: The raised threshold reduces both false positives and true positives. The FPR improves, but coverage also degrades. The technique the rule detects now has a lower score on the coverage heat map — an unrecognised consequence of the post-incident remediation. Step 6: The detection programme has fewer false positives but less coverage. Analysts are less fatigued but the attack surface is larger. The net security outcome is negative. The two intervention points: (1) before Step 1 — calibrate thresholds before production deployment so FPR is within analyst capacity from day one; (2) before Step 2 — track FPR per rule with automated alerting so the detection engineering team knows about high-FPR rules before analysts develop suppression heuristics. Both interventions are built in this section.

Part 3 Roc Calibration

Heading

Threshold Calibration: ROC Curve Analysis and Operating Point Selection

Body

A detection threshold is not a security decision. It is an engineering decision about where on the precision-recall tradeoff curve the deployment operates. Lower threshold means more alerts, higher recall, lower precision. Higher threshold means fewer alerts, lower recall, higher precision. The correct operating point depends on the deployment context: what is the analyst capacity, what is the acceptable false positive rate, and what is the cost of a missed true positive? The ROC (Receiver Operating Characteristic) curve plots True Positive Rate (TPR = TP / (TP + FN)) against False Positive Rate (FPR = FP / (FP + TN)) for all possible threshold values. A perfect detector hugs the top-left corner: TPR of 1.0, FPR of 0.0 at some threshold. A random classifier produces a diagonal line from (0,0) to (1,1). The area under the ROC curve (AUC) is a threshold- independent measure of detector quality: AUC of 1.0 is perfect; 0.5 is random. For the seven-track gateway, the ROC calibration procedure uses the test corpus from Section 11.02 (known-bad and known-good fixtures) augmented with a sample of recent production traffic (anonymised, with analyst-confirmed disposition labels). The threshold_calibration_harness.py deliverable runs this procedure for Track 1's centroid gate, Track 2 and Track 7 — the three heuristic-layer components whose thresholds were set empirically in Part 2. Operating point selection criteria per track: Track 1 keyword rule (injection keyword matching): Not threshold-based; keyword lists have binary match semantics. FPR is controlled by keyword precision, not threshold. Target FPR: 1%. If the current keyword list produces >1% FPR on the known-good corpus, the list needs narrowing or the rule needs context conditions added. Track 1 centroid gate (cosine similarity threshold): Continuous threshold. Target FPR: 5%. The similarity gate is a heuristic that will produce near-boundary FPs on technical users. A 5% FPR produces approximately one false alert per 20 flagged requests — acceptable as a flag (analyst review) but not as a block (immediate rejection). The centroid gate fires as a flag; the keyword rule or the injection classifier is required to block. Track 2 (perplexity detector): Continuous threshold. Target FPR: 0.5%. Track 2 flags inputs for adversarial review. A 0.5% FPR means the analyst sees five false positives per 1,000 flagged requests. The low target reflects that Track 2 flags high-priority suspicious inputs (optimised adversarial suffixes); a higher FPR would dilute the signal at the adversarial review queue. Track 7 (squeezer disagreement + adversarial classifier): Compound threshold. Target FPR: 5% for squeezer alone (L2 component); 2% for the compound condition (squeezer AND classifier). The compound condition''s FPR is substantially lower than the squeezer alone because the classifier filters the near-boundary squeezer FPs — exactly the design intent of the compound rule in Section 11.06. The harness generates the ROC curve, marks the current threshold on the curve, and proposes the threshold value at the target FPR operating point. If the current threshold is already at or better than the target FPR, no change is recommended. If the current threshold produces higher FPR than the target, the harness returns the calibrated threshold with a warning that TPR will decrease and the coverage heat map should be re-run after the calibration is applied.

Part 4 Exception Management

Heading

Exception Management: Suppressing Without Disabling

Body

An exception is a structured exclusion of a known-good traffic source from a detection rule. Exceptions are not defeats — a properly managed exception list reduces FPR without reducing coverage because the excluded traffic source is not the adversary. An automation account that runs 50,000 templated queries per day is not a model extraction attacker; excluding it from Track 6 rate detection does not reduce coverage against the actual extraction threat. Exceptions become defeats when they are unmanaged. Three failure modes: Failure mode 1 — Exception list scope creep. An exception is added for a specific automation account. Six months later, the same exception is applied to the entire IP range of the data centre hosting the automation, because the account IP changed. Another six months later, a threat actor who has compromised a server in that data centre uses that IP range to conduct extraction attacks that the now-over-broad exception suppresses. Unmanaged scope creep turns a precise exception into a blind spot. Failure mode 2 — Exception without review cadence. Exceptions are added but never reviewed. The automation account that required the exception is decommissioned. The exception remains, now covering traffic from whatever process has inherited that account identifier. The exception is no longer protecting a known-good source; it is suppressing an unknown source. Failure mode 3 — Exception as a substitute for calibration. A rule produces many false positives. Instead of calibrating the threshold, the team adds exceptions for every known false positive source. The exception list grows to hundreds of entries. The rule''s effective coverage is now unknown — it detects whatever the exceptions have not suppressed, which is a subset of the original detection surface that no one has mapped. The structured exception management system in false_positive_manager.py enforces three controls: (1) every exception has an owner, an expiry date, and a business justification; (2) exceptions are reviewed quarterly and expired exceptions are automatically removed; (3) the exception list is version-controlled in the rule repository alongside the rule it modifies — an exception change requires a PR with the same review process as a rule change.

Part 5 Baselining

Heading

Baselining: Flagging Deviation Rather Than Absolute Value

Body

Absolute thresholds produce false positives against high-volume legitimate users. A researcher who legitimately queries the model API 500 times per day for their academic work triggers Track 6''s session rate threshold (100 requests) many times per session. The absolute threshold does not distinguish the researcher''s legitimate high-volume usage from an attacker''s extraction campaign with similar volume. Baselining shifts the detection question from "is this value above the absolute threshold?" to "is this value anomalous relative to this entity''s established normal behaviour?" For the researcher who typically makes 500 requests per session, a session with 600 requests is not anomalous. A session with 5,000 requests — ten times their established baseline — is anomalous and warrants investigation. For a user whose baseline is 10 requests per session, a session with 150 requests is fifteen times their baseline and is anomalous. The baseline model operates on three entity types: Per-user baseline: the rolling 30-day mean and standard deviation of each metric (session request count, query entropy, query variance) for each user_id. A metric value more than three standard deviations above the user''s 30-day mean triggers a baseline anomaly flag. The anomaly flag is not a block — it is input to the Track 6 ensemble that combines absolute threshold, baseline anomaly, and per-user accumulator signals with confidence weighting. Per-endpoint baseline: the rolling 7-day mean and standard deviation of aggregate metrics (total request volume, unique user count, flagged request fraction) for each API endpoint. Anomalies at the endpoint level indicate coordinated multi-user activity that per-user baselining cannot detect. Per-hour baseline: the rolling 4-week mean for each metric by hour of day. A request volume at 3am that is three standard deviations above the normal 3am volume is flagged regardless of whether it exceeds the absolute threshold, because 3am is not normal business hours for the user population. Baselining requires at least 14 days of production traffic before it produces reliable baseline models. During the first 14 days of deployment, the system operates on absolute thresholds only, with a warning flag in the alert metadata indicating that baseline models are not yet established. After 14 days, the baseline anomaly score is computed and the detection ensemble weights it alongside the absolute threshold score.

Part 6 Fpr Dashboard

Heading

FPR Dashboard and the False Positive Review Queue

Body

Per-rule FPR tracking requires two components: the collection mechanism (tagging each alert with rule_id and analyst disposition) and the monitoring mechanism (computing per-rule FPR from the collection and alerting when it breaches target). The false_positive_manager.py deliverable implements both. The FPR computation: FPR = confirmed_false_positives / (confirmed_false_positives + confirmed_true_positives) for each rule, computed over a rolling 7-day window. Alerts that have not yet received analyst disposition are excluded from the FPR computation — they are pending, not positive or negative. The 7-day rolling window ensures that a calibration change takes effect in the FPR metric within one week. FPR target breach: when a rule''s 7-day rolling FPR exceeds its documented target by more than 20% relative (e.g. a rule with a 5% FPR target breaches at 6%), the false_positive_manager.py opens a ticket in the detection engineering queue. The ticket includes: rule ID, rule title, current FPR, FPR target, the most recent 10 false positive inputs (anonymised), and the recommended first action from the FPR management playbook (check exception list, re-run threshold calibration, or add context conditions). The false positive review queue operates on an SLA: every confirmed false positive receives analyst disposition within 48 hours of alert generation. The 48-hour SLA ensures that the rolling FPR computation reflects recent production behaviour, not stale alert data. Alerts that exceed 72 hours without disposition generate an automated escalation to the detection engineering lead. Feedback loop: every confirmed false positive is added to the known-good test fixture corpus (Section 11.02) as a regression test case. The rule ID is tagged on the fixture. If a future rule change causes the regression test to fail — meaning the rule would have flagged this previously-confirmed false positive again — the CI pipeline blocks the PR with an explicit regression error. This closes the loop from analyst disposition to rule improvement. The FPR dashboard view (for leadership) shows three metrics per rule: current FPR, FPR target, and 30-day FPR trend (improving, stable, or degrading). Rules with a degrading trend that have not yet breached the target are flagged amber — an early warning signal that allows calibration before the target is breached and before the detection engineering queue is triggered.

#!/usr/bin/env python3
'''false_positive_manager.py
Per-rule FPR tracker: rolling 7-day FPR per rule, target enforcement,
DaC queue integration, and exception list management.
Chapter 11, Section 11.09 — AI Security Mastery
Author: Raghav Dinesh | github: ruwgxo

Usage:
  python3 false_positive_manager.py --report
  python3 false_positive_manager.py --add-disposition <rule_id> <alert_id> tp|fp
  python3 false_positive_manager.py --add-exception <rule_id> <source_type> <value>
  python3 false_positive_manager.py --review-exceptions
'''

from __future__ import annotations
import argparse
import json
import pathlib
import sys
import uuid
from dataclasses import dataclass, field
from datetime import date, datetime, timedelta, timezone
from typing import Literal

# ---------------------------------------------------------------------------
# Configuration
# ---------------------------------------------------------------------------

DATA_DIR = pathlib.Path('fpm_data')
DISPOSITIONS_FILE = DATA_DIR / 'dispositions.json'
EXCEPTIONS_FILE = DATA_DIR / 'exceptions.json'
FPR_BREACH_RELATIVE_MARGIN = 0.20   # 20% relative above target triggers DaC queue

# Per-rule FPR targets (track → target)
FPR_TARGETS: dict[str, float] = {
    'track_1_injection_keyword':       0.01,
    'track_1_jailbreak_keyword':       0.01,
    'track_1_jailbreak_classifier':    0.05,
    'track_1_centroid_gate':           0.05,
    'track_2_perplexity':              0.005,
    'track_6_extraction_rate':         0.02,
    'track_7_squeezer_only':           0.05,
    'track_7_compound':                0.02,
    'upstream_ch8_poisoning_monitor':  0.005,
}

Disposition = Literal['tp', 'fp', 'pending']

# ---------------------------------------------------------------------------
# Data models
# ---------------------------------------------------------------------------

@dataclass
class AlertDisposition:
    alert_id: str
    rule_id: str
    disposition: Disposition
    analyst: str
    timestamp: str
    input_snippet: str = ''     # anonymised first 80 chars of the triggering input

@dataclass
class ExceptionEntry:
    exception_id: str
    rule_id: str
    source_type: str            # user_id | ip_range | account_pattern | session_tag
    source_value: str
    owner: str
    justification: str
    created_date: str
    expiry_date: str
    reviewed_date: str = ''

@dataclass
class FPRReport:
    rule_id: str
    window_days: int
    tp_count: int
    fp_count: int
    pending_count: int
    fpr: float
    fpr_target: float
    breach: bool
    trend: str                  # 'improving' | 'stable' | 'degrading' | 'insufficient_data'

# ---------------------------------------------------------------------------
# Storage helpers
# ---------------------------------------------------------------------------

def _load_json(path: pathlib.Path) -> list:
    if not path.exists():
        return []
    with open(path) as f:
        return json.load(f)

def _save_json(path: pathlib.Path, data: list) -> None:
    DATA_DIR.mkdir(parents=True, exist_ok=True)
    with open(path, 'w') as f:
        json.dump(data, f, indent=2)

# ---------------------------------------------------------------------------
# Disposition management
# ---------------------------------------------------------------------------

def add_disposition(
    rule_id: str,
    alert_id: str,
    disposition: Disposition,
    analyst: str = 'analyst',
    input_snippet: str = '',
) -> AlertDisposition:
    dispositions: list[dict] = _load_json(DISPOSITIONS_FILE)
    entry = AlertDisposition(
        alert_id=alert_id,
        rule_id=rule_id,
        disposition=disposition,
        analyst=analyst,
        timestamp=datetime.now(timezone.utc).isoformat(),
        input_snippet=input_snippet[:80],
    )
    dispositions.append(entry.__dict__)
    _save_json(DISPOSITIONS_FILE, dispositions)
    print(f'Disposition recorded: {rule_id} / {alert_id} → {disposition}')
    if disposition == 'fp':
        print(f'  → Add input snippet to tests/fixtures/known_good/ as regression case.')
    return entry

# ---------------------------------------------------------------------------
# FPR computation
# ---------------------------------------------------------------------------

def compute_fpr(rule_id: str, window_days: int = 7) -> FPRReport:
    all_dispositions: list[dict] = _load_json(DISPOSITIONS_FILE)
    cutoff = datetime.now(timezone.utc) - timedelta(days=window_days)

    window = [
        d for d in all_dispositions
        if d['rule_id'] == rule_id
        and datetime.fromisoformat(d['timestamp']) >= cutoff
    ]
    tp = sum(1 for d in window if d['disposition'] == 'tp')
    fp = sum(1 for d in window if d['disposition'] == 'fp')
    pending = sum(1 for d in window if d['disposition'] == 'pending')
    total_decided = tp + fp

    fpr = fp / total_decided if total_decided > 0 else 0.0
    target = FPR_TARGETS.get(rule_id, 0.05)
    breach_threshold = target * (1 + FPR_BREACH_RELATIVE_MARGIN)
    breach = fpr > breach_threshold and total_decided >= 10  # min 10 decisions

    # Trend: compare first half vs second half of window
    mid = datetime.now(timezone.utc) - timedelta(days=window_days // 2)
    first_half = [d for d in window if datetime.fromisoformat(d['timestamp']) < mid]
    second_half = [d for d in window if datetime.fromisoformat(d['timestamp']) >= mid]
    def half_fpr(half: list[dict]) -> float:
        tp_h = sum(1 for d in half if d['disposition'] == 'tp')
        fp_h = sum(1 for d in half if d['disposition'] == 'fp')
        return fp_h / (tp_h + fp_h) if (tp_h + fp_h) > 0 else 0.0
    if total_decided < 10:
        trend = 'insufficient_data'
    elif half_fpr(second_half) < half_fpr(first_half) - 0.01:
        trend = 'improving'
    elif half_fpr(second_half) > half_fpr(first_half) + 0.01:
        trend = 'degrading'
    else:
        trend = 'stable'

    return FPRReport(
        rule_id=rule_id,
        window_days=window_days,
        tp_count=tp,
        fp_count=fp,
        pending_count=pending,
        fpr=fpr,
        fpr_target=target,
        breach=breach,
        trend=trend,
    )

# ---------------------------------------------------------------------------
# DaC queue integration
# ---------------------------------------------------------------------------

def open_dac_queue_ticket(report: FPRReport) -> None:
    '''
    Opens a detection engineering queue ticket for an FPR breach.
    In production: calls the ticketing system API (Jira, Linear, GitHub Issues).
    Here: prints the ticket draft and writes to a local breach log.
    '''
    ticket_id = str(uuid.uuid4())[:8].upper()
    ticket = {
        'ticket_id': f'DET-{ticket_id}',
        'type': 'fpr_breach',

def _fpr_recommendation(report: FPRReport) -> str:
    if report.fpr_target <= 0.01:
        return 'Check keyword list precision; add context NOT conditions; review top-10 FP inputs.'
    elif report.trend == 'degrading':
        return 'Traffic pattern has shifted; re-run threshold_calibration_harness.py on recent sample.'
    elif report.fpr > report.fpr_target * 2:
        return 'Significant breach; consider emergency threshold recalibration and exception list review.'
    else:
        return 'Re-run threshold_calibration_harness.py; review exception list for expired entries.'

@dataclass

    score: float
    label: int          # 1 = known-bad (positive), 0 = known-good (negative)

    threshold: float
    tpr: float
    fpr: float

# ---------------------------------------------------------------------------
# ROC curve computation

def compute_roc(examples: list[ScoredExample]) -> list[ROCPoint]:
    '''Compute ROC curve by sweeping threshold over all unique score values.'''
    thresholds = sorted({e.score for e in examples}, reverse=True)
    n_pos = sum(1 for e in examples if e.label == 1)
    n_neg = sum(1 for e in examples if e.label == 0)
    if n_pos == 0 or n_neg == 0:
        return []

    points: list[ROCPoint] = []
    for thresh in thresholds:
        tp = sum(1 for e in examples if e.score >= thresh and e.label == 1)
        fp = sum(1 for e in examples if e.score >= thresh and e.label == 0)
        points.append(ROCPoint(
            threshold=thresh,
            tpr=tp / n_pos,
            fpr=fp / n_neg,
        ))
    # Add (0,0) baseline point
    points.append(ROCPoint(threshold=float('inf'), tpr=0.0, fpr=0.0))
    points.sort(key=lambda p: p.fpr)
    return points

def compute_auc(roc_points: list[ROCPoint]) -> float:
    '''Trapezoidal AUC.'''
    if len(roc_points) < 2:
        return 0.0
    auc = 0.0
    sorted_pts = sorted(roc_points, key=lambda p: p.fpr)
    for i in range(1, len(sorted_pts)):
        dx = sorted_pts[i].fpr - sorted_pts[i - 1].fpr
        avg_y = (sorted_pts[i].tpr + sorted_pts[i - 1].tpr) / 2
        auc += dx * avg_y
    return auc

def find_operating_point(
    roc_points: list[ROCPoint],
    fpr_target: float,
) -> ROCPoint:
    '''Find the ROC point closest to but not exceeding fpr_target.'''
    candidates = [p for p in roc_points if p.fpr <= fpr_target]
    if not candidates:
        # All points exceed target; return lowest FPR point
        return min(roc_points, key=lambda p: p.fpr)
    # Among candidates at or below target, pick highest TPR
    return max(candidates, key=lambda p: p.tpr)

def find_current_point(
    roc_points: list[ROCPoint],
    current_threshold: float,
) -> ROCPoint:
    '''Find the ROC point corresponding to the current deployed threshold.'''
    if not roc_points:
        return ROCPoint(current_threshold, 0.0, 0.0)
    closest = min(roc_points, key=lambda p: abs(p.threshold - current_threshold))
    return closest

Common Mistakes

Id

CM11.09.1

Mistake

Setting a single FPR target across all rules in the gateway rather than per-rule targets

Why It Happens

A uniform FPR target is simpler to enforce and communicate. Setting different targets for different tracks requires understanding the detection mechanism and analyst impact of each rule individually.

Why It Matters

A uniform 5% FPR target is too permissive for Track 1's keyword rule (which should be at 1%) and too restrictive for Track 1's centroid gate (where 5% is correct). Applying a uniform target miscalibrates both: the keyword rule generates five times as many false positives as necessary, and the centroid gate is calibrated too tightly, reducing true positive coverage to meet a target that was designed for a different detection mechanism.

Correct Approach

Set FPR targets per rule based on the detection mechanism, the alert action (block vs flag), and the analyst queue capacity. Block rules (Track 1 keywords) warrant lower FPR targets than flag rules (Track 1 centroid gate). High-priority analyst queues (Track 2 adversarial review) warrant lower FPR targets than general SOC queues.

Id

CM11.09.2

Mistake

Treating an exception list as a permanent suppression mechanism rather than a time-bounded operational control

Why It Happens

Exceptions solve an immediate problem. Once the false positive is suppressed, the problem feels resolved and there is no pressure to revisit the exception.

Why It Matters

Without expiry dates and quarterly review, exception lists grow monotonically. Over 12–18 months, a well-intentioned exception list for known automation accounts can expand to cover entire IP ranges, entire departments, and eventually entire user populations — each expansion individually justified, collectively creating large blind spots.

Correct Approach

Every exception has a maximum 90-day lifetime enforced by false_positive_manager.py. Renewal requires owner re-confirmation and updated justification. Expired exceptions are removed automatically. The exception list is version-controlled; removing an exception is a PR with the same review requirement as adding one.

Id

CM11.09.3

Mistake

Calibrating thresholds using the same corpus that was used to build the detection rule

Why It Happens

The rule development corpus is available and labelled. Using it for calibration saves the effort of collecting a separate production traffic sample.

Why It Matters

A threshold calibrated on the development corpus is optimistic. The development corpus is not representative of production traffic: it over-samples adversarial inputs (to ensure rule development), under-samples the full range of legitimate inputs, and may not reflect recent changes in user behaviour or prompt patterns. A threshold at 5% FPR on the development corpus may produce 20% FPR on production.

Correct Approach

Calibrate on a recent production traffic sample with analyst-confirmed labels. The sample must cover at least 14 days to capture weekly traffic patterns. If production traffic has not yet been collected, run the threshold at a conservative (high) setting initially and calibrate downward as labelled production data accumulates.

Id

CM11.09.4

Mistake

Applying threshold calibration without re-running the ATT&CK coverage heat map

Why It Happens

Calibration is perceived as a tuning operation, not a coverage operation. The mental model is: "I am improving the FPR without changing what the rule detects."

Why It Matters

Raising a threshold to reduce FPR also reduces TPR. If the TPR reduction is large enough, the technique that was at score 1 (partial coverage) moves closer to score 0 (no effective coverage for the attack variant near the new threshold). The coverage heat map does not automatically detect this unless it is re-run after the calibration.

Correct Approach

Run attck_coverage_heatmap.py --diff immediately after any threshold calibration is applied to staging. If any technique score regresses in the diff output, the calibration must be reviewed: either the threshold change is too aggressive, or the coverage gap it creates is accepted and documented in the technique''s residual_gap field.

Id

CM11.09.5

Mistake

Tracking FPR as a 30-day rolling average, masking recent breach events

Why It Happens

Longer averaging windows produce smoother metrics and fewer false alarms on the FPR monitoring system itself. A 30-day window feels more stable.

Why It Matters

A rule calibration applied on day 28 that causes a significant FPR spike will contribute only 3/30 of the rolling window. The 30-day average stays below the breach threshold even as the actual current FPR is many times the target. The breach goes undetected until the spiked data dominates the rolling window.

Correct Approach

Use a 7-day rolling window for FPR computation as implemented in false_positive_manager.py. A 7-day window is responsive enough to detect calibration-induced FPR spikes within one week while smoothing over normal day-to-day traffic variance. If desired, compute both 7-day (operational alert) and 30-day (trend reporting) windows simultaneously, and breach-alert on the 7-day metric only.

Section Summary

What You Learned

False positive management is the operational discipline that prevents detection programmes from eroding through alert fatigue. The seven-track gateway has three primary FP sources — near-boundary legitimate inputs, legitimate automation, and benign obfuscated prompts — each requiring a different mitigation. The alert fatigue death spiral has two intervention points: pre-deployment threshold calibration and real-time per-rule FPR monitoring. ROC curve analysis selects operating points at target FPR levels; per-rule targets range from 0.5% (Track 2) to 5% (Track 1's centroid gate and Track 7's squeezer alone). Exception management requires expiry dates, quarterly review, and version control. Baselining shifts detection from absolute to entity-relative thresholds, reducing FPR for high-volume legitimate users. The FPR management dimension advances from L1 to L3 after deploying false_positive_manager.py with target enforcement and DaC queue integration.

Key Terms

Term

Alert fatigue death spiral

Definition

The self-reinforcing failure sequence in which high FPR leads analysts to dismiss alerts, causing missed true positives, causing incidents, causing threshold increases, causing coverage reduction. Broken by pre-deployment calibration and real-time per-rule FPR monitoring.

Term

ROC curve

Definition

A plot of True Positive Rate against False Positive Rate across all threshold values. The operating point is selected where FPR meets the per-rule target. AUC (area under the ROC curve) is a threshold-independent quality measure.

Term

Exception

Definition

A time-bounded, owner-attributed suppression of detection alerts for a specific known-good traffic source. Maximum 90-day lifetime; auto-expired; version-controlled. Not a substitute for threshold calibration.

Term

Baselining

Definition

A per-entity (user, endpoint, hour) normal behaviour model. Detection fires when a metric deviates more than 3 standard deviations from the entity''s rolling mean, rather than when it exceeds an absolute threshold. Reduces FPR for high-volume legitimate users.

Term

FPR target breach

Definition

The condition in which a rule''s 7-day rolling FPR exceeds its documented target by more than 20% relative. Triggers a DaC queue ticket with the rule ID, current FPR, FPR target, and recommended first action.
