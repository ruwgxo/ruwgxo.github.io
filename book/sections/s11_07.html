Sigma Rules: Advanced Patterns, Correlation, and Campaign Detection

By the end of this section
  • Write time-windowed aggregation conditions using count, min, max, avg, and sum, specifying window duration and group-by field
  • Author a Sigma correlation rule that joins alerts from two or more gateway tracks into a campaign-level detection
  • Construct a sequence rule for the probe → inject → exfiltrate pattern within a defined session window
  • Implement allowlist exception management in a Sigma rule using filter selections and not conditions
  • Map the Sigma rule lifecycle stages (draft → review → testing → production → deprecated) to CI pipeline behaviours
  • Produce a cross-reference of all seven-track gateway Sigma rules as a unified portfolio inventory

Section Overview

One Line Summary

Single-event Sigma rules detect individual signals; correlation rules converge those signals into campaign-level detections that no single track can produce alone — a Track 1 injection followed by Track 6 query acceleration within ten minutes is a confirmed extraction attempt, invisible to either track working independently.

Why This Section Exists

Section 11.06 built fluency in single-event Sigma rules: one log event, one detection condition, one alert. The seven-track gateway runs seven such rules on every request. But the most dangerous AI attacks are not single-event affairs. Model extraction is a campaign: thousands of queries across many sessions, each individually innocuous. A full jailbreak with exfiltration is a sequence: probe the model's boundaries, find a jailbreak that works, extract the target content, confirm extraction in the response. Single-event rules see individual frames of this film; correlation rules see the plot. Section 11.07 introduces the three advanced Sigma patterns that transform the gateway from a single-event detector into a campaign-aware detection system: aggregation over time windows (rate-based abuse at scale), correlation rules (joining alerts from multiple tracks into a unified campaign alert), and sequence rules (ordered event chains within a session window). It also addresses exception management — the allowlist machinery that prevents known-good automation from flooding the correlation layer with false positives — and establishes the Sigma rule lifecycle that governs the full portfolio from draft to retirement.

Position In Chapter

Section 11.07 is the second half of the Sigma pair. Section 11.06 established the rule format and single-event patterns; Section 11.07 extends to multi-event and cross-track patterns. Together they complete the Sigma portfolio that Section 11.08 uses as the primary evidence for the detection maturity assessment.

Part 1 Aggregation Deep Dive

Heading

Aggregation Conditions: Time Windows and Group-By

Body

Section 11.06 introduced the aggregation operator as Operator 4, showing a count condition for Track 6. Here the full aggregation syntax is developed — all five functions across all three log categories — because aggregation is the bridge between single-event signature detection and stateful campaign detection. Sigma supports five aggregation functions: count (number of matching events), min and max (minimum and maximum value of a field across matching events), avg (mean value of a field), and sum (total value of a field). All five follow the same structural pattern: a selection block defines which events to aggregate; the condition line specifies the function, the field, the group-by key, the comparison operator, and the threshold. The time window is specified by the backend, not by Sigma itself: Sigma''s aggregation conditions define what to count and how to threshold; the target platform (Splunk, Elastic, Sentinel) applies its own time window syntax when compiling the rule. For the gateway''s Python backend, the time window is configured in the query monitor''s rolling window parameter. This is a known limitation of Sigma''s portability: time window semantics vary across backends and must be agreed per deployment. Count aggregation — detecting volume abuse: detection: rapid_queries: user_id: '*' gateway_action: 'pass' condition: rapid_queries | count(request_id) by user_id > 500 The group-by field (user_id) makes this a per-user count: an individual user who makes more than 500 passing requests is flagged. Without group-by, the count would be across all users and would fire on normal aggregate traffic volume. Group-by is not optional for rate-based AI security rules. Avg aggregation — detecting sustained low-entropy query sessions: detection: low_entropy_session: session_action: 'normal' condition: low_entropy_session | avg(query_entropy_avg) by user_id < 2.0 This fires when a user''s mean query entropy across their sessions averages below 2.0 bits — consistent with systematic boundary-probing rather than normal conversational usage. It fires on the session-level log (ai_session category), not on per-request logs. Min aggregation — detecting systematic query variance reduction: detection: low_variance_pattern: session_request_count|gte: 50 condition: low_variance_pattern | min(query_variance) by user_id < 0.10 The minimum query_variance across all sessions with at least 50 requests falls below 0.10 — indicating that at some point the user ran an extremely uniform query sequence, consistent with boundary probing even if other sessions were more varied. Sum aggregation — detecting budget exhaustion: detection: budget_burn: user_id: '*' condition: budget_burn | sum(budget_consumed_pct) by user_id > 90 This fires when a user''s cumulative budget consumption exceeds 90% — a useful secondary signal for extraction campaigns that exhaust query budgets deliberately. The time window discipline: rate-based rules must specify a window that is narrow enough to catch fast attacks (a burst extraction that completes in 10 minutes would evade a 24-hour count window with a threshold above its per-10-minute volume) and wide enough to accumulate evidence from slow attacks (a slow-drift extraction that spreads 500 queries over three days would evade a 1-hour window). The gateway uses two window settings: a fast window (15 minutes) for burst detection with a low threshold and a slow window (24 hours) for campaign detection with a high threshold. Both fire independently; either can trigger an alert.

Part 2 Correlation Rules

Heading

Correlation Rules: Joining Tracks into Campaign Alerts

Body

A Sigma correlation rule joins the output alerts of two or more individual Sigma rules into a higher-level campaign detection. It does not inspect raw log events; it inspects the alert stream produced by the rules it references. A correlation rule that joins Track 1 (injection alert) with Track 6 (extraction signal) fires when both alerts appear for the same user within a defined time window. Neither alert alone confirms a campaign; both together do. Sigma correlation rules use the type: correlation header and reference source rules by their rule ID (UUID) in the rules field. The group-by and timespan fields define the correlation window and the grouping key. The condition specifies how many of the referenced rules must fire, in what order, and within what window. Correlation rule structure for a confirmed extraction attempt (Track 1 + Track 6): title: Confirmed Extraction Attempt — Injection Followed by Query Acceleration id: d7e8f9a0-b1c2-4d3e-4f5a-b6c7d8e9f0a1 type: correlation status: stable description: > Correlates a Track 1 injection alert with a Track 6 extraction signal for the same user within a 10-minute window. The sequence is consistent with an attacker probing model boundaries via injection then accelerating API queries to extract decision surface information. Covers AML.T0051 + AML.T0040 campaign chain. references: - 'https://atlas.mitre.org/techniques/AML.T0051' - 'https://atlas.mitre.org/techniques/AML.T0040' author: 'ruwgxo, 2026-05-30' date: 2026-05-30 modified: 2026-05-30 tags: - attack.initial_access - attack.collection - atlas.aml.t0051 - atlas.aml.t0040 - owasp.llm.01 - owasp.llm.10 type: correlation rules: injection_alert: title: 'LLM Direct Prompt Injection via Known Prefix — Track 1' extraction_signal: title: 'Model Extraction via High-Volume Low-Variance Query Pattern — Track 6' group-by: - user_id timespan: 10m condition: gte: 1 ordered: true falsepositives: - 'Security researchers conducting combined injection and extraction tests in authorised exercises' - 'Automated test pipelines that run injection tests immediately before extraction tests' level: critical The ordered: true field requires the injection alert to precede the extraction signal within the 10-minute window. Without ordering, the correlation would fire even if the extraction came first — a possible but less indicative sequence. For campaign patterns with a clear temporal logic (probe before extract), ordering adds precision. The correlation rule''s level is critical even if the individual source rules are medium or high. The correlation provides confirmation that neither rule provides alone: two independent track signals for the same user within a narrow window are much more likely to represent a real attack than either signal alone. Confirmed campaigns warrant critical-level alerting even when individual signals are uncertain. Three correlation rules for the seven-track gateway portfolio: Correlation 1 — Injection-to-Extraction campaign (Track 1 → Track 6, window 10m, ordered). The most important correlation in the portfolio: injection probing followed by query acceleration is the textbook model extraction approach. Correlation 2 — Jailbreak-then-Adversarial campaign (Track 1 → Track 7, window 5m, ordered). A jailbreak attempt followed by an adversarial input signal indicates an attacker probing the model''s alignment bypass and adversarial robustness simultaneously — consistent with a targeted attack that aims to both bypass content policy and manipulate classification outputs. Correlation 3 — Semantic Gate → Repeated Flagging (Track 1's centroid gate flagging more than three times within 15 minutes for the same user). Repeated near-miss similarity scores indicate an adversary iteratively refining an injection to stay below the block threshold while approaching it — a prompt optimisation attack pattern.

Part 3 Sequence Rules

Heading

Sequence Rules: Ordered Event Chains

Body

Sequence rules are a specialised form of correlation that requires not just that multiple events occur within a window but that they occur in a specific order. The probe → inject → exfiltrate pattern is the paradigm case: a sophisticated attacker begins by probing the model''s capabilities and restrictions (low-signal queries that do not trigger any track), then attempts injection (Track 1's injection or jailbreak detection fires), then attempts to extract a target from the model''s response (specific response patterns indicative of successful exfiltration). Sequence rules in Sigma use the type: correlation with an ordered: true flag and multiple named rule references. The pipeline must evaluate them in order: only if the first rule fires does it begin watching for the second; only if the second fires within the window does it begin watching for the third. A three-stage sequence rule for the probe-inject-exfiltrate pattern: title: Probe-Inject-Exfiltrate Sequence — AI Gateway Attack Chain id: e8f9a0b1-c2d3-4e5f-6a7b-c8d9e0f1a2b3 type: correlation status: experimental description: > Three-stage ordered sequence: (1) high session request volume without injection signals (probing phase), (2) injection or jailbreak alert fires (Track 1), (3) response entropy drops sharply (successful exfiltration pattern). All three stages must occur in order within a 30-minute session window. Covers the full AML.T0051 → AML.T0040 attack chain. tags: - attack.initial_access - attack.collection - attack.exfiltration - atlas.aml.t0051 - atlas.aml.t0040 - owasp.llm.01 - owasp.llm.10 type: correlation rules: probe_phase: title: 'Session Request Volume Above Baseline — Probing Pattern' inject_phase: title: 'LLM Direct Prompt Injection via Known Prefix — Track 1' exfil_phase: title: 'Response Entropy Drop — Successful Exfiltration Signal' group-by: - user_id - session_id timespan: 30m condition: gte: 3 ordered: true falsepositives: - 'Automated test suites that run load tests followed by functionality tests including injection test cases' level: critical The exfil_phase rule (response entropy drop) is a new rule not in the original gateway portfolio. Sequence rules often reveal detection gaps: to complete a sequence correlation, you need a rule for every stage of the attack chain, not just the stages that are currently instrumented. The probe-inject-exfiltrate sequence requires a response-entropy monitor — a rule that fires when output_entropy_avg drops sharply within a session — that Track 6 does not currently implement. This is an appropriate addition to the detection backlog triggered by the sequence rule design process. Sequence rules are status: experimental by design. They require the most tuning of any rule type: the window must be wide enough to catch real attack sequences (which may pause between stages) but narrow enough to avoid false correlations between unrelated events from different sessions. Start with a wide window and tighten it based on production observation.

Part 4 Exception Management

Heading

Exception Management: Allowlists in Sigma Rules

Body

Every production rule produces false positives from known-good sources: automated testing pipelines that run injection strings as fixtures, batch inference jobs with high query rates that look like extraction, internal benchmark tools that probe model performance with repetitive queries. Without exception management, the correlation layer drowns in alerts from known-good automation. With it, these sources are filtered before the rule fires. Sigma implements exceptions through filter selections combined with a not condition. A filter selection is a named selection block that matches known-good events; the condition excludes it explicitly. This is preferable to building exceptions into the positive selection (which makes the detection logic harder to read) or suppressing at the SIEM level (which hides the exception from the rule''s audit trail). Exception pattern for a known-good automated test pipeline (source IP or service account): detection: high_volume: session_request_count|gte: 100 known_test_pipeline: user_id: - 'svc-regression-tests' - 'svc-load-tester' - 'svc-benchmark-runner' condition: high_volume and not known_test_pipeline Exception pattern for a known-safe model that always produces high squeezer disagreement due to its unusual output distribution: detection: high_squeezer: track_7_squeezer_score|gte: 0.70 safe_model_exception: model_name: - 'internal-test-model-v1' - 'canary-model-qa' - 'benchmark-reference-model' condition: high_squeezer and not safe_model_exception Exception lifecycle: exceptions must be versioned and reviewed on the same cadence as the rules that contain them. An exception added for a test pipeline that no longer exists continues silently suppressing alerts. An exception for a model name that has been retired may now match a different model if names are reused. The rule_metadata_validator.py from Section 11.02 should be extended to require a review date on each filter selection block; exceptions older than 90 days without a review are flagged in CI. Exception documentation: every filter selection must have a corresponding entry in the falsepositives field explaining why the exception exists, when it was added, and who approved it: falsepositives: - 'svc-regression-tests: automated regression pipeline; approved by security team 2026-05-30' - 'internal-test-model-v1: produces high squeezer score due to unusual output distribution; approved by detection team 2026-04-15' This documentation is the audit trail. An analyst who receives an alert and wonders why a particular source is not triggering it can read the falsepositives field and understand the exception without hunting through commit history.

Part 5 Lifecycle

Heading

Sigma Rule Lifecycle: Draft to Retirement

Body

Every Sigma rule in the portfolio has a status field that tracks its lifecycle stage. The gateway uses five stages with defined entry and exit criteria enforced by the CI pipeline and the sigma_rule_lifecycle_manager.py deliverable. Draft — a rule is in draft when it has been written but has not yet been reviewed. Draft rules do not appear in the CI pipeline''s deployment stage; they are committed to the repository in a feature branch for review. The draft stage ends when a peer review is approved and the status field is advanced to experimental. Experimental — a rule is experimental when it has passed peer review and has been deployed to the staging environment. It runs against real traffic on staging for a minimum of two weeks. During this period the detection engineer monitors alert volume, FPR, and any new false positive sources. The experimental stage ends when: (a) the rule has run for two weeks on staging with no unacceptable FPR, and (b) it has produced at least one confirmed true positive (or the detection engineer has explicitly accepted that no TP opportunity arose during staging). Status advances to test. Test — a rule in test status is deployed to production with an explicit flag in the SIEM that identifies it as under evaluation. SOC analysts see the alerts but with a "test rule" label; they are asked to provide disposition (TP/FP) but the rule does not feed into SLA metrics. The test stage lasts a minimum of four weeks in production. The lifecycle manager tracks the FPR over this period. If FPR exceeds 15%, the rule is returned to experimental for calibration. If FPR stays below 10%, status advances to stable. Stable — a fully deployed production rule. Stable rules feed into SLA metrics, feed the FPR tracking database, and feed the coverage heat map. A stable rule is re-evaluated for calibration when its FPR exceeds 10% over any rolling 30-day window. Re-evaluation may result in a threshold change (staying in stable with a new modified date), a demotion to test (for significant logic changes), or initiation of retirement. Deprecated — retirement initiation. The rule is suppressed (produces no alerts) but remains deployed. The lifecycle manager watches for a two-week clean window: if no confirmed true positives would have been caught by the rule during the suppression period (determined from threat intelligence and manual review), the rule is promoted to removed. If a TP is identified during suppression, retirement is halted and the rule returns to stable. Deprecated rules are removed from the repository only after the two-week window passes without a TP — never deleted immediately. The sigma_rule_lifecycle_manager.py deliverable implements this lifecycle programmatically: it reads the status field from all rules in the repository, computes how long each rule has been in its current status, flags rules that have exceeded their stage duration without advancing, and produces a lifecycle report for the weekly detection engineering sync.

        atlas_techniques=['AML.T0051', 'AML.T0040'],
    ),
]

# ---------------------------------------------------------------------------
# Correlation engine
# ---------------------------------------------------------------------------

class CorrelationEngine:
    '''
    Processes an alert stream and emits CampaignAlert objects when
    correlation patterns are satisfied.

    Per-user alert buffers are maintained in memory with a rolling window
    eviction policy. In production, replace with a Redis-backed session store
    for horizontal scalability.
    '''

    def __init__(
        self,
        patterns: list[CorrelationPattern] | None = None,
    ) -> None:
        self.patterns = patterns or CORRELATION_PATTERNS
        # user_id -> list of Alert, sorted by timestamp ascending
        self._buffer: dict[str, list[Alert]] = defaultdict(list)

    def process(self, alert: Alert) -> list[CampaignAlert]:
        '''
        Process one alert. Returns a list of CampaignAlert objects triggered
        by this alert. Empty list if no correlation fires.
        '''
        self._buffer[alert.user_id].append(alert)
        self._evict_stale(alert.user_id, alert.timestamp)
        campaign_alerts: list[CampaignAlert] = []
        for pattern in self.patterns:
            result = self._evaluate_pattern(pattern, alert.user_id, alert.timestamp)
            if result:
                campaign_alerts.append(result)
        return campaign_alerts

    def _evict_stale(self, user_id: str, now: datetime) -> None:
        '''Remove alerts older than the maximum window across all patterns.'''
        max_window = max(p.window_minutes for p in self.patterns)
        cutoff = now - timedelta(minutes=max_window)
        self._buffer[user_id] = [
            a for a in self._buffer[user_id]
            if a.timestamp >= cutoff
        ]

    def _evaluate_pattern(
        self,
        pattern: CorrelationPattern,
        user_id: str,
        now: datetime,
    ) -> CampaignAlert | None:
        window_start = now - timedelta(minutes=pattern.window_minutes)
        window_alerts = [
            a for a in self._buffer[user_id]
            if a.timestamp >= window_start
        ]

        if pattern.ordered:
            return self._evaluate_ordered(pattern, window_alerts, user_id, now)
        else:
            return self._evaluate_unordered(pattern, window_alerts, user_id, now)

    def _evaluate_ordered(
        self,
        pattern: CorrelationPattern,
        window_alerts: list[Alert],
        user_id: str,
        now: datetime,
    ) -> CampaignAlert | None:
        '''All required rule titles must appear in order within the window.'''
        matched: list[Alert] = []
        required_iter = iter(pattern.required_rule_titles)
        current_required = next(required_iter, None)

        for alert in sorted(window_alerts, key=lambda a: a.timestamp):
            if current_required and alert.rule_title == current_required:
                matched.append(alert)
                current_required = next(required_iter, None)
            if current_required is None:
                break   # all required stages matched in order

        if current_required is None and len(matched) == len(pattern.required_rule_titles):
            return self._make_campaign_alert(pattern, user_id, matched, now)
        return None

    def _evaluate_unordered(
        self,
        pattern: CorrelationPattern,
        window_alerts: list[Alert],
        user_id: str,
        now: datetime,
    ) -> CampaignAlert | None:
        '''min_matches of required_rule_titles must appear (any order).'''
        matched_by_title: dict[str, list[Alert]] = defaultdict(list)
        for alert in window_alerts:
            if alert.rule_title in pattern.required_rule_titles:
                matched_by_title[alert.rule_title].append(alert)

        # Count total matches across all required titles
        total_matches = sum(len(v) for v in matched_by_title.values())
        if total_matches >= pattern.min_matches:
            source_alerts = [
                a for alerts in matched_by_title.values()
                for a in alerts
            ]
            return self._make_campaign_alert(pattern, user_id, source_alerts, now)
        return None

    def _make_campaign_alert(
        self,
        pattern: CorrelationPattern,
        user_id: str,
        source_alerts: list[Alert],
        now: datetime,
    ) -> CampaignAlert:
        import uuid
        session_id = source_alerts[0].session_id if source_alerts else ''
        return CampaignAlert(
            campaign_id=str(uuid.uuid4())[:8],
            correlation_name=pattern.name,
            user_id=user_id,
            session_id=session_id,
            source_alerts=source_alerts,
            level=pattern.level,
            atlas_techniques=pattern.atlas_techniques,
            triggered_at=now,
            description=pattern.description,
        )

#!/usr/bin/env python3
'''sigma_rule_lifecycle_manager.py
Tracks Sigma rule lifecycle stages across the detection portfolio.
Flags rules exceeding stage duration; enforces suppression window.
Produces weekly lifecycle report for detection engineering sync.
Chapter 11, Section 11.07 — AI Security Mastery
Author: Raghav Dinesh | github: ruwgxo

Usage:
  python3 sigma_rule_lifecycle_manager.py detections/rules/
  python3 sigma_rule_lifecycle_manager.py detections/rules/ --report
  python3 sigma_rule_lifecycle_manager.py detections/rules/ --check-deprecated
'''

from __future__ import annotations
import argparse
import pathlib
import sys
from dataclasses import dataclass
from datetime import date, timedelta
from typing import Literal

import yaml

# ---------------------------------------------------------------------------
# Stage durations (minimum days before advancing)
# ---------------------------------------------------------------------------

STAGE_MIN_DAYS: dict[str, int] = {
    'experimental': 14,   # 2 weeks on staging
    'test': 28,           # 4 weeks in production
    'stable': 0,          # indefinite; no minimum
    'deprecated': 14,     # 2-week suppression window
}

STAGE_WARNING_DAYS: dict[str, int] = {
    'experimental': 21,   # flag if still experimental after 3 weeks
    'test': 42,           # flag if still in test after 6 weeks
    'stable': 0,
    'deprecated': 21,     # flag if not cleared after 3 weeks
}

Status = Literal['experimental', 'test', 'stable', 'deprecated']

# ---------------------------------------------------------------------------
# Data model
# ---------------------------------------------------------------------------

@dataclass
class RuleLifecycleRecord:
    filename: str
    title: str
    rule_id: str
    status: str
    date_created: date
    date_modified: date
    days_in_status: int
    flag: str           # '' | 'overdue' | 'suppression_window_passed'
    action_required: str

# ---------------------------------------------------------------------------
# Parser
# ---------------------------------------------------------------------------

def load_rule(path: pathlib.Path) -> dict | None:
    with open(path) as f:
        try:
            return yaml.safe_load(f)
        except yaml.YAMLError:
            return None

def parse_record(path: pathlib.Path, today: date) -> RuleLifecycleRecord | None:
    rule = load_rule(path)
    if not rule or not isinstance(rule, dict):
        return None
    status = rule.get('status', '')
    if status not in STAGE_MIN_DAYS and status != 'stable':
        return None   # draft or unknown; skip

    date_str = rule.get('modified') or rule.get('date', '')
    try:
        date_modified = date.fromisoformat(str(date_str))
    except (ValueError, TypeError):
        date_modified = today

    date_created_str = rule.get('date', date_str)
    try:
        date_created = date.fromisoformat(str(date_created_str))
    except (ValueError, TypeError):
        date_created = date_modified

    days_in_status = (today - date_modified).days
    warning_threshold = STAGE_WARNING_DAYS.get(status, 0)
    flag = ''
    action = 'No action required.'

    if status == 'deprecated':
        min_days = STAGE_MIN_DAYS['deprecated']
        if days_in_status >= min_days:
            flag = 'suppression_window_passed'
            action = (
                f'Suppression window complete ({days_in_status} days). '
                'Review for confirmed TPs during suppression. If none, remove rule.'
            )
    elif warning_threshold > 0 and days_in_status >= warning_threshold:
        flag = 'overdue'
        action = (
            f'Rule has been {status} for {days_in_status} days '
            f'(warning threshold: {warning_threshold} days). '
            'Review FPR and advance lifecycle stage or return for calibration.'
        )

    return RuleLifecycleRecord(
        filename=path.name,
        title=rule.get('title', 'unknown')[:60],
        rule_id=str(rule.get('id', 'unknown'))[:36],
        status=status,
        date_created=date_created,
        date_modified=date_modified,
        days_in_status=days_in_status,
        flag=flag,
        action_required=action,
    )

# ---------------------------------------------------------------------------
# Report
# ---------------------------------------------------------------------------

def print_lifecycle_report(records: list[RuleLifecycleRecord]) -> int:
    by_status: dict[str, list[RuleLifecycleRecord]] = {}
    for r in records:
        by_status.setdefault(r.status, []).append(r)

    flagged = [r for r in records if r.flag]
    today = date.today()

    print(f'\nSigma Rule Lifecycle Report — {today.isoformat()}')
    print(f'Total rules tracked: {len(records)}')
    for status in ('stable', 'test', 'experimental', 'deprecated'):
        count = len(by_status.get(status, []))
        print(f'  {status:<14}: {count}')
    print(f'  Flagged:        {len(flagged)}')
    print()

    if flagged:
        print('Flagged rules (action required):')
        for r in flagged:
            print(f'  [{r.flag.upper()}] {r.filename}')
            print(f'    Title:    {r.title}')
            print(f'    Status:   {r.status} for {r.days_in_status} days (modified {r.date_modified})')
            print(f'    Action:   {r.action_required}')
        print()

    print('Full portfolio:')
    print(f'  {"File":<45} {"Status":<14} {"Days":<6} {"Flag"}')
    print('  ' + '-' * 80)
    for r in sorted(records, key=lambda x: (x.status, -x.days_in_status)):
        flag_str = f'[{r.flag.upper()}]' if r.flag else ''
        print(f'  {r.filename:<45} {r.status:<14} {r.days_in_status:<6} {flag_str}')

    return 1 if flagged else 0

# ---------------------------------------------------------------------------
# Entry point
# ---------------------------------------------------------------------------

def main() -> int:
    parser = argparse.ArgumentParser(description='Sigma rule lifecycle manager')
    parser.add_argument('rules_dir', help='Directory containing Sigma rule files')
    parser.add_argument('--report', action='store_true',
                        help='Print full lifecycle report (default behaviour)')
    parser.add_argument('--check-deprecated', action='store_true',
                        help='Exit non-zero if any deprecated rules have passed suppression window')
    args = parser.parse_args()

    rules_dir = pathlib.Path(args.rules_dir)
    if not rules_dir.exists():
        print(f'Error: rules directory not found: {rules_dir}')
        return 1

    today = date.today()
    rule_files = sorted(
        list(rules_dir.rglob('*.yml')) + list(rules_dir.rglob('*.yaml'))
    )
    records = [r for path in rule_files if (r := parse_record(path, today)) is not None]

    if args.check_deprecated:
        passed = [r for r in records if r.flag == 'suppression_window_passed']
        if passed:
            print(f'{len(passed)} deprecated rule(s) have passed the suppression window:')
            for r in passed:
                print(f'  {r.filename}: {r.days_in_status} days suppressed. Remove or restore.')
            return 1
        print('No deprecated rules have exceeded the suppression window.')
        return 0

    return print_lifecycle_report(records)

if __name__ == '__main__':
    sys.exit(main())

Common Mistakes

Id

CM11.07.1

Mistake

Using the same time window for fast-burst attacks and slow-campaign attacks in a single aggregation rule

Why It Happens

A single count threshold with a single window feels cleaner than two rules. Practitioners choose a compromise window that is neither short enough to catch fast attacks nor long enough to accumulate slow campaign evidence.

Why It Matters

A burst extraction attack that delivers 500 queries in 15 minutes generates an average rate of 500/1440 per minute over 24 hours — well below a 24-hour count threshold tuned for slow campaigns. A slow campaign that spreads 500 queries over 48 hours generates 10 queries per hour — well below a 15-minute burst threshold. A single-window rule is blind to one of the two attack profiles.

Correct Approach

Deploy two rules for each rate-based detection: a fast-window rule (15 minutes, low threshold) for burst attacks and a slow-window rule (24 hours, high threshold) for campaigns. Both reference the same log fields; only the window and threshold differ. The sigma_rule_builder.py templates support generating both variants from a single spec with a fast_window and slow_window parameter.

Id

CM11.07.2

Mistake

Building correlation rules before the source single-event rules are at stable status

Why It Happens

Correlation feels like the natural next step after writing the source rules. The detection engineer authors all rules in one sprint.

Why It Matters

A correlation rule built on experimental or test source rules inherits those rules'' instability. If a source rule is calibrated (threshold change, keyword list update), the correlation''s firing behaviour changes implicitly. A correlation that fired on experimental source rule A may no longer fire after A is calibrated to stable — but the correlation''s status is still stable, creating a misleading coverage picture.

Correct Approach

Correlation rules are only authored after all source rules have reached stable status. The sigma_rule_lifecycle_manager.py can be extended to check that all referenced source rule titles are stable before promoting a correlation rule beyond experimental.

Id

CM11.07.3

Mistake

Treating exception filter selections as permanent suppressions without review dates

Why It Happens

Exceptions are added during an incident or during initial tuning. Once the alert volume drops, the exception is forgotten. Review dates are not required by the metadata standard.

Why It Matters

An exception for svc-regression-tests added in January 2025 may be suppressing alerts from a production service that was renamed to svc-regression-tests in December 2025 after the original test pipeline was decommissioned. The exception is now suppressing real attack alerts from a production account that happens to share the old test pipeline name.

Correct Approach

Every filter selection block carries a comment with the exception approval date and owner. The rule_metadata_validator.py is extended to extract these dates and flag exceptions older than 90 days in CI. The sigma_rule_lifecycle_manager.py quarterly report includes an exception audit as a mandatory section.

Id

CM11.07.4

Mistake

Ordering correlation rule sources by alert frequency rather than attack sequence logic

Why It Happens

The most frequently firing rule is placed first in the required_rule_titles list because it is expected to provide the earliest signal. But alert frequency does not reflect attack sequence order.

Why It Matters

The extraction campaign correlation requires injection before extraction: the attacker probes (injection signal) then extracts (query accumulation signal). If the rule orders them by frequency — Track 6 fires more often than Track 1, so Track 6 is listed first — the correlation requires extraction before injection, which is the wrong sequence and will not fire on the actual attack pattern.

Correct Approach

Order required_rule_titles by the attack sequence logic, not by alert frequency. Document the sequence reasoning in the correlation rule''s description field. Test the ordering by simulating the attack sequence in the staging environment before setting the correlation rule to stable status.

Id

CM11.07.5

Mistake

Skipping the experimental status phase for correlation rules that seem obviously correct

Why It Happens

A correlation of Track 1 and Track 6 feels mathematically correct — injection followed by extraction is clearly malicious. Why waste two weeks on staging?

Why It Matters

Correlation rules are the most sensitive to production traffic patterns. A CI test environment cannot replicate the diverse patterns of real user behaviour that produce false correlations: a security researcher who runs injection tests then a legitimate load test in the same session within 10 minutes will trigger the extraction campaign correlation. Without staging observation, these false correlation patterns are invisible until the rule is in production generating critical-level false positives.

Correct Approach

All correlation rules begin at experimental status and serve the two-week staging period regardless of how logically sound the correlation appears. The staging period for correlation rules is more valuable than for single-event rules because the interaction between tracks is harder to predict from theory than from observation of real traffic.

Section Summary

What You Learned

Advanced Sigma patterns transform the gateway from a single-event detector into a campaign-aware detection system. Aggregation conditions with count, min, max, avg, and sum enable rate-based detection with fast-window and slow-window variants for burst and campaign attacks respectively. Correlation rules join alert streams from multiple tracks into campaign-level detections; the three gateway correlation rules (injection-extraction, jailbreak-adversarial, semantic near-miss repetition) and one experimental sequence rule (probe-inject-exfiltrate) produce the critical-level campaign alerts that single-event rules cannot. Exception management via filter selections with not conditions and review-dated comments prevents known-good automation from generating false correlations. The Sigma rule lifecycle (experimental → test → stable → deprecated) governs every rule in the portfolio, enforced by the lifecycle manager. The full portfolio now contains twelve rules across seven tracks.

Key Terms

Term

Correlation rule

Definition

A Sigma rule of type: correlation that joins the output alerts of two or more source rules into a campaign-level detection. Fires when all required source rules produce alerts for the same user within a defined time window, optionally in a specified order.

Term

Sequence rule

Definition

A correlation rule with ordered: true and three or more stages, where each stage must fire in sequence within the window. Used for multi-phase attack chains (probe → inject → exfiltrate). Requires a Sigma rule for every stage of the attack sequence.

Term

Exception management

Definition

The use of filter selection blocks combined with not conditions to exclude known-good event sources from detection rules. Exceptions are versioned, review-dated, and documented in the falsepositives field. Exceptions older than 90 days without review are flagged in CI.

Term

Fast window / slow window

Definition

The two-rule pattern for rate-based aggregation: a fast window (e.g. 15 minutes, low threshold) catches burst attacks; a slow window (e.g. 24 hours, high threshold) catches campaigns. Both are required; a single window misses one of the two attack profiles.

Term

Sigma lifecycle

Definition

The five-stage progression of a detection rule: draft (unreviewed) → experimental (staging, 2 weeks minimum) → test (production with label, 4 weeks minimum) → stable (full production) → deprecated (2-week suppression before removal). Enforced by sigma_rule_lifecycle_manager.py.
