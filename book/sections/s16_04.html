Chapter 16 · Section 4 · ~6 pages

Datadog Integration: Logs API and Metrics

Section Overview

One Line Summary

The second platform connector, and the first with two channels: detections pushed through the Datadog Logs API for per-detection detail, and detection rates submitted through the metrics interface for the aggregate picture -- the metrics connecting to the Chapter 14 Section 14.08 observability signals so operational and detection metrics share one platform.

Why This Section Exists

Splunk showed the connector shape with a single channel: push each detection as an event. Datadog adds the dimension that a SIEM-plus-observability platform makes natural -- the aggregate. A detection is two things at once: an individual event a responder investigates, and a data point in a rate a team watches for trends. Datadog is built to hold both, so the connector uses both channels. The Logs API carries each detection as a structured log with tags Datadog facets on and the full event in the message; the metrics interface carries counts by detector, verdict, and severity as time series that dashboards and monitors are built on. The second channel is the reason this section is distinct rather than a repeat of Splunk. In Chapter 14 Section 14.08, the gateway's operational metrics -- latency, throughput, error rates -- were instrumented for observability. Detection metrics belong on the same platform, because the questions cross over: an operations engineer watching gateway health and a security analyst watching detection rates are looking at the same system, and Datadog lets them share dashboards, correlate a detection spike with a latency spike, and alert on both. Submitting detection counts under a metric namespace alongside the observability metrics is what unifies the two views. The connector is a push integration on both channels -- the gateway owns delivery of logs and metrics alike -- and, as with Splunk, it is tested end to end on a stub transport.

Position In Chapter

Section 16.04 is the second of the three platform connectors and follows the connector shape 16.03 established, adding the metrics channel. It consumes the detection-event schema of 16.01 and connects its metrics channel to the Chapter 14 Section 14.08 observability signals, so the detection rates sit beside the operational metrics. The two-channel pattern -- detail plus aggregate -- informs how the summary (16.07) frames what a complete platform integration delivers.

Prose Content

Part 1

Title

Two Channels: Detail and Aggregate

Body

A detection is two things at once. It is an individual event -- this request, this verdict, this evidence -- that a responder opens and investigates. And it is a data point in a rate -- one of the N injections blocked this hour -- that a team watches for trends and spikes. Splunk's connector treated the detection as an event; Datadog's connector treats it as both, because Datadog is a platform built to hold logs and metrics side by side, and using only one channel would waste half of what it offers. So the connector has two channels. The Logs API channel pushes each detection as a structured log, carrying the full event and the tags Datadog facets on, for the investigator who needs the detail. The metrics channel submits aggregated counts -- detections per detector, verdict, and severity -- as time series, for the analyst and the operations engineer who need the trend. Both are push: the gateway submits logs and metrics as detections occur, owning delivery of each. The two channels are not redundant; they answer different questions about the same detections, and the rest of the section builds each and connects the metrics channel to the observability work of Chapter 14.

Part 2

Title

The Logs API: Per-Detection Detail

Body

The Datadog Logs API accepts structured log entries, and the detection-event schema maps onto one cleanly. The log's tags carry the dimensions a team slices on -- detector, verdict, severity, surface -- as key:value pairs, so a query for 'all high-severity jailbreak blocks' is a tag filter rather than a text search. The log's status is derived from the detection's severity, mapping the schema's severity levels onto Datadog's status levels so a critical detection reads as critical in the Datadog log stream and colours and sorts accordingly. The hostname carries the emitting gateway instance, and the timestamp is converted to the millisecond epoch Datadog expects. The message holds the full detection event as JSON. As with Splunk's body, this is the deliberate choice that keeps an investigation possible: the tags make the common slice fast, but the complete detection -- scores, confidence, evidence, session, surface -- lives in the message, so an analyst who filters down to one alert has everything the detector knew. The tags are the index; the message is the record. Getting the status mapping right matters more than it looks: it is what makes Datadog's severity-based alerting and visual triage work on detections, so a critical exfiltration block stands out from a medium PII flag without a custom rule.

Part 3

Title

The Metrics Channel: Aggregate Rates

Body

The metrics channel answers the question the logs cannot answer efficiently: how many, how fast, trending which way? The connector aggregates a batch of detection events into count metric series, one series per combination of detector, verdict, and severity, each tagged with those dimensions. Two blocked jailbreaks in the same batch become one series with a count of two, not two separate points -- the aggregation is the point, because a metric is about the rate, not the individual event. The series sit under a configured metric namespace, so all detection metrics share a common prefix and are easy to find and dashboard together. Aggregating at the connector rather than making Datadog count raw logs is a cost and clarity choice. Counting logs works but is expensive and imprecise; submitting pre-aggregated counts gives Datadog exact rates cheaply, and the dimensional tags let a dashboard break the total down by detector or severity on demand. This is the same discipline as the Chapter 14 cost work applied to the metrics channel: send the aggregate the platform needs, not the raw stream it would have to reduce. The metrics channel turns the detection stream into the rates a team monitors, and the next part connects those rates to the observability metrics already on the platform.

Part 4

Title

Connecting to the Chapter 14 Observability Signals

Body

Chapter 14 Section 14.08 instrumented the gateway with the golden signals -- latency, traffic, errors, saturation -- and put them on an observability platform so the system could be operated. Those are operational metrics: how the gateway is running. Detection metrics are a different family: what the gateway is catching. But they belong on the same platform, because the two families answer questions that constantly cross over. A spike in detection rate alongside a spike in latency might be an attack driving both; a drop in detections alongside normal traffic might be a detector silently failing. Separated onto two platforms, those correlations are invisible; together on Datadog, they are one dashboard. So the connector submits detection metrics under a namespace that sits alongside the Chapter 14 observability metrics, and the payoff is a unified operational picture. An operations engineer watching gateway health and a security analyst watching detection rates look at the same Datadog, can build shared dashboards, and can write monitors that span both families -- alert when detections spike, when a detector's rate drops to zero, when detection latency and volume rise together. This is why Datadog gets a metrics channel that Splunk's section did not emphasise: the platform is where the suite's detection signals and the gateway's operational signals become one view, closing the loop the observability chapter opened.

Part 5

Title

Testing Both Channels End to End

Body

The connector is validated on a stub transport that captures both channels. The tests check the logs path -- correct faceting tags, the severity-to-status mapping across all levels, the full detection preserved in the message, the millisecond timestamp -- and, separately, the metrics path -- that events aggregate correctly, so two identical detections become one series with a count of two rather than two series or two points. A combined test confirms that a batch produces one log per event and the right number of aggregated series, and that both channels report success. Testing the aggregation explicitly is what makes the metrics channel trustworthy. A logs channel is easy to reason about -- one event, one log -- but a metrics channel that miscounts is worse than none, because a dashboard that shows the wrong rate is believed. So the harness asserts the counts directly: N identical detections yield a single series with count N, and distinct detections yield distinct series. As with Splunk, the stub proves the mapping and delivery contract without a live Datadog, and pointing the connector at a real Logs API and metrics endpoint is a configuration change carrying an environment-sourced API key. With Datadog holding both the detail and the aggregate, Section 16.05 builds the third connector for the Elastic Stack.

Deliverable 1

Title

The Datadog Connector

Filename

datadog_integration.py

Description

The two-channel Datadog connector: to_datadog_log maps a detection event to a Datadog log with faceting tags, a severity-derived status, and the full event in the message; to_datadog_metrics aggregates events into count series by detector, verdict, and severity; DatadogConnector pushes both channels behind a swappable transport. Runs standalone on an in-memory stub.

Implementation Notes

Python 3.12, single quotes throughout per book convention, standard-library json, time, dataclasses, and typing only. The DetectionEvent is a dict via sample_event for standalone running; in the suite it imports DetectionEvent from detection_event_schema.py. StubDatadogTransport captures both channels; the real transport POSTs to the Logs API and the series endpoint with a DD-API-KEY header. Self-checks that identical detections aggregate into one series with the summed count and that severity maps to the right status.

Code

# datadog_integration.py
# Section 16.04: Datadog Integration -- Logs API and Metrics
# 20260121 | AI Security Mastery -- Chapter 16 by Raghav Dinesh
# Single quotes throughout per book convention
#
# The second platform connector, and the first with two channels. It pushes
# detection events into Datadog through the Logs API, and submits detection
# metrics -- counts by detector, verdict, and severity -- through the metrics
# interface. The logs give per-detection detail; the metrics give the aggregate
# picture that connects to the Chapter 14 Section 14.08 observability signals.

import json
import time
from dataclasses import dataclass
from typing import Any, Dict, List, Optional


def sample_event() -> Dict[str, Any]:
    return {
        'schema_version': '1.0', 'event_id': 'req-2001:jailbreak',
        'timestamp': '2026-01-21T11:00:00Z', 'detector': 'jailbreak',
        'verdict': 'block', 'severity': 'high', 'score': 0.88, 'confidence': 0.91,
        'latency_ms': 5.1, 'surface': 'input', 'request_id': 'req-2001',
        'session_id': 'sess-9', 'source': 'prod-gateway-2',
        'evidence': [{'source': 'ml', 'label': 'jailbreak_classifier', 'detail': 'roleplay framing'}],
        'iocs': [], 'labels': {},
    }


class DatadogTransport:
    def submit_logs(self, api_key: str, logs: List[Dict[str, Any]]) -> Dict[str, Any]:
        raise NotImplementedError
    def submit_metrics(self, api_key: str, series: List[Dict[str, Any]]) -> Dict[str, Any]:
        raise NotImplementedError


class StubDatadogTransport(DatadogTransport):
    def __init__(self) -> None:
        self.logs: List[Dict[str, Any]] = []
        self.metrics: List[Dict[str, Any]] = []
    def submit_logs(self, api_key, logs):
        self.logs.extend(logs); return {'status': 'ok'}
    def submit_metrics(self, api_key, series):
        self.metrics.extend(series); return {'status': 'ok'}


@dataclass
class DatadogConfig:
    site: str = 'datadoghq.com'
    log_source: str = 'ai-detection'
    metric_namespace: str = 'ai.detection'
    service: str = 'detection-gateway'
    api_key_env_var: str = 'DD_API_KEY'

    def validate(self) -> None:
        assert self.log_source and self.metric_namespace, 'log source and metric namespace required'
        assert self.service, 'service is required'


def _iso_to_epoch(ts: str) -> int:
    return int(time.mktime(time.strptime(ts, '%Y-%m-%dT%H:%M:%SZ')))


def _dd_status(severity: str) -> str:
    return {'info': 'info', 'low': 'notice', 'medium': 'warning',
            'high': 'error', 'critical': 'critical'}.get(severity, 'info')


def to_datadog_log(event: Dict[str, Any], cfg: DatadogConfig) -> Dict[str, Any]:
    '''Map a detection event to a Datadog log. Tags carry the faceting
    dimensions; the message holds the full detection as JSON.'''
    tags = [f'detector:{event["detector"]}', f'verdict:{event["verdict"]}',
            f'severity:{event["severity"]}', f'surface:{event["surface"]}']
    return {'ddsource': cfg.log_source, 'service': cfg.service, 'ddtags': ','.join(tags),
            'hostname': event['source'], 'timestamp': _iso_to_epoch(event['timestamp']) * 1000,
            'status': _dd_status(event['severity']), 'message': json.dumps(event, sort_keys=True)}


def to_datadog_metrics(events: List[Dict[str, Any]], cfg: DatadogConfig) -> List[Dict[str, Any]]:
    '''Aggregate events into Datadog count series: one per (detector, verdict,
    severity). These aggregate rates connect to the Chapter 14 observability signals.'''
    now = int(time.time())
    counts: Dict[tuple, int] = {}
    for e in events:
        key = (e['detector'], e['verdict'], e['severity'])
        counts[key] = counts.get(key, 0) + 1
    series: List[Dict[str, Any]] = []
    for (detector, verdict, severity), n in sorted(counts.items()):
        series.append({'metric': f'{cfg.metric_namespace}.count', 'type': 'count',
                       'points': [[now, n]],
                       'tags': [f'detector:{detector}', f'verdict:{verdict}', f'severity:{severity}']})
    return series


class DatadogConnector:
    '''Two-channel push connector: Logs API for detail, metrics for aggregate rate.'''
    name = 'datadog'
    model = 'push'

    def __init__(self, transport: Optional[DatadogTransport] = None,
                 config: Optional[DatadogConfig] = None) -> None:
        self._transport = transport if transport is not None else StubDatadogTransport()
        self._cfg = config if config is not None else DatadogConfig()

    def send(self, events: List[Dict[str, Any]], api_key: str = 'stub-key') -> Dict[str, Any]:
        self._cfg.validate()
        logs = [to_datadog_log(e, self._cfg) for e in events]
        metrics = to_datadog_metrics(events, self._cfg)
        lr = self._transport.submit_logs(api_key, logs)
        mr = self._transport.submit_metrics(api_key, metrics)
        return {'logs_sent': len(logs), 'metric_series': len(metrics),
                'logs_ok': lr.get('status') == 'ok', 'metrics_ok': mr.get('status') == 'ok'}


if __name__ == '__main__':
    stub = StubDatadogTransport()
    conn = DatadogConnector(transport=stub)
    events = [sample_event(),
              {**sample_event(), 'event_id': 'req-2002:jailbreak', 'request_id': 'req-2002'},
              {**sample_event(), 'detector': 'pii_scanner', 'verdict': 'flag', 'severity': 'medium',
               'event_id': 'req-2003:pii', 'request_id': 'req-2003'}]
    result = conn.send(events)
    print('result:', result)
    jb = [s for s in stub.metrics if 'detector:jailbreak' in s['tags'] and 'verdict:block' in s['tags']]
    assert len(jb) == 1 and jb[0]['points'][0][1] == 2
    assert result['logs_sent'] == 3 and result['metric_series'] == 2
    assert result['logs_ok'] and result['metrics_ok']
    assert stub.logs[0]['status'] == 'error'
    print('datadog logs + metrics aggregation: ok')

# datadog_integration_test.py
# Section 16.04: Datadog Integration End-to-End Test
# 20260121 | AI Security Mastery -- Chapter 16 by Raghav Dinesh
# Single quotes throughout per book convention
#
# Confirms both Datadog channels end to end on the stub transport: the Logs API
# path produces logs with the right tags, status, and full-detection message,
# and the metrics path aggregates events into count series by dimension.

from datadog_integration import (DatadogConnector, StubDatadogTransport, DatadogConfig,
                                 to_datadog_log, to_datadog_metrics, sample_event)


def test_log_mapping() -> None:
    log = to_datadog_log(sample_event(), DatadogConfig())
    assert 'detector:jailbreak' in log['ddtags']
    assert log['status'] == 'error'
    assert '"score": 0.88' in log['message'] or '"score":0.88' in log['message']
    assert isinstance(log['timestamp'], int)


def test_metric_aggregation() -> None:
    events = [sample_event(), sample_event(),
              {**sample_event(), 'detector': 'toxicity_detector', 'verdict': 'flag', 'severity': 'medium'}]
    series = to_datadog_metrics(events, DatadogConfig())
    assert len(series) == 2
    jb = [s['points'][0][1] for s in series if any('detector:jailbreak' in t for t in s['tags'])][0]
    assert jb == 2


def test_both_channels_delivered() -> None:
    stub = StubDatadogTransport()
    result = DatadogConnector(transport=stub).send([sample_event() for _ in range(4)])
    assert result['logs_sent'] == 4
    assert result['metric_series'] == 1
    assert result['logs_ok'] and result['metrics_ok']
    assert len(stub.logs) == 4 and len(stub.metrics) == 1


def test_severity_status_mapping() -> None:
    for sev, status in [('info', 'info'), ('medium', 'warning'), ('high', 'error'), ('critical', 'critical')]:
        log = to_datadog_log({**sample_event(), 'severity': sev}, DatadogConfig())
        assert log['status'] == status, (sev, log['status'])


if __name__ == '__main__':
    tests = [test_log_mapping, test_metric_aggregation, test_both_channels_delivered, test_severity_status_mapping]
    for t in tests:
        t(); print(f'PASS {t.__name__}')
    print(f'{len(tests)}/{len(tests)} datadog integration tests passed')

Datadog Integration Configuration

datadog_config.py

Configuration for the connector: the Datadog site, log source, metric namespace, and service, with the API key read from the environment. Code

# datadog_config.py
# Section 16.04: Datadog Integration Configuration
# 20260121 | AI Security Mastery -- Chapter 16 by Raghav Dinesh
# Single quotes throughout per book convention
#
# Configuration for the Datadog connector. The metric namespace is the key knob:
# it places detection metrics beside the Chapter 14 observability metrics. The API
# key is read from the environment.

import os
from dataclasses import dataclass, asdict
from typing import Any, Dict


@dataclass
class DatadogDeploymentConfig:
    site: str = 'datadoghq.com'
    log_source: str = 'ai-detection'
    metric_namespace: str = 'ai.detection'
    service: str = 'detection-gateway'
    env: str = 'prod'
    api_key_env_var: str = 'DD_API_KEY'

    def logs_endpoint(self) -> str:
        return f'https://http-intake.logs.{self.site}/api/v2/logs'
    def metrics_endpoint(self) -> str:
        return f'https://api.{self.site}/api/v2/series'
    def resolve_api_key(self) -> str:
        key = os.environ.get(self.api_key_env_var, '')
        assert key, f'{self.api_key_env_var} is not set -- Datadog API key required'
        return key
    def validate(self) -> None:
        assert self.site in ('datadoghq.com', 'datadoghq.eu', 'us3.datadoghq.com'), 'unknown Datadog site'
        assert self.log_source and self.metric_namespace and self.service, 'required fields missing'
    def redacted(self) -> Dict[str, Any]:
        d = asdict(self); d['api_key'] = '(from ' + self.api_key_env_var + ')'; return d


PRODUCTION = DatadogDeploymentConfig()
EU = DatadogDeploymentConfig(site='datadoghq.eu')


if __name__ == '__main__':
    os.environ.setdefault('DD_API_KEY', 'demo-key-not-real')
    for name, cfg in [('production', PRODUCTION), ('eu', EU)]:
        cfg.validate()
        print(f'{name:11} logs={cfg.logs_endpoint()}')
    print('api key resolves:', bool(PRODUCTION.resolve_api_key()))
    print('all datadog profiles valid')

Common Mistakes

Mistake 1

Description

Sending detections to Datadog only as logs, skipping the metrics channel

Why It Happens

The logs channel alone gets every detection into Datadog, so the integration looks complete once logs flow.

Consequence

There is no cheap, exact rate to dashboard or alert on, so the team either counts logs expensively or misses trends and spikes entirely.

Correct Approach

Use both channels: logs for per-detection detail and pre-aggregated count metrics for the rates a team monitors and alerts on.

Mistake 2

Description

Submitting one metric point per detection instead of aggregating by dimension

Why It Happens

It mirrors the logs path -- one event, one submission -- and feels consistent.

Consequence

The metrics volume balloons, costs rise, and the series are noisier and less precise than a clean count per detector, verdict, and severity.

Correct Approach

Aggregate events into count series by dimension at the connector, so Datadog gets exact rates cheaply and dashboards break them down by tag.

Mistake 3

Description

Putting detection metrics on a separate platform from the operational metrics

Why It Happens

Detection and operations feel like different teams' concerns, so the metrics land wherever each team already looks.

Consequence

A detection spike and a latency spike cannot be correlated because they live on different platforms, and the cross-cutting questions go unanswered.

Correct Approach

Submit detection metrics under a namespace alongside the Chapter 14 observability metrics, so both families share dashboards and monitors.

Mistake 4

Description

Not mapping severity to Datadog's status, leaving every detection at the same level

Why It Happens

The log flows fine without a status, and severity is already in the tags, so setting status feels redundant.

Consequence

Datadog's severity-based alerting and visual triage do not work on detections, so a critical exfiltration block looks identical to a medium PII flag.

Correct Approach

Map the schema severity onto Datadog's status levels, so severity-based alerting, colouring, and sorting work on detections out of the box.
